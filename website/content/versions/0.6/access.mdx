---
title: Access rules
description: Decide who reads which rows and fields, and who creates, updates and deletes them.
---

Every query runs as a caller: an anonymous visitor, a signed-in user, or
Master, the server's own code. A model's `.with({ access })` decides what
each caller may do, and a model without rules is closed to everyone but
Master. Each rule is a plain function that returns `true` or `false`:

```ts
import { graphql } from '@ultimabase/graphql'
import { allOf, allow, anyOf, defineModel } from 'ultimabase'
import type { Caller } from 'ultimabase'

// A comment: everyone reads, and only a signed-in user creates; no one
// updates or deletes, as a missing key is closed.
export const Comment = defineModel({
	name: 'Comment',
	use: [graphql()],
	fields: (f) => ({ body: f.string() }),
}).with({
	access: {
		read: allow.public,
		create: ({ caller }) => caller.kind === 'user',
	},
})
```

The full example, with its tests: [`examples/access-rules`](https://github.com/MrEkinox/ultimabase/tree/main/examples/access-rules).

`allow.public`, `allow.readOnly` and `allow.private` cover the common cases:
`access: allow.readOnly` lets everyone read and only Master write. The tests
write `ada` and `grace` for `{ as: asUser({ id }) }`, two signed-in users.
Ada creates a comment; a visitor, who has no `{ as }`, cannot:

```ts
await Comment.create({ data: { body: 'Well said' } }, ada)
await expect(Comment.create({ data: { body: 'Spam' } })).rejects.toMatchObject({
	code: 'ACCESS_DENIED',
})
```

| To                                      | Use                                                    |
| --------------------------------------- | ------------------------------------------------------ |
| show each caller some rows              | [a `read` rule](#read-rules)                           |
| refuse a create, an update, a delete    | [`create`, `update`, `delete`, `write`](#write-rules)  |
| hide or protect one field               | [a field's `access`](#field-rules)                     |
| give rows to a project's members        | [a filter through a relation](#rights-from-a-relation) |
| let an owner write a group's rows       | [`where` in a write rule](#rights-over-a-groups-rows)  |
| act as the server                       | [`master`](#master)                                    |
| choose between rules, roles and the ACL | [Rules, roles or ACL](#rules-roles-or-acl)             |

Rules are synchronous and run no query: a check that needs another row goes
in a [hook](/docs/next/hooks). The tests read and write an `Article`, whose
rules the sections show in pieces.

## Read rules

A read rule returns `true` to let every row through, `false` to hide them
all, or a filter built with the `where` it receives, in the form of a
query's `where`. `Article` shows everyone what is published, and an author
their drafts too:

```ts
// Everyone reads what is published; an author reads their drafts too.
read: anyOf(
	({ where }) => where({ status: 'published' }),
	({ caller, where }) =>
		caller.kind === 'user' && where({ authorId: caller.user.id }),
),
```

- `anyOf` joins the rules' filters with `OR`, `allOf` with `AND`.
- A read rule does not see the row: to decide on a row's values, filter on
  them.
- The filter joins every query on the model, so pages, counts and relation
  filters stay exact.

Ada writes a draft and a published article:

```ts
await Article.create(
	{ data: { title: 'Draft', notes: 'Check the dates.' } },
	ada,
)
await Article.create(
	{ data: { title: 'Launch', status: 'published', notes: 'Embargo.' } },
	ada,
)
```

Each caller reads what its rule lets through:

```ts
// The filter joins the query: pages and counts stay exact.
const select = { title: true }
expect(await Article.findMany({ select }, ada)).toEqual([
	{ title: 'Draft' },
	{ title: 'Launch' },
])
expect(await Article.findMany({ select }, grace)).toEqual([{ title: 'Launch' }])
expect(await Article.count({}, grace)).toBe(1)
```

## Write rules

`create`, `update` and `delete` each take a rule; `write` covers the three,
and a specific key wins over it. `Article` lets a user create, an author
update, and an author delete a draft only. Its rules read the caller's id with
`userId`:

```ts
/** The caller's user id, or `undefined` for anyone else. */
const userId = (caller: Caller) =>
	caller.kind === 'user' ? caller.user.id : undefined
```

```ts
create: ({ caller }) => caller.kind === 'user',
update: ({ caller, record }) => record.authorId === userId(caller),
// An author deletes their own drafts, and nothing published.
delete: allOf(
	({ caller, record }) => record.authorId === userId(caller),
	({ record }) => record.status === 'draft',
),
```

A write rule receives:

- the stored `record`, on `update` and `delete`;
- the written `value`, on `create` and `update`.

A row the caller cannot read cannot be written either: it is `NOT_FOUND`, so
a refusal never tells that the row exists. Grace reads no draft of Ada's, so
to her it does not exist:

```ts
const draft = await Article.create({ data: { title: 'Draft' } }, ada)
expect(draft.authorId).toBe('ada')

// Grace reads no draft of Ada's: for her, it does not exist.
await expect(
	Article.update({ where: { id: draft.id }, data: { title: 'Mine' } }, grace),
).rejects.toMatchObject({ code: 'NOT_FOUND' })
```

A refused write writes nothing and fails with `ACCESS_DENIED`. Its `details`
name the model, the operation and the field whose rule refused. Once Ada
publishes her draft, it refuses her delete:

```ts
await Article.update(
	{ where: { id: draft.id }, data: { status: 'published' } },
	ada,
)
// Published, the article can no longer be deleted by its author.
await expect(
	Article.delete({ where: { id: draft.id } }, ada),
).rejects.toMatchObject({
	code: 'ACCESS_DENIED',
	details: { model: 'Article', operation: 'delete' },
})
```

## Field rules

A field's `.with({ access })` takes one rule, or one per operation: `read`,
`create`, `update`, and `write` for both writes. A field rule runs after the
model's, only when the write names the field. It receives the row's `record`
and the field's `value`.

`authorId` is written once, with the caller's id: nobody signs for someone
else. A field rule refuses with the field in its `details`:

```ts
title: f.string(),
status: f.enumOf(['draft', 'published'], { default: 'draft' }),
// Written once, with the caller's id: nobody signs for someone else.
authorId: f.string({ default: ({ caller }) => userId(caller) }).with({
	access: {
		create: ({ caller, value }) => value === userId(caller),
		update: allow.private,
	},
}),
```

```ts
// A field rule: nobody signs an article for someone else.
await expect(
	Article.create({ data: { title: 'Fake', authorId: 'grace' } }, ada),
).rejects.toMatchObject({
	code: 'ACCESS_DENIED',
	message: 'Article create refused.',
	details: { model: 'Article', operation: 'create', field: 'authorId' },
})
```

`.with<{ authorId: string }>({ ... })` types the fields a rule reads:
`defineModel` checks that each type matches the model's. A field rule sees
`record.id` typed and the other fields as `unknown` otherwise.

```ts
// The author's notes: other readers get the article without them.
notes: f.string({ optional: true }).with<{ authorId: string }>({
	access: {
		read: ({ caller, record }) => record.authorId === userId(caller),
	},
}),
```

A read rule on a field hides its value from the rows it refuses:

```ts
// A field read rule hides the value, row by row.
const [launch] = await Article.findMany({}, grace)
expect(launch).not.toHaveProperty('notes')
```

A caller other than Master cannot filter, sort or aggregate on such a field,
which would reveal the value one guess at a time:

```ts
// Nor can a filter guess it.
await expect(
	Article.findMany({ where: { notes: { contains: 'E' } } }, grace),
).rejects.toMatchObject({
	code: 'INVALID_QUERY',
	message:
		'where.notes: Article.notes has a read rule; only Master filters on it.',
})
```

- `allow.private` leaves the field to Master: the transports leave it out of
  their schema.
- `allow.public` and `allow.readOnly` are no read rule: everyone filters and
  sorts on a field that has them, and only the writes are checked.
- `featured` has `allow.readOnly`: only the server writes it.

```ts
// Only the server features an article.
featured: f.boolean({ default: false }).with({ access: allow.readOnly }),
```

## Rights from a relation

A read rule's filter goes through relations as a query's does. A project's
members read it, and the tasks in it, with no role to keep in step. `Person`
and `Project` relate by `members`:

```ts
export const Person = defineModel({
	name: 'Person',
	use: [graphql()],
	fields: (f) => ({
		name: f.string(),
		projects: f.many(() => Project, { inverse: 'members' }),
		owned: f.many(() => Project, { inverse: 'owner' }),
	}),
}).with({ access: allow.readOnly })
```

```ts
fields: (f) => ({
	name: f.string(),
	owner: f.one(() => Person),
	members: f.many(() => Person, { inverse: 'projects' }),
	tasks: f.many(() => Task, { inverse: 'project' }),
}),
```

The project's members read it, through the relation to the caller:

```ts
access: {
	// Its members read a project, through the relation to the caller.
	read: ({ caller, where }) =>
		caller.kind === 'user' &&
		where({ members: { some: { id: caller.user.id } } }),
	// A rule sees the row's own `one` relations as `{ id }`: enough here.
	update: ({ caller, record }) => record.owner.id === userId(caller),
},
```

A task's `project` is a relation too, so its members read it one relation
further:

```ts
fields: (f) => ({
	title: f.string(),
	done: f.boolean({ default: false }),
	project: f.one(() => Project, { onDelete: 'cascade' }),
}),
```

```ts
// The members of its project read a task, one relation further.
read: ({ caller, where }) =>
	caller.kind === 'user' &&
	where({
		project: { is: { members: { some: { id: caller.user.id } } } },
	}),
```

The tests write `ada`, `grace` and `alan` for the callers of three people, and
`graceId` for Grace's id. Ada owns the project `project` and is a member with
Grace; Alan is in none.

A member who leaves the project reads none of its tasks from the next query on,
and a [live read](/docs/next/realtime#rights) follows the relations its filter
goes through:

```ts
await Task.create(
	{ data: { title: 'Parse', project: { connect: { id: project.id } } } },
	ada,
)
// Grace is a member: she reads the task; Alan is not.
expect(await Task.count({}, grace)).toBe(1)
expect(await Task.count({}, alan)).toBe(0)
```

```ts
// Out of the project, Grace reads nothing from her next query on.
await Project.update(
	{
		where: { id: project.id },
		data: { members: { disconnect: [{ id: graceId }] } },
	},
	{ as: master },
)
expect(await Task.count({}, grace)).toBe(0)
```

- Each read joins the relation. PostgreSQL indexes every relation's key, and
  both columns of a join table, so the join needs no index of yours.
- With the [auth plugin](/docs/next/auth), `{ viewer: true }` on a relation to
  the user model stands for the caller: `members: { some: { viewer: true } }`.

## Rights over a group's rows

A write rule receives the row, with its own `one` relations as `{ id }`:
`Project.update` above checks `record.owner`. To go further, a model's
`create`, `update`, `delete` or `write` rule returns `where(...)`, as a read
rule does. `Task.write` keeps a task's writes to its project's owner, and
refuses with a `PublicError`, imported from `ultimabase`:

```ts
// Only the project's owner writes its tasks: the row matches the
// filter before an update or a delete, and after a create or an
// update, so no task moves to a project of someone else's.
write: ({ caller, where }) =>
	caller.kind === 'user' &&
	where(
		{ project: { is: { owner: { is: { id: caller.user.id } } } } },
		new PublicError(
			'NOT_PROJECT_OWNER',
			'Only the project’s owner writes its tasks.',
		),
	),
```

The row must match the filter:

- an update's row, before the write and after it, so no task moves to another
  owner's project;
- a delete's row, before;
- a create's row, after, with the relations it connects or creates.

Grace, a member, reads `task`, a task Ada created in `project`, but the rule
refuses her update:

```ts
// Grace reads the task, but the rule refuses her writes.
const refused = {
	code: 'NOT_PROJECT_OWNER',
	message: 'Only the project’s owner writes its tasks.',
}
await expect(
	Task.update({ where: { id: task.id }, data: { done: true } }, grace),
).rejects.toMatchObject(refused)
```

She cannot delete it, nor create another in the project:

```ts
await expect(
	Task.delete({ where: { id: task.id } }, grace),
).rejects.toMatchObject(refused)
```

```ts
await expect(
	Task.create(
		{ data: { title: 'Lex', project: { connect: { id: project.id } } } },
		grace,
	),
).rejects.toMatchObject(refused)
```

Ada, the owner, updates the task and deletes it:

```ts
// Ada, the owner, does both.
const done = await Task.update(
	{ where: { id: task.id }, data: { done: true } },
	ada,
)
expect(done.done).toBe(true)
await Task.delete({ where: { id: task.id } }, ada)
```

A row outside the filter refuses the whole write, an `updateMany` or a
`deleteMany` included, and nothing is written. The error is the one `where`
takes as its second argument, a `PublicError`, or `ACCESS_DENIED` without one.

## Master

Master skips every rule. Server code passes `{ as: master }`. A transport acts
as Master only with the master key (see [HTTP](/docs/next/http)), and in
production only with a key written `{ key, production: true }` (see
[Deploy](/docs/next/deploy)). Ada cannot feature an article; Master can:

```ts
const draft = await Article.create({ data: { title: 'Draft' } }, ada)
await expect(
	Article.update({ where: { id: draft.id }, data: { featured: true } }, ada),
).rejects.toMatchObject({ code: 'ACCESS_DENIED' })
const featured = await Article.update(
	{ where: { id: draft.id }, data: { featured: true } },
	{ as: master },
)
expect(featured.featured).toBe(true)
```

A function or a hook receives the `caller` it runs for: `{ as: caller }` runs
the rules for that caller, `{ as: master }` acts as the server. `allow.readOnly` is no read
rule, so the author filters on `featured`:

```ts
// allow.readOnly is no read rule: the author filters on the field.
const listed = await Article.findMany(
	{ where: { featured: { equals: true } } },
	ada,
)
expect(listed.map(({ id }) => id)).toEqual([draft.id])
```

## Over the transports

A client meets the same rules, with the same error. An anonymous caller
creates an article:

```graphql
mutation {
	createArticle(data: { title: "Hi" }) {
		id
	}
}
```

```json
{
	"errors": [
		{
			"message": "Article create refused.",
			"locations": [{ "line": 2, "column": 2 }],
			"path": ["createArticle"],
			"extensions": {
				"code": "ACCESS_DENIED",
				"details": { "model": "Article", "operation": "create" }
			}
		}
	],
	"data": null
}
```

The caller comes from the request: the [auth plugin](/docs/next/auth) reads
a session and adds `signedIn`, `isOwner`, `isSelf` and `isAuthenticated` to
the rules; [roles](/docs/next/roles) adds `hasRole`.

## Rules, roles or ACL

Each kind of right has its tool:

| The right                                                         | Fits                                          | Why                                                                                                                         |
| ----------------------------------------------------------------- | --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Follows from data the app holds: a membership, an owner, a status | A read rule's filter, through a relation      | Nothing to keep in step: a member who leaves reads nothing more. Conditions on the row join the same filter.                |
| Given to a person across the app: an admin, a moderator, support  | [Roles](/docs/next/roles) and `hasRole`       | The right belongs to the person, not to a group's data.                                                                     |
| Chosen row by row, by a user: share this note with Ada and Grace  | The [ACL](/docs/next/acl), by user or by role | The right is the data: nothing else holds it.                                                                               |
| Migrated from Parse                                               | Roles and the ACL                             | They match Parse's `_Role` and ACLs one to one; moving a group's rights to a relation later removes the hooks that sync it. |

They combine: an operation passes the model's access rules, then the ACL
picks among the rows they let through. A role given during a request counts
from the next one ([Roles](/docs/next/roles#inherit-roles)), and a live read
is planned again when a role, an ACL or a session changes
([Realtime](/docs/next/realtime#rights)).

## Details

- The logger receives the details of a refused write, and the caller's id.
- `updateMany` and `deleteMany` run the write rules on each row.
- A read rule on a field makes it optional in the rows a query returns, in a
  `select` or an `include` too: `notes` reads `string | undefined`. A hook's
  or a rule's `record` still has every field.
- A group's write filter goes through the same relations as a read rule's. It
  is checked in the write's own statement, or by one count per filter in its
  transaction.

## Reference

### `access`

| Where   | Form                                                    | Operations                                                       |
| ------- | ------------------------------------------------------- | ---------------------------------------------------------------- |
| a model | a rule, or `{ read, create, update, delete, write }`    | `write` stands for `create`, `update` and `delete`               |
| a field | a rule, or `{ read, create, update, write }`            | `write` stands for `create` and `update`                         |
| either  | a missing key, on a model: closed; on a field: no check | a specific key wins over `write`; a single rule covers every one |

### What a rule receives

| Rule           | Facts                                        | Returns                    |
| -------------- | -------------------------------------------- | -------------------------- |
| model `read`   | `caller`, `operation`, `where`               | `true`, `false`, `where()` |
| model `create` | `caller`, `operation`, `value` (the data)    | `boolean`                  |
| model `update` | `caller`, `operation`, `record`, `value`     | `boolean`                  |
| model `delete` | `caller`, `operation`, `record`              | `boolean`                  |
| field `read`   | `caller`, `operation`, `record`              | `boolean`                  |
| field `create` | `caller`, `operation`, `value` (the field's) | `boolean`                  |
| field `update` | `caller`, `operation`, `record`, `value`     | `boolean`                  |

`record` holds the stored row: `id`, `createdAt`, `updatedAt`, each field,
and each `one` relation as `{ id }` or `null`. A relation's `value` is ids,
never data: `{ id }` or `null` for a `one`, `{ connect, disconnect, create,
delete }` lists of `{ id }` for a `many`.

`caller` is one of:

| `caller.kind` | Other keys                                     |
| ------------- | ---------------------------------------------- |
| `'anonymous'` | none                                           |
| `'user'`      | `user`: `{ id }`, or the registered user model |
| `'master'`    | `master.source`: `'code'` or `'key'`           |

`declare module 'ultimabase' { interface Register { readonly user: typeof
User } }` types `caller.user` as the user model's row: see
[Authentication](/docs/next/auth).

### Rules

| Rule              | Effect                                                                           |
| ----------------- | -------------------------------------------------------------------------------- |
| `allow.public`    | Everyone.                                                                        |
| `allow.readOnly`  | Everyone reads; nobody but Master writes.                                        |
| `allow.private`   | Nobody but Master.                                                               |
| `anyOf(...rules)` | True when one rule is; the filters joined with `OR`, refused as `ACCESS_DENIED`. |
| `allOf(...rules)` | True when every rule is; each filter checked alone, with its own error.          |

### Errors

| Code            | When                                                                                                                                   | `details`                            |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| `ACCESS_DENIED` | A write rule refused, or a row outside its filter given no error: `Article create refused.`                                            | `{ model, operation, field?, via? }` |
| `NOT_FOUND`     | An update or a delete of a row the read rule hides.                                                                                    | none                                 |
| `INVALID_QUERY` | A filter, a sort or an aggregate on a field with a read rule: `where.notes: Article.notes has a read rule; only Master filters on it.` | none                                 |

`via` names the relation a nested write came through, as `'Post.comments'`.
A client's filter refused as `INVALID_QUERY` answers `BAD_USER_INPUT`, a
`400`.

### Limits

- A rule returns its result directly, never a `Promise`, and cannot query.
- A model rule returns `true`, `false` or `where(...)`; any other value
  throws `A read rule returns a boolean or a filter.` or `A write rule returns
a boolean or a filter.` A field rule returns a boolean:
  `A field rule returns a boolean.`
- A field read rule cannot return a filter.
- A virtual a field read rule hides, and the `_count` of a hidden relation,
  are typed as present.
