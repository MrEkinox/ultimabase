---
title: PostgreSQL
description: Store the models in PostgreSQL, sync its tables in development, and change them in production with migration files.
---

`postgres()` stores the models in a PostgreSQL database, version 15 or
later. In development, each start syncs the tables to the models. For
production, `migrate create` writes each change as an SQL file that you
commit; `migrate deploy` applies those files.

```npm
npm install @ultimabase/postgres
```

```ts title="src/app.ts"
import { graphqlPlugin } from '@ultimabase/graphql'
import { httpPlugin } from '@ultimabase/http'
import { postgres } from '@ultimabase/postgres'
import { defineApp } from 'ultimabase'
import { Project, Task } from './models.ts'

export const app = defineApp({
	// Outside production, a start syncs the tables to the models; in
	// production it checks that the migrations deployed match them.
	database: postgres({ url: process.env['DATABASE_URL'] }),
	// Listens on PORT, or 3000.
	plugins: [httpPlugin(), graphqlPlugin()],
	models: [Project, Task],
	// Accepted in production, where it needs 32 characters at least.
	masterKey: { key: process.env['MASTER_KEY'], production: true },
})
```

The full example, with its tests: [`examples/postgres`](https://github.com/MrEkinox/ultimabase/tree/main/examples/postgres).

| To                                    | Use                                               |
| ------------------------------------- | ------------------------------------------------- |
| connect to a database                 | [`postgres({ url })`](#connect)                   |

## Connect

`url` is a connection string such as
`postgres://user:password@localhost:5432/app`. The `ultimabase` commands
run the application that `ultimabase.config.ts` exports. They look for the
migration files in `migrations/`, beside it:

```ts title="ultimabase.config.ts"
export { app as default } from './src/app.ts'
```

## Development

Outside production, a start syncs the tables to the models:

```bash
npx ultimabase dev
```

`dev` sets `NODE_ENV` to `development` and starts the application. When a
file changes, it restarts it, and syncs the tables again. `sync` does the
same without starting the application. The first one logs `Created the
database's tables.`, and the next:

```console title="Terminal"
$ npx ultimabase sync
The database already matches the models.
```

Each change logs a line, such as `Synced Task: added priority, 0 in the
rows it held.` A sync applies a change only when it keeps the rows.

### A change that deletes data

A sync refuses a change that deletes data, prints the SQL it would run, and
says what to do:

```bash
npx ultimabase sync --force
```

- `--force` applies the change to this development database.
- Or write it as a migration, whose SQL you can edit (see
  [Migrations](#migrations)).

A sync also refuses a change the rows cannot take, such as a required field
without a default on a table that holds rows. Make the field optional, give
it a default, or rebuild the database with `npx ultimabase reset`.

## The tables

Each model is a table, each field a column, named in snake case: `Task` is
`task`, `createdAt` is `created_at`. `dbName` names a table or a column
yourself (see [Models and fields](/docs/next/models)).

```ts title="src/models.ts"
export const Project = defineModel({
	name: 'Project',
	use: [graphql()],
	fields: (f) => ({
		name: f.string({ unique: true }),
		tasks: f.many(() => Task, { inverse: 'project' }),
	}),
	// Open to every client, to keep the example on the database.
}).with({ access: allow.public })

export const Task = defineModel({
	name: 'Task',
	use: [graphql()],
	fields: (f) => ({
		title: f.string(),
		done: f.boolean({ default: false }),
		// Added after the first migration: the second one adds its column.
		priority: f.number({ integer: true, default: 0 }),
		// A project's tasks are deleted with it.
		project: f.one(() => Project, { onDelete: 'cascade' }),
	}),
}).with({ access: allow.public })
```

| Field                      | Column                                                                                                                          |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `id`                       | `uuid`, the primary key                                                                                                         |
| `createdAt`, `updatedAt`   | `timestamptz not null`                                                                                                          |
| `f.string()`               | `text collate "C"`                                                                                                              |
| `f.number()`               | `double precision`; `integer` with `integer: true`                                                                              |
| `f.decimal()`              | `numeric(precision, scale)`                                                                                                     |
| `f.boolean()`              | `boolean`                                                                                                                       |
| `f.dateTime()`             | `timestamptz`                                                                                                                   |
| `f.date()`                 | `date`                                                                                                                          |
| `f.json()`                 | `jsonb`                                                                                                                         |
| `f.enumOf()`               | `text`, with a check of its values                                                                                              |
| a list (`list: true`)      | `text[]`, `double precision[]` or `integer[]`                                                                                   |
| `f.one()`, the side stored | `<field>_id uuid`, indexed unless a key or an index starts with it, with a foreign key checked at commit                        |
| `f.many()` both ways       | a table `<table>_<field>`, with a `<table>_id` column per side                                                                  |
| `search: true`             | a generated `_search` column, with a GIN index                                                                                  |
| `within`                   | a foreign key over the key and the parent's column, `_within_fkey`, to a unique key on the target's `(id, <parent>_id)`         |
| `within` on a `many`       | a `<parent>_id` column on the join table, and per side a `_within_fkey` to that side's `(id, <parent>_id)`, `on update cascade` |

- A required field is `not null`; an optional one is nullable.
- A unique field or index is a unique constraint.
- An index with `contains: true` installs the `pg_trgm` extension, which
  needs the right to create it.

## Migrations

When the models change, write the change as a migration:

```bash
npx ultimabase migrate create add_priority
```

Here, `priority` was added to `Task`. The command wrote
`migrations/20261029230454_add_priority.sql`, named after the time in UTC,
and updated `migrations/schema.json`, the models the migrations lead to.
Commit both:

```sql title="migrations/20261029230454_add_priority.sql"
-- ultimabase schema 2fd2b10f400fc79147980938759b63aa232ffc47d63c95701d415c339b13725c

alter table "task" add column "priority" integer not null default 0;
```

- The first line is the hash of the models after the file. A deploy uses it
  to check that the files match the models.
- A statement that deletes data or may fail on the rows gets a comment
  above it, such as `-- removing "Locker.label" deletes data.`
- Read the file, and edit it before you commit it.

### Your own SQL

When no model changed, `migrate create` writes a file for your SQL: a data
change, a view, an index of your own. It prints `Wrote
migrations/20261029230505_first_tasks_urgent.sql: no model changed, write
your SQL in it.` Here, the update is written in it:

```sql title="migrations/20261029230505_first_tasks_urgent.sql"
-- ultimabase schema 2fd2b10f400fc79147980938759b63aa232ffc47d63c95701d415c339b13725c

-- The tasks written before priorities came first.
update "task" set "priority" = 1 where not "done";
```

A `check` constraint of your own refuses a row with `VALIDATION_FAILED`,
one issue naming it: `The row breaks the check visit_ended.` A rule a hook
can hold instead stays in TypeScript, and chooses the writes it checks
([hooks](/docs/next/hooks#a-rule-across-a-rows-fields)).

### A statement outside a transaction

Each file runs in a transaction: if a statement fails, the file is rolled
back. Some statements cannot run in a transaction, such as
`create index concurrently`. Put such a statement alone in its file, with
`-- ultimabase no transaction` as the second line:

```sql title="migrations/20261029230507_open_tasks_index.sql"
-- ultimabase schema 2fd2b10f400fc79147980938759b63aa232ffc47d63c95701d415c339b13725c
-- ultimabase no transaction

-- Built without locking the table against writes.
create index concurrently "task_open_idx" on "task" ("project_id") where not "done";
```

### Deploy

`migrate status` says what a deploy would do, and exits 1 while it has
something to do. `migrate deploy` applies the files the database lacks, in
order:

```console title="Terminal"
$ npx ultimabase migrate status
20261026200257_init.sql is pending.
20261029230454_add_priority.sql is pending.
20261029230505_first_tasks_urgent.sql is pending.
20261029230507_open_tasks_index.sql is pending.
```

```console title="Terminal"
$ npx ultimabase migrate deploy
Applied 20261026200257_init.sql.
Applied 20261029230454_add_priority.sql.
Applied 20261029230505_first_tasks_urgent.sql.
  update "task" set "priority" = 1 where not "done": UPDATE 0
Applied 20261029230507_open_tasks_index.sql.
$ npx ultimabase migrate status
The database is up to date.
```

Running it, its stops and its refusals in production are on
[Deploy](/docs/next/deploy).

### Test a migration

Deploy applies migrations only to a database they built. After a sync, it
is refused:

```console title="Terminal"
$ npx ultimabase migrate deploy
Development sync changed this database since its last deploy: deploy applies migrations only to a database they built.
Restore the dump you test on, or rebuild this database from the migrations with `npx ultimabase reset`.
```

`reset` drops every table, then applies the migrations. It gives you the
database production will have:

```console title="Terminal"
$ npx ultimabase reset
Dropped project, task.
Applied 20261026200257_init.sql.
Applied 20261029230454_add_priority.sql.
Applied 20261029230505_first_tasks_urgent.sql.
  update "task" set "priority" = 1 where not "done": UPDATE 0
Applied 20261029230507_open_tasks_index.sql.
```

To test a data migration on real rows, restore a dump of production in
development, then run `npx ultimabase migrate deploy`.

## Tests

`testApplication(app, { database: 'declared' })` runs a test file on the
application's own PostgreSQL, in a schema of the file's own: its tables are
emptied before each test, and the schema is dropped after the last one.

```ts title="src/tasks.postgres.test.ts"
// On the database DATABASE_URL names: the file's own schema, its tables
// emptied before each test, dropped after the last.
testApplication(app, { database: 'declared' })

it('starts with empty tables', async () => {
	expect(await Project.count({}, { as: master })).toBe(0)
})
```

Name these files `*.postgres.test.ts`, and keep the other tests on
`memory()` (see [Testing](/docs/next/testing)).

## Options

`connections` sets the pool's size, `prepared` whether a composed
statement is planned once per connection, `searchLanguage` the language of
the search, and `statementTimeout` how long a statement may run:

```ts title="src/search.postgres.test.ts"
database: postgres({
	url: process.env['DATABASE_URL'],
	// At most 20 queries at once; the next waits up to 10 s for one.
	connections: 20,
	// Each statement planned once per connection: `false` behind a pooler
	// that cannot keep them.
	prepared: true,
	// Words stemmed as English: "running" finds "runs".
	searchLanguage: 'english',
	// A statement that runs past 10 s is ended; a migration is not.
	statementTimeout: 10_000,
}),
```

`searchLanguage` names a text search configuration of the server, such as
`'english'` or `'french'`. It stems the words that `_search` reads:

```ts title="src/search.postgres.test.ts"
await Article.create(
	{ data: { body: 'She runs every morning' } },
	{ as: master },
)
const found = await Article.findMany(
	{ where: { _search: 'running' } },
	{ as: master },
)
expect(found.map((article) => article.body)).toEqual(['She runs every morning'])
```

### Behind a pooler

The adapter plans a statement it composes once per connection, which
PostgreSQL would otherwise do on every run. A pooler that shares server
connections between clients may then find a statement unknown.

- PgBouncer in transaction mode needs version 1.21 or later and
  `max_prepared_statements` above 0.
- Where it cannot, `postgres({ url, prepared: false })` plans each
  statement every time, at the cost of that planning under load.

### A statement timeout

With `statementTimeout: 10_000`, PostgreSQL ends a statement that runs
longer than 10 s, a wait for a lock included. The request fails with a
`500`, and the connection serves on. A migration is never ended.

A connection whose statement has no answer 10 s past the timeout, as when
the database moved to another address, is given up. Unset, a statement
runs as long as it takes.

## Details

### Renames

When a sync or a migration drops a field or a table that looks renamed, it
says so:

- A removed field that looks renamed: the refusal says `-- a rename? keep
its data: give Locker.title dbName: 'label'.` That `dbName` keeps the old
  column, with its data, under the new field.
- Several added fields may be the removed one: the refusal lists them,
  `give one of Locker.title, Locker.code dbName: 'label'.`, and a migration
  file lists one `rename column` line for each. Replace the drop, and the
  line adding the field you keep, with the right one.
- An added field that two removed ones may be is named for neither.
- A removed table that looks renamed, a model's or a join's, gets the same
  hint in a migration file, one statement per line: it renames the table,
  then its keys and indexes. Replace the drop, and the line creating the
  new table, with them.
- A `oneOf`'s keys take no `dbName`: when the removed field may be one, the
  refusal says `--force` loses its data and a migration keeps it.

### Defaults in a migration

- A required field added with a fixed default takes it in the stored rows,
  and its column keeps it, so that code still running without the field can
  still insert during a deploy.
- A change of the column's type drops the default.
- A list without a default is empty in the stored rows: a comment below its
  statement says so, and that is where to write the values the rows need.

### Constraints

- A case-insensitive unique field or index is a unique index over `lower()`
  of its text columns, named `_lower_key`, which also serves an insensitive
  `equals`.
- A unique index with a `where` is a partial unique index,
  `create unique index … where …`, its name ending in a hash of its
  predicate. A new `where` drops it and creates it again, and rows that
  already share a value fail the migration.
- The foreign keys have no `on delete`: UltimaBase runs `onDelete` itself,
  with the hooks and access rules.
- A relation's `within` key is checked at commit too: a concurrent write or
  SQL of your own that parts a row from its target's parent fails the
  transaction with the kernel's `VALIDATION_FAILED`, its issue on the row's
  relation.
- With an optional parent, a check `_within_check` keeps the key `null`
  while the parent's is, and fails the statement with the same issue.
- A many-to-many's join table stores each link's parent: a row moved to
  another parent carries its links, and the other side's key refuses at
  commit a link left across two parents.
- `migrate create` fills that column from the rows each link holds, then
  adds the keys, which fail while a link crosses two parents.
- Constraint names end in `_pkey`, `_key`, `_lower_key`, `_fkey`,
  `_within_fkey`, `_check`, `_within_check` and `_idx`. A name longer than
  PostgreSQL's 63 bytes keeps its first 54 bytes plus an 8-character hash.

## Reference

### `postgres(options)`

| Option             | Type                          | Default    | Effect                                                                   |
| ------------------ | ----------------------------- | ---------- | ------------------------------------------------------------------------ |
| `url`              | `string \| undefined`         | required   | The connection string. Unset or empty, the start is refused.             |
| `connections`      | whole number, 1 or more       | `10`       | The connections opened at most; a query waits up to 10 s for a free one. |
| `searchLanguage`   | `string`                      | `'simple'` | The text search configuration `_search` reads words in.                  |
| `prepared`         | `boolean`                     | `true`     | Plans a composed statement once per connection; `false` plans every run. |
| `statementTimeout` | whole number of ms, 1 or more | none       | Ends a statement that runs longer; a migration runs unbounded.           |

### Commands

| Command                            | Effect                                                                                                                    |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `ultimabase dev`                   | Starts the application in development, syncs the tables, and restarts it when a file changes.                             |
| `ultimabase sync [--force]`        | Syncs a development database to the models; `--force` applies a change that deletes data.                                 |
| `ultimabase reset [--force]`       | Drops every table of a development database, then applies the migrations; `--force` allows a database on another machine. |
| `ultimabase migrate create <name>` | Writes the models' changes as a migration, or an empty one for your SQL. `name` holds lowercase letters, digits and `_`.  |
| `ultimabase migrate deploy`        | Applies the pending migrations.                                                                                           |
| `ultimabase migrate status`        | Says what a deploy would do; exits 1 if anything.                                                                         |
| `ultimabase start`                 | Starts the application in production (see [Deploy](/docs/next/deploy)).                                                   |

Each takes `--config <path>` for a config other than `ultimabase.config.ts`,
and exits 1 when it fails. `dev`, `sync`, `reset` and `migrate create` load
the `.env` file beside the config, without changing a variable already set;
`start`, `migrate deploy` and `migrate status` never read it.

Once the application serves, a pool that stays full or a server it cannot
reach answers the client 503 `UNAVAILABLE`, with `Retry-After: 1` and
`The database is busy: try again shortly.` or `The database cannot be
reached: try again shortly.`; the message above is logged, at `error`.

A warning at start says when the database's locale folds case for ASCII
only: `mode: 'insensitive'` then misses `É` and `é`, and a case-insensitive
unique key lets both in. Create the database
with a UTF-8 locale, such as `en_US.UTF-8`.

### Limits

- PostgreSQL 15 or later.
- A migration waits 5 s at most for a table another session holds.
- A file marked `-- ultimabase no transaction` holds one statement; if it
  fails, nothing is rolled back.
- `sync` and `reset` refuse production; `reset` refuses another machine
  without `--force`.
