An adapter is the object an application's `database` holds, and it only stores
and reads rows. `timed` runs another adapter, counts its calls and logs the
slow ones:

<include cwd meta='title="src/timed.ts"'>
	../examples/adapter/src/timed.ts#types
</include>

The full example, with its tests: [`examples/adapter`](https://github.com/MrEkinox/ultimabase/tree/main/examples/adapter).

`memory()` and `postgres()` are two adapters. The kernel sends each read and
write fully prepared: its filters normalized, its ids, dates and defaults set
and its access rules applied. An adapter is not a plugin: an application has
one. `timed` counts its calls, each a round trip to the database. An
application uses it as any adapter:

<include cwd meta='title="src/app.ts"'>
	../examples/adapter/src/app.ts#app
</include>

## Check it with the contract suite

`testAdapter`, from `@ultimabase/testing`, runs the contract suite on an
adapter: 131 tests of what every adapter does alike, through the public API.
An adapter that passes it runs every query, plugin and transport of

## Start and stop

`start` receives the models, the kernel's logger and, when realtime is on, the
change feed. It connects; `stop` disconnects. `timed` keeps the logger for its
warnings and passes all three on:

sides and its indexes, `{ name, fields, indexes }`. `id`, `createdAt` and
`updatedAt` are implicit. For the example's `Author` and `Post`, `start`
receives these fields, among others. A scalar field with a default:

## Reads

`find` returns the rows of a `Read`, `count` counts the rows a filter keeps,
and `aggregate` returns one list per group. `timed` times each one:

<include cwd meta='title="src/timed.ts"'>
	../examples/adapter/src/timed.ts#reads
</include>

A read arrives normalized. The tests record each read in `sent.reads`.
`Post.findMany({ where: { slug: 'hello' }, include: { author: true } })`
reaches `find` as:

<include cwd meta='title="src/adapter.test.ts"'>
	../examples/adapter/src/adapter.test.ts#read
</include>

- `fields` lists the fields to return, the access rules' hidden ones left out.
- `include` holds each relation's own read, at any depth.
- `orderBy` always ends with `id`, so the order is total and a `cursor`
  resumes where a page ended.
- A read with `lock` locks the rows it returns, in `id` order, until its
  transaction ends.

## Writes

`write` runs a whole `Write` and returns the rows its `read` selects. `timed`
times it, and `empty`, which removes every row:

<include cwd meta='title="src/timed.ts"'>
	../examples/adapter/src/timed.ts#write
</include>

A write is one unit: its checks first, then its changes, then its read. A
`Post.create` that connects the author `ada` sends three parts. First its
checks:

<include cwd meta='title="src/adapter.test.ts"'>
	../examples/adapter/src/adapter.test.ts#write-checks
</include>

Then its changes, here one insert:

<include cwd meta='title="src/adapter.test.ts"'>
	../examples/adapter/src/adapter.test.ts#write-row
</include>

Then the read of the rows to return:

<include cwd meta='title="src/adapter.test.ts"'>
	../examples/adapter/src/adapter.test.ts#write-read
</include>

- Each check counts the rows a filter keeps. When one counts other than its
  `count`, the write writes nothing and throws `CheckFailed`.
- The changes are inserts, updates, deletes, and links and unlinks of
  `many`-to-`many` pairs.
- An update's `compute` computes a number or a list on each row: `increment`,
  `decrement`, `multiply` and `divide`, `push`, `pushUnique` and `remove`.
- With `before`, the read selects among the rows the write deleted, as they
  were.

## Transactions

`begin` returns a `Transaction`: the reads and `write`, then `commit` or
`rollback`. The kernel begins one for `transaction()`, and for a write that
locks its rows first. `timed` wraps the `tx` its adapter returns in
`timedTransaction`, and times each call of it. Each is a round trip, the commit
included:

<include cwd meta='title="src/timed.ts"'>
	../examples/adapter/src/timed.ts#transaction
</include>

<include cwd meta='title="src/timed.ts"'>
	../examples/adapter/src/timed.ts#begin
</include>

- A transaction's writes are seen by its own reads and by no one else's before
  the commit.
- A failed write in a transaction leaves it to be rolled back, even when the
  callback catches the error.

### Serializable transactions

`begin({ isolation: 'serializable' })` begins one for
`transaction(run, { isolation: 'serializable' })`.

- An adapter that cannot hold that isolation throws from `begin`, never begins
  a weaker one.
- One that runs its transactions one at a time, as `memory()`, already holds
  it.
- When the database aborts a transaction for a conflict with another, a
  serialization failure or a deadlock, the adapter throws `Conflict`, and the
  kernel runs a serializable callback again.

Here the database aborts the first commit: a wrapped `begin` returns its `tx`
with this `commit`, and `conflicts` starts at 1.

<include cwd meta='title="src/adapter.test.ts"'>
	../examples/adapter/src/adapter.test.ts#conflict
</include>

The callback runs twice, and its write is kept once. `transaction` comes from
`ultimabase`, `Author` is the example's model, and the tests write `M` for
`{ as: master }`:

<include cwd meta='title="src/adapter.test.ts"'>

## The change feed

With realtime on, `start` receives a `Feed`. Once a write commits, the adapter
calls `changed` with what it changed, on every server: PostgreSQL sends it
through its notifications. It calls `lost` when changes may stop coming, as
when its listener loses its connection, and `missed` when changes may have
been lost, as once it listens again.

- A rollback, a failed write and an update that changes nothing send nothing.
- How changes group into entries and calls is the adapter's.

The feed is the third argument of `start`:
`start({ models }, logger, { changed, lost, missed })`. Here `adapter` is a `memory()`
started with a `changed` that pushes to `fed`, and `author` stands for a row
with the id `a1` and its dates. An insert is fed once it commits:

<include cwd meta='title="src/adapter.test.ts"'>
	../examples/adapter/src/adapter.test.ts#feed
</include>

A change lists at most `feedIds` ids or pairs; past that, it lists none:

<include cwd meta='title="src/adapter.test.ts"'>

</include>

An update lists the fields it set, `updatedAt` included, unless they are every
field or, as JSON, longer than `feedFields`. The model `Wide` has a field
named by that many characters:

## Migrations

An adapter for a database that keeps its tables has `migrations`. An adapter
for a database that starts empty every time, as `memory()`, has none.

- The kernel then syncs the tables in development and checks them in
  production.
- The CLI writes and deploys migration files; see
  [PostgreSQL](/docs/next/postgres).

`timed` passes its adapter's on:

<include cwd meta='title="src/timed.ts"'>
	../examples/adapter/src/timed.ts#migrations
</include>

- A snapshot is JSON in the adapter's own format: what its database makes of
  the models.
- `plan` gives the statements from one snapshot to the models', each with what
  it does and, for the log, what it loses or may break.
- `apply` runs a sync or a deploy under a lock one database holds at a time.
  A sync is refused when the database's snapshot is no longer its `from`,
  and a deploy when the database applied a file its `known` does not name:
  another process changed the database since the plan was read.

## Reference

### `Adapter`

| Member                         | Does                                                                 |
| ------------------------------ | -------------------------------------------------------------------- |
| `start(schema, logger, feed?)` | Connects, then the kernel syncs or checks the tables.                |
| `stop()`                       | Disconnects.                                                         |
| `empty()`                      | Removes every model's rows, join rows included; keeps the tables.    |
| `find(read)`                   | The rows of a `Read`.                                                |
| `count(read)`                  | How many rows `where` keeps.                                         |
| `aggregate(read)`              | One list per group: its keys' values, then its aggregates'.          |
| `write(write)`                 | Runs a `Write` whole, returns the rows its `read` selects.           |
| `begin(options?)`              | A `Transaction`; `{ isolation: 'serializable' }` or a throw.         |
| `migrations?`                  | How the database follows the models; none for one that starts empty. |

A `Transaction` has `find`, `count`, `aggregate`, `write`, `commit()` and
`rollback()`.

### `Schema`

`{ models }`, each model `{ name, dbName?, fields, indexes }`, each index
`{ fields, unique, contains }` (`contains` serves `contains` and
`mode: 'insensitive'`).

| Field kind | Properties                                                                                                                                                                                                                      |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `scalar`   | `name`, `type` (`string`, `number`, `decimal`, `boolean`, `dateTime`, `date`, `json`, `enum`), `values?`, `list`, `integer?`, `precision?`, `scale?`, `optional`, `unique`, `search?`, `dbName?`, `default?`                    |
| `one`      | `name`, `target`, `inverse`, `stored`, `unique`, `optional`, `onDelete` (`cascade`, `restrict`, `setNull`), `dbName?`, `within?` (`{ target, source }`: the target's `target` field equals the row's `source`, a field or `id`) |
| `many`     | `name`, `target`, `inverse`, `join`, `filtered?`, `from?`, `within?` (the `one` both models share)                                                                                                                              |

An integer runs from -2³¹ to 2³¹ - 1. A decimal is a string at its `scale`.
A list is never `null`: `[]` when empty.

### `Read` and `Write`

| Shape       | Properties                                                                                                                                              |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Read`      | `model`, `where?`, `orderBy?` (ending with `id`), `cursor?`, `skip?`, `take?`, `fields?`, `include?`, `count?`, `lock?`, `distinct?`                    |
| `CountRead` | `model`, `where?`                                                                                                                                       |
| `Write`     | `checks?`, `changes`, `read?`, `before?`                                                                                                                |
| `Check`     | `model`, `where`, `count`, `lock?`                                                                                                                      |
| `Change`    | `insert` `{ model, row }`, `update` `{ model, where, set, compute? }`, `delete` `{ model, where }`, `link` and `unlink` `{ model, field, id, targets }` |

In a change, a stored `one` key is the target's id or `null`.

### Errors

| Throw                                                 | When                                                                                      | The developer sees                                                                   |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `UniqueViolation(model, fields)`                      | A unique index refuses a row.                                                             | `UNIQUE_VIOLATION`, `details: { model, fields }`                                     |
| `CheckFailed(index)`                                  | A check counts other than its `count`.                                                    | The error of that check: `NOT_FOUND` or `RELATION_RESTRICTED`                        |
| `OutOfRange(model, field)`                            | A computed number leaves its range or is not finite.                                      | `VALIDATION_FAILED`, the field's range in `issues`                                   |
| `RelationViolation(model, field, target, restricted)` | A foreign key refuses a write.                                                            | `NOT_FOUND`, or `RELATION_RESTRICTED` with `details: { model, field }`               |
| `MigrationFailed(at, reason, locked?)`                | The database refuses a statement or a file; `locked` when it waited too long for a table. | The start, `migrate deploy` or `reset` stops with the statement and the reason       |
| `Conflict()`                                          | The database aborts a transaction for a conflict with another.                            | A serializable transaction runs again; `CONFLICT` after 10 attempts, else `INTERNAL` |

### The feed

| Name         | Value or shape                                                                                       |
| ------------ | ---------------------------------------------------------------------------------------------------- |
| `Feed`       | `changed(changes)`, `lost()`, `missed()`                                                             |
| `Changed`    | `insert`, `update`, `delete` `{ model, ids?, fields? }`; `link`, `unlink` `{ model, field, pairs? }` |
| `feedIds`    | `1000`: the most ids or pairs a change lists.                                                        |
| `feedFields` | `1500`: the longest list of fields, as JSON, an update lists.                                        |

A delete's links go with its rows, unlisted. How changes group into entries
and calls is the adapter's.

### `Migrations`

| Member                 | Does                                                                                                                                |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `snapshot(schema)`     | What the database makes of the models, as JSON.                                                                                     |
| `plan(from, schema)`   | The statements from a snapshot, or `undefined` for an empty database.                                                               |
| `stored()`             | The database's snapshot and the migrations applied, if any.                                                                         |
| `apply(run, counted?)` | Runs a `sync` (statements) or a `deploy` (files) under a lock; `counted` hears the rows each statement of a committed file changed. |
| `reset()`              | Drops every table, for `ultimabase reset`; returns the models' tables.                                                              |
| `remote?`              | The database's host when it is not on this machine: `reset` needs `--force`.                                                        |

A `Statement` is `{ sql, model, does, loses?, tries?, rename? }`.

### `testAdapter`

`testAdapter(name, create, { roundTrips })` declares a Vitest `describe` named
`the ${name} adapter`.

- `create` returns a new adapter for each test, on an empty database.
- `roundTrips` returns how many round trips the adapters have made so far,
  `BEGIN` and `COMMIT` included; the suite checks the differences.

It covers reads, filters, sorts, counts, aggregates, groups, nested writes,
cascades, lists, JSON paths, decimals, dates, searches, transactions, the feed
and round trips.
