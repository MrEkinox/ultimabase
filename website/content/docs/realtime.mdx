title: Realtime
description: Follow a list, a row or a function live, over GraphQL subscriptions or Server-Sent Events.
---

`@ultimabase/realtime` makes a model's reads live: a client subscribes to a
list or a row, gets it once, then only what changed. `realtime()` goes in a
model's `use`:

```npm
npm install @ultimabase/realtime @ultimabase/live
```

<include cwd meta='title="src/models.ts"'>
	../examples/realtime/src/models.ts#task
</include>

The full example, with its tests: [`examples/realtime`](https://github.com/MrEkinox/ultimabase/tree/main/examples/realtime).

`realtimePlugin()` goes in the application's plugins. It needs no transport of
its own: `graphqlPlugin()` and `restPlugin()` serve the live reads when it is
there.

</include>

| To                                   | Use                                                 |
| ------------------------------------ | --------------------------------------------------- |
| follow a list                        | [a `subscription`](#a-live-list)                    |
| follow one row                       | [`where: { id }`](#a-live-row)                      |
| get the whole list on each change    | [page mode](#page-mode)                             |
| follow a list in React               | [`useLiveSubscription`](#react-and-apollo)          |
| follow a list over REST              | [`liveFetch`](#over-server-sent-events)             |
| follow a computed value              | [a live function](#live-functions)                  |
| follow a virtual field               | [it follows what it read](#virtual-fields)          |
| serve live reads on your own socket  | [`plugins.realtime.connect`](#a-socket-of-your-own) |
| close the sockets during maintenance | [`closeUpgrades`](#maintenance)                     |
| follow a list longer than `maxLive`  | [live, then ordinary queries](#long-lists)          |

Each change is placed with the read's filter and order by the server, so the
client never repeats them, and every read is checked under its own caller's
[rights](#rights).

## A live list

A subscription has the name, the arguments, the selection and the type of the
query it follows: replace `query` by `subscription`. GraphQL subscriptions go
over WebSocket, on the GraphQL path, with
[graphql-ws](https://the-guild.dev/graphql/ws).

## React and Apollo

`ultimabaseLive()`, from `@ultimabase/live/apollo`, is an Apollo link placed
before the WebSocket link: it applies each change to the list it holds and
hands Apollo the result.

```npm
npm install @apollo/client graphql-ws rxjs
```

	../examples/realtime/src/TaskList.tsx#apollo
</include>

The subscription is Apollo's own document:

<include cwd meta='title="src/TaskList.tsx"'>
	../examples/realtime/src/TaskList.tsx#document
</include>

`useLiveSubscription`, from `@ultimabase/live/react`, takes the options of
Apollo's `useSubscription` and returns its result plus `fetchMore`, which adds
rows to the list on the same socket, and `fetchingMore`, true while it runs:

<include cwd meta='title="src/TaskList.tsx"'>
	../examples/realtime/src/TaskList.tsx#list
</include>

- `fetchMore()` adds a page of the first page's size, and `fetchMore({ first })`
  that many rows.
- It grows the variable that the root field's `first` (or `take`) reads,
  whatever its name, and resolves once the rows arrived; `data` stays in
  between.
- A call during a growth is ignored.
- A growth that fails goes to `error` and `onError`, and the list goes on as
  it was.

## Over Server-Sent Events

A REST list or row URL with `Accept: text/event-stream` is live too.
`liveFetch(url, { headers })` sets the header, applies the changes, and hands
each listener the whole result, here `a` and `b`. `running.url` is the server's
address:

	../examples/realtime/src/app.test.ts#sse
</include>

It reads over `fetch`, so it sends an `Authorization` header, which
`EventSource` cannot. `fetchMore` grows the list, as in React, here to `a`, `b`
and `c`:

<include cwd meta='title="src/app.test.ts"'>
	../examples/realtime/src/app.test.ts#sse-more
</include>

- It resumes where it was within 10 seconds.
- One stream serves every listener of the same `liveFetch`.

## Virtual fields

A live row or list that selects a
[virtual field](/docs/next/models#virtual-fields) follows the rows its `run` or
`runMany` read, as a live function does: a write that may change a value
computes the rows again, as the subscriber, and sends those whose value
changed. A delete in a model it read computes them all again.

Each subscriber computes its own value, since a read rule may give each a
different one:

- A write to a model a virtual reads costs one run for each subscriber that
  shows a row it read.
- A list of 1000 rows that 1000 subscribers share takes seconds to follow such
  a write; a list each, a few milliseconds.

## Maintenance

[`@ultimabase/maintenance`](/docs/next/maintenance) does what follows on every
server, and refuses the requests too. By hand:

`httpPlugin({ upgrade })` answers each WebSocket upgrade before the plugin that
takes it, GraphQL's included. A `Response` refuses it, sent as it is, and
`undefined` lets it through. It runs after the origin check and reads no
caller. During maintenance, it refuses every new socket:

## Rights

A live read is checked as its query is: the read rules, the `beforeFind`
[hooks](/docs/next/hooks), the field rules. When the caller's rights change,
because a role, an [ACL](/docs/next/acl) or a session changed:

- The server plans the read again and sends the rows that left as `gone`.
- A caller that is no longer the same user, or a session that ended, closes
  its live reads.
- Every caller is built again every five minutes too, for what a hook reads
  outside the database.

## Limits and errors

A live list follows at most `maxLive` rows, 50 000 by default, or the model's
own `.with({ realtime: { maxLive } })`. Nested rows do not count: a nested list
is bounded by its `take`. The `Task` model here sets 50. A `first` past it at
subscribe is refused:

<include cwd meta='title="Request"'>
	../examples/realtime/src/requests/too-many.graphql
</include>

<include cwd meta='title="Response"'>
	../examples/realtime/src/requests/too-many.json
</include>

Over Server-Sent Events, `subscribe`'s second function gets the refusal, a
`LiveError`:

<include cwd meta='title="src/app.test.ts"'>
	../examples/realtime/src/app.test.ts#limits-sse
</include>

- Both numbers are in `details: { limit, rows }`, the limit and the rows the
  list would follow: under `extensions.details` over
  GraphQL, in the `400` body over REST, as `LiveError.details` in
  `@ultimabase/live`.
- `fetchMore` is not refused at the limit: it adds what fits, then
  `hasNextPage` is `false` and a growth does nothing. The rows loaded stay
  live, and `totalCount` stays true.
- A connection following more than `maxConnectionRows` rows in all refuses the
  growth: `liveFetch`'s `fetchMore` rejects, the hook's goes to `error`, and
  the list goes on following its window as it was.
- Over GraphQL, a live list returns at most 50 values a row it reads, the rows
  it nests included; past them, it is refused at subscribe.
- A failed live read does not reconnect. Over GraphQL, the subscription gets
  `errors`, as a query does.

## Long lists

A list can be longer than `maxLive`. Follow its first rows live, over REST.
The request sorts with `orderBy`, here
`encodeURIComponent('[{"rank":"asc"}]')`, and each page has the shape
`{ edges, pageInfo: { hasNextPage, endCursor } }`:

<include cwd meta='title="src/history.ts"'>
	../examples/realtime/src/history.ts#history-live
</include>

Once `hasNextPage` is `false`, read the next ones with ordinary queries, from
the cursor where the live window ends. `after` holds it, and `older` the tasks
read so far:

<include cwd meta='title="src/history.ts"'>
	../examples/realtime/src/history.ts#history-more
</include>

`history(url)` returns `{ shown, more, stop }`: `shown()` is the live rows,
then `older`, and `more()` grows the list.

The live list keeps its first `maxLive` rows up to date; the next ones are read
once. A row added at the top pushes the last live one out of the window: a page
that must keep it on screen keeps the rows it showed.

## Details

- A message keeps the object of every row it did not change, so a row component
  in `memo` renders only the rows that did.
- Past some thousands of rows, use a virtual list: mounting every row is what
  costs, not the messages.
- A message costs the rows it changed, whatever the list's size: 1.2 ms at
  50 000 rows.
- The hook reads with `no-cache`, and the link writes each row to Apollo's
  cache alone, so a fragment elsewhere reads it, and holds it there until it
  leaves the list or the read closes.
- A row deleted or no longer readable leaves the cache too, so no other
  component keeps showing it.
- A plain `useSubscription` through the link works as well, but Apollo then
  writes the whole list on each message: 2.3 s at 50 000 rows.

## Reference

### `realtime()` and `realtimePlugin(options)`

`realtime()` takes no option; a model sets its own limit with
`.with({ realtime: { maxLive } })`, a function its wait with
`.with({ realtime: { debounce } })`.

| Option              | Default   | Effect                                                  |
| ------------------- | --------- | ------------------------------------------------------- |
| `maxLive`           | 50 000    | The most rows a live list follows, nested rows apart.   |
| `maxSubscriptions`  | 100       | The most live reads one connection holds.               |
| `maxConnectionRows` | 100 000   | The most list rows one connection follows in all.       |
| `refresh`           | 5 minutes | How often, in milliseconds, each caller is built again. |
| `liveFunctions`     | none      | Plugin queries made live, as `auth.viewer`.             |

### Messages

| Key                        | Comes                    | Effect                                                                    |
| -------------------------- | ------------------------ | ------------------------------------------------------------------------- |
| `data`                     | first, and in page mode  | The read's result, as its query gives it.                                 |
| `extensions.live.revision` | every message            | One more than the last; a missing number reads the list afresh.           |
| `extensions.live.resume`   | with the first result    | The token that `fetchMore` and a reconnection resume with.                |
| `changes`                  | when `edges` is selected | `{ upsert, after }`: a row placed after another, `after: null` first.     |
|                            |                          | `{ remove, gone }`: a row out of the window; `gone` if deleted or hidden. |
| `totalCount`, `pageInfo`   | when they changed        | Their new values, when selected.                                          |

A change after a quiet is sent at once; the next ones wait for 50 ms to have
passed, and are sent as one message.

A nested relation's count, its connection's `totalCount` or `_count`, is
sent again with its row when a related row is created or deleted. A related
row that moves to another row sends the row it joins again, not the one it
left, whose count stays as it was until that row changes.

A count alone, `tasks { totalCount }` over GraphQL or
`first=0&totalCount=true` over REST, follows no row: it reads no node, and
each change sends the new `totalCount` and no row.

### Transports

| Transport | How                                                                                                                                                                                                        |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GraphQL   | WebSocket on the GraphQL path, protocol `graphql-transport-ws`; page mode as `extensions: { live: { mode: 'page' } }`.                                                                                     |
| REST      | `GET` with `Accept: text/event-stream`; events `resume`, `data`, `live` and `error`, each `id` its revision; `mode=page`; a resume sends `resume=` its token and `Last-Event-ID` the revision it last saw. |

The caller is the upgrade request's, by cookie or `Authorization`, or
`connection_init`'s `{ authorization: 'Bearer …' }`.

- An upgrade from an `Origin` the HTTP plugin's CORS does not allow is a `403`.
- A socket whose caller becomes another user closes with `4403`.
- A socket whose server could not read its caller or follow its reads closes
  with `1013`, and its client connects again.
- A query or mutation sent over the socket reads its caller again first, as
  over HTTP; a subscription keeps the connection's.
- A client message is at most 1 MB; the server pings every 12 seconds.
- Over SSE, a row that does not exist is `null`, not a `404`, and a model that
  is not live is a `400`.

### The viewer

| Member                               | Effect                                                                    |
| ------------------------------------ | ------------------------------------------------------------------------- |
| `plugins.realtime.connect(request)`  | The viewer of the request's caller.                                       |
| `viewer.list(model, args, send)`     | A live list; `send` gets each message. Returns `{ grow, resend, close }`. |
| `viewer.row(model, { where }, send)` | A live row, by a unique `where`.                                          |
| `viewer.onClose(listener)`           | Runs `listener` once the viewer closes; at once if it is closed.          |
| `viewer.close()` and `viewer.closed` | Closes every live read; whether it is closed.                             |
| `viewer.failed`                      | Whether it ended on a failure of the server, not for its caller.          |

A listener that throws is logged; the others still run.

### `@ultimabase/live`

| Export                                                   | Effect                                                                                      |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `applyLive(list, message)`                               | The list with the message's changes; `undefined` if it names a row the list lacks.          |
| `liveFetch(url, { headers })`                            | `{ subscribe(listener, failed), fetchMore({ first }) }`; `subscribe` returns what stops it. |
| `LiveError`                                              | A failed live read: `code`, `message`, and the server's `details` if any.                   |
| `ultimabaseLive()`, from `./apollo`                      | The Apollo link, before the WebSocket link.                                                 |
| `useLiveSubscription(document, options)`, from `./react` | `useSubscription`'s result, plus `fetchMore` and `fetchingMore`.                            |

Apollo 4 with `graphql` and `rxjs`, and React 18 or 19, are optional peer
dependencies.

### Errors

| Code                | Message                                                                                         |
| ------------------- | ----------------------------------------------------------------------------------------------- |
| `VALIDATION_FAILED` | `first is over 50, the most a live list follows.`, with `details: { limit, rows }`.             |
| `VALIDATION_FAILED` | `A connection holds at most 100 live reads.`, `A connection follows at most 100000 rows.`       |
| `VALIDATION_FAILED` | `Author is not live.`: the selection reaches a model whose `use` lacks `realtime()`.            |
| `VALIDATION_FAILED` | `A live list sorts by Task's own fields: author reads another row.`                             |
| `VALIDATION_FAILED` | `A live comments list needs a take.`, for a nested list.                                        |
| `BAD_USER_INPUT`    | `Task is not live: list realtime() in its use.`, a stream of a model that is not live, a `400`. |
| `BAD_USER_INPUT`    | `first is at most 100 on Task in page mode.`                                                    |
| `BAD_USER_INPUT`    | `Select the node's id to follow a live list.`, from the client.                                 |
| `BAD_USER_INPUT`    | `fetchMore grows a live list: its root field needs first or take from a variable.`              |
| `BAD_USER_INPUT`    | `fetchMore grows a live subscription once it runs.`                                             |
| `BAD_USER_INPUT`    | `first must be a positive integer.`                                                             |
| `INTERNAL`          | `The live read closed.`: the server closed it.                                                  |

At start: `realtime's maxLive must be a positive integer.`, and
`addTask is a mutation: it cannot be live.`

### Limits

- A list follows a window from its top: `first`, never `after`, `before`,
  `last` or `skip`.
- A live list sorts by the model's own fields.
- Writes made outside UltimaBase, as raw SQL, are not seen.
- With [PostgreSQL](/docs/next/postgres), changes arrive through
  `pg_notify`, once the transaction commits.
