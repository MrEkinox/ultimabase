A hook is a model's own code, run on each of its reads and writes. A model's
`.with({ hooks })` lists them:

<include cwd meta='title="src/tag.ts"'>
	../examples/hooks/src/tag.ts#tag
</include>

The full example, with its tests: [`examples/hooks`](https://github.com/MrEkinox/ultimabase/tree/main/examples/hooks).

| To                                  | Use                                                           |
| ----------------------------------- | ------------------------------------------------------------- |
| change the data before it's written | [`beforeCreate`, `beforeUpdate`](#change-the-data)            |
| refuse a write                      | [any `before*` hook](#refuse-a-write)                         |
| hide rows                           | [`beforeFind`](#hide-rows)                                    |
| write more with the row             | [`afterCreate`, `afterUpdate`, `afterDelete`](#after-a-write) |
| compare a row's fields              | [`afterCreate`, `afterUpdate`](#a-rule-across-a-rows-fields)  |
| email, call a webhook               | [`afterCreateCommit` and the others](#once-it-commits)        |
| limit a person's writes             | [`beforeCreate`](#limit-a-persons-writes)                     |
| number rows in order                | [the parent's `beforeUpdate`](#number-rows-in-order)          |

Each hook receives the `caller` of the query, and may be `async`. A query it
makes passes its own `{ as }`: `{ as: caller }` for the caller's rules,
`{ as: master }` for none, with `master` from `ultimabase`.

The sections below show the hooks of a support ticket, which starts like this.
Its tests write `as` for `{ as: master }`.

## Change the data

`beforeCreate` receives the `data` of the create; `beforeUpdate` the stored
`record` and the `data` of the update. Each changes `data` in place:

<include cwd meta='title="src/models.ts"'>
	../examples/hooks/src/models.ts#change
</include>

<include cwd meta='title="src/app.test.ts"'>
	../examples/hooks/src/app.test.ts#before
</include>

- They run after the access rules, and before the write.
- `beforeCreate` runs after the defaults: a field with a default is already
  set, in its value and in its type.
- A field a hook writes skips its field access rules: here `closedAt`, which
  no client writes.
- The data is checked again after the hooks: a required field left empty fails
  with `VALIDATION_FAILED` and `Required.`, so a hook may fill it.

## Hide rows

`beforeFind` returns a filter built with `where`, or nothing:

<include cwd meta='title="src/models.ts"'>
	../examples/hooks/src/models.ts#find
</include>

<include cwd meta='title="src/app.test.ts"'>
	../examples/hooks/src/app.test.ts#find
</include>

The filter joins every query that reaches the model, whoever the caller, Master
included: lists, counts, includes, relation filters, and the rows an update or
a delete targets. This is how [soft delete](/docs/next/soft-delete) hides the
deleted rows.

`operation` says what the rows are found for: `'read'`, `'update'` or
`'delete'`.

## After a write

`afterCreate`, `afterUpdate` and `afterDelete` run in the write's transaction,
once the row is written. `record` is the row as written, and an update's
`previous` the row before:

<include cwd meta='title="src/models.ts"'>
	../examples/hooks/src/models.ts#after
</include>

<include cwd meta='title="src/app.test.ts"'>
	../examples/hooks/src/app.test.ts#after
</include>

- What they write commits with the row, and a hook that throws undoes it all.
- `create` and `update` read their row again after these hooks, so the returned
  row shows what they wrote.

## A rule across a row's fields

A rule that compares fields of one row reads the row as written, in
`afterCreate` and `afterUpdate`: an update's `data` holds only the fields it
changes, `record` all of them. Here a call ends with a reason:

<include cwd meta='title="src/models.ts"'>
	../examples/hooks/src/models.ts#row-rule
</include>

<include cwd meta='title="src/models.ts"'>

<include cwd meta='title="src/app.test.ts"'>

The hooks run for every caller, Master included, and for each row of a
`createMany` or an `updateMany`. A throw undoes the write.

## Once it commits

`afterCreateCommit`, `afterUpdateCommit` and `afterDeleteCommit` get the same
facts as the `after*` hooks, and run once the transaction commits. They are for
what cannot be undone: an email, a webhook, a message to another service. Here
`outbox` stands for an email service: an array of the messages sent.

<include cwd meta='title="src/models.ts"'>
	../examples/hooks/src/models.ts#commit
</include>

A rollback sends nothing, and the ticket stays open:

<include cwd meta='title="src/app.test.ts"'>
	../examples/hooks/src/app.test.ts#rollback
</include>

A commit sends it:

<include cwd meta='title="src/app.test.ts"'>
	../examples/hooks/src/app.test.ts#commit
</include>

- The write, or the outermost [transaction](/docs/next/transactions), resolves
  once they are done, so a test or a serverless function never ends before them.
- A `*Commit` hook that throws is logged at `error` and is not thrown: the write
  is already committed.
- A `*Commit` hook runs in memory: a crash before it ends loses it. What must
  happen even then goes in a [job](/docs/next/jobs), enqueued from an `after*`
  hook in the write's transaction.

## Limit a person's writes

The HTTP server limits each address's requests
([rate limit](/docs/next/http#rate-limit)). A limit per person on a write is a
`beforeCreate` hook that counts the caller's recent rows and throws
`TOO_MANY_ATTEMPTS`, sent with HTTP 429 and `Retry-After`.

A comment stores its author, and only a signed-in person may create one:

<include cwd meta='title="src/models.ts"'>
	../examples/hooks/src/models.ts#comment
</include>

<include cwd meta='title="src/models.ts"'>
	../examples/hooks/src/models.ts#limit
</include>

<include cwd meta='title="src/app.test.ts"'>
	../examples/hooks/src/app.test.ts#limit
</include>

- Each person's comments count apart.
- It counts writes, not requests: a GraphQL document that creates ten comments
  with aliases counts ten.
- Writes sent at the same instant may each pass the count; a limit that must
  never be exceeded runs the write in a
  [serializable transaction](/docs/next/transactions#serializable-transactions).

## Number rows in order

A card goes after the last card of its board, those the caller cannot read
included, so the server numbers it. Its `position` returns no default: a
create may leave it out, and the check after the hooks still requires it.

<include cwd meta='title="src/cards.ts"'>
	../examples/hooks/src/cards.ts#card
</include>

The cards one write creates are written together, after all their hooks, so
each card's own hook would read the same last position. The board numbers
them first:

<include cwd meta='title="src/cards.ts"'>
	../examples/hooks/src/cards.ts#board
</include>

<include cwd meta='title="src/app.test.ts"'>
	../examples/hooks/src/app.test.ts#cards

- A position the write gives is kept.
- Cards created at the same instant, in two writes, may take the same
  position; order them by `position`, then `createdAt`.

## Details

### `beforeFind`

- A create returns its row even when the filter hides it.
- A `cascade` delete reaches the hidden rows too.

### A rule and `setNull`

`afterUpdate` also runs on the rows a `setNull` relation empties when its target
is deleted. The hook decides when its rule applies: a rule that needs the
relation can check only the writes that change it, comparing `record` with
`previous`, and the delete goes through.

A `check` constraint written in SQL holds at every write, and would refuse that
delete; [postgres()](/docs/next/postgres#your-own-sql) returns its refusal as
`VALIDATION_FAILED`.

## Reference

### Hooks

| Hook                | Receives                       | Runs                                     |
| ------------------- | ------------------------------ | ---------------------------------------- |
| `beforeFind`        | `caller`, `operation`, `where` | on each query that reaches the model     |
| `beforeCreate`      | `caller`, `data`               | after the access rules, before the write |
| `beforeUpdate`      | `caller`, `record`, `data`     | after the access rules, before the write |
| `beforeDelete`      | `caller`, `record`             | after the access rules, before the write |
| `afterCreate`       | `caller`, `record`             | after the write, in its transaction      |
| `afterUpdate`       | `caller`, `record`, `previous` | after the write, in its transaction      |
| `afterDelete`       | `caller`, `record`             | after the write, in its transaction      |
| `afterCreateCommit` | as `afterCreate`               | once the transaction commits             |
| `afterUpdateCommit` | as `afterUpdate`               | once the transaction commits             |
| `afterDeleteCommit` | as `afterDelete`               | once the transaction commits             |

`record` and `previous` hold `id`, `createdAt`, `updatedAt`, each field, and
each `one` relation as `{ id }` or `null`. `beforeFind` returns
`where({ ... })` or nothing; the others return nothing. Each hook also receives
`logger`, the application's logger.

### When they run

- The plugins' hooks run first, in the order of `plugins`, then the model's.
- `createMany`, `updateMany` and `deleteMany` run the hooks of each row.
- A nested write runs the hooks of each model it writes. A row a relation
  write moves runs `beforeUpdate`, with `data` holding the relation as
  `{ connect: { id } }` or `{ disconnect: true }`, then `afterUpdate`.
- A cascade runs the `beforeUpdate` of its `setNull` rows, then the
  `beforeDelete` of the deleted rows, the deepest first; the `after*` hooks
  follow in the same order. See [Relations](/docs/next/relations).
- A nested write runs the `before*` hooks of all its rows, then writes them
  together: a hook does not see the rows created beside its own. See
  [Number rows in order](#number-rows-in-order).
- `beforeFind` runs once per query and model.

### Errors

| Thrown by a hook | The client receives                                      |
| ---------------- | -------------------------------------------------------- |
| a `PublicError`  | its code, message and details                            |
| any other error  | `INTERNAL`, with a correlation id; the message is logged |
| in a `*Commit`   | nothing: logged at `error`, the write already resolved   |

### Limits

- There is no `afterFind`: a value computed on read is a
  [virtual field](/docs/next/models).
- A hook's own queries run its hooks too: a hook that updates its own model
  runs again.
