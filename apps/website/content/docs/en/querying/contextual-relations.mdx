A relation can own a reusable target `where` when every traversal through that
field represents the same narrower application view. The filter may be a static
object or a synchronous request-aware resolver.

```ts title="src/channel.ts" fixture="querying/contextual-relations.ts"
import { Schema } from '@ultimabase/core'

export const Channel = Schema.define({
	className: 'QueryChannel',
	fields: (field) => ({
		messages: field.relation({
			target: 'QueryMessage',
			where: ({ context, where }) =>
				context.access.mode === 'master' ? where : where.eq('published', true),
		}),
		name: field.string({ required: true }),
	}),
})

export const Message = Schema.define({
	className: 'QueryMessage',
	fields: (field) => ({
		body: field.string({ required: true }),
		published: field.boolean({ default: false }),
	}),
})
```

The supplied `WhereBuilder` starts empty, is immutable, and targets the exact
related schema. The callback runs synchronously at most once per exact relation
field in one root operation. It receives request context but no source item,
adapter, database, transaction, transport request, or authority grant.

## Effective visible collection

Every relation read intersects, in order:

```text
physical membership
AND the relation's declared where
AND the caller's target where
AND target authorization row filters
AND target protected constraints
```

The declaration and caller filter never replace one another. The same
intersection drives relation handles, eager includes, REST relationship
projections, GraphQL relation connections, quantifiers, emptiness, and counts.

## Shaping is not authorization

This filter narrows only traversal through the exact relation field. It cannot
prevent the same target from being read through a schema-root query or another
relationship. Use Access, ACL, and protected constraints for security.

Master authority does not automatically bypass relation shaping. The example
explicitly returns the empty builder for Master because that difference is part
of this relation's declared application behavior.

## Read and write boundaries

The filter affects reads, not physical membership. It does not change
`connect`, `disconnect`, `set`, or `clear`, and it does not remove hidden edges.
A target excluded from the read view may still be changed when ordinary
mutation policy permits it.

The callback remains private Runtime behavior. It does not enter Typegen,
transport metadata, the public Query AST, or adapter requests. Adapters receive
only normalized portable predicates after Core has resolved and bounded them.
