UltimaBase separates concerns that are often collapsed into “auth.” Keeping the
layers distinct prevents a valid identity, a routing header, or a convenient
filter from becoming an accidental permission.

| Layer             | Answers                                                              | Typical owner                                     |
| ----------------- | -------------------------------------------------------------------- | ------------------------------------------------- |
| Identity          | Who is associated with this request?                                 | Password Auth or another identity plugin          |
| Authentication    | Is the presented credential valid?                                   | The credential-owning plugin                      |
| Authorization     | May this subject perform this operation on these objects and fields? | Access, ACL, or another policy plugin             |
| Validation        | Is this input structurally and semantically valid?                   | Core plus installed Validation and Hooks behavior |
| Read shaping      | Which application-defined view does this path present?               | Query and relation declarations                   |
| Trusted authority | Is this audited server code allowed to bypass authorization?         | Core `MasterAuthority`                            |

Core has exactly two authority modes: `anonymous` and `master`. An authenticated
principal remains in anonymous Core authority unless a separate, application-owned
Master credential is verified. Authentication establishes identity and grants no
authorization.

Authorization is optional and composable. Installing Access or ACL contributes a
protected policy; omitting them contributes no neutral handler. When multiple
policies are installed, Core combines their decisions monotonically: denials remain
denials, row predicates use `AND`, and field or result sets can only narrow.

> **Security boundary:** A relation `where`, a UI filter, or a transport projection
> shapes one read path. It does not protect the same object through another query.
> Use Access, ACL, or another protected policy for authorization.

Master is trusted, server-side authority. It bypasses authorization decisions, but
Core still runs structural validation, installed application validation, Hooks,
transactions, database constraints, lifecycle work, and integrity maintenance.

Continue with [Password Authentication](./password-authentication) for local users,
[Access](./access) for application policy, [ACL](./acl) for per-object policy, and
[Master Authority](./master-authority) for trusted maintenance work.
