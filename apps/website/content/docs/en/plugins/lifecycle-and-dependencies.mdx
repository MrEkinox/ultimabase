Use a dependency when provider-first declaration or lifecycle order is part of
the contract. Dependencies—not the source array—control ordering.

```ts title="src/lifecycle.ts"
import { definePlugin } from '@ultimabase/core'

export const storagePlugin = definePlugin({
	core: '^0.0.0',
	pluginId: 'community.storage',
	setup: () => ({ connected: false }),
	version: '1.0.0',
})

export const searchPlugin = definePlugin({
	core: '^0.0.0',
	dependencies: [{ pluginId: 'community.storage', version: '^1.0.0' }],
	hooks: {
		connect: ({ pluginExports }) => {
			void pluginExports.ready
		},
		dispose: ({ pluginExports }) => {
			void pluginExports.ready
		},
	},
	pluginId: 'community.search',
	setup: () => ({ ready: true as const }),
	version: '1.0.0',
})
```

The fixed startup sequence is static declaration, application-capability
materialization, setup, connect, schema preparation, Runtime start, then
transport start. Stop and dispose run in reverse dependency order. A nested
plugin is only configuration sugar over the same global graph; its parent sets
the corresponding lifecycle relationship and grants no privileges.

Use `optionalDependencies` when that ordering is needed only if another plugin
is installed. Use a `peer` when presence and version compatibility are required
but lifecycle ordering would be false coupling. A peer grants no capability
read or setup export.

Capability requirements default to materialization phase and create
provider-first ordering. Use `phase: 'setup'` only for a genuine peer protocol
whose application values can materialize independently; it creates no later
lifecycle guarantee. Cycles and missing required providers fail before effects.
