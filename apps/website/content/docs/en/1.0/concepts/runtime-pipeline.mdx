Every direct TypeScript, REST, and GraphQL operation enters one Core-owned
Runtime pipeline. Transports normalize their wire formats; they do not issue
SQL, evaluate policy, or invent a parallel execution path.

```text
normalize → structural validation → policy and target loading
          → resolve input → final structural validation → policy re-check
          → before behavior → persistence → after behavior
          → output restrictions → commit → post-commit events
```

## Why the order matters

The initial structural check rejects malformed input before application code
runs. Target-aware input resolution and arithmetic projection happen only after
the visible target can be loaded and locked. Core then repeats mandatory
structural validation without replaying defaults or generators.

Policy contributions are monotonic: deny-only guards, row filters, adapter
constraints, field restrictions, and output subsets can narrow accumulated
access but never broaden it. Value-dependent policy is evaluated again after
the final mutation candidate exists.

Business after-Hooks still run inside the transaction and may abort it.
Post-commit subscribers run only after the outer commit succeeds. Master
authority bypasses authorization policy, not validation, Hooks, transactions,
database constraints, or integrity work.

## One path, different owners

Core fixes the invariant order. Optional plugins contribute only through their
declared boundaries, and the database adapter receives the final protected
persistence work. This keeps transport presentation separate from application
semantics.

Use [Mutations and Transactions](../mutations/transactions) for application
code, [Run Lifecycle Hooks](../guides/run-lifecycle-hooks) for business behavior,
and [Errors](../apis/errors) for the boundary that serializes failures.
