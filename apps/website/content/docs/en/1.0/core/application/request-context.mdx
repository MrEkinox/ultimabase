A request context carries one operation through one exact compiled application.
It holds request identity, diagnostic source, metadata, cancellation, Core
authority, and typed values contributed by installed plugins.

## Scope before identity

The application boundary comes first. An HTTP request must select one mounted
application before its transport handler begins. Direct TypeScript callers get
the same scope from that application's request engine.

Core has only two authority modes:

- `anonymous` is the ordinary non-privileged mode;
- `master` is trusted server-side authority created and verified by that exact
  application.

Authentication plugins may add a typed subject or session to the context. That
does not create a third Core mode and grants nothing by itself; Access, Roles,
and ACL remain independent policy providers.

## Attribution is not authorization

Request IDs, source labels, headers, metadata, and plugin values improve
tracing and application logic. None of them can manufacture Master authority.
A raw Master key, when explicitly enabled for HTTP, is verified and audited by
the selected application's Core authority boundary before it becomes a trusted
context.

Contexts are immutable snapshots. Derived execution retains the application,
authority, metadata, cancellation signal, and active transaction without
exposing a mutable engine or adapter to transports.

[Master Authority](/docs/1.0/core/security-foundations/master-authority) for the trust boundary, and
[HTTP Applications](/docs/1.0/plugins/official/http-and-apis/http) for transport selection.
