UltimaBase takes its inspiration from Parse Server: classes, pointers,
relations, ACLs, roles and a Master key keep familiar names. It is not a Parse
Server clone. This page maps what you know from Parse Server to UltimaBase,
shows common tasks side by side, explains what works differently and why, and
lists what UltimaBase does not offer yet.

<Callout type="warn" title="Not compatible with Parse clients or data">
	UltimaBase does not implement the Parse REST or GraphQL wire format, so Parse
	SDK clients cannot connect to it, and there is no tool that migrates a Parse
	database. Moving an application means rewriting its schema and server code.
</Callout>

This page compares with Parse Server 9.10.5 and the Parse JavaScript SDK
8.6.2, checked on 2026-10-17. The [comparison overview](/docs/1.0.0/comparison/overview)
puts both side by side with the other systems.

## Common tasks side by side

Each task names the Parse Server API in prose and shows the UltimaBase code
from a tested example in the repository. The examples call their application
`ultimabase` and their factory `App`.

### Declare a class

In Parse Server, a class can appear on the first save, its field types lock
after the first write, and an optional defined schema in the server options
declares fields, indexes and class-level permissions[^p3]<sup>,</sup>[^p7]. In UltimaBase
you declare every schema in TypeScript and list it in the application; nothing
is created implicitly. Pointers and relations are fields of the schema:

<include cwd meta='title="src/schema.ts"'>
	../../examples/queries/src/schema.ts#post
</include>

The model types, filter types and include types of `Post` come from this
declaration, with no generation step.

### Create an object

Parse Server: `new Parse.Object('Post')`, `set(...)`, then `save()`[^p3]. In
UltimaBase there is no object to save; you call the schema's `createOne` with
the data and choose what the result contains:

<include cwd meta='title="src/writes.ts"'>
	../../examples/queries/src/writes.ts#create-post
</include>

`updateOne`, `upsertOne`, `deleteOne` and their `Many` variants follow the same
shape; see [Create](/docs/1.0.0/core/writing-data/create).

### Query objects

Parse Server: `new Parse.Query('Post')` with `equalTo`, `descending`, `limit`
and `select`, then `find()`[^p3]. In UltimaBase one object holds the whole
query:

<include cwd meta='title="src/reads.ts"'>
	../../examples/queries/src/reads.ts#published-posts
</include>

Parse's `first()` corresponds to `findOne`, and `count()` to `count`.
UltimaBase has no `distinct`, `aggregate` or `fullText` equivalent.

### Load related objects

Parse Server: `query.include('author')`[^p3]. UltimaBase's `include` takes its
own selection, filter, ordering and limit for each relation:

<include cwd meta='title="src/reads.ts"'>
	../../examples/queries/src/reads.ts#post-context
</include>

Where Parse Server uses `matchesQuery` or `relatedTo`, UltimaBase filters on a
relation with `some`, `none`, `every` or `count`:

<include cwd meta='title="src/reads.ts"'>
	../../examples/queries/src/reads.ts#relation-filters
</include>

### Write several objects atomically

Parse Server groups writes through the REST `/batch` endpoint with
`transaction: true`, which the source code describes but the guides do
not[^p8]. In UltimaBase every mutation already runs in a transaction, and
`ultimabase.transaction` groups several of them; a thrown error rolls all of
them back:

<include cwd meta='title="src/transactions.ts"'>
	../../examples/queries/src/transactions.ts#publish
</include>

### Use the master key

Parse Server: pass `{ useMasterKey: true }` to a server-side call; the master
key bypasses ACLs and class-level permissions[^p1]. UltimaBase keeps the option
name, but Master must be configured on the application with an audit callback,
and it bypasses authorization only:

<include cwd meta='title="tests/master.test.ts"'>
	../../examples/queries/tests/master.test.ts#context-and-master
</include>

Validation, hooks, transactions and integrity checks still run. A client flag,
header or request context never creates Master; see
[Know what Master bypasses](/docs/1.0.0/core/security-foundations/master-authority#know-what-master-bypasses).

### Set class-level and field permissions

Parse Server: class-level permissions per operation, pointer permissions and
`protectedFields`[^p2]<sup>,</sup>[^p11]. UltimaBase's Access plugin attaches one rule per
operation to the schema. A read rule returns a filter that becomes part of the
database query, a field rule hides or protects one field, and an operation
without a rule is denied:

<include cwd meta='title="src/schema.ts"'>
	../../examples/access/src/schema.ts#article
</include>

Rules are TypeScript functions, so a rule can compare the caller with a field,
as a pointer permission does in Parse Server, or with any other condition.

### Share an object with an ACL

Parse Server: `new Parse.ACL(user)`, `setReadAccess`, `setRoleWriteAccess`[^p2].
In UltimaBase the Object ACLs plugin adds a per-row ACL to schemas that declare
`acl: true`, with a default ACL for new rows:

<include cwd meta='title="src/schema.ts"'>
	../../examples/acl/src/schema.ts#note
</include>

Grants and revocations are part of an ordinary update:

<include cwd meta='title="src/sharing.ts"'>
	../../examples/acl/src/sharing.ts#share
</include>

### Define roles

Parse Server: `Parse.Role` objects with users, child roles, and role-based ACL
entries[^p3]. UltimaBase's Roles plugin declares a role schema, its members and
the roles to create at start:

<include cwd meta='title="src/schema.ts"'>
	../../examples/roles/src/schema.ts#staff-role
</include>

Access rules then check membership, including inherited roles:

<include cwd meta='title="src/schema.ts"'>
	../../examples/roles/src/schema.ts#post
</include>

### Run code before and after a save

Parse Server: `Parse.Cloud.beforeSave` and `Parse.Cloud.afterSave`[^p4]. In
UltimaBase the Hooks plugin attaches hooks to the schema. `resolveInput`
rewrites the input, `beforeOperation` can refuse the write,
`afterOperation` writes related data in the same transaction, and
`afterCommit` runs external effects once the transaction has committed:

<include cwd meta='title="src/schema.ts"'>
	../../examples/hooks/src/schema.ts#post
</include>

Hooks never run for reads. There is no `beforeFind` or `afterFind`; see
[What works differently](#what-works-differently-and-why).

### Define a Cloud function

Parse Server: `Parse.Cloud.define('name', handler, validator)`, called with
`Parse.Cloud.run` or the REST `/functions` route[^p4]<sup>,</sup>[^p5]. UltimaBase's
custom operation declares its input and output with a validator; the REST
plugin exposes it and describes it in OpenAPI:

<include cwd meta='title="src/operations.ts"'>
	../../examples/rest/src/operations.ts#operation
</include>

[Operations and GraphQL](/docs/1.0.0/plugins/build-a-plugin/operations-and-graphql)
shows how to bind the same operation to GraphQL.

### Validate fields

Parse Server: Cloud Function validators and checks in `beforeSave`[^p4]. The
UltimaBase Validation plugin attaches a Standard Schema validator (such as Zod)
or a function to each field, plus a schema-level check:

<include cwd meta='title="src/schema.ts"'>
	../../examples/validation/src/schema.ts#event
</include>

### Sign users up and in

Parse Server: `Parse.User` with `signUp` and `logIn`; email verification and
password reset need an email adapter[^p3]<sup>,</sup>[^p1]. UltimaBase's auth plugin
designates a user schema, and the password method adds the identifier fields:

<include cwd meta='title="src/schema.ts"'>
	../../examples/auth/src/schema.ts#member
</include>

<include cwd meta='title="tests/sign-up.test.ts"'>
	../../examples/auth/tests/sign-up.test.ts#sign-up
</include>

<include cwd meta='title="tests/sign-up.test.ts"'>
	../../examples/auth/tests/sign-up.test.ts#login
</include>

UltimaBase sends no email itself: verification, reset and email-change flows
call delivery callbacks that your application supplies. See
[Password Authentication](/docs/1.0.0/plugins/official/password-authentication).

### Test the application

Parse Server's README shows how to run a local server with a test MongoDB or
Docker[^p1]. UltimaBase ships `testApplication`, which starts your application
against PostgreSQL in Testcontainers with one database schema per test worker;
see [Test an Application](/docs/1.0.0/guides/test-an-application).

## What works differently and why

- **Schemas are declared, never inferred from writes.** Parse Server can create
  classes and fields from the data it receives[^p3]. UltimaBase registers every
  schema explicitly so that the same declaration produces the database tables,
  the TypeScript types and the rules, and a typo cannot create a column.
- **There is no Active Record.** A `Parse.Object` tracks its changes and saves
  itself. UltimaBase models are immutable values; every write is a call such as
  `createOne` or `updateOne` that goes through one operation pipeline. Server
  code, REST and GraphQL therefore get the same validation, rules, hooks and
  transaction.
- **Core is small; features are plugins you install.** Parse Server ships its
  features in one package, configured through server options and
  adapters[^p1]<sup>,</sup>[^p11]. UltimaBase Core knows schemas, queries, operations,
  transactions and Master only. Access, ACLs, roles, hooks, validation,
  authentication, HTTP, REST and GraphQL are optional plugins, and community
  plugins use the same public contracts.
- **Master is audited and narrower.** The Parse Server master key bypasses ACLs
  and class-level permissions[^p1]. UltimaBase Master is configured on the
  application with a mandatory audit callback, bypasses authorization only, and
  can never come from client input.
- **Transactions are the default.** Each UltimaBase mutation runs in a
  transaction together with its hooks, nested writes and reference updates.
- **No read hooks.** Parse Server's `beforeFind` and `afterFind` can rewrite
  queries and results[^p4]. UltimaBase compiles Access read rules into the
  database query instead, so pagination and counts stay consistent with what
  the caller may see, and computed values come from
  [virtual fields](/docs/1.0.0/core/data-modeling/virtual-fields).
- **PostgreSQL only.** Parse Server supports MongoDB and PostgreSQL[^p1].
  UltimaBase Core is database-independent, but PostgreSQL is the only database
  plugin.
- **Types end to end.** The Parse JavaScript SDK types objects with a generic
  attributes record that is not derived from your schema[^p13]. UltimaBase
  infers types from the schema declarations.

## What UltimaBase does not offer yet

| Parse Server capability                                       | UltimaBase status                                                                                                                  |
| ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| LiveQuery[^p2]                                                | Planned: [Realtime](/docs/1.0.0/project/roadmap#application-capabilities)                                                          |
| `Parse.File` and file adapters[^p2]                           | Planned: [File fields](/docs/1.0.0/project/roadmap#next-priorities)                                                                |
| Third-party sign-in adapters[^p10]                            | Planned: [More authentication](/docs/1.0.0/project/roadmap#application-capabilities)                                               |
| Multi-factor authentication adapter, described in source[^p9] | Planned after OAuth, in [More authentication](/docs/1.0.0/project/roadmap#application-capabilities)                                |
| Jobs[^p4]                                                     | Planned: [Background jobs](/docs/1.0.0/project/roadmap#application-capabilities)                                                   |
| Parse Dashboard[^p12]                                         | Planned: [Administration](/docs/1.0.0/project/roadmap#shipping-and-operations)                                                     |
| Client SDKs[^p13]                                             | Planned: a [TypeScript SDK](/docs/1.0.0/project/roadmap#apis-and-developer-tools); clients use REST or GraphQL today               |
| GeoPoint and Polygon[^p3]                                     | Planned among the [advanced field plugins](https://github.com/MrEkinox/ultimadatabase/blob/main/ROADMAP.md#advanced-field-plugins) |
| Push notifications[^p2]                                       | Not on the roadmap                                                                                                                 |
| Anonymous users[^p5]                                          | Not on the roadmap                                                                                                                 |
| `fullText`, `distinct` and `aggregate` queries[^p3]           | Not on the roadmap; `count` is the only aggregate                                                                                  |
| MongoDB[^p1]                                                  | Not on the roadmap                                                                                                                 |
| `beforeFind` and `afterFind`[^p4]                             | Not planned: reads are filtered by Access rules                                                                                    |
| Email adapter[^p1]                                            | Not planned: the auth plugin calls delivery callbacks you supply                                                                   |
| Migration from a Parse database                               | Not planned                                                                                                                        |

Planned is not shipped: the [Roadmap](/docs/1.0.0/project/roadmap) gives no
dates or order.
