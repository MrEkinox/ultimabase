Prisma ORM is a typed database client: you describe models in its schema
language, generate a client, and keep authorization, validation, hooks and APIs
in your own application. UltimaBase covers the data layer too, with a similar
query vocabulary, and adds the backend around it: every call, from server code,
REST or GraphQL, goes through the same rules, validation, hooks and
transaction. This page maps Prisma ORM concepts to UltimaBase.

This page compares with Prisma ORM 7 (7.10.1), checked on 2026-10-17. Prisma
ORM 8 is a release candidate that changes the schema file, the generation
command, the query shape and the transaction API[^pr17][^pr18]; the notes say
where it differs. See the [comparison overview](/docs/1.0.0/comparison/overview)
for a summary table.

## Common tasks side by side

| Task                    | Prisma ORM 7                                                          | UltimaBase                                                     |
| ----------------------- | --------------------------------------------------------------------- | -------------------------------------------------------------- |
| Declare a model         | A `model` block, then `migrate dev` and `generate`[^pr1][^pr2][^pr11] | `App.Schema.define`; no generation step                        |
| Query with a relation   | `findMany` with `include`[^pr7]                                       | `findMany` with `include`                                      |
| Create with nested data | `create` with `connect` or nested `create`[^pr7]                      | `createOne` with `connect` or nested `create`                  |
| Group writes            | Interactive `$transaction` with a `tx` client[^pr8]                   | `ultimabase.transaction`; no transaction client to pass around |
| Intercept queries       | A client extension's `query` component[^pr9]                          | Schema or global hooks                                         |
| Raw SQL                 | `$queryRaw`, `$executeRaw`[^pr31]                                     | No raw SQL API                                                 |
| Aggregate               | `aggregate`, `groupBy`[^pr5]                                          | `count` only                                                   |

## What works differently and why

- **ORM or backend.** Prisma ORM leaves authorization, validation, hooks, APIs
  and authentication to you. UltimaBase enforces them in one operation
  pipeline, so a REST request and a server call obey the same rules. The cost
  is a narrower data layer: one database and no raw SQL.
- **No generation step.** Prisma ORM generates a client from a separate schema
  language[^pr11]. UltimaBase declares schemas in TypeScript and infers the
  types, so there is nothing to regenerate after a change.
- **No raw SQL.** Prisma ORM offers raw queries as an escape hatch[^pr31].
  UltimaBase exposes none, so no query can skip the rules and hooks. Work that
  needs SQL runs outside UltimaBase on your own connection, and then outside
  its guarantees too.
- **Migrations.** Prisma Migrate produces versioned migration files[^pr2].
  UltimaBase synchronizes the schema at startup; versioned migrations are
  [planned](/docs/1.0.0/project/roadmap#next-priorities).
- **Databases.** Prisma ORM 7 supports PostgreSQL, MySQL, MariaDB, SQLite, SQL
  Server and CockroachDB[^pr13]. UltimaBase supports PostgreSQL only.
- **Stability.** Prisma ORM 7 is stable, and Prisma ORM 8 replaces client
  extensions with middleware and drops the transaction isolation and timeout
  options[^pr18][^pr29]. UltimaBase is pre-release, and its APIs may change
  too.

## What UltimaBase does not offer yet

| Prisma ORM capability                        | UltimaBase status                                                                                                            |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Versioned migrations[^pr2]                   | Planned: [PostgreSQL migrations](/docs/1.0.0/project/roadmap#next-priorities)                                                |
| `aggregate` and `groupBy`[^pr5]              | Not on the roadmap; `count` is the only aggregate                                                                            |
| Databases other than PostgreSQL[^pr13]       | Not on the roadmap                                                                                                           |
| Raw SQL[^pr31]                               | Not planned                                                                                                                  |
| Choosing a transaction isolation level[^pr8] | Not on the roadmap; transactions are at least read-committed, see [Transactions](/docs/1.0.0/core/writing-data/transactions) |

Planned is not shipped: the [Roadmap](/docs/1.0.0/project/roadmap) gives no
dates or order.
