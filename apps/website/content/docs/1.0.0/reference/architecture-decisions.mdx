Architecture Decision Records explain why important boundaries were chosen,
what they replaced, and which alternatives were deliberately rejected. They
are useful when you author a plugin, investigate an invariant, or propose a
change that crosses package, security, persistence, or public API ownership.

## Choose the right source

| Question                                  | Start here                                               |
| ----------------------------------------- | -------------------------------------------------------- |
| How do I complete an application task?    | This public documentation                                |
| What does one package export today?       | Its README and public package root                       |
| What behavior actually runs?              | Developer declarations and compiled application behavior |
| Why does an architectural boundary exist? | The accepted ADR and its refinements                     |
| What work is planned or complete?         | The issue backlog and active plan                        |

An ADR is historical evidence, not beginner documentation and not a substitute
for current package contracts. Accepted decisions are not rewritten to hide
their history; a later decision refines or supersedes them explicitly. That
means older examples or names inside an ADR can remain intentionally historical.

## When to read or write one

Read the linked ADR when a public guide calls out a security or architecture
boundary that affects your design. Propose a new decision before changing
dependency direction, storage format, public API conventions, or security
semantics. Ordinary usage does not require reading the ADR collection.

For the product-level boundary, start at [What is UltimaBase](/docs/1.0.0).
For current public entry points, use [Reference](/docs/1.0.0/reference/package-index). For
plugin architecture, continue with [Plugin System](/docs/1.0.0/plugins/overview).
