## Context

An UltimaBase application is built in three steps, and each step needs the
previous one: the plugins give the factory `App` its types, the schemas are
declared from `App`, and the application `ultimabase` registers those
schemas. [Quick Start](/docs/1.0.0/quick-start) generates this layout, the
[repository examples](https://github.com/MrEkinox/ultimadatabase/tree/main/examples)
all follow it, and [Manual Installation](/docs/1.0.0/manual-installation)
builds it by hand.

## Mental model

<Callout title="The rule">
	Plugins, then schemas, then the instance. `app.ts` imports no schema.
</Callout>

| File                | Holds                                                                 | Imports                     |
| ------------------- | --------------------------------------------------------------------- | --------------------------- |
| `src/app.ts`        | `export const App = UltimaBase.use(...plugins)`                       | plugin packages only        |
| `src/schemas/*.ts`  | `export const Task = App.Schema.define({ ... }).with({ ... })`        | `App`, other schema modules |
| `src/ultimabase.ts` | `export const ultimabase = new App({ schemas })` and `Register`, once | `App`, every schema         |
| `src/main.ts`       | `start()`, then the work of this process                              | `ultimabase`                |

Each role has one name: the factory is always `App`, the application is
always `ultimabase`. The [modeling example](https://github.com/MrEkinox/ultimadatabase/tree/main/examples/modeling)
keeps its factory alone in `app.ts`:

<include cwd meta='title="src/app.ts"'>
	../../examples/modeling/src/app.ts#factory
</include>

Schema modules import `App` and each other. Relation targets are thunks, such
as `target: () => Book`, so two modules may reference each other:

```ts twoslash title="src/schemas/author.ts"
// @filename: src/app.ts
import { UltimaBase } from '@ultimabase/core'
import { postgresPlugin } from '@ultimabase/postgres-plugin'

export const App = UltimaBase.use(postgresPlugin())
// @filename: src/schemas/book.ts
import { App } from '../app.ts'
import { Author } from './author.ts'

export const Book = App.Schema.define({
	className: 'Book',
	fields: (f) => ({
		title: f.string({ required: true }),
		author: f.pointer({ target: () => Author, required: true }),
	}),
})
// @filename: src/ultimabase.ts
import { App } from './app.ts'
import { Author } from './schemas/author.ts'
import { Book } from './schemas/book.ts'

export const ultimabase = new App({ schemas: [Author, Book] })

declare module '@ultimabase/core' {
	interface Register {
		readonly app: typeof ultimabase
	}
}
// @filename: src/schemas/author.ts
// ---cut---
import { App } from '../app.ts'
import { Book } from './book.ts'

export const Author = App.Schema.define({
	className: 'Author',
	fields: (f) => ({
		name: f.string({ required: true }),
		books: f.relation({ target: () => Book, mappedBy: 'author' }),
	}),
})
```

### Why `app.ts` imports no schema

Node.js runs each module once, after the modules it imports, but two modules
that import each other cannot both run after the other: one of them runs
first and sees the other's exports before they exist. A reference inside a
thunk such as `target: () => Book` is safe, because it is read later. The
`App.Schema.define(...)` call is not: it reads `App` while the module runs.

Suppose `author.ts` declared `App` and imported `book.ts`, and `book.ts`
imported `App` from `author.ts`. Loading `author.ts` first starts `book.ts`
before `author.ts` has created `App`, and Node.js stops with
`ReferenceError: Cannot access 'App' before initialization`. Loading
`book.ts` first happens to work, so the failure depends on which file an
entry point or a test imports first.

When `App` lives in a module that imports no schema, any schema module that
imports it gets a finished `App`, whatever the import order. Keep the
references between schemas inside thunks and rule callbacks for the same
reason.

### Plugin-owned schemas

Plugins can add schema factories to `App`: [Password
Authentication](/docs/1.0.0/plugins/official/password-authentication) adds
`App.UserSchema` and [Roles](/docs/1.0.0/plugins/official/roles) adds
`App.RoleSchema`. Their declarations are schemas like the others: put each in
a schema module, import `App`, and list it in `ultimabase.ts`.

<include cwd meta='title="src/schema.ts"'>
	../../examples/auth/src/schema.ts#member
</include>

### Plugins that reference a schema

A plugin created from a schema, such as one contributing Hooks to `Post`,
cannot join `App`: `app.ts` would then import a schema. Add it where the
application is created, with `new (App.use(plugin))({ ... })`:

<include cwd meta='title="src/ultimabase.ts"'>
	../../examples/hooks/src/ultimabase.ts#application
</include>

### Plugin order

The order of the plugins inside `use()` does not decide whether they work.
Core sorts the plugins by their declared dependencies, so a plugin always
starts after the plugins it depends on, wherever each one appears in the
list. Position only breaks ties between plugins that do not depend on each
other.

## Boundaries

- Each file holds one role, not a fixed number of declarations: a small
  application may keep every schema in one `schema.ts`, and a larger one may
  group them by topic, as long as each module imports `App` from `app.ts`.
- `UltimaBase.Schema.define(...)` declares a schema without any plugin. It
  suits a library that ships schemas for several applications; an
  application declares from `App`, whose plugin options it needs as soon as
  it installs a plugin.
- Schemas are registered explicitly: a schema module that `ultimabase.ts`
  does not list is not part of the application.
- `Register` is declared once, next to the application it names.
