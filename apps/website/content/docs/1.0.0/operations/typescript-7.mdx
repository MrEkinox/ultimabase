UltimaBase supports TypeScript 6 and TypeScript 7. TypeScript 7 is the
recommended compiler for type checking and editor feedback: its native
compiler reports diagnostics about three times faster on UltimaBase schemas. Tools that load the
TypeScript JavaScript API, such as typescript-eslint, keep running on
TypeScript 6 installed beside it.

## Outcome

Your project type-checks with TypeScript 7.0.2, and your linter and other
API-based tools keep TypeScript 6. On the repository's schema declaration
benchmark, the time from an edit to its diagnostics is:

| Schemas | TypeScript 7 | TypeScript 6 |
| ------: | -----------: | -----------: |
|      50 |       0.54 s |       1.85 s |
|     200 |       1.89 s |       5.57 s |

These are medians measured on 2026-10-13 with the
[form D benchmark](https://github.com/MrEkinox/ultimadatabase/blob/main/examples/schema-form-d/README.md)
(cyclic schemas with relations, Access rules and the `Register` declaration).
They are reference points for one machine, not a guarantee for your project.

## Prerequisites

- A project from [Quick Start](/docs/1.0.0/quick-start) or
  [Manual Installation](/docs/1.0.0/manual-installation), with Node.js 24 or
  newer.
- TypeScript 6 installed as `typescript`. The project initializer writes
  `typescript` `^6.0.3`.
- Your schemas use the `Register` declaration described in
  [Schemas](/docs/1.0.0/core/data-modeling/schemas#register-and-compile).

## Steps

### Install TypeScript 7 under an alias

Install the TypeScript 7 package under another name, so `typescript` stays
TypeScript 6:

```bash tab="npm" tab-group="package-manager"
npm install --save-dev typescript-7@npm:typescript@7.0.2
```

```bash tab="yarn"
yarn add --dev typescript-7@npm:typescript@7.0.2
```

```bash tab="pnpm"
pnpm add --save-dev typescript-7@npm:typescript@7.0.2
```

TypeScript 7.0 does not provide the TypeScript JavaScript API that
typescript-eslint, language-service plugins and declaration bundlers import
from `typescript`. Replacing `typescript` with TypeScript 7 would break them.

### Run TypeScript 7 from your scripts

Both packages declare a `tsc` binary, so call TypeScript 7 by its path rather
than through `tsc`:

```json title="package.json"
{
	"scripts": {
		"typecheck": "node node_modules/typescript-7/bin/tsc --noEmit",
		"lint": "eslint ."
	},
	"devDependencies": {
		"typescript": "^6.0.3",
		"typescript-7": "npm:typescript@7.0.2",
		"typescript-eslint": "^8.65.0"
	}
}
```

`typecheck` uses TypeScript 7 with your existing `tsconfig.json`. `lint` runs
typescript-eslint, which resolves `typescript` and therefore TypeScript 6. The
path assumes a `node_modules` layout (npm, pnpm, or Yarn with the
`node-modules` linker).

### Use TypeScript 7 in your editor

The edit timings above come from the TypeScript 7 language server, which the
`typescript-7` package provides (`tsc --lsp --stdio`). Point your editor's
TypeScript 7 integration at that package. An editor that uses `typescript`
keeps TypeScript 6 behavior and timings.

## Verify

Check that each name resolves to the intended compiler:

```bash
node node_modules/typescript-7/bin/tsc --version
node node_modules/typescript/bin/tsc --version
```

The first command prints `Version 7.0.2` and the second a 6.x version. Then
run your `typecheck` and `lint` scripts: both finish without errors on a
project that type-checked before.

Hovers and messages for name-keyed types such as `Model<"Todo">` are the same
on both compilers. TypeScript 7 can report an error inside a multi-line call
on the offending property instead of the first line of the call, so check
`@ts-expect-error` comments placed above such a call with both compilers.

## Next steps

Keep both compilers in continuous integration while you support TypeScript 6
consumers. Read [Schemas](/docs/1.0.0/core/data-modeling/schemas) for the
declaration form whose cost these timings measure, and
[Test an Application](/docs/1.0.0/guides/test-an-application) to add runtime
checks beside type checking.
