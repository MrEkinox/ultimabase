UltimaBase is [pre-release](/docs/1.0.0/project/release-status). This checklist identifies
boundaries to verify before accepting public traffic; it is not a deployment
template or a claim that a particular application is production-ready.

## Prerequisites

Have a configured application and a planned database and host. Complete
[Manual Installation](/docs/1.0.0/manual-installation) against a disposable
database before evaluating a public environment.

## Steps

### Prepare configuration and data

- Run Node.js 24 or newer and check that the UltimaBase packages you install
  belong to a [compatible set](/docs/1.0.0/reference/package-index#platform-and-version-compatibility).
  Set `NODE_ENV=production`: official plugins then default to the production
  behavior (schema policy `fail`, listener on every interface, no GraphQL
  introspection, no explorer route) unless an option says otherwise, and
  `postgresPlugin()` reads `DATABASE_URL` at start. Do not send raw
  `process.env` values to browser code. See [Application](/docs/1.0.0/core/application#configure-the-application).
- If you use PostgreSQL, give the application a dedicated database account and
  choose its [schema policy](/docs/1.0.0/plugins/official/postgresql#direct-schema-policies)
  deliberately. `override` changes supported physical structures; it is not
  an unattended production migration strategy. `fail` checks a prepared
  schema for drift, while `ignore` leaves preparation to another process.
- Tune the PostgreSQL [connection](/docs/1.0.0/plugins/official/postgresql#connection-settings)
  for your host: `ssl`, `max`, and `statementTimeoutMs`, plus `connectRetries`
  when the database may start after the application (Docker, Kubernetes).
  `debug: { slowQueryMs }` logs slow statements without their values.
- Test your own backup and restore procedure before depending on stored data.
  UltimaBase does not provide one or ship an official migration runner yet.

### Protect public requests

- Review every REST or GraphQL route you expose. Authentication supplies an
  identity, not authorization: configure the intended
  [Access](/docs/1.0.0/plugins/official/access) and, where needed,
  [Object ACLs](/docs/1.0.0/plugins/official/acl-permissions). Verify both an
  allowed request and a denied request against the mounted application.
- Read the Access startup lines: one `warn` line per `allowWithoutRule`
  opening and one `info` line listing schemas without any rule. Production
  refuses to start while an opening is `'development'`; replace it with schema
  rules or an explicit `true`.
- Configure the [HTTP browser policy](/docs/1.0.0/plugins/official/http)
  (`browser.origins`) for each public application, and
  `requireApplicationId: true` when several applications share one proxy.
  Browser-origin policy is disabled by default; enabling CORS does not grant
  access or protect against CSRF.
- Provide TLS termination and HTTP/2 in the proxy or platform you control.
  Behind proxies, set `trustProxy` to their hop count or addresses, and set
  `rateLimit` (in memory per process by default, or a shared store). The HTTP
  plugin already applies a 30-second deadline, a 1 MiB body limit and security
  headers; review them for your routes. The
  [Hono Server](/docs/1.0.0/plugins/official/hono-server#keep-the-boundary-intact)
  plugin bounds shutdown with `shutdownTimeoutMs`.

### Keep credentials at their owners

- Load database credentials and Master keys from your server environment or a
  secret manager. Never commit them, put them in generated declarations, send
  them to a browser, or include them in public errors and reports.
- If configured, keep [Master Authority](/docs/1.0.0/core/security-foundations/master-authority)
  server-side and connect its `onUse` callback to an audit sink that meets your
  durability requirements. A successful elevation must complete its audit.
- If installed, let [Password Authentication](/docs/1.0.0/plugins/official/password-authentication)
  retain password verifiers and session digests in its owner-private storage.
  Handle raw session tokens only at issuance and credential boundaries.

### Exercise lifecycle and ownership

- Start and dispose the application in the target environment, including a
  failed-start path. The host process owns signal handling and graceful
  shutdown; [Application](/docs/1.0.0/core/application#start-and-dispose)
  explains the framework lifecycle.
- Point the platform's health checks at the `GET /health` health endpoint (200 or 503 from
  `ultimabase.health()`), and enable `accessLog` if you need request lines.
  Provide the metrics or tracing, backups, and operational alerts your
  deployment needs. UltimaBase currently ships no observability product, cache,
  job system, administration UI, deployment template, backup policy, or
  service-level guarantee.

## Verify before exposure

Confirm that startup and disposal complete. For each capability you install,
verify its relevant boundary: schema policy against a prepared database,
allowed and denied public requests, and Master audit delivery where Master is
configured. Test these in the environment you intend to expose. If a check
fails, follow
[Troubleshooting](/docs/1.0.0/operations/troubleshooting) and the failing
plugin's own troubleshooting section; never disable a security boundary just
to make startup pass.

## Next steps

Keep the provider-specific backup, restore, observability, and shutdown
procedures with your deployment. Revisit this checklist when you add a public
route, plugin, credential, or application instance.
