## Overview

`@ultimabase/postgres-plugin` is the official database provider. It turns
compiled schemas and Core operations into PostgreSQL tables, queries,
transactions, indexes, and constraints. The plugin owns `pg` and Drizzle
internally; application code uses UltimaBase schemas and Query, not Drizzle or
a raw database client.

The plugin can prepare a database schema directly at startup. It does **not**
ship a migration runner. Importing the package alone does not install the
provider; add `postgresPlugin()` to the application's `.use()` chain.

Every TypeScript block on this page is copied from the
[postgres example](https://github.com/MrEkinox/ultimadatabase/tree/main/examples/postgres),
a small newsroom backend whose tests check each result described here.

## Installation

You need Node.js 24+, a reachable PostgreSQL database, and an UltimaBase
application. The database itself must already exist; the plugin can prepare
tables inside it. For a complete first project, follow
[Manual Installation](/docs/1.0.0/manual-installation).

Install the plugin in that project:

```bash tab="npm" tab-group="package-manager"
npm install @ultimabase/postgres-plugin
```

```bash tab="yarn"
yarn add @ultimabase/postgres-plugin
```

```bash tab="pnpm"
pnpm add @ultimabase/postgres-plugin
```

The package names describe the intended npm installation experience while
UltimaBase remains pre-release.

## Configuration

Supply at most one of `url` or `pool`. Without either, `postgresPlugin()`
reads the `DATABASE_URL` environment variable when the application starts,
not when the plugin is created: schemas and the application import and
type-check without environment. A missing or empty variable fails `start()`
with a message naming `DATABASE_URL` and the `url` option, never the value.
The example uses a disposable development database and lets the plugin own
its connection pool; keep `DATABASE_URL` out of source control. Install the
plugin on the application factory; `database` is the configured
`postgresPlugin()` shown in [Connection settings](#connection-settings):

</include>

Register the schemas, then start the application from its entry point:

</include>

<include cwd meta='title="src/main.ts"'>
	../../examples/postgres/src/main.ts#start

The example does not set `schemaPolicy`, so outside production it uses
`override` and creates its tables on the first start.

<Callout type="warn" title="Use override only on a reviewed database">
	`override` can create or alter physical structures. Use this example with a
	disposable development database. Do not point it at shared or production data
	without reviewing the proposed schema and a recovery plan.
</Callout>

| Plugin option  | Purpose                                                                                                    |
| -------------- | ---------------------------------------------------------------------------------------------------------- |
| `url`          | Non-empty connection URL; it wins over `DATABASE_URL`. The plugin owns the pool.                           |
| `pool`         | Existing `pg`-compatible pool. Your application owns, configures, and closes it.                           |
| `connection`   | Pool settings with `url` or `DATABASE_URL`: see [Connection settings](#connection-settings).               |
| `schemaPolicy` | `'override'`, `'fail'`, or `'ignore'`; the default depends on `NODE_ENV`, see below.                       |
| `debug`        | `{ logQueries, slowQueryMs }`: statement logs without values, see [Debugging queries](#debugging-queries). |

Do not pass both `url` and `pool`. Creating `UltimaBase` does not contact the
database. `start()` verifies a connection, returns the borrowed client to its
pool, and then runs schema preparation. With `url`, the plugin owns the pool
and `dispose()` closes it:

	../../examples/postgres/tests/connection.test.ts#lifecycle
</include>

`whileStarted` is `'connected'` and `afterDispose` is `'closed'`. An injected
`pool` stays yours: `dispose()` leaves it open, and you close it:

### Connection settings

With `url` or `DATABASE_URL`, `connection` tunes the pool that the plugin
creates. An injected `pool` keeps its own settings and rejects `connection`.

<include cwd meta='title="src/database.ts"'>
	../../examples/postgres/src/database.ts#database
</include>

| Setting              | Effect                                                                                                         |
| -------------------- | -------------------------------------------------------------------------------------------------------------- |
| `max`                | Maximum pooled connections (default 10).                                                                       |
| `ssl`                | `true`, or `{ rejectUnauthorized, ca, cert, key }` with PEM strings. An `sslmode` in the URL takes precedence. |
| `statementTimeoutMs` | Cancels a statement that runs longer; it fails with the driver code `57014`.                                   |
| `idleTimeoutMs`      | Closes a pooled connection idle this long; `0` keeps it (default 10 s).                                        |
| `connectRetries`     | Retries the first connection of `start()` after 0.5 s, 1 s, 2 s, 4 s, then 8 s (default 0).                    |

Use `connectRetries` when the database may still be starting, as in Docker
Compose or Kubernetes. Each failed attempt logs one `warn` line naming only the
driver code.

### Debugging queries

`debug` logs statements through the plugin logger, never their values. The
example above keeps only `slowQueryMs`; during development, add
`logQueries: true`, as in
`postgresPlugin({ debug: { logQueries: true, slowQueryMs: 500 } })`.

`logQueries` writes one `info` line per statement, with its duration and its
text with `$1` placeholders. `slowQueryMs` writes one `warn` line per statement
that takes at least that many milliseconds; it is cheap enough to keep in
production.

### Table and column names

PostgreSQL derives a plural `snake_case` table name from `className`
(`StaffMember` → `staff_members`) and a `snake_case` column from each field
(`createdAt` → `created_at`). Queries, results, and errors keep the field
names. The `postgres: { table }` rule of `.with` chooses an exact
table identifier, and the stored-field `postgres.renamedFrom` names the
previous column for a data-preserving rename (the schema's `indexes` stay in
`define`, see [Where each declaration goes](/docs/1.0.0/core/data-modeling/schemas#where-each-declaration-goes)):

<include cwd meta='title="src/schema.ts"'>
	../../examples/postgres/src/schema.ts#article
</include>

The comments name the column type of each field kind: `int` and `bigint` use
`bigint`, `decimal` uses `numeric` with its precision and scale, `dateTime`
uses `timestamp(3) with time zone`, and lists, `json`, and `object` fields
use `jsonb`. A pointer is a `uuid` column with a named foreign key; a relation
is a hidden join table.

Use `renamedFrom` only when an existing managed column is actually being
renamed, and remove it once every database has applied the rename. The
configured `App` types both from the installed plugin; a factory without the
plugin rejects them. Field-level `postgres` is limited to stored fields.

## Behavior and limitations

### Direct schema policies

| Policy     | Startup behavior                                                         | Typical use                                       |
| ---------- | ------------------------------------------------------------------------ | ------------------------------------------------- |
| `override` | Inspect the current schema and transactionally apply supported changes.  | Reviewed development or maintenance database.     |
| `fail`     | Inspect and reject any drift without changing the database.              | Guard an already prepared database.               |
| `ignore`   | Skip structural inspection and preparation; still verify the connection. | Another reviewed process owns schema preparation. |

When you omit `schemaPolicy`, the plugin reads `NODE_ENV` when it is created:
`production` selects `fail`, so a deployed application never changes its
schema by itself, and any other value selects `override`. An explicit
`schemaPolicy` always wins, so a production deployment that should synchronize
on startup must write `schemaPolicy: 'override'` deliberately.

`override` can create missing tables and apply supported column type,
nullability, default, identity, primary-key, foreign-key, and index changes.
It does not infer that unmatched tables or columns should be dropped. Indexes
are different: on a managed table, `override` drops an index that no schema
declares, such as one created by hand or by a newer release of the
application. Removed fields and plugin-owned storage need an explicit
migration plan. Unsupported
structures on a managed table stop direct preparation rather than being
approximated. No official migration runner is shipped yet.

`override` also protects existing data:

- Each applied change logs one `info` line, such as
  `schema change applied: add column "articles"."title" (text, optional)`.
- Only widening type conversions apply (a wider `numeric`, `bigint` to a
  `numeric` that holds it, a finer `time` or `timestamp`). Turning a `float`
  field into a `string`, for example, refuses to start and asks for a
  migration.
- A managed table that keeps a required column without default that no field
  declares refuses to start, because every insert would fail. When a field of
  the same type appears at the same time, the message suggests the forgotten
  `renamedFrom`.

A database created before columns became `snake_case` is not converted: the
check above reports its camelCase columns. Rename them outside UltimaBase
before starting.

Preparation always follows the configured `schemaPolicy`. Select `ignore`
explicitly when external tooling manages schema changes. The former
`postgresSchemaPreparationCapability` marker is removed; it cannot suppress
direct synchronization. `renamedFrom` still applies explicit column renames
under `override`, as shown above.

### Index preparation

Declare single-field and composite indexes through Core's
[Schemas](/docs/1.0.0/core/data-modeling/schemas#indexes) API, not through
Drizzle or SQL, as `Article` does above. An edge with its own data is an
ordinary schema with a composite unique index:

<include cwd meta='title="src/schema.ts"'>
	../../examples/postgres/src/schema.ts#contribution
</include>

PostgreSQL generates deterministic physical names and preserves the declared
field order. A unique index is also the exact conflict target used by
[Unique Upserts](/docs/1.0.0/core/writing-data/upserts).

A declaration does not prove that an existing database already has the index.
`override` applies supported changes; `fail` reports drift; `ignore` does
not check. Review existing data before adding uniqueness: duplicate values
make index creation fail. Several `NULL` values never conflict in a unique
index, so also declare `required: true` when absence must be forbidden.

A partial index compiles to `CREATE [UNIQUE] INDEX ... WHERE ...`. Its physical
name includes a hash of the predicate, so `override` replaces an index whose
predicate changed.

### Errors, conflicts, and health

PostgreSQL enforces referential actions with foreign keys inside the
operation's transaction. Driver failures become neutral Core errors: SQLSTATE
23505 is `UNIQUE_VIOLATION` (with the logical schema and index fields), 23503 is
`REFERENCE_VIOLATION`, and 40001 or 40P01 (serialization failure, deadlock) is
the retryable `TRANSACTION_CONFLICT`, which Core retries for automatic
mutation transactions. Other data and integrity errors stay
`VALIDATION_ERROR`. Each statement runs at `READ COMMITTED`, and mutation
targets are locked with `SELECT ... FOR UPDATE` until commit.

<include cwd meta='title="tests/integrity.test.ts"'>
	../../examples/postgres/tests/integrity.test.ts#unique-violation
</include>

`duplicate` rejects with `UNIQUE_VIOLATION`, `publicDetails`
`{ schema: 'StaffMember', fields: ['email'] }`, and the public message
`A StaffMember with the same email already exists.`; the value itself is
never reported.

The adapter declares every built-in filter operator and partial indexes, and
answers `ultimabase.health()` with a trivial query on its pool. No `ping()`
helper is exported.

### Connection and data boundaries

A URL-backed pool belongs to the application; an injected pool stays yours.
Neither connection URLs, raw pools, Drizzle objects, nor driver messages appear
in public plugin exports, framework errors, or logs. The server-side message of a
failed connection names only the driver code, such as
`PostgreSQL connection verification failed [SQLSTATE 28P01].` for rejected
credentials, `[SQLSTATE 3D000]` for a missing database, or `[ECONNREFUSED]`
when nothing listens at the address. Reads and mutations still use
Core's policy and Runtime pipeline. This provider never grants access or
installs Access, ACL, authentication, REST, or GraphQL.

UltimaBase runs no manual SQL: a raw statement would bypass Access, ACL, Soft
Delete, and hooks. For reports, query the database with your own pool outside
UltimaBase, ideally on a read-only account; no UltimaBase rule applies there.
To keep the tables in a dedicated PostgreSQL schema, set `search_path` in the
connection URL, for example `?options=-c%20search_path%3Dmy_app`. The
example's tests build such a URL for the applications they start themselves:

</include>

## Troubleshooting

| Symptom                                                                   | Check                                                                                                                            | Next action                                                                                                                   |
| ------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `INTERNAL_ERROR` with “The database connection could not be established.” | Confirm `DATABASE_URL` is loaded, the database already exists, and network/TLS settings work with a supported PostgreSQL client. | Correct connectivity or credentials without logging the URL.                                                                  |
| `VALIDATION_ERROR` at startup with `schemaPolicy: 'fail'`                 | Compare the compiled schema with the live managed tables in trusted server diagnostics.                                          | Prepare the reviewed change through a controlled process; do not switch production blindly to `override`.                     |
| `VALIDATION_ERROR`: required column(s) that no field declares             | A field was renamed or removed while its `NOT NULL` column stayed.                                                               | Declare `renamedFrom` on the new field, or make the column optional, give it a default, or drop it with a reviewed migration. |
| `VALIDATION_ERROR`: applies only widening type conversions                | A field changed to a type that cannot hold every stored value.                                                                   | Restore the field type, or convert the column with a reviewed migration outside UltimaBase.                                   |
| `VALIDATION_ERROR` for an unsupported structure                           | Check for a view, partitioned table, generated column, or unsupported index or constraint on a managed table.                    | Keep that structure under an explicit migration owner.                                                                        |
| `INTERNAL_ERROR` during direct synchronization                            | Check sanitized server diagnostics and database permissions; a physical change may have failed.                                  | Fix the cause and restart after reviewing the database state.                                                                 |

Check that the environment variable exists without printing its value:

```sh
node -e "process.exit(process.env.DATABASE_URL ? 0 : 1)"
```

Do not send connection strings, SQL values, raw driver causes, or credentials
to an HTTP client or public report. If the failure persists, collect the
UltimaBase and PostgreSQL versions, schema policy, lifecycle stage, and
sanitized driver code, then follow
[Reporting a problem](/docs/1.0.0/operations/troubleshooting#report-a-problem).
