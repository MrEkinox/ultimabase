## Overview

`@ultimabase/rest-plugin` contributes the experimental JSON REST route
graph. It decodes accepted requests into the same Core Query and mutation
operations used by direct TypeScript. REST neither opens a listener nor
provides authentication, authorization, or a database.

Importing the package does not expose routes. Add `restPlugin()` and the
separate [HTTP](./http) application boundary to the same application.

## Installation

These packages are pre-release. Use the locally built repository example linked
from [Manual Installation](/docs/1.0.0/manual-installation) to evaluate the
current code; the registry commands below describe installation after publication.

Install REST in an UltimaBase project:

```bash tab="npm" tab-group="package-manager"
npm install @ultimabase/rest-plugin
```

```bash tab="yarn"
yarn add @ultimabase/rest-plugin
```

```bash tab="pnpm"
pnpm add @ultimabase/rest-plugin
```

A running API also needs `@ultimabase/http-plugin`, a server provider such
as [Hono Server](./hono-server), and a database provider such as
[PostgreSQL](./postgresql). Install and configure those siblings explicitly;
REST does not install them. Follow [Manual Installation](/docs/1.0.0/manual-installation)
for the initial project and database setup.

## Configuration

The schema's `.with({ rest })` rule selects its routes by the schema method
names. This complete local example exposes only `findMany` and `findOne`; it
does not install authentication or authorization. Use a disposable development
database and keep the listener on `127.0.0.1`.

```ts title="src/ultimabase.ts"
import { UltimaBase } from '@ultimabase/core'
import { httpPlugin } from '@ultimabase/http-plugin'
import { postgresPlugin } from '@ultimabase/postgres-plugin'
import { restPlugin } from '@ultimabase/rest-plugin'
import { honoServerPlugin } from '@ultimabase/hono-server-plugin'

const databaseUrl = process.env.DATABASE_URL
if (!databaseUrl) throw new Error('DATABASE_URL is required')

const Application = UltimaBase.use(
	postgresPlugin({ schemaPolicy: 'override', url: databaseUrl }),
)
	.use(httpPlugin({ appId: 'blog' }))
	.use(restPlugin({ default: false, openapi: true }))
	.use(honoServerPlugin({ host: '127.0.0.1', port: 1337 }))

const Post = Application.Schema.define({
	className: 'Post',
	fields: (f) => ({
		title: f.string({ required: true }),
	}),
}).with({ rest: { findMany: true, findOne: true } })

export const ultimabase = new Application({
	schemas: [Post],
})
```

Start this configuration from the [managed listener entry point](./hono-server#start-and-stop-the-managed-listener).
It keeps serving until Ctrl+C and awaits disposal. The exported configuration
can also be loaded by Typegen without opening a database or listener.
The `rest` rule is typed by the installed plugin without first running
Typegen. Schema declaration does not register it; `schemas: [Post]` does.

`default: false` disables every method unless the schema opts in. The schema
above enables only reads, so no protected policy is required. **REST refuses
to start when it would expose a write** (create, update, delete, upsert, bulk
or a plugin command) and no protected policy plugin is installed; install one,
such as [Access](./access), or pass `restPlugin({ publicWrites: true })` to
let every client write on purpose (ADR-0294). Configure
[authentication](./password-authentication) if you need an identity and enforce
authorization with [Access](./access) or [ACL](./acl-permissions). Review every
enabled route: authentication alone grants no permission. The PostgreSQL
`override` policy can alter tables; do not point this example at shared or
production data without a reviewed schema plan.

| Plugin option  | Purpose                                                                     |
| -------------- | --------------------------------------------------------------------------- |
| `basePath`     | Mount prefix, `/api` by default; `/api/v1` versions your own API.           |
| `bodyLimit`    | Maximum JSON request body; inherits `httpPlugin({ bodyLimit })`.            |
| `pagination`   | `{ defaultTake, maxTake }` of collection reads, 100 and 1,000.              |
| `default`      | `true`, `false` or per-method defaults inherited by every schema.           |
| `hide`         | Public operations this instance does not expose.                            |
| `openapi`      | Serves the OpenAPI 3.1 description at `{basePath}/openapi.json`.            |
| `publicWrites` | Starts with exposed writes and no protected policy: every client may write. |
| `instanceId`   | Distinguishes explicit REST configurations in one application.              |

The `rest` rule accepts `false`, `true`, or a map from method name to boolean.
Each omitted method inherits `restPlugin({ default })`, then REST's built-in
default. `rest: false` exposes none of a schema's routes; `rest: true` exposes
all of them, plugin commands included. A plugin-owned schema cannot expose
routes.

## Behavior and limitations

### Routes by method name

The protocol version is not in the URL: every REST response carries
`X-UltimaBase-Rest-Version: 1`. Under the default `/api` root, an
application-owned schema exposes:

| Method key   | Method and path below `/api`                        | Built-in default |
| ------------ | --------------------------------------------------- | ---------------- |
| `findMany`   | `GET /classes/Post`, `POST /classes/Post/query`     | On               |
| `findOne`    | `GET /classes/Post/{id}`, `GET` or `POST .../first` | On               |
| `exists`     | `GET` or `POST /classes/Post/exists`                | On               |
| `createOne`  | `POST /classes/Post`                                | On               |
| `updateOne`  | `PATCH /classes/Post/{id}`                          | On               |
| `deleteOne`  | `DELETE /classes/Post/{id}`                         | On               |
| `count`      | `GET` or `POST /classes/Post/count`                 | Off              |
| `upsertOne`  | `POST /classes/Post/upsert`                         | Off              |
| `createMany` | `POST /classes/Post/bulk/create`                    | Off              |
| `updateMany` | `POST /classes/Post/bulk/update`                    | Off              |
| `deleteMany` | `POST /classes/Post/bulk/delete`                    | Off              |
| `upsertMany` | `POST /classes/Post/bulk/upsert`                    | Off              |

`{id}` must be a UUID v7. Class names are case-sensitive and are not
pluralized. `rest: { count: true }` enables count **in addition to** the
built-in routes. A method that is off answers `405` with an `Allow` header
listing the methods the path accepts; a schema with no route at all answers
`404`. Master authority does not enable a route.

A plugin command uses the same keys: `.with({ rest: { softDeleteOne: true } })`
adds `POST /classes/Post/{id}/soft-delete-one`. Only request-authority
commands on one row can be exposed; Master-only and many-row commands never
are. A command is exposed only when its rule names it, or when the rule or the
plugin default is `true`. See [Soft Delete](./soft-delete) for a concrete
example.

### Request and response shape

With the local configuration above, run:

```bash title="terminal"
curl -i 'http://127.0.0.1:1337/api/classes/Post?select=id,title&take=10'
```

On a fresh database, expect HTTP `200` and `{ "results": [], "nextCursor": null }`.
For a filtered read, use simple GET parameters or the JSON `POST /query` form:

```bash title="terminal"
curl -i -X POST \
  -H 'Content-Type: application/json' \
  --data '{"where":{"title":"Hello"},"select":{"id":true,"title":true},"take":10}' \
  http://127.0.0.1:1337/api/classes/Post/query
```

`where` as JSON is the only filter form: there are no per-field URL filters,
which would collide with the reserved parameters. `"title": "Hello"` is the
equality shorthand of `{ "eq": "Hello" }`; on a pointer field the shorthand
value is the target's UUID string. GET accepts `where` as URL-encoded JSON,
`orderBy` and `select` as comma-separated fields, `include` as relationship
paths or JSON, and a positive `take` and either a non-negative `skip` or an
opaque `after` cursor. POST reads accept the corresponding typed Query input as
JSON, with `after` as the cursor string. Collection reads default to 100 items;
the default maximum is 1,000, and a larger `take` fails with
`REST_READ_INVALID_INPUT`. Set other values with
`restPlugin({ pagination: { defaultTake: 20, maxTake: 200 } })`, the same
option as GraphQL's.

Without `skip`, a collection read also returns `nextCursor`: the cursor of its
last row when more rows follow, otherwise `null`. Pass it back as `after` with
the same `orderBy` to read the next page; each page starts strictly after the
previous one, so inserts and deletes between calls never repeat or skip an
unchanged row. The cursor is unsigned and stays valid across restarts and
instances: it only names a position, which the caller could also request as a
filter. A malformed cursor, one for another schema or ordering, or `after`
combined with `skip` fails with HTTP `400` `VALIDATION_ERROR` and
`details: { "parameter": "after" }`. Fields REST selects only to encode the
cursor are not returned. See
[Ordering and Pagination](/docs/1.0.0/core/reading-data/ordering-and-pagination). REST rejects unknown or duplicate parameters rather than
silently ignoring them. A non-empty JSON body must use `application/json` and
stay within `bodyLimit`.

Success envelopes follow the operation: collections and bulk mutations return
`{ "results": [...] }`; singular reads, mutations, and operations return
`{ "result": ... }`; count and exists return `{ "count": 1 }` and
`{ "exists": true }`. A first read with no visible match returns
`{ "result": null }`. Create and bulk create return HTTP `201`; other
successful operations return `200`.

Mutations use the same schema commands and automatic transaction boundaries
as TypeScript. Bulk is ordered, itemized, atomic, and never partial-success.
Ordinary create and update bodies contain the field data directly; item DELETE
has no body. Upsert and bulk use their schema-command-shaped JSON bodies. REST
decodes input, then Core applies structural validation and any installed
Validation, Access, ACL, and Hooks behavior. A public route is not itself a
permission rule.

Mutation results obey the row read rules. A client allowed to write a row it
cannot read asks for the identifier alone: `?select=id` on create, update and
delete, or `"select": { "id": true }` in an upsert or bulk body. Any other
selection of an unreadable result fails with `403` and nothing is written.

### Public operations

A plugin declares which of its operations are meant for clients, such as
[Password Auth](./password-authentication)'s `signUp` and `login`; every
installed transport exposes them, and an operation not declared public is
never exposed. Hide one with `restPlugin({ hide: [passwordAuthOperations.refresh] })`.
An operation answers `POST /api/operations/{name}` with exactly
`{ "input": value }`, unless its owner declares a static path such as
`/api/auth/login`. The configured `basePath` applies to these routes too.

An application operation needs no plugin: `defineOperation` from
`@ultimabase/plugin-kit` takes Standard Schema validators, and you install it
with `UltimaBase.use(...)`.

```ts title="src/operations.ts"
import { defineOperation } from '@ultimabase/plugin-kit'
import { z } from 'zod'

export const createInvoice = defineOperation({
	name: 'createInvoice',
	input: z.object({
		customer: z.string().min(2),
		amount: z.number().positive(),
	}),
	output: z.object({ invoice: z.string() }),
	handler: async ({ input }) => ({
		invoice: `${input.customer}-${input.amount}`,
	}),
})
```

`UltimaBase.use(createInvoice)` exposes `POST /api/operations/createInvoice`.
Input that the validator rejects answers `422` `VALIDATION_ERROR` with
`details.issues` (`path` starts with `input`); a result the output validator
rejects is a server error. The handler runs with the caller's authority:
schema reads and writes inside it obey the installed policies.

### OpenAPI

`restPlugin({ openapi: true })` serves `GET /api/openapi.json`, an OpenAPI 3.1
document of the routes this instance exposes: paths, request and response
bodies, fields and their wire types. Constraints come from validators that
can describe themselves as JSON Schema (Standard JSON Schema, as Zod does): a
field's `validation` and an application operation's `input` and `output`.
The document never describes an access rule.

### Errors

After REST dispatch, errors use
`{ error: { code, message, retryable, requestId, details? } }`. A malformed
request answers `400` and locates the problem in
`details: { parameter, path, reason }`, for example
`{ "parameter": "where", "path": ["views", "gt"], "reason": "must be a safe integer" }`
(the exposed schema is public). A disabled method returns 405, permission
failures 403, hidden or missing targets 404, validation failures 422, and
storage conflicts (`UNIQUE_VIOLATION`, `REFERENCE_VIOLATION`, and the
retryable `TRANSACTION_CONFLICT`) 409. A
[`PublicError`](/docs/1.0.0/core/runtime/api-errors#publicerror) thrown by
application code returns 400 with its code, message and details. Unexpected
exceptions become a safe `REST_INTERNAL_ERROR` response rather than exposing
internal diagnostics; the server logs them with their stack.
The response carries `X-UltimaBase-Request-Id`; keep it with the safe code when
reporting a failure. Earlier application identity or credential failures retain
the HTTP plugin's envelope and never enter REST.

## Troubleshooting

If startup reports that REST exposes writes without a protected policy plugin,
install a policy such as Access or opt in with `publicWrites: true`. If a
route is missing, check the schema's `rest` rule, the plugin default, the
configured `basePath`, and whether the schema is application-owned. In the
local example, create, update, and delete deliberately answer 405 because
`default: false` disables them. An operation that is not listed is not
declared public by its owner, or is hidden by `restPlugin({ hide })`.

If a request fails before REST begins, check [HTTP troubleshooting](./http#troubleshooting)
for application ID, credentials, browser policy, and request correlation. If
REST rejects a request, read `error.details`: it names the parameter, the
path inside it and the reason. Do not use Master authority to bypass a missing
Access or ACL policy.
