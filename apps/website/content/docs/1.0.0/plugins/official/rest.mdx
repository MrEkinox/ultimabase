## Overview

`@ultimabase/rest-plugin` contributes the experimental JSON REST v1 route
graph. It decodes accepted requests into the same Core Query and mutation
operations used by direct TypeScript. REST neither opens a listener nor
provides authentication, authorization, or a database.

Importing the package does not expose routes. Add `restPlugin()` and the
separate [HTTP](./http) application boundary to the same application.

## Installation

Install REST in an UltimaBase project:

```bash tab="npm" tab-group="package-manager"
npm install @ultimabase/rest-plugin
```

```bash tab="yarn"
yarn add @ultimabase/rest-plugin
```

```bash tab="pnpm"
pnpm add @ultimabase/rest-plugin
```

A running API also needs `@ultimabase/http-plugin`, a server provider such
as Hono, and a database provider such as [PostgreSQL](./postgresql).
Install and configure those siblings explicitly; REST does not install them.

## Configuration

The schema's `rest` option selects its generated routes. The factory controls
the mount and application-wide defaults:

```ts title="src/rest.ts"
import { Schema } from '@ultimabase/core'
import { restPlugin } from '@ultimabase/rest-plugin'

export const Post = Schema.define({
	className: 'Post',
	fields: (field) => ({
		title: field.string({ required: true }),
	}),
	rest: { count: true },
})

export const rest = restPlugin({
	basePath: '/api',
})
```

Include `Post` in `schemas` and `rest` in `plugins` alongside HTTP, a
database provider, and a server provider. Generated routes are public
exposure, **not** authorization: set
`acknowledgeUnverifiedProtection: true` only after reviewing Access, ACL,
authentication, and the intended public surface.

| Plugin option | Purpose                                                              |
| ------------- | -------------------------------------------------------------------- |
| `basePath`    | Mount prefix, `/api` by default; REST appends `/v1`.                 |
| `bodyLimit`   | Maximum JSON request body, 1 MiB by default.                         |
| `maxLimit`    | Maximum accepted collection limit, 1,000 by default.                 |
| `default`     | Sparse generated-route defaults inherited by application schemas.    |
| `operations`  | Exact plugin-operation tokens to expose; none are public by default. |
| `instanceId`  | Distinguishes explicit REST configurations in one application.       |

## Behavior and limitations

Application schemas expose find, get, first, exists, create, update, and delete
by default. Count, upsert, and bulk routes require explicit opt-in.
Plugin-owned schemas never receive generated CRUD routes.

### Request and response shape

Routes use `/api/v1/classes/{Schema}` for collections and
`/api/v1/classes/{Schema}/{uuid}` for items with the default `basePath`.
Real requests must identify the exact HTTP application:

```ts title="src/read-posts.ts"
export const readPostsOverRest = () =>
	fetch('https://api.example/api/v1/classes/Post', {
		headers: { 'X-UltimaBase-Application-Id': 'blog' },
	})
```

GET query parameters and complex JSON POST bodies normalize into the same
Query AST as TypeScript. Collection reads default to 100 items; the default
maximum is 1,000. A request body, when present, must use
`application/json` and stay below the configured limit.

Success envelopes follow the operation:

```json
{ "results": [{ "id": "generated-id", "title": "One Runtime" }] }
{ "result": { "id": "generated-id", "title": "One Runtime" } }
{ "count": 1 }
{ "exists": true }
```

Mutations use the same schema commands and automatic transaction boundaries
as TypeScript. Bulk is ordered, itemized, atomic, and never partial-success.
Application operations remain private until exact tokens are listed in
`restPlugin({ operations })`.

## Troubleshooting

If startup reports `UNVERIFIED_PUBLIC_TRANSPORT_PROTECTION`, review the
generated routes and policy before adding the acknowledgement. If a route is
missing, check the schema's `rest` option, the plugin default, the configured
`basePath`, and whether the schema is application-owned.

If a request fails before REST begins, check [HTTP troubleshooting](./http#troubleshooting)
for application ID, credentials, browser policy, and request correlation. If
REST rejects a request, verify the method, JSON body size and content type,
UUID item ID, and supported query parameters. Do not use Master authority to
bypass a missing Access or ACL policy.
