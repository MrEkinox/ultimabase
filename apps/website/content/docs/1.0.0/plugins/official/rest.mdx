## Overview

`@ultimabase/rest-plugin` contributes the experimental JSON REST route
graph. It decodes accepted requests into the same Core Query and mutation
operations used by direct TypeScript. REST neither opens a listener nor
provides authentication, authorization, or a database.

Importing the package does not expose routes. Add `restPlugin()` and the
separate [HTTP](./http) application boundary to the same application.

Every TypeScript block on this page is copied from the
[REST example](https://github.com/MrEkinox/ultimadatabase/tree/main/examples/rest),
a small blog backend whose tests send each request shown here with
`testApplication`'s in-memory `t.fetch` and check the answers described.

## Installation

These packages are pre-release. Use the locally built repository example linked
from [Manual Installation](/docs/1.0.0/manual-installation) to evaluate the
current code; the registry commands below describe installation after publication.

Install REST in an UltimaBase project:

```bash tab="npm" tab-group="package-manager"
npm install @ultimabase/rest-plugin
```

```bash tab="yarn"
yarn add @ultimabase/rest-plugin
```

```bash tab="pnpm"
pnpm add @ultimabase/rest-plugin
```

A running API also needs `@ultimabase/http-plugin`, a server provider such
as [Hono Server](./hono-server), and a database provider such as
[PostgreSQL](./postgresql). Install and configure those siblings explicitly;
REST does not install them. Follow [Manual Installation](/docs/1.0.0/manual-installation)
for the initial project and database setup.

## Configuration

Install REST on the application factory beside the HTTP foundation, a server
provider and a database provider. The example also installs [Access](./access),
which decides what clients may do, and one application operation:

<include cwd meta='title="src/schema.ts"'>
	../../examples/rest/src/schema.ts#factory
</include>

| Plugin option  | Purpose                                                                     |
| -------------- | --------------------------------------------------------------------------- |
| `basePath`     | Mount prefix, `/api` by default; `/api/v1` versions your own API.           |
| `bodyLimit`    | Maximum JSON request body; inherits `httpPlugin({ bodyLimit })`.            |
| `pagination`   | `{ defaultTake, maxTake }` of collection reads, 100 and 1,000.              |
| `default`      | `true`, `false` or per-method defaults inherited by every schema.           |
| `hide`         | Public operations this instance does not expose.                            |
| `openapi`      | Serves the OpenAPI 3.1 description at `{basePath}/openapi.json`.            |
| `publicWrites` | Starts with exposed writes and no protected policy: every client may write. |
| `instanceId`   | Distinguishes explicit REST configurations in one application.              |

The schema's `.with({ rest })` rule selects its routes by the schema method
names. `Post` keeps the built-in routes and adds `count` and the bulk create:

<include cwd meta='title="src/schema.ts"'>
	../../examples/rest/src/schema.ts#post
</include>

`Author` turns its writes off, so clients only read authors, and `Tag` has no
route at all; posts still link and include tags:

<include cwd meta='title="src/schema.ts"'>
	../../examples/rest/src/schema.ts#author
</include>

<include cwd meta='title="src/schema.ts"'>
	../../examples/rest/src/schema.ts#tag
</include>

The `rest` rule accepts `false`, `true`, or a map from method name to boolean.
Each omitted method inherits `restPlugin({ default })`, then REST's built-in
default; `restPlugin({ default: false })` makes every schema opt in.
`rest: false` exposes none of a schema's routes; `rest: true` exposes all of
them, plugin commands included. A plugin-owned schema cannot expose routes.
The rule is typed by the installed plugin, with no generation step, and goes
in the final `.with(...)`, never in `define`. Schema declaration does not
register it; `schemas: [...]` does:

<include cwd meta='title="src/ultimabase.ts"'>
	../../examples/rest/src/ultimabase.ts#application
</include>

Start it from a separate entry point; leaving the `await using` scope awaits
`dispose()` when the process finishes. The listener keeps serving until
Ctrl+C. Use a disposable development database: the PostgreSQL `override`
policy, the default outside production, can alter tables.

<include cwd meta='title="src/main.ts"'>
	../../examples/rest/src/main.ts#start
</include>

**REST refuses to start when it would expose a write** (create, update,
delete, upsert, bulk or a plugin command) and no protected policy plugin is
installed. Install one, such as [Access](./access), as the example does, or
pass `publicWrites: true` to let every client write on purpose (ADR-0294).
This second application has no policy plugin:

<include cwd meta='title="src/guestbook.ts"'>
	../../examples/rest/src/guestbook.ts#public-writes
</include>

Without `publicWrites`, its start fails with
`REST exposes writes (POST /api/classes/Entry, …) but no protected policy plugin is installed`.
Read-only routes need neither. Configure
[authentication](./password-authentication) if you need an identity and enforce
authorization with [Access](./access) or [ACL](./acl-permissions). Review every
enabled route: authentication alone grants no permission, and an exposed route
grants none either.

## Behavior and limitations

### Routes by method name

The protocol version is not in the URL: every REST response carries
`X-UltimaBase-Rest-Version: 1`. REST owns only the roots it serves below its
base path (`classes`, `operations`, `openapi.json` and the roots of declared
operation paths), so other plugins share `/api`: authentication serves
`/api/auth/*`. Any other path under `/api`, such as `/api/v1/classes/Post`,
answers the HTTP foundation's `HTTP_NOT_FOUND`, without the REST version
header. Under the default `/api` root, an application-owned schema exposes:

| Method key   | Method and path below `/api`                        | Built-in default |
| ------------ | --------------------------------------------------- | ---------------- |
| `findMany`   | `GET /classes/Post`, `POST /classes/Post/query`     | On               |
| `findOne`    | `GET /classes/Post/{id}`, `GET` or `POST .../first` | On               |
| `exists`     | `GET` or `POST /classes/Post/exists`                | On               |
| `createOne`  | `POST /classes/Post`                                | On               |
| `updateOne`  | `PATCH /classes/Post/{id}`                          | On               |
| `deleteOne`  | `DELETE /classes/Post/{id}`                         | On               |
| `count`      | `GET` or `POST /classes/Post/count`                 | Off              |
| `upsertOne`  | `POST /classes/Post/upsert`                         | Off              |
| `createMany` | `POST /classes/Post/bulk/create`                    | Off              |
| `updateMany` | `POST /classes/Post/bulk/update`                    | Off              |
| `deleteMany` | `POST /classes/Post/bulk/delete`                    | Off              |
| `upsertMany` | `POST /classes/Post/bulk/upsert`                    | Off              |

`{id}` must be a UUID v7. Class names are case-sensitive and are not
pluralized. `rest: { count: true }` enables count **in addition to** the
built-in routes. A method that is off answers `405` with an `Allow` header
listing the methods the path accepts:

<include cwd meta='title="tests/errors.test.ts"'>
	../../examples/rest/tests/errors.test.ts#method-not-allowed
</include>

The answer is `405` `REST_METHOD_NOT_ALLOWED` with `Allow: GET`. A schema
with no route at all, like `Tag`, answers `404` `REST_NOT_FOUND`, so a hidden
schema is not revealed. Master authority does not enable a route.

A plugin command uses the same keys: `.with({ rest: { softDeleteOne: true } })`
adds `POST /classes/Post/{id}/soft-delete-one`. Only request-authority
commands on one row can be exposed; Master-only and many-row commands never
are. A command is exposed only when its rule names it, or when the rule or the
plugin default is `true`. See [Soft Delete](./soft-delete) for a concrete
example.

### Reading

A collection read accepts simple GET parameters:

<include cwd meta='title="tests/reads.test.ts"'>
	../../examples/rest/tests/reads.test.ts#list-posts
</include>

It answers `200` with the two most viewed posts and a cursor:
`{ "results": [{ "title": "Hello", "views": 42, "id": "…" }, …], "nextCursor": "…" }`.
`select` and `orderBy` take comma-separated fields, and a leading `-` sorts
descending. `id` is always returned.

`where` as JSON is the only filter form: there are no per-field URL filters,
which would collide with the reserved parameters. In GET, it is URL-encoded:

<include cwd meta='title="tests/reads.test.ts"'>
	../../examples/rest/tests/reads.test.ts#where-get
</include>

The JSON `POST /query` form takes the corresponding typed Query input, here
the two posts titled `Beta` or never viewed:

<include cwd meta='title="tests/reads.test.ts"'>
	../../examples/rest/tests/reads.test.ts#query-post
</include>

`"title": "Hello"` is the equality shorthand of `{ "eq": "Hello" }`; on a
pointer field the shorthand value is the target's UUID string. GET also
accepts `include` as relationship paths or JSON, a non-negative `take`, and
either a non-negative `skip` or an opaque `after` cursor. POST reads take
`after` as the cursor string. A collection read without `take` returns
`pagination.defaultTake` rows, 100 by default and 20 in the example; a `take`
above `maxTake` (1,000 by default) fails with `400` `REST_READ_INVALID_INPUT`.
GraphQL's `pagination` option has the same shape.

Without `skip`, a collection read also returns `nextCursor`: the cursor of its
last row when more rows follow, otherwise `null`. Pass it back as `after` with
the same `orderBy` to read the next page:

<include cwd meta='title="tests/reads.test.ts"'>
	../../examples/rest/tests/reads.test.ts#next-page
</include>

Each page starts strictly after the previous one, so inserts and deletes
between calls never repeat or skip an unchanged row. The cursor is unsigned
and stays valid across restarts and instances: it only names a position,
which the caller could also request as a filter. A malformed cursor, one for
another schema or ordering, or `after` combined with `skip` fails with HTTP
`422` `VALIDATION_ERROR` and `details: { "parameter": "after" }`. Fields REST
selects only to encode the cursor are not returned. See
[Ordering and Pagination](/docs/1.0.0/core/reading-data/ordering-and-pagination).
REST rejects unknown or duplicate parameters rather than silently ignoring
them.

A single read names the row by its identifier; `include` loads the related
rows:

<include cwd meta='title="tests/reads.test.ts"'>
	../../examples/rest/tests/reads.test.ts#read-post
</include>

The result holds the selected `title`, the included `author` object and the
`tags` array. A pointer that is not included is returned as its tagged
identity, `{ "type": "pointer", "className": "Author", "id": "…" }`.
`first`, `count` and `exists` take the same `where`:

<include cwd meta='title="tests/reads.test.ts"'>
	../../examples/rest/tests/reads.test.ts#first-count-exists
</include>

They answer `{ "result": null }` when no visible row matches,
`{ "count": 5 }` and `{ "exists": false }`.

### Writing

Ordinary create and update bodies contain the field data directly. A pointer
accepts `connect` or `create`, and a relation `create` and `connect`, beside
the scalar fields:

<include cwd meta='title="tests/writes.test.ts"'>
	../../examples/rest/tests/writes.test.ts#create-post
</include>

Create answers `201` with `{ "result": … }`; `select` and `include` query
parameters shape the result as in a read. An update additionally accepts
`update` on a pointer, `null` to unlink an optional pointer, `update`,
`disconnect` and `set` on a relation (`set: []` removes every visible
member), and `{ "increment": n }` or `{ "decrement": n }` on a number:

<include cwd meta='title="tests/writes.test.ts"'>
	../../examples/rest/tests/writes.test.ts#update-post
</include>

It answers `200` with `views: 1`, `author: null` and the `guides` tag alone.
Item DELETE has no body; it answers `200` with the row as it was before the
delete:

<include cwd meta='title="tests/writes.test.ts"'>
	../../examples/rest/tests/writes.test.ts#delete-post
</include>

A hidden `connect`, `set` or `disconnect` target answers `404` exactly like a
missing one, so a link cannot probe for rows the caller may not read:

<include cwd meta='title="tests/errors.test.ts"'>
	../../examples/rest/tests/errors.test.ts#missing-link
</include>

The answer is `404` `NOT_FOUND` with `details: { "field": "author", "schema": "Author" }`.
Upsert and bulk use their schema-command-shaped JSON bodies and cannot carry
relationship fields in this version. Bulk is ordered, itemized, atomic, and
never partial-success: if one item fails, nothing is written.

<include cwd meta='title="tests/writes.test.ts"'>
	../../examples/rest/tests/writes.test.ts#bulk-create
</include>

Bulk create answers `201` with `{ "results": [{ "slug": "part-1", "id": "…" }, …] }`;
other successful operations answer `200`.

Mutations use the same schema commands and automatic transaction boundaries
as TypeScript. REST decodes input, then Core applies structural validation and
any installed Validation, Access, ACL, and Hooks behavior. A public route is
not itself a permission rule. A non-empty JSON body must use
`application/json` and stay within `bodyLimit`.

Mutation results obey the row read rules. A client allowed to write a row it
cannot read asks for the identifier alone: `?select=id` on create, update and
delete, or `"select": { "id": true }` in an upsert or bulk body. `Feedback`
accepts creates and no read:

<include cwd meta='title="src/schema.ts"'>
	../../examples/rest/src/schema.ts#feedback
</include>

<include cwd meta='title="tests/writes.test.ts"'>
	../../examples/rest/tests/writes.test.ts#write-only
</include>

It answers `201` with `{ "result": { "id": "…" } }`. Any other selection of an
unreadable result fails with `403` and nothing is written.

### Public operations

A plugin declares which of its operations are meant for clients, such as
[authentication](./password-authentication)'s `signUp` and `login`; every
installed transport exposes them, and an operation not declared public is
never exposed. Hide one with `restPlugin({ hide: [authOperations.refresh] })`;
an application served by authentication's own `/api/auth` routes may hide them all.
An operation answers `POST /api/operations/{name}` with exactly
`{ "input": value }`, unless its owner declares a static REST path such as
`/reports/daily`. The configured `basePath` applies to these routes too.

An application operation needs no plugin: `defineOperation` from
`@ultimabase/plugin-kit` takes Standard Schema validators, and you install it
with `UltimaBase.use(...)`, as the factory above does.

<include cwd meta='title="src/operations.ts"'>
	../../examples/rest/src/operations.ts#operation
</include>

A client calls it with its input wrapped in `input`:

<include cwd meta='title="tests/operations.test.ts"'>
	../../examples/rest/tests/operations.test.ts#call-operation
</include>

It answers `200` with `{ "result": { "minutes": 2 } }`. Input that the
validator rejects answers `422` `VALIDATION_ERROR` with `details.issues`
(`path` starts with `input`); a body that is not exactly `{ "input": value }`
answers `400` `REST_OPERATION_INVALID_INPUT`; a result the output validator
rejects is a server error. The handler runs with the caller's authority:
schema reads and writes inside it obey the installed policies.

### OpenAPI

`restPlugin({ openapi: true })` serves `GET /api/openapi.json`, an OpenAPI 3.1
document of the routes this instance exposes: paths, request and response
bodies, fields and their wire types.

<include cwd meta='title="tests/operations.test.ts"'>
	../../examples/rest/tests/operations.test.ts#openapi
</include>

In the example, the document has `findManyAuthor` but no write on
`/classes/Author`, `countPost`, nothing for `Tag`, and the `readingTime`
input with `minLength: 1` on `text`. `PostCreateInput` and `PostUpdateInput`
describe `author` and `tags` with the link commands REST accepts (`connect`
and `create`, plus `update`, `disconnect` and `set` in an update); upsert and
bulk bodies refuse them. Constraints come from validators that
can describe themselves as JSON Schema (Standard JSON Schema, as Zod does): a
field's `validation` and an application operation's `input` and `output`.
The document never describes an access rule.

### Errors

After REST dispatch, errors use
`{ error: { code, message, retryable, requestId, details? } }`. A malformed
request answers `400` and locates the problem in
`details: { parameter, path, reason }`:

<include cwd meta='title="tests/errors.test.ts"'>
	../../examples/rest/tests/errors.test.ts#bad-filter
</include>

The answer is `400` `REST_READ_INVALID_INPUT` with
`{ "parameter": "where", "path": ["views", "gt"], "reason": "must be a safe integer" }`
(the exposed schema is public). A disabled method returns `405`, permission
failures `403`, hidden or missing targets `404`, validation failures `422`,
and storage conflicts (`UNIQUE_VIOLATION`, `REFERENCE_VIOLATION`, and the
retryable `TRANSACTION_CONFLICT`) `409`: a second post with the slug `hello`
answers `409` `UNIQUE_VIOLATION` with `details: { "schema": "Post", "fields": ["slug"] }`.
A field the caller may not read, such as `reviewNote`, is absent from results,
and selecting, filtering or sorting by it answers `403` `PERMISSION_DENIED`. A
[`PublicError`](/docs/1.0.0/core/runtime/api-errors#publicerror) thrown by
application code returns 400 with its code, message and details. Unexpected
exceptions become a safe `REST_INTERNAL_ERROR` response rather than exposing
internal diagnostics; the server logs them with their stack.
The response carries `X-UltimaBase-Request-Id`, equal to `error.requestId`;
keep it with the safe code when reporting a failure. Earlier application
identity or credential failures retain the HTTP plugin's envelope and never
enter REST: an unknown `X-UltimaBase-Application-Id` answers `404`
`HTTP_APPLICATION_UNKNOWN` without the REST version header.

## Troubleshooting

If startup reports that REST exposes writes without a protected policy plugin,
install a policy such as Access or opt in with `publicWrites: true`. If a
route is missing, check the schema's `rest` rule, the plugin default, the
configured `basePath`, and whether the schema is application-owned. A `405`
names a method the rule turned off, as `POST /api/classes/Author` in the
example; a `404` on a whole schema means it has no route. An operation that is
not listed is not declared public by its owner, or is hidden by
`restPlugin({ hide })`.

If a request fails before REST begins, check [HTTP troubleshooting](./http#troubleshooting)
for application ID, credentials, browser policy, and request correlation. If
REST rejects a request, read `error.details`: it names the parameter, the
path inside it and the reason. Do not use Master authority to bypass a missing
Access or ACL policy.
