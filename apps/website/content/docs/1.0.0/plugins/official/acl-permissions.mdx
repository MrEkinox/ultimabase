## Overview

`@ultimabase/acl-permissions-plugin` stores an access-control list on each
row of the schemas that call `.acl()`. An ACL grants object-level `read`,
`update`, and `delete` rights to public, authenticated, exact-principal, or
role subjects. The plugin enforces those rights through Core protected
constraints and database filtering, not by loading every row and filtering
afterward.

**Access or ACL?** [Access](./access) computes one rule for all rows of a
schema (`read: ({ where }) => where.eq('published', true)`). ACL stores the
rights of each row with the row, so one document can be shared with Alice and
another with Bob. When both are installed, their restrictions compose; neither
can widen the other.

An ACL does **not** decide who may create a record: govern creation with
Access. Authentication identifies a caller and [Roles](./roles) can supply
role membership; neither grants an ACL right unless the stored ACL names that
subject.

Every TypeScript block on this page is copied from the
[ACL example](https://github.com/MrEkinox/ultimadatabase/tree/main/examples/acl),
a small notebook application whose tests check each result described here.

## Installation

Start with an UltimaBase application and a database provider that supports
the ACL field and protected containment constraints, such as
[PostgreSQL](./postgresql). Install the ACL package:

```bash tab="npm" tab-group="package-manager"
npm install @ultimabase/acl-permissions-plugin
```

```bash tab="yarn"
yarn add @ultimabase/acl-permissions-plugin
```

```bash tab="pnpm"
pnpm add @ultimabase/acl-permissions-plugin
```

<include cwd meta='title="src/main.ts"'>
	../../examples/acl/src/main.ts#start
</include>

A member who creates a note is the only one to see it:

<include cwd meta='title="tests/notes.test.ts"'>
	../../examples/acl/tests/notes.test.ts#create-note
</include>

`mine` holds the note and `theirs` is empty: the ACL narrows the read in the
database, without an error. For Grace, an update or a delete of that note
finds no row and returns `null`. `new ACL(principal)` grants `read` and
`write` to its owner, like `new Parse.ACL(user)`, and an anonymous principal
gives an empty ACL. The group `'write'` means `update` and `delete`, as in
Access: `new ACL().grantPublic('read', 'write')`.

`default` may also be one fixed ACL, or a function of the created values
(`data`, typed from the schema's fields) and the request `principal`. The
rule also accepts:

- `resolveInput`: recomputes the ACL from the row's data on each create and
  singular update that carries no explicit ACL; returning `undefined` keeps
  the default or the current ACL.
- `clientSharing`: lets clients share rows (see below).
- `existingRows`: the ACL that rows already in the table receive when
  `.acl()` is added (see below).
- `limits`: overrides `aclPlugin({ limits: { maxPrincipals, maxRoles } })`
  (100 principals and 50 roles by default) for this schema. Public and
  authenticated grants do not count, and a repeated grant for one subject
  counts once. The limit binds Master too: a fourth member shared on a note
  fails with `VALIDATION_ERROR`.

Here `resolveInput` lets every signed-in member read a published page:

<include cwd meta='title="src/schema.ts"'>
	../../examples/acl/src/schema.ts#page
</include>

<include cwd meta='title="tests/pages.test.ts"'>
	../../examples/acl/tests/pages.test.ts#publish-page
</include>

`forMembers` holds the published page; `forAnonymous` is empty, because
`grantAuthenticated()` applies only when a principal is resolved. Unpublishing
the page recomputes its ACL again. Each item of an `updateMany` is recomputed
like an `updateOne`.

Master may write a complete ACL in `createOne`, `updateOne`, and `updateMany`
item data; it is written as is, without `resolveInput`. Master may also filter
on the ACL itself:

<include cwd meta='title="src/admin.ts"'>
	../../examples/acl/src/admin.ts#master-acl
</include>

An `upsert` update cannot replace an ACL, even for Master, and fails with
`VALIDATION_ERROR`.

## Behavior and limitations

### Sharing a row

Share or unshare a row without reading its ACL first. The change applies to
the locked row inside the update's transaction, so two concurrent shares never
overwrite each other:

<include cwd meta='title="src/sharing.ts"'>
	../../examples/acl/src/sharing.ts#share
</include>

`revoke` removes every right of the principal, or only the `permissions` it
lists. Master may share any row. A client may share only when the schema
allows it, as the note's rule does:

<include cwd meta='title="src/schema.ts"'>
	../../examples/acl/src/schema.ts#client-sharing
</include>

On a row a client can read, `clientSharing` decides instead of the `update`
right: a member who only reads the note is refused with `PERMISSION_DENIED`,
and a member who cannot read it finds no row (`null`). A client never grants
a right it does not hold itself on that row; replacing the complete ACL stays
reserved to Master.

### Reading an ACL

The `acl` field is not part of ordinary results. `select: { acl: true }` is
accepted for Master and, when the schema declares `clientSharing`, on the rows
`clientSharing` allows:

<include cwd meta='title="tests/notes.test.ts"'>
	../../examples/acl/tests/notes.test.ts#select-acl
</include>

Any other row makes the read fail with `PERMISSION_DENIED`. Clients never
filter or order by `acl`, even with `clientSharing`: a `where` naming it, also
inside `AND`, `OR`, `NOT` or a relation filter, fails with `PERMISSION_DENIED`,
and an `include` filtered on it reads as absent.

`acl.entries()` lists who holds which rights: `public` and `authenticated`
when they hold any, users as Pointers, and roles as references whose name
Roles' `resolveRoleReference(entry.role)` reads. The resolved role row is
untyped, because a stored reference does not name its role schema:

<include cwd meta='title="src/admin.ts"'>
	../../examples/acl/src/admin.ts#entries
</include>

For an announcement, the result is `['public: read', 'role editors: update, delete']`.

### ACL with Access and roles

Access and ACL compose: each narrows what the other allows. Announcements
carry one fixed ACL that everyone reads and that the `editors` role changes,
while Access hides drafts and lets only editors create:

<include cwd meta='title="src/schema.ts"'>
	../../examples/acl/src/schema.ts#members
</include>

<include cwd meta='title="src/schema.ts"'>
	../../examples/acl/src/schema.ts#announcement
</include>

<include cwd meta='title="tests/announcements.test.ts"'>
	../../examples/acl/tests/announcements.test.ts#announce
</include>

An anonymous caller reads the published announcement through the public
entry, and the editor updates it through the role entry. For a member
without the role, Access lets the update run but the ACL keeps the row out of
reach (`null`), and Access refuses the create. The public entry covers drafts
too, yet Access still hides them from every caller but Master. A static
default with role grants needs a role provider such as Roles at startup, and
role names resolve to stable role IDs before an ACL is stored.

### Adding or removing ACL on a table with rows

When PostgreSQL synchronization adds the `acl` column to a table:

- an empty table gets the column directly;
- a table with rows gives them a fixed value, without rewriting the table:
  the `default` when it is one ACL, else `existingRows`;
- a function `default` without `existingRows` stops `start()` with the steps
  to follow: declare `existingRows`, or empty the table first.

Under `schemaPolicy: 'fail'` nothing changes and the drift message names the
value existing rows would receive. The column is `NOT NULL`. Removing `.acl()`
later keeps the column and its data, gives rows written afterward an empty
ACL, and drops the index.

### Values and enforcement

`ACL` is immutable: each grant, revoke, or replacement returns a new value.

<include cwd meta='title="tests/values.test.ts"'>
	../../examples/acl/tests/values.test.ts#acl-value
</include>

`value` still grants Ada `read`, `update`, and `delete`; `updated` grants her
`read` only. `grantPublic()` applies to everyone; `grantAuthenticated()`
applies only when a principal is resolved. `grantPrincipal()` uses one exact
Pointer and `grantRole()` a role reference a compatible role provider
resolves. The closed rights are `read`, `update`, and `delete`. `toJSON()`
produces detached, versioned data, and `ACL.fromJSON()` strictly validates it:
unknown keys, versions, or rights are rejected.

PostgreSQL stores the ACL as indexed JSONB on the same row, written
atomically with its object. Master bypasses ACL authorization, but not size
validation, reference integrity, events, or transactions.

### Change events

Each ACL change emits an optional notification after commit; a rollback
publishes nothing, and assigning an equivalent ACL emits nothing. A plugin
observes them:

<include cwd meta='title="src/acl-audit-plugin.ts"'>
	../../examples/acl/src/acl-audit-plugin.ts#acl-audit-plugin
</include>

The payload names the `actor`, the `target` row, the `operation` (`create`,
`update`, or `upsert`), and a `diff` of the `read`, `update`, and `delete`
rights added and removed per public, authenticated, principal, or role
subject.

## Troubleshooting

- **`.acl()` is missing from autocomplete:** declare the schema from the
  configured factory that installs `aclPlugin()`.
- **`acl.default` is required:** `.with({ acl: { default } })` must follow
  `.acl()`.
- **A record is unexpectedly invisible:** inspect its ACL with Master. An
  empty ACL denies ordinary object rights.
- **A share is denied:** the schema needs `clientSharing`, it must allow the
  row, and the client must hold every right it grants.
- **`start()` stops on existing rows:** add `existingRows` to the rule, or use
  a fixed `default`.
- **An ACL exceeds its entry limit:** check the effective `maxPrincipals` and
  `maxRoles`; repeated rights for one subject count once.
