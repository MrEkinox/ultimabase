## Overview

`@ultimabase/http-plugin` is the Fetch-compatible foundation every HTTP
transport shares. It does not open a socket: a server plugin such as
[Hono Server](./hono-server) serves it. It owns application identity, the
built-in health route, application routes, CORS, the request deadline, the
body limit, security headers, rate limits, the access log and port-free
testing (ADR-0323).

The code on this page comes from the tested
[HTTP example](https://github.com/MrEkinox/ultimadatabase/tree/main/examples/http),
a small links API whose tests prove what the page describes.

## Installation

These packages are pre-release. Use the locally built repository example linked
from [Manual Installation](/docs/1.0.0/manual-installation) to evaluate the
current code; the registry commands below describe installation after publication.

Install the application HTTP boundary:

```bash tab="npm" tab-group="package-manager"
npm install @ultimabase/http-plugin
```

```bash tab="yarn"
yarn add @ultimabase/http-plugin
```

```bash tab="pnpm"
pnpm add @ultimabase/http-plugin
```

REST and GraphQL routes need their own transport plugins. The
[`@ultimabase/api-server`](/docs/1.0.0/reference/package-index) preset installs
HTTP, REST, GraphQL and the Hono server together.

## Configuration

`httpPlugin()` needs no option. The example's API sets most of them:

<include cwd meta='title="src/http.ts"'>
	../../examples/http/src/http.ts#http-options
</include>

`apiServer({ http })` installs `httpPlugin(http)` beside REST and the
managed Hono server; `UltimaBase.use(httpPlugin(http))` installs it alone:

<include cwd meta='title="src/schema.ts"'>
	../../examples/http/src/schema.ts#factory
</include>

| Option                 | Default                                                    |
| ---------------------- | ---------------------------------------------------------- |
| `appId`                | `'main'`                                                   |
| `requireApplicationId` | `false`: requests without the header reach the application |
| `browser`              | CORS disabled                                              |
| `master`               | Master header refused; `true` enables it                   |
| `routes`               | none                                                       |
| `health`               | `{ path: '/health' }`; `false` removes it                  |
| `requestTimeoutMs`     | `30_000`                                                   |
| `bodyLimit`            | `1_048_576` bytes for every route                          |
| `securityHeaders`      | `nosniff`, `X-Frame-Options: DENY`, HSTS on HTTPS          |
| `trustProxy`           | unset: the socket peer is the client                       |
| `rateLimit`            | none                                                       |
| `accessLog`            | `false`                                                    |

`requestTimeoutMs` is a whole number of milliseconds from 1 through
2147483647, the largest delay a JavaScript timer honors.

## Behavior and limitations

### Application identity

The public `appId` grants no authority. A request without
`X-UltimaBase-Application-Id` reaches the only application of the process; a
different value is refused:

<include cwd meta='title="tests/identity.test.ts"'>
	../../examples/http/tests/identity.test.ts#unknown-application
</include>

```json title="404 response"
{
	"error": {
		"code": "HTTP_APPLICATION_UNKNOWN",
		"message": "The HTTP application is unknown.",
		"requestId": "3f0c8f9e-1d1b-4d6c-9d43-6f2f3b9b8c11",
		"retryable": false
	}
}
```

With several applications behind one proxy, `requireApplicationId: true`
makes the header mandatory again.

### Application routes and health

`routes` takes the same record as the plugin helper `httpRoutes`: keys are
`"<METHOD> /<path>"`, values a handler `(request, { context }) => Response` or
`{ handle, bodyLimit?, rateLimit? }`. No plugin is needed for an application
route. The handler runs with the request context already active:

<include cwd meta='title="src/routes.ts"'>
	../../examples/http/src/routes.ts#routes
</include>

<include cwd meta='title="tests/routes.test.ts"'>
	../../examples/http/tests/routes.test.ts#status
</include>

An anonymous request reads `{ "mode": "anonymous", "partner": null }`. A
`PublicError` thrown by a handler answers 400 with its code, message and
details, in the same envelope as the HTTP errors:

<include cwd meta='title="tests/routes.test.ts"'>
	../../examples/http/tests/routes.test.ts#contact-invalid
</include>

```json title="400 response"
{
	"error": {
		"code": "CONTACT_INVALID",
		"message": "Give an email address to reply to.",
		"details": { "field": "email" },
		"requestId": "8d5ab1e5-c43f-49d8-95f6-1f6e7c64ddc6",
		"retryable": false
	}
}
```

Any other handler failure propagates to the server plugin.

`GET /health` answers 200 `{ "status": "OK" }` or 503
`{ "status": "DEGRADED" }` from `ultimabase.health()`, without application
header or credential, whichever transports are installed. Move it with
`health: { path: '/healthz' }` or remove it with `health: false`.

### Limits and security headers

Request bodies are limited to 1 MiB for every route, counted while the body
streams; a larger one is answered `HTTP_PAYLOAD_TOO_LARGE`. A route sets its
own `bodyLimit`, as the contact route does, and `restPlugin({ bodyLimit })` or
`graphqlYogaPlugin({ bodyLimit })` replaces it for that transport.

Responses carry `X-Content-Type-Options: nosniff` and `X-Frame-Options: DENY`,
plus `Strict-Transport-Security` on HTTPS. Each is configurable under
`securityHeaders`, and `securityHeaders: false` removes them. TLS and HTTP/2
come from the proxy or platform in front of the server.

<include cwd meta='title="src/http.ts"'>
	../../examples/http/src/http.ts#security-headers
</include>

### Rate limits and proxies

`rateLimit: { default: { perMinute } }` limits requests per client address and
minute:

<include cwd meta='title="src/http.ts"'>
	../../examples/http/src/http.ts#rate-limit
</include>

<include cwd meta='title="tests/limits.test.ts"'>
	../../examples/http/tests/limits.test.ts#rate-limited
</include>

The 301st request of a minute from that address gets `HTTP_RATE_LIMITED`
(429) with `Retry-After`. Routes may add stricter limits, counted in addition
to the default. The built-in health route is never limited, since probes often
share one address.

Behind proxies, set `trustProxy` to the number of proxy hops or their exact
addresses: only then are `X-Forwarded-For` and `X-Forwarded-Proto` believed.
The client is the nearest `X-Forwarded-For` entry that is not one of your
proxies; what a client writes before it never changes the address that is
counted. Behind a fetch handler without a socket peer, as on edge and
serverless platforms, the platform in front counts as one hop; exact addresses
are checked against the socket peer, so they need one.

When neither a socket peer nor a trusted `X-Forwarded-For` entry names the
client, as with the in-memory `fetch` without `remoteAddress` or a fetch
handler without `trustProxy`, its address is unknown. Every such request then
shares one bucket per limit: failing closed is safer than skipping the limit.
The first such request of a process logs one warning that points to
`trustProxy` and to `remoteAddress`, from the server provider or the in-memory
`fetch`. Context resolvers receive `clientAddress: undefined`, and
[Password Authentication](./password-authentication) records `null`.

Counts live in memory per process; pass a `store` with an
`increment(key, expiresAt)` method to share them, for example in Redis. A
failing store refuses requests rather than letting them through.

<include cwd meta='title="src/counters.ts"'>
	../../examples/http/src/counters.ts#store
</include>

### Access log

`accessLog: true` writes one line per request through the application logger:
method, path, status, duration and request ID, never bodies, query strings or
credentials.

### Browser policy

Browser-origin behavior is disabled by default.
`browser: { origins, credentials? }` enables it
for exact origins:

<include cwd meta='title="src/http.ts"'>
	../../examples/http/src/http.ts#browser
</include>

Allowed methods come from the mounted routes and allowed headers from the
installed plugins: `Content-Type`, the application and request ID headers,
`Authorization` with a plugin that resolves credentials (such as
[Password Authentication](./password-authentication)), and the Master header
only with `master: true`. The plugin exports the effective policy:

<include cwd meta='title="tests/browser.test.ts"'>
	../../examples/http/tests/browser.test.ts#effective-policy
</include>

Without a policy, a browser preflight is refused with
`CORS is not enabled: configure browser.origins`.

CORS controls browser responses; it is not authentication, authorization, CSRF
protection, or protection from non-browser clients: a request from another
origin is still answered, only without the CORS headers its browser needs. A
wildcard origin is incompatible with credentials and Master transport.

### Master

`master: true` enables the canonical `X-UltimaBase-Master-Key` header, only
with a configured `MasterAuthority`, which verifies and audits it:

<include cwd meta='title="src/ultimabase.ts"'>
	../../examples/http/src/ultimabase.ts#application
</include>

<include cwd meta='title="tests/identity.test.ts"'>
	../../examples/http/tests/identity.test.ts#master-request
</include>

A wrong key is refused with `HTTP_APPLICATION_REJECTED`; without the header
the request stays anonymous, and the example's Access rules let it only read.
Do not expose a raw Master key to browser code.

### Credentials from requests

A plugin turns request credentials into request context values with a
resolver; it never grants Master authority. The example resolves a partner
from a Bearer token, and an unknown token is refused with
`HTTP_APPLICATION_REJECTED` before any route runs:

<include cwd meta='title="src/partners.ts"'>
	../../examples/http/src/partners.ts#partner-credentials
</include>

<include cwd meta='title="tests/identity.test.ts"'>
	../../examples/http/tests/identity.test.ts#partner-request
</include>

`/status` then reads `{ "mode": "anonymous", "partner": "acme" }`. Route
handlers never see the `Authorization` or `Cookie` headers, only the values
resolvers derived. Password Authentication uses the same mechanism for its
sessions.

### Test without a server

<include cwd meta='title="tests/routes.test.ts"'>
	../../examples/http/tests/routes.test.ts#fetch
</include>

The request takes the same path as a network request, CORS included, without
a server or a port. The application must be started; `testApplication()`
starts it, and its `t.fetch(path, init)` sends the same requests from the
local peer `127.0.0.1`, as a local server would.

Without a server the request has no socket peer. A fetch handler that knows
the client address from its platform, as on edge and serverless platforms,
passes it as `remoteAddress`; it is then the socket peer, so `trustProxy`
applies to it:

<include cwd meta='title="tests/client-address.test.ts"'>
	../../examples/http/tests/client-address.test.ts#remote-address
</include>

### Connect a server and a transport

The [Hono Server](./hono-server) guide covers managed and existing listeners.
Add [REST](./rest) or [GraphQL](./graphql) to expose data routes through the
same foundation.

### Implement a server provider

A custom server consumes `httpApplicationCapability` and
`httpBrowserPolicyCapability`. Keep one optional HTTP application and pass it,
with the original header pairs and the socket peer `remoteAddress`, to
`dispatchHttpApplicationRequest(application, input)`. Without `remoteAddress`
the client address is unknown unless `trustProxy` names it. Clear the owner before
teardown. When no owner remains, the helper still validates header cardinality
and correlation, then returns the safe HTTP rejection envelope.

The application boundary also owns exact browser-bootstrap URLs such as
`/__ultimabase/apps/blog/graphiql`. See [GraphQL](./graphql) for the browser
tool setup.

ETag, OpenTelemetry tracing, connection takeover for realtime plugins and
`multipart` bodies are not provided yet.

## Troubleshooting

Before a route starts, HTTP returns a private, non-cacheable envelope with a
stable code and `X-UltimaBase-Request-Id`:

| Code                        | First interpretation                                            |
| --------------------------- | --------------------------------------------------------------- |
| `HTTP_BAD_REQUEST`          | malformed or ambiguous request evidence                         |
| `HTTP_APPLICATION_REJECTED` | credentials rejected, or a missing header under strict identity |
| `HTTP_APPLICATION_UNKNOWN`  | the header names another application                            |
| `HTTP_CORS_DISABLED`        | a browser preflight reached an application without CORS         |
| `HTTP_NOT_FOUND`            | no selected route owns the path                                 |
| `HTTP_PAYLOAD_TOO_LARGE`    | the request body exceeded the route's limit                     |
| `HTTP_RATE_LIMITED`         | the client exceeded a rate limit; retry after `Retry-After`     |
| `HTTP_REQUEST_TIMEOUT`      | the shared request deadline expired                             |
| `HTTP_INTERNAL_ERROR`       | the pre-dispatch boundary failed safely                         |

Reproduce without credentials first:

```sh
curl -i http://127.0.0.1:1337/health
```

Record status, stable error code, and request ID. A client may send its own
`X-UltimaBase-Request-Id` (letters, digits, `.`, `_`, `:` and `-`, at most 128)
to correlate its logs; another value is refused with `HTTP_BAD_REQUEST`.
Confirm the public `appId`, mount, method, and route. Never combine Bearer and
cookie credentials. Do not copy Authorization, Cookie, Master values, or
request bodies into logs or reports.

If the boundary still rejects the request, follow
[Reporting a problem](/docs/1.0.0/operations/troubleshooting#report-a-problem)
with sanitized evidence. Widening CORS or switching to Master authority cannot
repair invalid identity or credentials.
