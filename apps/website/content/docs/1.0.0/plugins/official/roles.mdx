## Overview

`@ultimabase/roles-plugin` stores application-local role membership and
hierarchy through a developer-defined role schema. A role reference is
immutable and can identify a normalized name or a stable UUID. The plugin
provides role subjects for policy, but membership never grants permission by
itself.

## Installation

Start with an UltimaBase application and a database provider. Install the
Roles package:

```bash tab="npm" tab-group="package-manager"
npm install @ultimabase/roles-plugin
```

```bash tab="yarn"
yarn add @ultimabase/roles-plugin
```

```bash tab="pnpm"
pnpm add @ultimabase/roles-plugin
```

Install [Access](./access) separately only if you use `hasRole()` in an
Access rule. ACL can consume role subjects without installing Access.

## Configuration

Define the exact member schema, then define and register a role schema:

```ts title="src/roles.ts"
import { Schema } from '@ultimabase/core'
import { RoleSchema, rolesPlugin } from '@ultimabase/roles-plugin'

export const Member = Schema.define({
	className: 'Member',
	fields: (field) => ({
		name: field.string({ required: true }),
	}),
})

export const AppRole = RoleSchema.define({
	className: 'Role',
	members: { schema: Member },
	deletion: { references: 'fail' },
	fields: (field) => ({
		description: field.string(),
	}),
})

export const roles = rolesPlugin()
export const editor = AppRole.role('editor')
```

Include `Member` and `AppRole` in `schemas`, and `roles` in `plugins`.
`rolesPlugin()` has no factory options. `members.schema` selects one exact
member schema. `deletion.references` accepts `'fail'` (the default),
`'preserve'`, or `'cascade'`; choosing a less restrictive deletion mode
requires reviewing what happens to external references. Custom `fields`,
indexes, Hooks, and supported schema options remain available on the role
schema.

## Behavior and limitations

`RoleSchema.define()` adds the framework-owned `name`, `members`, and
nested `roles` fields. Names are normalized and unique within the schema.
`AppRole.role('editor')` selects a name; `AppRole.role({ id })` selects
an exact UUID. Neither reference performs I/O. A UUID remains stable after
renaming the role.

Persisted roles expose `addMember()`, `removeMember()`, `addRole()`,
and `removeRole()`. The plugin validates hierarchy cycles and emits optional
events after commit. A role, a role hierarchy, and an authenticated principal
grant nothing by themselves. [Access](./access) must explicitly use
`hasRole()`, or [Object ACLs](./acl-permissions) must grant rights to that role.

Master authority does not imply role membership. Role maintenance may
initiate audited internal Master queries, but it does not lend that authority
to Access, ACL, or the caller.

## Troubleshooting

If `RoleSchema` is rejected during application compilation, confirm
`rolesPlugin()` is installed and the role and member schemas are registered
in the same application. If `hasRole()` cannot resolve the current member,
check that Access and the exact member resolver are configured; membership
storage alone does not identify a request.

If a deletion fails, inspect the role's `deletion.references` policy and its
member, child-role, and external references. Do not switch to `cascade`
merely to make an unexplained failure disappear.
