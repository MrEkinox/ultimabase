## Overview

`@ultimabase/roles-plugin` stores roles as ordinary application schemas with
typed members and included roles. You declare each role schema with
`App.RoleSchema.define(...)` and its member schema; the plugin supplies the
membership resolver, role queries, and seed roles. A role reference identifies
a role. An application may declare several role schemas.
A role, a role hierarchy, and an authenticated principal
grant nothing by themselves.

Use [Access](./access) to make a role an operation or field decision through
`hasRole()`. [Object ACLs](./acl-permissions) can grant rights to a role through
Core's separate protected-policy boundary; ACL does not require the official
Access plugin. Authentication supplies the current member but also grants
nothing on its own.

## Installation

Start with an UltimaBase application and database provider. Install the
optional Roles package:

```bash tab="npm" tab-group="package-manager"
npm install @ultimabase/roles-plugin
```

```bash tab="yarn"
yarn add @ultimabase/roles-plugin
```

```bash tab="pnpm"
pnpm add @ultimabase/roles-plugin
```

Role storage and administration work without Access, and Roles does not
depend on the Access package: `hasRole()` returns a Core policy predicate that
Access, ACL and other policy plugins accept. The example below also uses
[Password Authentication](./password-authentication) to identify the current
member. Roles' internal membership queries elevate with the plugin's own
audited privilege; administrative commands from your server code use
configured, audited
[Master Authority](/docs/1.0.0/core/security-foundations/master-authority).

## Configuration

Installing `rolesPlugin()` adds `App.RoleSchema` to the configured factory.
Declare a role schema with the schema of its members, then end with
`.with({ ... })` like any schema. The current member is the request principal
resolved by Core when it belongs to the member schema; here the
authentication principal points to the `AppUser` class declared through
`App.UserSchema`, so `hasRole()` can evaluate the caller's membership:

```ts title="src/roles.ts"
import { hasRole } from '@ultimabase/roles-plugin'
import { Application } from './application.js'

// The authenticated User reads only its own profile, which sign-up and login
// return.
export const AppUser = Application.UserSchema.define({
	className: 'User',
}).with({
	access: {
		read: ({ principal, where }) =>
			where.in('id', principal === undefined ? [] : [principal.id]),
	},
})

export const AppRole = Application.RoleSchema.define({
	className: 'Role',
	members: () => AppUser,
	deletion: 'fail',
	// Created at start() when missing; existing roles are left unchanged.
	ensure: ['editor', 'administrator'],
	fields: (f) => ({
		description: f.string(),
	}),
}).with({
	access: {
		read: true,
		create: false,
		update: false,
		delete: false,
	},
})

export const EditorRole = AppRole.role('editor')

export const Post = Application.Schema.define({
	className: 'Post',
	fields: (f) => ({ title: f.string({ required: true }) }),
}).with({
	access: {
		read: true,
		update: hasRole(EditorRole),
	},
})
```

`members` is a function so that the role and member schemas may reference each
other, like relation targets. Declare `Register` with `typeof ultimabase` as
for any application (ADR-0297); role schemas need no special declaration.

### Assemble the application

Install the identity, policy, and role plugins once on the configured factory.
`AppUser`, `AppRole` and `Post` are developer schemas declared from that
factory; Access denies every operation their rules do not open:

```ts title="src/application.ts"
import { accessPlugin } from '@ultimabase/access-plugin'
import { password } from '@ultimabase/auth-password'
import { authPlugin } from '@ultimabase/auth-plugin'
import { UltimaBase } from '@ultimabase/core'
import { postgresPlugin } from '@ultimabase/postgres-plugin'
import { rolesPlugin } from '@ultimabase/roles-plugin'

const databaseUrl = process.env.DATABASE_URL
if (!databaseUrl) throw new Error('DATABASE_URL is required')

export const Application = UltimaBase.use(postgresPlugin({ url: databaseUrl }))
	.use(authPlugin({ methods: [password({ identifier: 'email' })] }))
	.use(accessPlugin())
	.use(rolesPlugin())
```

```ts title="src/ultimabase.ts"
import { MasterAuthority } from '@ultimabase/core'
import { Application } from './application.js'
import { AppRole, AppUser, Post } from './roles.js'

const masterKey = process.env.ULTIMABASE_MASTER_KEY
if (!masterKey) throw new Error('ULTIMABASE_MASTER_KEY is required')

export const ultimabase = new Application({
	masterAuthority: new MasterAuthority({
		keys: [{ id: 'server', value: masterKey }],
		onUse: (event) => console.info('Master use', event.reason),
	}),
	schemas: [AppUser, AppRole, Post],
})
```

Keep startup in the existing entry point from
[Manual Installation](/docs/1.0.0/manual-installation#start-and-verify): await
`ultimabase.start()` there and always await `dispose()` when the process finishes.
This configuration module stays safe to load for static Typegen generation.

Use a disposable database or a reviewed PostgreSQL schema policy while
developing. Replace the console audit with a reliable sink before deployment;
never send Master credentials to a browser. `rolesPlugin()` takes no factory
options; each role schema declares its behavior:

| `App.RoleSchema.define` option | Purpose                                                                                      |
| ------------------------------ | -------------------------------------------------------------------------------------------- |
| `members`                      | A function returning the schema of the persisted direct members                              |
| `fields`                       | Ordinary custom fields beside `name`, `members` and `includedRoles`                          |
| `deletion`                     | External-reference policy: `'fail'` (default), `'preserve'`, or `'cascade'`                  |
| `ensure`                       | Role names created at `start()` when missing (idempotent, existing roles unchanged)          |
| `resolveCurrent`               | Special cases only: maps request-local identity to a member Pointer instead of the principal |

Rules (`access`, `hooks`), indexes and plugin options go in the final
`.with({ ... })`; shape methods such as `.acl()` may be chained before it.
The factory adds `name`, `members`, and `includedRoles`; do not redeclare
them. Role schemas remain available to trusted server Query, but are not
automatically published as generated REST or GraphQL CRUD routes.

## Behavior and limitations

### Create roles and manage membership

`ensure` creates seed roles at `start()`. Persist other roles through the
ordinary schema commands. Run administrative commands only from trusted server
code with audited Master authority when the role schema denies ordinary
mutations, as in the configuration above:

```ts title="src/seed-roles.ts"
import { AppRole, AppUser } from './roles.js'

const master = { useMasterKey: true } as const
const editor = await AppRole.findOneOrThrow(
	{ where: { name: 'editor' } },
	master,
)
await AppRole.updateOne(
	{
		where: { name: 'administrator' },
		data: { includedRoles: { connect: [editor.id] } },
	},
	master,
)

export const addEditor = (userId: string) =>
	AppRole.updateOne(
		{
			where: { id: editor.id },
			data: { members: { connect: [AppUser.pointer(userId)] } },
			select: { id: true },
		},
		master,
	)
```

Members and included roles change through the ordinary relation commands of
`createOne` and `updateOne` (ADR-0308): `members: { connect: [...] }`,
`disconnect`, or `set`, with IDs or Pointers of the member schema.
`includedRoles` changes hierarchy: connecting Editor to Administrator's
`includedRoles` means Editor's members are members of Administrator too. The
opposite link would mean the opposite inheritance. Role results are plain data
without commands (ADR-0310): these relation writes are the only way to change
membership and hierarchy.

These commands use normal relation writes, validation, Access, Hooks when
installed, and automatic transactions; each linked member or role must be
visible to the caller. The plugin rejects self or indirect cycles and emits its
membership and hierarchy events for links made through these commands as well. A membership or hierarchy change is visible to a **new** request;
membership is resolved once and cached within an active request, so do not
expect a policy check already in progress to reread changed membership.

### Query roles outside rules

`ultimabase.plugin(rolesPlugin)` exposes the same computation and cache as
the rules:

```ts
const roles = ultimabase.plugin(rolesPlugin)
await roles.has(EditorRole) // the current request's member, inside a request
await roles.has(EditorRole, { principal: AppUser.pointer(userId) })
await roles.current(AppRole) // ['administrator', 'editor']: names, inheritance included
```

`has(role)` and `current(schema)` read the current request, so call them
inside a hook, a rule or an operation handler; with `{ principal }`, `has`
checks that member anywhere on the server.

### Choose a role reference

`AppRole.role('editor')` creates a normalized name reference;
`AppRole.role({ id: editor.id })` creates an exact UUID reference. Both are
immutable, schema-qualified, and perform no database I/O. Stored names are
trimmed, NFKC-normalized, lowercased, and unique within that role schema.
Renaming changes what a name reference resolves to; the persisted UUID stays
stable. Prefer the UUID form for long-lived references after a role exists.

`resolveRoleReference(reference, options)` loads a stored role when server
code needs its row. It fails explicitly for an unknown name or ID and for
ambiguous name storage; merely constructing a reference does not prove a
matching role exists.

### Use roles in policy

`hasRole(EditorRole)` returns a named Core
[policy predicate](/docs/1.0.0/core/security-foundations/request-identity#policy-predicates),
accepted wherever an Access rule returns a decision. In the example, it grants
`Post.update` only when the request principal is a direct or inherited Editor
member. Without `resolveCurrent`, the current member is the request principal
when it belongs to the member schema; a principal of another schema, or none,
denies. `resolveCurrent` remains for special cases: it may be asynchronous but
must return a Pointer of the member schema, or `undefined` when there is no
current member.

If a rule uses `hasRole()` without any application-local role-resolver
provider, execution raises `PLUGIN_CAPABILITY_MISSING` before business Hooks
or storage. Installing `rolesPlugin()` provides that resolver; a community
provider may supply the same neutral capability. Master authority does not
imply membership. Master bypasses the official Access rule as authority, not
by pretending `hasRole()` returned `true`.

ACL can grant rights to a role reference independently of the Access plugin.
The ACL and Roles plugins resolve that reference through Core's neutral
subject boundary; role membership alone still grants nothing. See
[Object ACLs](./acl-permissions) for persisted grants.

### Deletion, events, and limits

| `deletion`       | Effect                                                                                                                       |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `fail` (default) | Rejects deletion while the role has members, child or parent edges, or references reported by another plugin                 |
| `preserve`       | Deletes the role and leaves external references inert; choose this only when the dangling-reference behavior is intentional  |
| `cascade`        | Requires Master, clears role edges, and invokes explicit cleanup contributions from reference owners in the same transaction |

`AppRole.deleteOne()` applies the policy.
`AppRole.deleteMany({ where: [{ id: { eq: firstId } }, { id: { eq: secondId } }] })`
applies it to each unique target in order, within one transaction. If a target
is missing or a policy fails, all deletions, cleanup and queued events roll back.
Do not switch to `cascade` just to silence `ROLE_DELETE_REFERENCED`; review every reference owner first.

Membership, hierarchy, and deletion events are optional post-commit
notifications. They are not delivered on rollback, and the Roles plugin does
not require Hooks. Hierarchy traversal rejects cycles and fails explicitly if
it exceeds 64 levels or 10,000 visited roles.

## Troubleshooting

- **`App.RoleSchema` is missing:** declare the role schema from the
  configured factory that installs `rolesPlugin()`, and register it. The
  `name`, `members`, and `includedRoles` fields cannot be replaced by custom
  fields.
- **`hasRole()` always denies:** verify that the request principal (or
  `resolveCurrent`, if declared) is a Pointer of the member schema. A session by itself
  supplies identity, not a role grant; confirm the persisted membership and
  hierarchy in the same application.
- **`PLUGIN_CAPABILITY_MISSING`:** the Access rule ran without an installed
  role-resolver provider. Install `rolesPlugin()` or an intentional compatible
  provider in that application.
- **Role deletion fails:** inspect direct members, child and parent roles,
  and external references under the schema's deletion policy. For `deleteMany()`,
  each target must satisfy that policy; a failure rolls back the whole batch.
- **`start()` fails on `ensure`:** creating seed roles is a Master write;
  configure the application's `masterAuthority`.
