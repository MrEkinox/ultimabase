## Overview

`@ultimabase/roles-plugin` stores roles as ordinary application schemas with
typed members and included roles. You declare each role schema with
`App.RoleSchema.define(...)` and its member schema; the plugin supplies the
membership resolver, role queries, and seed roles. A role reference identifies
a role. An application may declare several role schemas.
A role, a role hierarchy, and an authenticated principal
grant nothing by themselves.

Use [Access](./access) to make a role an operation or field decision through
`hasRole()`. [Object ACLs](./acl-permissions) can grant rights to a role through
Core's separate protected-policy boundary; ACL does not require the official
Access plugin. Authentication supplies the current member but also grants
nothing on its own.

Every TypeScript block on this page is copied from the
[roles example](https://github.com/MrEkinox/ultimadatabase/tree/main/examples/roles),
a small newsroom application whose tests check each result described here.

## Installation

Start with an UltimaBase application and database provider. Install the
optional Roles package:

```bash tab="npm" tab-group="package-manager"
npm install @ultimabase/roles-plugin
```

```bash tab="yarn"
yarn add @ultimabase/roles-plugin
```

```bash tab="pnpm"
pnpm add @ultimabase/roles-plugin
```

Role storage and administration work without Access, and Roles does not
depend on the Access package: `hasRole()` returns a Core policy predicate that
Access, ACL and other policy plugins accept. Roles' internal membership
queries elevate with the plugin's own audited privilege; administrative
commands from your server code use configured, audited
[Master Authority](/docs/1.0.0/core/security-foundations/master-authority).

Declare a role schema with the schema of its members, then end with

and its rules let every caller read roles but change none:

	../../examples/roles/src/schema.ts#staff-role

`members` is a function so that the role and member schemas may reference each
other, like relation targets. The current member is the request principal
resolved by Core when it belongs to the member schema. With
[Password Authentication](./password-authentication), the principal points to
the class declared through `App.UserSchema`: use that class as the member
schema. The example's tests set the principal directly.

`hasRole()` turns a role reference into a rule:

<include cwd meta='title="src/schema.ts"'>
	../../examples/roles/src/schema.ts#post
</include>

Register the schemas in the application. Staff administration runs from
trusted server code with audited Master authority:

<include cwd meta='title="src/ultimabase.ts"'>
	../../examples/roles/src/ultimabase.ts#application
</include>

Declare `Register` with `typeof ultimabase` as for any application (ADR-0297);
role schemas need no special declaration. Start the application from a
separate entry point. `start()` creates the `ensure` roles; the hierarchy is
ordinary data, which server code links once the application has started:

<include cwd meta='title="src/main.ts"'>
	../../examples/roles/src/main.ts#start
</include>

Use a disposable database or a reviewed PostgreSQL schema policy while
developing. Replace the console audit with a reliable sink before deployment;
never send Master credentials to a browser. `rolesPlugin()` takes no factory
options; each role schema declares its behavior:

| `App.RoleSchema.define` option | Purpose                                                                                      |
| ------------------------------ | -------------------------------------------------------------------------------------------- |
| `members`                      | A function returning the schema of the persisted direct members                              |
| `fields`                       | Ordinary custom fields beside `name`, `members` and `includedRoles`                          |
| `deletion`                     | External-reference policy: `'fail'` (default), `'preserve'`, or `'cascade'`                  |
| `ensure`                       | Role names created at `start()` when missing (idempotent, existing roles unchanged)          |
| `resolveCurrent`               | Special cases only: maps request-local identity to a member Pointer instead of the principal |

Rules (`access`, `hooks`), indexes and plugin options go in the final
`.with({ ... })`; shape methods such as `.acl()` may be chained before it.
The factory adds `name`, `members`, and `includedRoles`; do not redeclare
them. Role schemas are application schemas: trusted server code queries them
like any schema, and the REST and GraphQL transports expose them like any
other schema, under their Access rules. The example's REST clients can list
staff roles but not create one; `rest: false` keeps a role schema off
[REST](./rest).

## Behavior and limitations

### Create roles and manage membership

`ensure` creates seed roles at `start()`. Persist other roles through the
ordinary schema commands. `StaffRole` has no write rule, so only trusted
server code with audited Master authority changes it; an ordinary caller,
even an administrator, is refused with `PERMISSION_DENIED`:

<include cwd meta='title="src/staff.ts"'>
	../../examples/roles/src/staff.ts#staff-admin
</include>

Members and included roles change through the ordinary relation commands of
`createOne` and `updateOne` (ADR-0308): `members: { connect: [...] }`,
`disconnect`, or `set`, with IDs or Pointers of the member schema.
`includedRoles` changes hierarchy: the members of an included role are members
of the role that includes it. Connecting Administrator to Editor's
`includedRoles` makes every administrator an editor; the opposite link would
make every editor an administrator. Role results are plain data without
commands (ADR-0310): these relation writes are the only way to change
membership and hierarchy.

<include cwd meta='title="tests/membership.test.ts"'>
	../../examples/roles/tests/membership.test.ts#membership
</include>

`adaRoles` is `['editor']`. `graceRoles` is `['administrator', 'editor']`:
Grace is an administrator, and an editor through Editor's included roles.

These commands use normal relation writes, validation, Access, Hooks when
installed, and automatic transactions; each linked member or role must exist
and be visible to the caller, or the command fails with `NOT_FOUND`. The plugin
rejects self or indirect cycles with `ROLE_HIERARCHY_CYCLE` and writes nothing:
in the example, connecting Editor to Administrator's `includedRoles` would
close one. It emits its membership and hierarchy events for links made through
these commands as well.

Who may manage a role schema is an ordinary Access decision. `Team`, a second
role schema, lets administrators create and update teams as callers:

<include cwd meta='title="src/schema.ts"'>
	../../examples/roles/src/schema.ts#team
</include>

<include cwd meta='title="tests/membership.test.ts"'>
	../../examples/roles/tests/membership.test.ts#team
</include>

`nightDesk.name` is `'night desk'`: role names are stored trimmed,
NFKC-normalized and lowercased, and are unique within their role schema, so a
second `'NIGHT DESK'` fails with `UNIQUE_VIOLATION`. A member who is not an
administrator gets `PERMISSION_DENIED`.

A membership or hierarchy change is visible to a **new** request. Membership
is resolved once and cached within an active request, so a policy check
already in progress does not reread changed membership:

<include cwd meta='title="tests/queries.test.ts"'>
	../../examples/roles/tests/queries.test.ts#request-cache
</include>

`sameRequest` is `{ before: false, after: false }`; `nextRequest` is `true`.

### Query roles outside rules

`ultimabase.plugin(rolesPlugin)` exposes the same computation and cache as
the rules:

<include cwd meta='title="tests/queries.test.ts"'>
	../../examples/roles/tests/queries.test.ts#queries
</include>

`graceIsEditor` is `true`, `graceRoles` is `['administrator', 'editor']`
(names, sorted, inheritance included), and `adaIsAdministrator` is `false`.
`has(role)` and `current(schema)` read the current request, so call them
inside a hook, a rule or an operation handler; outside a request they fail
with `MISSING_EXECUTION_CONTEXT`. With `{ principal }`, `has` checks that
member anywhere on the server. An anonymous request holds no role.

### Choose a role reference

`StaffRole.role('editor')` creates a normalized name reference;
`StaffRole.role({ id })` creates an exact UUID reference and rejects a value
that is not a UUID. Both are immutable, schema-qualified, and perform no
database I/O. Renaming changes what a name reference resolves to; the
persisted UUID stays stable. Prefer the UUID form for long-lived references
after a role exists:

<include cwd meta='title="tests/queries.test.ts"'>
	../../examples/roles/tests/queries.test.ts#references
</include>

After the rename, `EditorById` resolves to the role now named
`'copy editor'`, and its members still hold it; `Editor` no longer matches a
stored role.

`resolveRoleReference(reference, options)` loads a stored role when server
code needs its row. It fails explicitly with `ROLE_REFERENCE_UNKNOWN` for an
unknown name or ID and with `ROLE_REFERENCE_AMBIGUOUS` for ambiguous name
storage; merely constructing a reference does not prove a matching role
exists.

### Use roles in policy

`hasRole(Editor)` returns a named Core
[policy predicate](/docs/1.0.0/core/security-foundations/request-identity#policy-predicates),
accepted wherever an Access rule returns a decision. In the example, it lets
the request principal create or update a post only when it is a direct or
inherited Editor member:

<include cwd meta='title="tests/policy.test.ts"'>
	../../examples/roles/tests/policy.test.ts#edit-post
</include>

Ada, an editor, renames the post. A member without the role and an anonymous
caller get `PERMISSION_DENIED`, and so does Ada when she tries to delete it:
that needs `hasRole(Administrator)`. Grace, an administrator and therefore an
editor, may do both.

Without `resolveCurrent`, the current member is the request principal when it
belongs to the member schema; a principal of another schema, or none, denies.
`resolveCurrent` remains for special cases: it may be asynchronous but must
return a Pointer of the member schema, or `undefined` when there is no current
member.

If a rule uses `hasRole()` without any application-local role-resolver
provider, execution raises `PLUGIN_CAPABILITY_MISSING` before business Hooks
or storage. Installing `rolesPlugin()` provides that resolver; a community
provider may supply the same neutral capability. Master authority does not
imply membership: as Master, `has()` answers `false` and `current()` an empty
list. Master bypasses the official Access rule as authority, not by
pretending `hasRole()` returned `true`.

ACL can grant rights to a role reference independently of the Access plugin.
The ACL and Roles plugins resolve that reference through a neutral role
contract that neither of them owns; role membership alone still grants
nothing. See [Object ACLs](./acl-permissions) for persisted grants.

### Deletion, events, and limits

| `deletion`       | Effect                                                                                                                       |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `fail` (default) | Rejects deletion while the role has members, child or parent edges, or references reported by another plugin                 |
| `preserve`       | Deletes the role and leaves external references inert; choose this only when the dangling-reference behavior is intentional  |
| `cascade`        | Requires Master, clears role edges, and invokes explicit cleanup contributions from reference owners in the same transaction |

`StaffRole` uses `fail`: deleting a role that still has a member fails with
`ROLE_DELETE_REFERENCED`, so the server empties it first:

<include cwd meta='title="tests/deletion.test.ts"'>
	../../examples/roles/tests/deletion.test.ts#delete-role
</include>

`StaffRole.deleteMany({ where: [{ name: 'administrator' }, { name: 'editor' }] })`
applies the policy to each unique target in order, within one transaction. If
a target is missing or a policy fails, all deletions, cleanup and queued
events roll back.

`Team` uses `cascade`. Its rule lets an administrator delete a team, but the
cascade still fails with `ROLE_DELETE_CASCADE_MASTER_REQUIRED` unless Master
runs it; the team's members then lose that role:

<include cwd meta='title="tests/deletion.test.ts"'>
	../../examples/roles/tests/deletion.test.ts#delete-team
</include>

Do not switch to `cascade` just to silence `ROLE_DELETE_REFERENCED`; review
every reference owner first.

Membership, hierarchy, and deletion events are optional post-commit
notifications. They are not delivered on rollback, and the Roles plugin does
not require Hooks. A plugin observes them with `onRoleEvent()` and
`provideRoleEventObserver()`, declares Roles as a peer and requests
`runtime:observe`:

<include cwd meta='title="src/role-audit.ts"'>
	../../examples/roles/src/role-audit.ts#role-audit
</include>

In the example, adding and removing Ada's editor role, then deleting the role,
logs three lines, one per committed change; the refused deletion logs nothing.
Hierarchy traversal rejects cycles and fails explicitly if it exceeds 64
levels or 10,000 visited roles.

## Troubleshooting

- **`App.RoleSchema` is missing:** declare the role schema from the
  configured factory that installs `rolesPlugin()`, and register it. The
  `name`, `members`, and `includedRoles` fields cannot be replaced by custom
  fields.
- **`hasRole()` always denies:** verify that the request principal (or
  `resolveCurrent`, if declared) is a Pointer of the member schema. A session by itself
  supplies identity, not a role grant; confirm the persisted membership and
  hierarchy in the same application, and remember that a request in progress
  keeps the membership it resolved first.
- **`PLUGIN_CAPABILITY_MISSING`:** the Access rule ran without an installed
  role-resolver provider. Install `rolesPlugin()` or an intentional compatible
  provider in that application.
- **`MISSING_EXECUTION_CONTEXT` from `has()` or `current()`:** the call ran
  outside a request. Call it from a hook, a rule or an operation handler, or
  pass `{ principal }` to `has()`.
- **Role deletion fails:** inspect direct members, child and parent roles,
  and external references under the schema's deletion policy. For `deleteMany()`,
  each target must satisfy that policy; a failure rolls back the whole batch.
- **`start()` fails on `ensure`:** Roles creates seed roles with its own
  `authority:elevate` privilege, without a `masterAuthority`; the error's
  `cause` names the write that failed (validation, a Hook or a constraint).
