## Overview

`@ultimabase/validation-plugin` adds application validation: a `validation`
option on fields, a schema check in `.with({ validation: … })`, and `check()` to
validate data without writing. Core always enforces requiredness, nullability,
canonical value shapes, defaults, immutable fields, and database integrity;
this plugin adds application rules on top. Importing the package alone does
not install them in an application.

Every TypeScript block on this page is copied from the
[validation example](https://github.com/MrEkinox/ultimadatabase/tree/main/examples/validation),
a small events backend whose tests check each result described here.

## Installation

Start from an UltimaBase application with a database provider, as in
[Manual Installation](/docs/1.0.0/manual-installation). Install this plugin
and, if you want one, a Standard Schema V1 library such as Zod:

```bash tab="npm" tab-group="package-manager"
npm install @ultimabase/validation-plugin zod
```

```bash tab="yarn"
yarn add @ultimabase/validation-plugin zod
```

```bash tab="pnpm"
pnpm add @ultimabase/validation-plugin zod
```

## Configuration

Install the plugin on the application factory. The example also installs
Access and REST, which open the REST writes it demonstrates; Validation needs
neither:

</include>

A field validator is a Standard Schema validator (Zod, Valibot, ArkType…) or
a function. A schema check, `validation` in `.with`, sees the
complete item:

<include cwd meta='title="src/schema.ts"'>
	../../examples/validation/src/schema.ts#event
</include>

The `room` validator calls `isRoomOpen()`, an asynchronous stand-in for a
booking service in `src/rooms.ts`; in the example, the `Basement` room is
closed. Register the schemas in the application that installs the plugin, and
start it from a separate entry point:

<include cwd meta='title="src/ultimabase.ts"'>
	../../examples/validation/src/ultimabase.ts#application
</include>

<include cwd meta='title="src/main.ts"'>
	../../examples/validation/src/main.ts#start
</include>

`validationPlugin()` takes no options. Types come from the schema itself,
without generated files. `define` takes no `validation` option: the schema
rule belongs in `.with({ validation: … })`, and field rules
stay on their fields (see [Where each declaration goes](/docs/1.0.0/core/data-modeling/schemas#where-each-declaration-goes)).

A Standard Schema validator must accept the field's value (its input may also
accept `null`, so a form schema can be reused) and return a value the field
can store. A mismatch is reported on the option, for example
`validation must accept string, got number`, and the option's hover names
`FieldValidator<string>`. A function validator receives the value and returns
`true`, a message, or `{ message, code }`; the `code` reaches the client. Both
may be `async`. Relation fields, virtual fields, and output descriptors do not
expose the option.

## Behavior and limitations

### What runs, and when

Validation is the last step before storage: defaults, generators, Hooks
`resolveInput` and Core's structural validation run first. A create validates
every present field. A Standard Schema validator's output is what gets
stored, so `z.string().trim()` trims the title:

<include cwd meta='title="tests/fields.test.ts"'>
	../../examples/validation/tests/fields.test.ts#transform
</include>

`event.title` is `'Autumn meetup'`, and so is the stored row. Formatting a
value belongs in the validator; deriving or cross-checking business data
belongs in Hooks `resolveInput`. Core checks the output structurally again
before storing it.

A field validator never runs for `null`. `summary` requires at least ten
characters, yet clearing it succeeds:

<include cwd meta='title="tests/fields.test.ts"'>
	../../examples/validation/tests/fields.test.ts#null-input
</include>

`cleared.summary` is `null`. Embedded object properties may have validators
too; an object's own validator does not run when one of its properties failed.

An update validates only the fields it writes, while the schema check always
sees the complete item as it would be stored:

<include cwd meta='title="tests/updates.test.ts"'>
	../../examples/validation/tests/updates.test.ts#changed-fields
</include>

The rename succeeds although `Hall B` has closed since the event was created;
`moved` rejects with `Hall B is closed` at `['update', 0, 'room', 'value']`.
Changing only `startsOn` still runs the schema check against the stored
`endsOn`:

<include cwd meta='title="tests/updates.test.ts"'>
	../../examples/validation/tests/updates.test.ts#update-check
</include>

`postponed` rejects with the `event.dates` issue at `['endsOn']`. An update
that increments or decrements a validated number checks the projected value
while keeping the database operation atomic:

<include cwd meta='title="tests/updates.test.ts"'>
	../../examples/validation/tests/updates.test.ts#book-seat
</include>

The first booking leaves `seatsLeft: 0`; the second rejects with `event.full`
at `['update', 0, 'seatsLeft', 'value']`, and the count stays `0`.

Validators may be `async`, but they run inside the transaction: a slow call
holds its locks. Uniqueness belongs to a unique index, not to a validator.
Master mutations take the same validation path; Master bypasses
authorization, not validation.

This projection applies to integer, bigint, float and decimal arithmetic. When
an operation has no prepared target from which to project the complete value, a
validated field updated by arithmetic is rejected rather than stored unchecked.

### Schema checks

A schema check is a function on the complete item, as in `Event`, returning
`true`, a message, an issue `{ path, message, code? }`, or a list of issues.
It may also be a Standard Schema object validator, whose output is not
stored:

<include cwd meta='title="src/schema.ts"'>
	../../examples/validation/src/schema.ts#ticket-tier
</include>

<include cwd meta='title="tests/schema-checks.test.ts"'>
	../../examples/validation/tests/schema-checks.test.ts#ticket-tier-check
</include>

`tier` keeps every field, and `inverted` rejects with
`The maximum cannot be below the minimum` at `['maxPerOrder']`, coded
`schema.validation`.

### One response for every issue

Core's structural issues (a missing required field, a wrong type) and every
validator issue are collected into one `VALIDATION_ERROR`. This create breaks
three field rules and the schema check:

<include cwd meta='title="tests/fields.test.ts"'>
	../../examples/validation/tests/fields.test.ts#all-issues
</include>

`attempt` rejects with a `FrameworkError` whose `publicDetails.issues` lists
the four issues, and nothing is written:

```json title="issues.json"
[
	{
		"code": "event.code",
		"message": "Use three capital letters",
		"path": ["input", "code"]
	},
	{
		"code": "field.validation",
		"message": "Basement is closed",
		"path": ["input", "room"]
	},
	{
		"code": "field.validation",
		"message": "Too small: expected string to have >=10 characters",
		"path": ["input", "summary"]
	},
	{
		"code": "event.dates",
		"message": "An event cannot end before it starts",
		"path": ["endsOn"]
	}
]
```

Each issue is `{ path, message, code }`: `field.validation` for a field
validator, `schema.validation` for a schema check, or the `code` a function
returned. A field path starts with the operation part (`['input', 'code']`
for a create, `['update', 0, 'room', 'value']` for an update); a schema
check's path is relative to the item. When Core finds a structural issue, the
field validators still run on the other fields, but the schema check waits
for a structurally valid item.

`updateMany` and the other bulk calls prefix each path with the item's index:

<include cwd meta='title="tests/updates.test.ts"'>
	../../examples/validation/tests/updates.test.ts#update-many
</include>

`updates` rejects with `event.code` at `[1, 'update', 0, 'code', 'value']`,
and the whole call fails: the first event keeps its code.

REST answers `422` with the list in `details.issues`; GraphQL reports it in
`extensions.details.issues`. With the example running, send an event without
its required title and with a bad code:

```bash title="create-event.sh"
curl --request POST \
  http://127.0.0.1:1337/api/classes/Event \
  --header 'Content-Type: application/json' \
  --data '{"code":"meetup","startsOn":"2026-11-02","endsOn":"2026-11-03","seatsLeft":40}'
```

Expect HTTP `422` with Core's issue and the validator's together:

```json title="create-event.response.json"
{
	"error": {
		"code": "VALIDATION_ERROR",
		"message": "The operation input is invalid.",
		"retryable": false,
		"requestId": "REQUEST_ID",
		"details": {
			"issues": [
				{
					"code": "field.required",
					"message": "Field is required",
					"path": ["input", "title"]
				},
				{
					"code": "event.code",
					"message": "Use three capital letters",
					"path": ["input", "code"]
				}
			]
		}
	}
}
```

### Validating without writing

`check()` runs the field validators and the schema check of a create, without
a write or a transaction, for forms, imports and tests:

<include cwd meta='title="tests/check.test.ts"'>
	../../examples/validation/tests/check.test.ts#check
</include>

`accepted` is `{ valid: true }`; `rejected` is `{ valid: false, issues }`
with the `event.code` and `event.dates` issues, at the paths `createOne`
reports. Nothing is written. Narrow the result on `valid`; hover a name to see
its type:

```ts twoslash title="Check result"
import { validationPlugin } from '@ultimabase/validation-plugin'

import { Event } from '../../examples/validation/src/schema.ts'
import { ultimabase } from '../../examples/validation/src/ultimabase.ts'

const data = {
	title: 'Autumn meetup',
	startsOn: '2026-11-02',
	endsOn: '2026-11-03',
	seatsLeft: 40,
}
// ---cut---
const result = await ultimabase.plugin(validationPlugin).check(Event, { data })
type Result = typeof result
//   ^?
if (!result.valid) {
	const [first] = result.issues
	//     ^?
}
```

It reports the plugin's issues only: Core's structural checks run when the
data is written.

Reads, included records, adapter results, and mutation results keep Core's
structural checks but do **not** rerun application validators.

## Troubleshooting

- **`validation` is an unknown option:** confirm `validationPlugin()` is
  installed on the configured factory used to declare the schema.
- **`validation must accept …` or `validation must return …`:** the validator's
  input or output type does not fit the field; use a validator of the field's
  type, or a function.
- **A value is rejected with `field.validation`:** inspect the issue path and
  message. The same rules apply to Master mutations.
- **A validator-contract error (`INTERNAL_ERROR`) occurs:** a validator threw,
  returned a malformed result, or a function returned something other than
  `true`, a message, or `{ message, code }`.
- **A value that fails an application rule still reads:** application
  validators do not run on reads. Enforce persistent invariants with a database
  constraint or a migration.
