## Overview

Soft deletion is an optional plugin capability. A schema opts into one explicit
mode; importing the package alone installs no behavior.

| Mode             | Native `deleteOne`                                | Additional application command |
| ---------------- | ------------------------------------------------- | ------------------------------ |
| `replace-delete` | Writes a tombstone instead of physically deleting | none                           |
| `explicit`       | Keeps native physical deletion                    | `softDelete`                   |

## Installation

Start with an application that has a database provider; see
[Manual Installation](/docs/1.0.0/manual-installation). Install the optional
plugin package:

```bash tab="npm" tab-group="package-manager"
npm install @ultimabase/soft-delete-plugin
```

```bash tab="yarn"
yarn add @ultimabase/soft-delete-plugin
```

```bash tab="pnpm"
pnpm add @ultimabase/soft-delete-plugin
```

## Configuration

Add `softDeletePlugin()` to the application plugin list, then state the mode on
each participating schema:

```ts title="src/schemas.ts"
import { Schema } from '@ultimabase/core'
import { softDeletePlugin } from '@ultimabase/soft-delete-plugin'

export const Post = Schema.define({
	className: 'Post',
	softDelete: 'explicit',
	fields: (field) => ({ title: field.string() }),
})

export const softDelete = softDeletePlugin({ defaultMode: 'disabled' })
```

Include `softDelete` in the application's `plugins` and `Post` in its `schemas`.
`defaultMode` accepts `disabled` (the default), `replace-delete`, or `explicit`.
Each schema may override it with `softDelete: false | 'replace-delete' |
'explicit'`; `false` disables the feature for that schema. Use
`defaultMode: 'disabled'` when every schema must opt in deliberately. Read
[Delete Data](/docs/1.0.0/core/writing-data/delete) and
[Master Authority](/docs/1.0.0/core/security-foundations/master-authority) before
exposing an application workflow around deletion.

## Behavior and limitations

### Delete, restore, and purge records

Once the application starts, the plugin exposes methods directly on the `Post`
schema class. Outside an active request, pass the exact `ultimabase` instance
as you would for native schema methods. `restore` and `purge` additionally
require a configured, audited `MasterAuthority`; never forward a
client-selected `useMasterKey` flag from transport input.

```ts title="src/soft-delete-post.ts"
import { Post } from './schemas.js'
import { ultimabase } from './ultimabase.js'

export const softDeletePost = (postId: string) =>
	Post.softDelete(
		{ id: postId, select: { isDeleted: true, title: true } },
		{ ultimabase },
	)

export const restorePost = (postId: string) =>
	Post.restore(
		{ id: postId, select: { isDeleted: true, title: true } },
		{ ultimabase, useMasterKey: true },
	)

export const purgePost = (postId: string) =>
	Post.purge(
		{ id: postId, select: { title: true } },
		{ ultimabase, useMasterKey: true },
	)
```

The original `ultimabase.schema(Post).softDelete(...)`, `.restore(...)`, and
`.purge(...)` handles remain available. For a persisted model, only explicit
soft delete has a direct `post.softDelete()` command. Another application may
use the same `Post` class without the plugin; passing that application rejects
the call rather than using the plugin installed elsewhere.

### Visibility semantics

Ordinary reads hide tombstones. That visibility rule also applies to normal
Master reads; Master authority is not a general switch for including deleted
records. `restore` and `purge` are private schema commands that
require explicit server-side Master authority. They are not model, REST,
GraphQL, or Access-policy branches.

### Limits

In explicit mode, native `deleteOne` remains the deliberate hard-delete path.
In replacement mode, physical purge stays on the private Master surface. Both
modes preserve the ordinary validation, Hook, transaction, integrity, and
protected-policy boundaries.

With the optional Access plugin, explicit soft delete has its own
`access.softDelete` rule rather than inheriting native update or delete rules.
Hooks likewise receive `beforeOperation.softDelete` and
`afterOperation.softDelete`. If the schema is exposed through REST or GraphQL,
the explicit mode adds `POST /api/v1/classes/{Schema}/{id}/soft-delete` or
`softDelete{Schema}` respectively. Replace-delete and disabled schemas add no
new transport endpoint. Restore and purge remain private even when a transport
is installed.

V1 has no deletion timestamp, retention job, include-deleted query, or nested
soft delete.

## Troubleshooting

If a deleted record remains visible, first confirm the schema's effective mode
and that the read goes through the compiled UltimaBase application. Verify that
find, count, exists, pointer, and relation reads omit a tombstone.
Restore it through trusted server code and verify the ordinary read returns it
again. If restore or purge is rejected, check that the selected application
installed the plugin and configured audited Master authority; neither command
is a public transport endpoint.
