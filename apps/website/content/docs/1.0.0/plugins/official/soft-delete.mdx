## Overview

`@ultimabase/soft-delete-plugin` lets you hide a record without removing its
stored data. It marks the record with `isDeleted: true` and stamps
`deletedAt`; this marked record is called a tombstone. Ordinary reads then treat
it as absent. A caller allowed by your rules can restore it, and trusted server
code can remove it for good with `purgeOne()`.

Each schema opts in with the `.softDelete()` shape method, before `.with(...)`:

| Declaration                        | `Post.deleteOne()` / `deleteMany()` | Added commands                                                                                    |
| ---------------------------------- | ----------------------------------- | ------------------------------------------------------------------------------------------------- |
| `.softDelete()`                    | Writes a tombstone                  | `softDeleteOne`, `softDeleteMany`, `restoreOne`, `restoreMany`, `purgeOne`, `purgeMany`           |
| `.softDelete({ mode: 'command' })` | Deletes the row permanently         | the same six commands; `softDeleteOne` and `softDeleteMany` are the only way to write a tombstone |
| no `.softDelete()`                 | Deletes the row permanently         | none                                                                                              |

This guide follows one `Post` schema in the default mode. Follow the
server-side flow, then use [REST](#rest) or [GraphQL](#graphql).
[Command mode](#keep-native-deletes-permanent) shows how to keep native deletes
permanent instead.

## Installation

Start from a working UltimaBase application with a database provider. Packages
are pre-release; follow [Manual Installation](/docs/1.0.0/manual-installation)
for the project layout and the linked repository example. These are the intended registry commands
once the package is published:

```bash tab="npm" tab-group="package-manager"
npm install @ultimabase/soft-delete-plugin
```

```bash tab="yarn"
yarn add @ultimabase/soft-delete-plugin
```

```bash tab="pnpm"
pnpm add @ultimabase/soft-delete-plugin
```

Importing the package installs no behavior. Add `softDeletePlugin()` to the
application that owns the schema; it takes no options. REST, GraphQL, Access,
and Hooks are optional integrations, installed separately.

The configured factory types `.softDelete()`, its commands, and the
`isDeleted` and `deletedAt` fields directly from the plugin declaration; no
generated declarations are needed. JavaScript executes the same compiled
application.

## Configuration

Install the plugin on the application factory, then opt a Post in:

```ts title="src/application.ts"
import { UltimaBase } from '@ultimabase/core'
import { postgresPlugin } from '@ultimabase/postgres-plugin'
import { softDeletePlugin } from '@ultimabase/soft-delete-plugin'

const databaseUrl = process.env.DATABASE_URL
if (!databaseUrl) throw new Error('DATABASE_URL is required')

export const Application = UltimaBase.use(
	postgresPlugin({ schemaPolicy: 'override', url: databaseUrl }),
	softDeletePlugin(),
)
```

```ts title="src/schemas.ts"
import { Application } from './application.js'

export const Post = Application.Schema.define({
	className: 'Post',
	fields: (f) => ({ title: f.string({ required: true }) }),
})
	.softDelete()
	.with({})
```

This example uses a **disposable development database**: PostgreSQL's
`override` policy can create or alter application tables. Master authority is
configured for the private purge step later; soft deletion and restoration do
not require it.

```ts title="src/ultimabase.ts"
import { MasterAuthority } from '@ultimabase/core'
import { Application } from './application.js'
import { Post } from './schemas.js'

const masterKey = process.env.ULTIMABASE_MASTER_KEY
if (!masterKey) throw new Error('ULTIMABASE_MASTER_KEY is required')

export const ultimabase = new Application({
	masterAuthority: new MasterAuthority({
		keys: [{ id: 'server', value: masterKey }],
		onUse: (event) => {
			// Replace this development sink with your production audit sink.
			console.info('Master use', event.reason)
		},
	}),
	schemas: [Post],
})

// One declaration per application gives name-keyed editor types.
declare module '@ultimabase/core' {
	interface Register {
		readonly app: typeof ultimabase
	}
}
```

Keep `ULTIMABASE_MASTER_KEY` server-side. A client must never choose
`useMasterKey` or receive that key. See [Master Authority](/docs/1.0.0/core/security-foundations/master-authority)
for audit configuration.

Start the exported application from a separate entry point:

```ts title="src/main.ts"
import { ultimabase } from './ultimabase.js'

await ultimabase.start()
```

## Behavior and limitations

### Create, soft-delete, and verify

In server code, call the schema class directly after `ultimabase.start()`.
Outside an active request, the class resolves the sole active application.

```ts title="src/soft-delete-flow.ts"
import { Post } from './schemas.js'

const post = await Post.createOne({
	data: { title: 'Draft announcement' },
})

const deleted = await Post.deleteOne({
	where: { id: post.id },
	select: { title: true, isDeleted: true, deletedAt: true },
})

const visible = await Post.findOne({
	where: { id: { eq: post.id } },
})
```

In the default mode `deleteOne()` writes the tombstone, so `deleted` is the
record **after** soft deletion: `isDeleted: true` and `deletedAt` set by the
server. `Post.softDeleteOne({ id })` does the same. Mutation results obey the
read rules: Core checks the row while it is still visible, before the deletion
hides it, and field rules still mask the returned fields. `visible` is `null`.
Repeating the deletion for that ID returns `null` (`deleteOne`) or fails with
`NOT_FOUND` (`softDeleteOne`), just as it does for an absent target.

Results are frozen plain data without methods (ADR-0310); a retained result
does not make a tombstone visible or allow you to soft-delete it twice.

### Restore

`restoreOne` brings a tombstone back and clears `deletedAt`:

```ts title="src/soft-delete-flow.ts (continued)"
const restored = await Post.restoreOne({
	id: post.id,
	select: { title: true, isDeleted: true, deletedAt: true },
})
```

`restored.isDeleted` is `false` and `restored.deletedAt` is `null`. Restore
preserves the ID, stored fields, pointers, and relation memberships; it only
sees tombstones, so an active or missing ID fails with `NOT_FOUND`.

Restoration is a request command: with [Access](./access) installed it needs an
`access.restoreOne` rule, and is closed when the rule is absent and no
`allowWithoutRule` key opens it. Without Access, any caller that reaches the command may run
it, like every other request operation. To keep restoration server-side, deny
it and run it with Master, which bypasses Access:

```ts title="src/schemas.ts (restore stays server-side)"
export const Post = Application.Schema.define({
	className: 'Post',
	fields: (f) => ({ title: f.string({ required: true }) }),
})
	.softDelete()
	.with({ access: { restoreOne: false, restoreMany: false } })
```

### Purge from server code

`purgeOne` permanently removes one tombstone. It requires configured, audited
Master authority; never forward a client-selected `useMasterKey` flag.

```ts title="src/soft-delete-flow.ts (continued)"
await Post.deleteOne({ where: { id: post.id } })

const purged = await Post.purgeOne(
	{ id: post.id, select: { title: true, isDeleted: true } },
	{ useMasterKey: true },
)
```

`purged` is the record **before** physical deletion, with `isDeleted: true`.
The row is now gone; `restoreOne()` cannot recover it. Purge follows the
database's ordinary integrity rules. Missing, active, and already purged
targets all produce the same `NOT_FOUND`.

### Many rows

`softDeleteMany`, `restoreMany`, and `purgeMany` target every row matching a
`where`, in one transaction. Each matching row goes through the same Access
rule, Hooks, readable-result check, and visibility as the one-row command; one
refused row rolls the whole command back.

```ts title="src/soft-delete-many.ts"
import { Post } from './schemas.js'

const hidden = await Post.softDeleteMany({
	where: { title: { startsWith: 'Draft' } },
	select: { deletedAt: true },
})

const back = await Post.restoreMany({
	where: { title: { startsWith: 'Draft' } },
})

const removed = await Post.purgeMany(
	{ where: { title: { startsWith: 'Draft' } } },
	{ useMasterKey: true },
)
```

Each resolves to one result per written row, in identifier order. A many-row
command sees only the rows it may target: `softDeleteMany` sees visible rows,
`restoreMany` and `purgeMany` see tombstones. Access rules use the command's
own name (`access.softDeleteMany`, `access.restoreMany`). Many-row commands are
not exposed through REST or GraphQL yet.

### Enable REST and GraphQL

Soft Delete discovers the installed transports automatically. The one-row
request commands `softDeleteOne` and `restoreOne` are exposed when the schema
is exposed by that transport and its plugin-mutation surface is enabled:

- REST: `rest: { mutations: true }` controls the additional schema-mutation
  routes. `rest: false` or `mutations: false` hides them.
- GraphQL: `graphql: { operations: { mutations: true } }` controls additional
  schema-mutation fields. `graphql: false` or `mutations: false` hides them.

Both mutation switches are on by default. They inherit the corresponding
transport's configured defaults; enabling exposure does not grant permission.
`purgeOne` and the many-row commands are never exposed.

For a local walkthrough of both APIs, install the HTTP, REST, GraphQL, Yoga,
and Hono packages described in [REST setup](./rest) and
[GraphQL with Yoga](./graphql#serve-graphql-over-http-with-yoga). Add the following
plugins to the existing application with `...apiPlugins` before starting it;
import `apiPlugins` from `./api-plugins.js` in `ultimabase.ts`. Use
[Hono's server entry point](./hono-server#start-and-stop-the-managed-listener)
so the API keeps serving between the requests below.

```ts title="src/api-plugins.ts"
import { graphqlPlugin } from '@ultimabase/graphql-plugin'
import { graphqlYogaPlugin } from '@ultimabase/graphql-yoga-plugin'
import { httpPlugin } from '@ultimabase/http-plugin'
import { restPlugin } from '@ultimabase/rest-plugin'
import { honoServerPlugin } from '@ultimabase/server-hono-plugin'

export const apiPlugins = [
	httpPlugin({ appId: 'blog' }),
	restPlugin({ acknowledgeUnverifiedProtection: true }),
	graphqlPlugin({ acknowledgeUnverifiedProtection: true }),
	graphqlYogaPlugin(),
	honoServerPlugin({ host: '127.0.0.1', port: 1337 }),
] as const
```

This local example exposes the schema's default read and write operations
without an authorization policy. Keep it on loopback with disposable data.
Before public exposure, configure [Access](./access) or [Object ACLs](./acl-permissions)
and review [public transport protection](/docs/1.0.0/operations/before-exposing-your-application).
The example explicitly acknowledges unverified protection for this local
walkthrough. Removing that acknowledgement produces
`UNVERIFIED_PUBLIC_TRANSPORT_PROTECTION`; acknowledging it does not add policy.

If your policy requires an authenticated caller, configure
[Password Authentication](./password-authentication) and send that caller's
session with `Authorization: Bearer SESSION_TOKEN` on the requests below.
Authentication alone grants no read or soft-delete permission.

### REST

These requests use the default `/api` prefix and the `blog` application ID
configured above. Create a fresh record for this walkthrough:

```bash title="create-post.sh"
curl --request POST \
  'http://127.0.0.1:1337/api/v1/classes/Post?select=id,title,isDeleted' \
  --header 'Content-Type: application/json' \
  --header 'X-UltimaBase-Application-Id: blog' \
  --data '{"title":"Draft announcement"}'
```

Expect HTTP `201` with `result.id`, the title, and `isDeleted: false`. Replace
`POST_ID` below with that returned UUID v7; it is a placeholder, not a valid ID.

```bash title="soft-delete-post.sh"
curl --request POST \
  http://127.0.0.1:1337/api/v1/classes/Post/POST_ID/soft-delete-one \
  --header 'Content-Type: application/json' \
  --header 'X-UltimaBase-Application-Id: blog' \
  --data '{"select":{"title":true,"isDeleted":true}}'
```

The ID belongs in the URL. The JSON body controls the result selection; the
command has no operation payload, so omit `input`. Send `{}` when you need the
default selection. Do not send `isDeleted` or `deletedAt` as create or update
data. In the default mode, a bodyless `DELETE` on the record writes the same
tombstone.

Expect HTTP `200` with the **post-delete** record:

```json title="soft-delete.response.json"
{
	"result": {
		"id": "POST_ID",
		"title": "Draft announcement",
		"isDeleted": true
	}
}
```

Now read the same ID through the ordinary get route:

```bash title="get-deleted-post.sh"
curl --include \
  http://127.0.0.1:1337/api/v1/classes/Post/POST_ID \
  --header 'X-UltimaBase-Application-Id: blog'
```

Expect HTTP `404` with `NOT_FOUND`. A repeated soft-delete request also returns
`404`. `POST …/POST_ID/restore-one` restores the record when your rules allow
it; there is no purge URL, including for clients with elevated credentials.

A custom REST `basePath` changes the `/api` prefix. Disabling `rest.mutations`
hides the command routes independently of native `rest.delete`.

### GraphQL

Use `POST http://127.0.0.1:1337/graphql` with these headers:

```json title="graphql-headers.json"
{
	"Content-Type": "application/json",
	"X-UltimaBase-Application-Id": "blog"
}
```

In an HTTP client, place each document in `query` and its variables in
`variables`. In a GraphQL explorer, paste them into the corresponding panes.
Create a separate Post so this example does not reuse the REST tombstone:

```graphql title="create-post.graphql"
mutation CreatePost {
	createPost(input: { title: "Draft announcement" }) {
		id
		title
		isDeleted
	}
}
```

Read the new ID from `data.createPost.id`; `isDeleted` is initially `false`.
Use that ID in the following variables:

```json title="post.variables.json"
{ "id": "POST_ID" }
```

```graphql title="soft-delete-post.graphql"
mutation SoftDeletePost($id: ID!) {
	softDeleteOnePost(input: { id: $id }) {
		id
		title
		isDeleted
	}
}
```

The generated field accepts `input: SoftDeleteOnePostInput!`, containing only
`id: ID!`. There is no `data` or `isDeleted` input. Select the fields you need
from the **post-delete** record:

```json title="soft-delete.graphql.response.json"
{
	"data": {
		"softDeleteOnePost": {
			"id": "POST_ID",
			"title": "Draft announcement",
			"isDeleted": true
		}
	}
}
```

Verify visibility with the same variables:

```graphql title="find-deleted-post.graphql"
query FindDeletedPost($id: ID!) {
	findOnePost(where: { id: { eq: $id } }) {
		id
		title
	}
}
```

Expect `{ "data": { "findOnePost": null } }`. Repeating the soft-delete mutation
instead produces a GraphQL error with `extensions.code: "NOT_FOUND"`; inspect
`errors`, even if the HTTP status is `200`. `restoreOnePost` restores the
record when your rules allow it; there is no purge field.

GraphQL derives `softDeleteOnePost` from the command and the generated model
name. Disabling `graphql.operations.mutations` hides these fields independently
of native `graphql.operations.delete`.

### Keep native deletes permanent

Declare `.softDelete({ mode: 'command' })` instead and restart with the new
compiled application:

```ts title="src/schemas.ts (command mode)"
export const Post = Application.Schema.define({
	className: 'Post',
	fields: (f) => ({ title: f.string({ required: true }) }),
})
	.softDelete({ mode: 'command' })
	.with({})
```

`Post.deleteOne()`, REST `DELETE`, and GraphQL `deletePost` now delete the
record permanently, and restore cannot recover it. `softDeleteOne` and
`softDeleteMany` are the only way to write a tombstone; the restore and purge
commands are the same as in the default mode.

### Unique values and restoration

A tombstone keeps its data and still occupies a unique value, unless the
unique index is partial. To let a deleted record release its slug, declare a
partial unique index in the final `.with` (the plugin never adds one
automatically):

```ts title="src/article.ts"
export const Article = Application.Schema.define({
	className: 'Article',
	fields: (f) => ({ slug: f.string({ required: true }) }),
})
	.softDelete()
	.with({
		indexes: [{ fields: ['slug'], unique: true, where: { isDeleted: false } }],
	})
```

If another row took the slug meanwhile, restoring the tombstone fails with
`UNIQUE_VIOLATION` and a message naming the command, row and field:
`Cannot run restoreOne on Article <id>: slug is now used by another row.` The
conflicting value is logged in the error's internal details, not returned to
the caller.

### Visibility, permissions, and limits

The plugin owns `isDeleted` and `deletedAt`. Do not declare them yourself or
write them through create, update, nested commands, REST, or GraphQL. You may
select them in results and filter or sort them like ordinary fields, subject to
installed field policy. A filter such as `where: { isDeleted: { eq: true } }`
still returns no tombstones: the plugin always combines ordinary reads with its
private `isDeleted: false` constraint, unless the caller holds `readDeleted`.

Tombstones are hidden from ordinary reads, counts, existence checks, pointer
and relation traversal, eager loading, and ordinary update or delete targets.
Direct database queries do not apply these application rules.

### Reading deleted rows: `readDeleted`

`.softDelete()` declares the schema permission `readDeleted` (ADR-0317). A
caller who holds it sees tombstones in ordinary reads, REST and GraphQL
included, and can filter and sort them (`where: { isDeleted: { eq: true } }`,
`orderBy: { deletedAt: 'desc' }`); without it the private filter applies.
Updates, deletes and request commands never reach tombstones through it.
With [Access](./access), grant it with a rule of the same name or with its own
`allowWithoutRule` key (`all`, `read` and `write` never include it):

```ts title="src/schemas.ts (an audit trash)"
export const Post = Application.Schema.define({
	className: 'Post',
	fields: (f) => ({ title: f.string({ required: true }) }),
})
	.softDelete()
	.with({ access: { read: true, readDeleted: hasRole(Auditor) } })
```

A caller without the permission never sees tombstones, whatever its `where`.
Master holds every permission, but its reads keep the trash filter by default,
so a server job using `useMasterKey` never processes deleted rows by accident
and does not need `where: { isDeleted: false }`. A Master read returns
tombstones only when its own `where` constrains `isDeleted`: any condition on
the schema's `isDeleted`, at any depth of `AND`, `OR` and `NOT` (a condition
inside a relation predicate does not count; an inclusion uses its own `where`):

```ts title="src/server-jobs.ts"
await Post.findMany(undefined, { useMasterKey: true }) // live rows only
await Post.findMany({ where: { isDeleted: true } }, { useMasterKey: true }) // the trash
await Post.count(
	{ where: { isDeleted: { in: [true, false] } } },
	{ useMasterKey: true },
) // every row
```

The rule applies to `findMany`, `findOne`, `findOneOrThrow`, `count`, `exists`,
inclusions, REST and GraphQL. Restore and purge keep reaching tombstones for
Master and for allowed callers.

With [Access](./access), each command has its own rule (`softDeleteOne`,
`softDeleteMany`, `restoreOne`, `restoreMany`) and `readDeleted` its own
permission rule; granting native update or delete does not grant them, and
purge is Master-only so it has none. With
[Hooks](./hooks), each command has its own `beforeOperation` and
`afterOperation` branch. REST, GraphQL, and TypeScript enter the same Runtime
pipeline and preserve transaction and protected-policy boundaries.

A soft deletion is an update: it triggers no `onDelete` referential action. A
pointer to a tombstone keeps its value, and including it returns `null` until a
purge physically deletes the row.

There is no deleter identity, reason, retention job, automatic purge, or
nested soft delete yet.

## Troubleshooting

- **The soft-delete route or field is missing:** check plugin installation,
  the `.softDelete()` call on that schema, schema exposure, and the transport's
  `mutations` switch. Many-row commands and purge are never exposed.
- **Soft deletion returns `NOT_FOUND`:** the ID may be absent, already deleted,
  or hidden by a policy. Repeating soft deletion does not succeed again.
- **A deleted record remains visible:** check the selected application, the
  schema's mode, the operation result, whether the caller holds
  `readDeleted`, and, for Master, whether its `where` names `isDeleted`.
  Direct database reads still see tombstones.
- **Native deletion cannot be restored:** in command mode, or on a schema
  without `.softDelete()`, native delete is permanent.
- **Restoration is refused:** check `access.restoreOne` and that the ID is a
  tombstone; a `UNIQUE_VIOLATION` means another row took a unique value.
- **Purge is rejected:** use trusted server code with audited Master authority
  and an existing tombstone.
- **TypeScript cannot find a field or command:** declare the schema from the
  configured factory that installs `softDeletePlugin()` and call
  `.softDelete()` before `.with(...)`. At runtime, start the sole owning
  application.
- **A request fails before reaching the operation:** check the application ID,
  credentials, and transport setup in [HTTP troubleshooting](./http#troubleshooting).
