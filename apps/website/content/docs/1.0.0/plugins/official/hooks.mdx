## Overview

`@ultimabase/hooks-plugin` adds the official lifecycle to an application.
Use a field Hook to normalize one supplied value, a schema Hook to change the
data of a write or inspect and reject it, and `afterCommit` or a typed event to
deliver an external effect after commit. Importing the package alone installs none of this behavior:
the application must include `hooksPlugin()`.

Hooks are optional business behavior, not an authorization layer. [Access](./access)
controls who may act; Core still owns structural validation and transactions.

Every TypeScript block on this page is copied from the
[hooks example](https://github.com/MrEkinox/ultimadatabase/tree/main/examples/hooks),
a small blog whose tests check each result described here.

## Installation

Start with an UltimaBase application and database provider, then install the
optional lifecycle plugin:

```bash tab="npm" tab-group="package-manager"
npm install @ultimabase/hooks-plugin
```

```bash tab="yarn"
yarn add @ultimabase/hooks-plugin
```

```bash tab="pnpm"
pnpm add @ultimabase/hooks-plugin
```

options: `global`, Hooks run for every schema (see [Global Hooks](#global-hooks)),
and `events`, the consumers of [typed events](#typed-events). The example
also installs Soft Delete, whose commands Hooks observe, and REST, which shows
how a client sees a Hook's error:

on the field. The example's `Post` trims titles, derives a slug from the data,

## Behavior and limitations

### Choose the right phase

| Hook                  | Runs                                                       | What it receives or changes                                                                                        |
| --------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Field `resolveInput`  | Before schema Hooks, for a present non-null value.         | The field's `value`; a returned value replaces it. `null` is stored as is without calling the Hook.                |
| Schema `resolveInput` | Once the target of an update is locked, before validation. | The `data` of a create, the `changes` of an update, or both for an upsert; a returned object replaces them.        |
| `beforeOperation`     | Before the write is stored.                                | The candidate `item`, the locked `originalItem`, and the `changes` of an update. Its return value is ignored.      |
| `afterOperation`      | After the write is stored, before commit.                  | The stored `item`, the `originalItem`, and the `changes` of an update. Its return value is ignored.                |
| `afterCommit`         | After the transaction commits, outside it.                 | The same input as `afterOperation`. The response does not wait for it; a failure is logged and rolls nothing back. |

Every phase accepts `create`, `update`, `upsert` and `delete` branches (no
`delete` for `resolveInput`) and an `all` branch that runs before the
operation's own branch. `all` also runs for plugin commands, such as Soft
Delete's `softDeleteOne`, with `kind` naming the operation or the command, so
`if (input.kind === 'softDeleteOne')` narrows the input. Each branch takes one callback or a non-empty array.
Hooks never run for reads, and no option skips them: Master bypasses
authorization, never Hooks.

### Field and input Hooks

The example's tests run each step below with
[`testApplication`](/docs/1.0.0/guides/test-an-application) and check its
result. Creating a post runs the field Hooks, then the schema's
`resolveInput.create`:

<include cwd meta='title="tests/data.test.ts"'>
	../../examples/hooks/tests/data.test.ts#create
</include>

The stored title is `Hello Hooks` and the slug `hello-hooks`. `summary` stays
`null`: a field Hook never runs for `null`, so `value.trim()` is never called
on it. A `resolveInput` Hook returns the replacement data, or `undefined` to
keep it, as `resolveInput.update` does when the title does not change.

### Plain data, atomic operations and link changes

Hooks receive plain frozen data, never Core's internal operation tree. `item`
and `originalItem` are the stored objects without methods; act on other rows
through the normal API, which joins the transaction and keeps the authority.

`changes` lists only what an update changes. Post's `afterCommit.update`
sends it as a webhook body; this update increments a counter, sets the author
and replaces the tags:

<include cwd meta='title="tests/data.test.ts"'>
	../../examples/hooks/tests/data.test.ts#update-changes
</include>

The webhook receives `views: { increment: 1 }`, `author` as the new Pointer,
`tags: { connect: [blue], disconnect: [red] }`, and Core's generated
`updatedAt`, nothing else. An atomic operation stays an operation in readable
form: it is never rewritten into a value. A relation's link changes appear as
`{ connect: [...ids], disconnect: [...ids] }`, a `set` shown as its
difference with the current members, including relations stored in a join
table. Link changes are read-only in `resolveInput`; change links in the
operation data instead.

An upsert's `resolveInput` and `beforeOperation` know its `mode`: `create` when
no object matched, `update` otherwise. `resolveInput.upsert` returns
`{ data, changes }`, or `undefined` to keep both; Post derives the slug only
when the upsert creates:

<include cwd meta='title="tests/data.test.ts"'>
	../../examples/hooks/tests/data.test.ts#upsert
</include>

The first call creates the post with the slug `imported-post`; the second
finds it by that slug and increments `views`.

`createMany`, `updateMany`, `upsertMany` and `deleteMany` run the item Hooks
once per item, in input order, inside one automatic transaction; their
`afterCommit` Hooks run once per item after the whole transaction commits.

### Transactions, replays and after-commit work

`resolveInput`, `beforeOperation` and `afterOperation` run inside the
transaction. Post's `afterOperation.update` writes a `PostTitleChange` row,
which joins the post's transaction:

<include cwd meta='title="tests/operations.test.ts"'>
	../../examples/hooks/tests/operations.test.ts#title-change
</include>

`changes` holds one row, from `Draft title` to `Final title`. Throw a
[`PublicError`](/docs/1.0.0/core/runtime/api-errors#publicerror) to tell the
client why a write is refused. Renaming a published post fails in
`beforeOperation.update`:

<include cwd meta='title="tests/operations.test.ts"'>
	../../examples/hooks/tests/operations.test.ts#public-error
</include>

`rename` rejects with the code `post.published-title` and nothing is stored.
The same request over REST answers `400` with that code and message, and
GraphQL reports it in `extensions.code`; any other error stays masked.

Throwing from any Hook, or anywhere in the transaction, rolls back every write
of the transaction, the rows written by Hooks included, and discards its
events. Here the publication and its title change are cancelled together:

<include cwd meta='title="tests/operations.test.ts"'>
	../../examples/hooks/tests/operations.test.ts#rollback
</include>

The post keeps its draft title, no `PostTitleChange` row exists, and the
`postPublished` event emitted by the Hook is never delivered.

These Hooks may also run several times for one call: when the database
reports a transient conflict, Core replays the whole automatic transaction,
Hooks included (at most three attempts). Keep them free of effects outside the
transaction (HTTP calls, e-mail, queue messages, files). External effects
belong in `afterCommit` or an event.

`afterCommit` Hooks run once the transaction has committed, outside it,
sequentially: the application's global Hooks, then the schema's `all`, then
the operation's branch. The client response does not wait for them:

<include cwd meta='title="tests/after-commit.test.ts"'>
	../../examples/hooks/tests/after-commit.test.ts#after-commit
</include>

`beforeDelivery` is empty: `createOne` resolved before `sendMessage` finished.
After `await t.afterCommit()`, the outbox holds the global audit message, then
the editors' message. A failure is logged and never rejects the call nor stops
the next Hooks. Delivery is best effort within the process: work still pending
when the process stops is lost. In tests, `await t.afterCommit()` of
`testApplication` from `@ultimabase/testing` waits for it.

### Typed events

Define an event once and bind emitters and consumers to that value:

<include cwd meta='title="src/events.ts"'>
	../../examples/hooks/src/events.ts#event
</include>

Emit from any Hook inside the transaction with `context.emit(event, payload)`,
and install the consumer in `hooksPlugin({ events })`: the factory above
installs `announcePost`, and Post's `afterOperation.update` emits
`postPublished` when a post is published:

<include cwd meta='title="tests/after-commit.test.ts"'>
	../../examples/hooks/tests/after-commit.test.ts#event
</include>

Once after-commit work has run, the subscribers received `New post: Launch`.
Events are delivered after commit like `afterCommit`: best effort, at most
once, in this process, without delaying the response. A consumer failure is
logged; an event without consumers does nothing; events of a rolled-back
transaction are discarded. A consumer may use the normal API, which starts its
own request. Durable delivery (an outbox written in the transaction, retries)
is left to a future queue plugin.

### Global Hooks

`hooksPlugin({ global })` declares the same phases and `all` for every schema
of the application. Its callbacks receive a generic `item` and the `schema`
name, and run before each schema's own Hooks. The factory above audits every
committed write with `afterCommit.all`, which receives `schema` and `kind`.
Global `all` also sees plugin commands; since they depend on each schema, its
`kind` is typed as `string`.

### Plugin-defined mutations

Installed schema mutations add their own branches. For example, with the
[Soft Delete plugin](./soft-delete), `softDeleteOne`, `restoreOne`, `purgeOne`
and their `Many` forms are separate logical branches of `beforeOperation`,
`afterOperation` and `afterCommit`. A `softDeleteOne` implemented by a physical
update runs `softDeleteOne` Hooks, not native `update` Hooks. `all` runs for
these commands too, before their own branch, with `kind` set to the command
name (`resolveInput` has no command form). The example's `Comment` uses
Soft Delete in command mode and narrows `all` on `kind`:

<include cwd meta='title="src/schema.ts"'>
	../../examples/hooks/src/schema.ts#comment
</include>

Hiding a comment runs the global audit, then the comment's `all` branch:

<include cwd meta='title="tests/after-commit.test.ts"'>
	../../examples/hooks/tests/after-commit.test.ts#command
</include>

The outbox receives `Comment.softDeleteOne` from the global Hook, then
`Hidden: Spam` for the moderators: `kind` names the command, not the physical
update.

### Contributed Hooks

Compatible plugins can contribute `globalHooks()`, `schemaHooks()`, or
`fieldHooks()` through `provideHookContributions()`. Their handlers retain
the contributing plugin's identity and privileges, and can read Core's
internal operation tree with `readHookInternals(input)`. Core derives the
`runtime:intercept` privilege a provider needs from the contribution;
`permissions` gives its reason. A provider declares the Hooks plugin as a
peer, with a range that accepts the installed version:

<include cwd meta='title="src/post-rules-plugin.ts"'>
	../../examples/hooks/src/post-rules-plugin.ts#post-rules-plugin
</include>

The handlers of `schemaHooks(Post, …)` are typed from `Post` itself, so the
contribution factory needs no return type, even though the application that
installs the plugin declares `Register`. Since the plugin targets `Post`, the
application installs it with `App.use(postRulesPlugin)` once `Post` exists, as
shown in [Configuration](#configuration). Deleting a published post then fails
with `post.published-delete`.

### Ordering, context, and recursion

Handlers run sequentially: contributing plugins in plugin order, then global
Hooks, then the schema's own Hooks (`afterOperation` unwinds in reverse). Field
input resolution precedes schema input resolution; `beforeOperation` precedes
persistence; `afterOperation` follows it and precedes commit.

Every callback receives a `HookContext` with a request ID, transaction ID,
cancellation signal, source, authority, hook identity, and the request
`principal` resolved by Core (`undefined` when anonymous; unchanged under
`useMasterKey`). It exposes no adapter, raw credential or transaction control,
and its capabilities close when the callback settles.

A Hook may write through the normal API, which runs Hooks again: a child
completing its parent re-enters the same Hook legitimately. In the example,
each reply increments its parent's `replies`, and that update increments the
grandparent's, up to the root:

<include cwd meta='title="tests/recursion.test.ts"'>
	../../examples/hooks/tests/recursion.test.ts#thread
</include>

`Root` counts 2 replies and `Answer` 1. Nesting is bounded to 16 Hook-issued
operations: a reply 17 levels deep fails with `RUNTIME_CALLBACK_RECURSION`,
rolls back, and the message shows the chain of schemas and operations
(`Comment.update-one -> Comment.update-one -> …`).

## Troubleshooting

- **`hooks` is rejected or absent in autocomplete:** install `hooksPlugin()` on
  the configured factory used to declare the schema.
- **A callback never runs:** check the schema or field, the operation branch,
  and whether the write supplies that field. A field Hook never runs for
  `null`. A plugin-defined mutation uses its own name rather than the physical
  update/delete name.
- **An `afterCommit` Hook or event did not run in a test:** await
  `t.afterCommit()` of `testApplication` from `@ultimabase/testing` before asserting; the
  response does not wait for after-commit work.
- **A write rolls back:** inspect the first thrown Hook or nested operation.
  `RUNTIME_CALLBACK_RECURSION` names the chain of more than 16 nested
  Hook-issued operations.
- **The application refuses a contributing plugin with
  `PLUGIN_PROTOCOL_INCOMPATIBLE`:** its `peers` range must accept the
  installed Hooks plugin version.
