## Overview

`@ultimabase/graphql-plugin` owns the executable schema. Yoga (HTTP), HTTP,
Hono and the explorer are independent, optional plugins; none installs its
siblings. `apiServer()` from `@ultimabase/api-server` returns them as one list
(ADR-0325).

## Installation

These packages are pre-release. Use the locally built repository example linked
from [Manual Installation](/docs/1.0.0/manual-installation) to evaluate the
current code; the registry commands below describe installation after publication.

For direct GraphQL execution, install the schema plugin:

```bash tab="npm" tab-group="package-manager"
npm install @ultimabase/graphql-plugin
```

```bash tab="yarn"
yarn add @ultimabase/graphql-plugin
```

```bash tab="pnpm"
pnpm add @ultimabase/graphql-plugin
```

Generated fields still need a database provider such as
[PostgreSQL](./postgresql), even when execution has no HTTP server. See
[Manual Installation](/docs/1.0.0/manual-installation) for the initial project.

To serve GraphQL over HTTP with the official [Hono Server](./hono-server)
provider, install the preset, which brings the GraphQL, Yoga, explorer, HTTP,
REST and Hono plugins:

```bash tab="npm" tab-group="package-manager"
npm install @ultimabase/api-server
```

```bash tab="yarn"
yarn add @ultimabase/api-server
```

```bash tab="pnpm"
pnpm add @ultimabase/api-server
```

## Configuration

`apiServer({ graphql })` installs `graphqlPlugin()`, `graphqlYogaPlugin()`,
`httpPlugin()` and `honoServerPlugin()`; `graphql: { explorer: 'graphiql' }`
adds the development explorer. This local example exposes only `getPost`,
`findOnePost` and `findManyPost`. Use a disposable development database:
PostgreSQL's `override` policy may create or alter tables.

```ts title="src/ultimabase.ts"
import { UltimaBase } from '@ultimabase/core'
import { apiServer } from '@ultimabase/api-server'
import { postgresPlugin } from '@ultimabase/postgres-plugin'

// postgresPlugin() reads DATABASE_URL at start; Hono listens on
// 127.0.0.1:1337 outside production.
const Application = UltimaBase.use(
	postgresPlugin(),
	...apiServer({ graphql: { default: false, explorer: 'graphiql' } }),
)
const Post = Application.Schema.define({
	className: 'Post',
	fields: (f) => ({ title: f.string({ required: true }) }),
}).with({ graphql: { findOne: true, findMany: true } })

export const ultimabase = new Application({
	schemas: [Post],
})

declare module '@ultimabase/core' {
	interface Register {
		readonly app: typeof ultimabase
	}
}
```

The same application without the preset installs each plugin:

```ts
UltimaBase.use(
	postgresPlugin(),
	httpPlugin(),
	graphqlPlugin({ default: false }),
	graphqlYogaPlugin(),
	graphqlExplorerPlugin(),
	honoServerPlugin(),
)
```

Start this configuration from the [managed listener entry point](./hono-server#start-and-stop-the-managed-listener).
It serves until Ctrl+C and then awaits disposal. Keep startup out of
`src/ultimabase.ts` so the direct scripts below can load it safely.

`default: false` disables every generated root and plugin command unless a
schema's rule enables it. Exposing only reads lets this application start
without a policy plugin; exposing a write without one refuses to start unless
`graphqlPlugin({ publicWrites: true })` opts in (ADR-0294). The loopback
listener, read-only exposure, and absence of credentials make this a learning
example, not a production configuration. Before binding publicly, configure
identity and [Access](./access) or [ACL](./acl-permissions) rules, then review
the complete exposed schema. Authentication alone grants no permission. Do
not use `override` against shared or production data without a reviewed
schema plan.

Install GraphQL before `Application.Schema.define(...)` so the
`.with({ graphql })` rule is typed from source, with no generation step.

For direct execution only, install `graphqlPlugin()` without HTTP, Yoga and
Hono. Its options are `default`, `hide` (public operations not to expose),
`limits` (document and execution budgets), `pagination` (the page window),
`publicWrites`, `schemas` (completed custom GraphQL schemas) and `sdl` (a
schema file written at startup). See [PostgreSQL](./postgresql) for physical
schema preparation and [HTTP](./http) for application identity validation.

## Behavior and limitations

### Choose the generated surface

GraphQL generates root fields for each exposed application-owned schema. The
tables below use `Post` as the GraphQL type name. GraphQL does not pluralize
or case-fold the schema's `className`; a custom `typeName` changes these field
suffixes.

An enum field declared with a string array gets one enum type named from its
schema and field path. Every field using the same shared enum from
`defineEnum('TaskPriority', [...])` uses one `TaskPriority` enum type (ADR-0310);
a name that collides with another generated type fails schema compilation.

The `src/ultimabase.ts` example above deliberately exposes **only** `getPost`,
`findOnePost` and `findManyPost`. The "default" column describes what a schema
would expose without that example's `default: false` setting. A disabled field
is absent from the endpoint's schema, even for Master; a document that selects
it fails validation with a hint naming the rule to set, for example
`Cannot query field "countPost" on type "Query". hint: enable graphql: { count: true } on Post`.

The rule keys are the schema method names, the same as REST and Access rules
(ADR-0325): `findOne` (`get<Type>` and `findOne<Type>`), `findMany`, `count`,
`exists`, `createOne`, `updateOne`, `deleteOne`, `upsertOne`, `createMany`,
`updateMany`, `deleteMany`, `upsertMany`, a plugin command such as
`softDeleteOne`, and `typeName`, which renames the generated type.
`graphql: false` removes one schema's generated surface. `graphql: true`
enables **every** generated root and command, including count, upsert, and
bulk. An object enables or disables each method it names; omitted methods
inherit `graphqlPlugin({ default })`, then the built-in defaults. A plugin
command is exposed only when a rule names it, or when the rule or the default
is `true`. Exposure never grants authorization.

### Generated queries

| Field          | Rule key   | Arguments                                                                  | What it returns                          | Default |
| -------------- | ---------- | -------------------------------------------------------------------------- | ---------------------------------------- | ------- |
| `health`       | (always)   | none                                                                       | `HealthStatus!`: `OK` or `DEGRADED`      | On      |
| `getPost`      | `findOne`  | `id: ID!`                                                                  | One `Post`; a missing target is an error | On      |
| `findOnePost`  | `findOne`  | `where: PostWhere`, `orderBy: [PostOrder!]`                                | First match or `null`                    | On      |
| `findManyPost` | `findMany` | `where: PostWhere`, `orderBy: [PostOrder!]`, `first: Int`, `after: String` | A `PostConnection!` page                 | On      |
| `countPost`    | `count`    | `where: PostWhere`                                                         | Matching-row count as `SafeInt!`         | Off     |
| `existsPost`   | `exists`   | `where: PostWhere`                                                         | Whether a match exists as `Boolean!`     | On      |

`health` answers `OK` or `DEGRADED`, as `ultimabase.health()`, and never the
detail; it is always present, so an application without any exposed schema
starts, with a warning. `findManyPost` returns `nodes`, `edges`, and
`pageInfo` with `endCursor` and `hasNextPage`. When `count` is enabled for the
schema, it also returns `totalCount`, computed by one count query only when
the document selects it; a relation connection has no count (its
`totalCount` is a `VALIDATION_ERROR`). Filters and ordering are generated from
the schema's actual fields; each filter lists only the operators the database
adapter declares (ADR-0301), and a field without any declared operator is
absent from the filter input. GraphQL selections choose result fields; there
is no `select` argument.

```graphql title="src/queries.graphql"
query FirstPosts {
	findManyPost(first: 10) {
		nodes {
			id
			title
		}
		pageInfo {
			endCursor
			hasNextPage
		}
	}
}
```

This query works with the read-only local configuration above. Pass
`pageInfo.endCursor` as `after` for the next page when `hasNextPage` is true.

### Generated mutations

| Field            | Rule key     | Required argument             | What it returns                     | Default |
| ---------------- | ------------ | ----------------------------- | ----------------------------------- | ------- |
| `createPost`     | `createOne`  | `input: PostCreateInput!`     | Created `Post!`                     | On      |
| `updatePost`     | `updateOne`  | `input: PostUpdateOneInput!`  | Updated `Post`                      | On      |
| `deletePost`     | `deleteOne`  | `input: PostDeleteOneInput!`  | Deleted `Post` preimage             | On      |
| `upsertPost`     | `upsertOne`  | `input: PostUpsertOneInput!`  | Created or updated `Post!`          | Off     |
| `createManyPost` | `createMany` | `input: PostCreateManyInput!` | Created `[Post!]!` items            | Off     |
| `updateManyPost` | `updateMany` | `input: PostUpdateManyInput!` | Updated `[Post!]!` items            | Off     |
| `deleteManyPost` | `deleteMany` | `input: PostDeleteManyInput!` | Deleted `[Post!]!` preimages        | Off     |
| `upsertManyPost` | `upsertMany` | `input: PostUpsertManyInput!` | Created or updated `[Post!]!` items | Off     |

The local example exposes **none** of these mutations. Enable only the
operations you intend to serve, after configuring authorization. For example,
with `.with({ graphql: { createOne: true } })` on `Post`, a caller can send:

```graphql title="src/mutations.graphql"
mutation CreatePost {
	createPost(input: { title: "Hello" }) {
		id
		title
	}
}
```

Create input fields come from the schema. Update and delete inputs target one
record by `id` or an exact unique `where`; upsert supplies `where`, `create`,
and `update` branches. Bulk operations are homogeneous, ordered, itemized,
and atomic, without partial success. GraphQL derives the result projection
from the selection set; it does not accept a `select` argument. Results obey
the row read rules: a selection of only `id` (and `__typename`) is always
allowed, so a client that may write a row it cannot read selects `{ id }`;
any other field fails with `PERMISSION_DENIED` and nothing is written. A
[`PublicError`](/docs/1.0.0/core/runtime/api-errors#publicerror) from
application code reaches the client with its code in `extensions.code`; other
errors are masked as `INTERNAL_SERVER_ERROR`. See
[Create Data](/docs/1.0.0/core/writing-data/create),
[Upserts](/docs/1.0.0/core/writing-data/upserts), and
[Bulk Operations](/docs/1.0.0/core/writing-data/bulk-operations) for the
underlying mutation behavior.

### Plugin and custom root fields

The tables cover generated schema operations, not a universal list for every
application. A plugin-owned schema does not receive generated CRUD fields.
An operation its owner declared public appears in every installed transport
(ADR-0324): [authentication](./password-authentication) contributes
`signUp`, `login`, `current`, `refresh`, `logout`, `changePassword` and the
account fields, with typed GraphQL bindings whose `user` is the application's
User type. `graphqlPlugin({ hide: [authOperations.refresh] })` hides one; an operation not declared
public never appears. A public operation without a GraphQL binding, such as
one declared with `defineOperation()`, becomes a mutation named after it
whose types derive from its validators, as REST's OpenAPI document does:
`planTrip(input: PlanTripInput!): PlanTripResult!`, with nested objects
named `<Parent><Property>`, string enums as enums, lists and nullability.
Any part GraphQL cannot describe, such as an open record, is `JSON`; the
operation's own validator still checks the input.
[Soft Delete](./soft-delete) contributes schema-specific `softDeleteOnePost`
and `restoreOnePost` mutations when the rule names them
(`graphql: { softDeleteOne: true }`). Custom GraphQL schemas may add other
root fields.

To inspect what **your** application exposes, run this standalone script
instead of the server entry point. It starts the same configuration, prints
the GraphQL plugin's deterministic schema, then releases its resources:

```ts title="src/print-graphql-schema.ts"
import { ultimabase } from './ultimabase.js'

await using app = await ultimabase.start()
console.log(app.plugin('@ultimabase/graphql-plugin').printSchema())
```

For graphql-codegen or gql.tada, `graphqlPlugin({ sdl: './schema.graphql' })`
writes the same SDL to that file each time the application starts.

Yoga answers introspection for browser schema discovery outside production
and refuses it when `NODE_ENV=production`, unless `introspection` is set
explicitly.

### GraphQL without HTTP

`@ultimabase/graphql-plugin` compiles one executable `GraphQLSchema` from the final
application graph. It imports no HTTP, Yoga, REST, authentication, policy, or
database provider. The setup export exposes `schema`, `execute()`, and
deterministic `printSchema()`. `execute()` needs a real request context bound to the same
started application. Foreign, forged, stale, cancelled, and disposed contexts
fail before resolver work.

The context is application-bound. Direct execution needs no HTTP server, but it
still passes generated operations through the same Core request executor as an
HTTP call.

For a standalone direct script, remove HTTP, Yoga and Hono from the
`src/ultimabase.ts` configuration, keeping PostgreSQL and GraphQL. The script
owns startup and cleanup; run it in its own process, not alongside another
initialized application in the same realm:

```ts title="src/direct-graphql.ts"
import { randomUUID } from 'node:crypto'
import { anonymous } from '@ultimabase/core/plugin'
import { ultimabase } from './ultimabase.js'

await using app = await ultimabase.start()
const graphql = app.plugin('@ultimabase/graphql-plugin')
const context = anonymous(app, {
	requestId: randomUUID(),
	source: 'internal',
}).context

const result = await graphql.execute({
	context,
	document: '{ findManyPost(first: 10) { nodes { id title } } }',
})
console.log(result.data)
```

To run a document as a given user, pass `principal` (a pointer, or
`undefined` for an anonymous caller): it replaces the authentication
provider's answer for that context, so `graphql.execute({ context, document,
principal: TodoUser.pointer(userId) })` evaluates every policy as that user.

Generated reads, mutations, nested writes, virtual fields, and public
plugin operations all delegate through Core's narrow application request executor.
Custom schema resolvers receive only `{ request: RequestContext }`, never the
application, executor, adapter, grant, transaction, or lifecycle control.

### Pagination and protection

Collections use Relay-style `edges`, `nodes`, and `pageInfo`, plus
`totalCount` on root connections when `count` is enabled.
`first` defaults to 100 and is capped at 1000; a larger `first` is a GraphQL
error. `graphqlPlugin({ pagination: { defaultTake: 20, maxTake: 200 } })` sets
other values, with the same option and defaults as REST. A root
collection maps `first` and `after` to Core's `take` and `after`: each edge
cursor is the opaque position of its node in the order completed by `id`, the
same cursor REST returns as `nextCursor`, and `hasNextPage` comes from one extra
row. Cursors are unsigned, because a position grants nothing the caller could
not request as a filter, so they stay valid across restarts and instances.
Inserts and deletes between pages never repeat or skip an unchanged node. A
malformed cursor, or one for another type or ordering, fails with
`VALIDATION_ERROR` and `details: { parameter: "after" }`. A relation
connection inside a node accepts the same `first`, `after`, `orderBy`, and
`where`: its edge cursors are positions of the target schema and `after`
continues every parent's collection after that position.

REST returns the same pages as a `{ results, nextCursor }` envelope; the visible
objects pass through the same Query normalization, policies, Runtime, and
database capability.

GraphQL, like REST, refuses to start when it exposes a write (a generated
mutation or a plugin command) and no protected policy such as Access is
installed, unless `graphqlPlugin({ publicWrites: true })` lets every client
write (ADR-0294). Exposure controls declarations only; it never grants access.

A selection of relations is one SQL statement: GraphQL turns it into a Core
`include`, and PostgreSQL reads every level in the same query. A virtual
field on included rows runs once per parent; declare `resolveMany` to resolve
all the rows of a read in one call (see
[Virtual Fields](/docs/1.0.0/core/data-modeling/virtual-fields)). Reading a
relation row by row in application code, for example
`todo.relation('tags').findMany()` in a loop, stays one query per row.

### Serve GraphQL over HTTP with Yoga

`@ultimabase/graphql-yoga-plugin` mounts the final schema through the shared
[HTTP application](./http). These remain separate plugins: GraphQL owns the schema,
Yoga owns the HTTP GraphQL route, HTTP selects the application, and a server
provider such as [Hono Server](./hono-server) opens the listener.
Install and configure each package you use; none is installed by its sibling.

By default, Yoga mounts `POST /graphql`, accepts UTF-8 JSON GraphQL requests,
and limits streamed bodies to 1 MiB. It rejects batching, uploads,
subscriptions, SSE, and its built-in GraphiQL UI. HTTP introspection is on in
development and off when `NODE_ENV=production`; an explicit `introspection`
value always wins. To change the route and limits:

```ts
graphqlYogaPlugin({
	bodyLimit: 512 * 1024,
	introspection: true,
	path: '/api/graphql',
})
```

HTTP selects the application and resolves its request context before Yoga begins.
Yoga validates documents with the application's rules, so a disabled feature
answers with the same hint, and forwards that context to the same GraphQL
execution capability as direct calls. It does not reimplement policies, virtual fields, contextual relations,
transactions, cancellation, or safe errors.

To verify the local setup, send a query:

```bash title="terminal"
curl -i -X POST \
  -H 'Content-Type: application/json' \
  --data '{"query":"{ findManyPost(first: 10) { nodes { id title } } }"}' \
  http://127.0.0.1:1337/graphql
```

On a fresh database, expect HTTP `200` with an empty `nodes` array inside
`data.findManyPost`. An `X-UltimaBase-Application-Id` header that names
another application is rejected by HTTP before Yoga executes the query. Introspection follows `NODE_ENV`: it
answers in development and is refused when `NODE_ENV=production`.

A successful HTTP status is not enough to decide whether a GraphQL operation
succeeded: inspect `errors` as well as `data`. GraphQL errors carry safe
`extensions.code`, `requestId`, and `retryable` values, plus approved details
when available. HTTP identity failures happen before Yoga and retain the HTTP
envelope. See [API Errors](/docs/1.0.0/core/runtime/api-errors) for the common
public error contract.

### Choose a development explorer

`@ultimabase/graphql-explorer-plugin` serves one browser explorer for the
installed GraphQL HTTP endpoint (ADR-0325); it installs neither GraphQL, Yoga,
HTTP nor a server. `apiServer({ graphql: { explorer: 'graphiql' } })` adds it.

| Explorer       | Option                                            | Route             |
| -------------- | ------------------------------------------------- | ----------------- |
| GraphiQL       | `graphqlExplorerPlugin()` (default)               | `/graphiql`       |
| Apollo Sandbox | `graphqlExplorerPlugin({ ui: 'apollo-sandbox' })` | `/apollo-sandbox` |

```ts
import { graphqlExplorerPlugin } from '@ultimabase/graphql-explorer-plugin'

const explorer = graphqlExplorerPlugin({ ui: 'graphiql' })
```

The explorer derives its environment from `NODE_ENV` when created: it serves
its route in development and, in production, only with
`allowInProduction: true`. An explorer that is served while Yoga
introspection is off refuses to start, naming the option to change. Open
`http://127.0.0.1:1337/graphiql`. An application that requires the
application header (several applications behind one server) serves the same
page at `/__ultimabase/apps/{appId}/graphiql`, and the page then sends the
header with its requests.

GraphiQL has no application or endpoint switcher. Apollo Sandbox fixes the
endpoint and disables endpoint editing and cookie controls. Neither embeds
credentials or authority. GraphiQL loads pinned esm.sh modules, each checked
against its integrity hash, so a changed file blocks the page; its editor
workers load their own modules without that check. Apollo Sandbox loads an
unpinned script Apollo publishes without a version, so whatever Apollo serves
runs in the page: a documented risk, limited by serving explorers in
development only. Both need network access to their CDN.

## Troubleshooting

If startup warns that GraphQL exposes no schema or operation, expose at least
one schema or a public operation; only the `health` field answers meanwhile.
If startup refuses public writes, install a policy plugin such as Access or
pass `graphqlPlugin({ publicWrites: true })`. A validation error with a
`hint:` names the rule that enables the field. If direct execution rejects a context, create it from the
same started application and do not retain it after cancellation or disposal.

For HTTP selection errors, first check that an
`X-UltimaBase-Application-Id` header, when sent, matches the configured
`appId`. If an explorer
refuses to start with `PLUGIN_CAPABILITY_MISSING` for
`ultimabase.graphql.introspection`, enable Yoga introspection or stop serving
the explorer in that environment. A missing explorer route in production is
expected unless `allowInProduction: true` is set. A cursor rejected with
`VALIDATION_ERROR` was produced for another type or `orderBy`: send the same
ordering as the read that returned it.
