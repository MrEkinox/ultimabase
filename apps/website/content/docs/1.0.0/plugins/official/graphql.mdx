## Overview

`@ultimabase/graphql-plugin` owns the executable schema. Yoga (HTTP), HTTP,
Hono and the explorer are independent, optional plugins; none installs its
siblings. `apiServer()` from `@ultimabase/api-server` returns them as one list
(ADR-0325).

The code on this page comes from the tested
[GraphQL example](https://github.com/MrEkinox/ultimadatabase/tree/main/examples/graphql):
a small blog whose tests send every document in memory with `t.fetch` and
check the answers shown here.

## Installation

These packages are pre-release. Use the locally built repository example linked
from [Manual Installation](/docs/1.0.0/manual-installation) to evaluate the
current code; the registry commands below describe installation after publication.

For direct GraphQL execution, install the schema plugin:

```bash tab="npm" tab-group="package-manager"
npm install @ultimabase/graphql-plugin
```

```bash tab="yarn"
yarn add @ultimabase/graphql-plugin
```

```bash tab="pnpm"
pnpm add @ultimabase/graphql-plugin
```

Generated fields still need a database provider such as
[PostgreSQL](./postgresql), even when execution has no HTTP server. See
[Manual Installation](/docs/1.0.0/manual-installation) for the initial project.

To serve GraphQL over HTTP with the official [Hono Server](./hono-server)
provider, install the preset, which brings the GraphQL, Yoga, explorer, HTTP,
REST and Hono plugins:

```bash tab="npm" tab-group="package-manager"
npm install @ultimabase/api-server
```

```bash tab="yarn"
yarn add @ultimabase/api-server
```

```bash tab="pnpm"
pnpm add @ultimabase/api-server
```

## Configuration

`apiServer({ graphql })` installs `graphqlPlugin()`, `graphqlYogaPlugin()`,
`httpPlugin()` and `honoServerPlugin()`; `explorer: 'graphiql'` adds the
development explorer. The `graphql` object takes the `graphqlPlugin` options,
plus `yoga` for the transport and `explorer`. The example also installs
[Access](./access), which decides what clients may do, and one application
operation:

<include cwd meta='title="src/schema.ts"'>
	../../examples/graphql/src/schema.ts#factory
</include>

| Plugin option  | Purpose                                                                       |
| -------------- | ----------------------------------------------------------------------------- |
| `default`      | `true`, `false` or per-method defaults inherited by every schema.             |
| `hide`         | Public operations this instance does not expose.                              |
| `limits`       | Document and execution budgets: size, tokens, depth, aliases, root fields.    |
| `pagination`   | `{ defaultTake, maxTake }` of connections, 100 and 1,000 by default.          |
| `publicWrites` | Starts with exposed writes and no protected policy: every client may write.   |
| `schemas`      | Completed custom `GraphQLSchema` values composed after the generated surface. |
| `sdl`          | A file the schema's SDL is written to at startup.                             |

The schema's `.with({ graphql })` rule selects its generated fields; it is
typed by the installed plugin, with no generation step, and goes in the final
`.with(...)`, never in `define`. Schema declaration does not register it;
`schemas: [...]` does:

<include cwd meta='title="src/ultimabase.ts"'>
	../../examples/graphql/src/ultimabase.ts#application
</include>

Start it from a separate entry point; leaving the `await using` scope awaits
`dispose()` when the process finishes. The listener keeps serving until
Ctrl+C. Keep startup out of `src/ultimabase.ts` so scripts and tests can load
it safely. Use a disposable development database: the PostgreSQL `override`
policy, the default outside production, can alter tables.

<include cwd meta='title="src/main.ts"'>
	../../examples/graphql/src/main.ts#start
</include>

The same plugins can be installed one by one. The example's second
application does so, with Yoga options and Apollo Sandbox, and
`graphqlPlugin({ default: false })` exposes only the reads `Note`'s rule
enables:

<include cwd meta='title="src/notes.ts"'>
	../../examples/graphql/src/notes.ts#notes
</include>

`default: false` disables every generated root and plugin command unless a
schema's rule enables it. Exposing only reads lets this application start
without a policy plugin. **GraphQL refuses to start when it exposes a write**
(a generated mutation or a plugin command) and no protected policy plugin
such as Access is installed:
`GraphQL exposes writes (createEntry, updateEntry, deleteEntry) but no protected policy plugin is installed: install one, such as accessPlugin(), or pass graphqlPlugin({ publicWrites: true }) to let every client write.`
`publicWrites: true` lets every client write on purpose (ADR-0294); public
operations do not count as writes. Configure identity and
[Access](./access) or [ACL](./acl-permissions) rules, then review the complete
exposed schema before binding publicly. Authentication alone grants no
permission, and exposure grants none either.

For direct execution only, install `graphqlPlugin()` without HTTP, Yoga and
Hono. See [PostgreSQL](./postgresql) for physical schema preparation and
[HTTP](./http) for application identity validation.

## Behavior and limitations

### Choose the generated surface

GraphQL generates root fields for each exposed application-owned schema. The
tables below use `Post` as the GraphQL type name. GraphQL does not pluralize
or case-fold the schema's `className`; a custom `typeName` changes these field
suffixes.

The rule keys are the schema method names, the same as REST and Access rules
(ADR-0325): `findOne` (`get<Type>` and `findOne<Type>`), `findMany`, `count`,
`exists`, `createOne`, `updateOne`, `deleteOne`, `upsertOne`, `createMany`,
`updateMany`, `deleteMany`, `upsertMany`, a plugin command such as
`softDeleteOne`, and `typeName`, which renames the generated type.
`graphql: true` enables **every** generated root and command, including count,
upsert, and bulk. An object enables or disables each method it names; omitted
methods inherit `graphqlPlugin({ default })`, then the built-in defaults. A
plugin command is exposed only when a rule names it, or when the rule or the
default is `true`. `Post` keeps the defaults and adds `countPost` and
`totalCount`:

<include cwd meta='title="src/schema.ts"'>
	../../examples/graphql/src/schema.ts#post
</include>

`Author` and `Comment` turn their root mutations off: clients only read
authors, and write comments through their post:

<include cwd meta='title="src/schema.ts"'>
	../../examples/graphql/src/schema.ts#author
</include>

<include cwd meta='title="src/schema.ts"'>
	../../examples/graphql/src/schema.ts#comment
</include>

`graphql: false` removes one schema's root fields and mutations (ADR-0333).
A schema without any exposed root or command contributes types only where an
exposed schema reaches it: through a pointer or relation field of an exposed
type, or a nested write input, transitively. `AuditEntry` holds its link to a
post itself, so nothing exposed reaches it:

<include cwd meta='title="src/schema.ts"'>
	../../examples/graphql/src/schema.ts#audit
</include>

No type, input or field name of `AuditEntry` appears in the printed schema,
and introspection answers `null` for `__type(name: "AuditEntry")`:

<include cwd meta='title="tests/schema.test.ts"'>
	../../examples/graphql/tests/schema.test.ts#hidden-schema
</include>

A hidden schema that an exposed relation or pointer does reach keeps only the
types those fields need (its object type, plus the connection, filters and
nested write inputs they use), and Access still decides every read and nested
write through them, as REST's `rest: false` keeps links and includes. To keep
such a link out of GraphQL, declare it on the hidden schema, as
`AuditEntry.post` does. An Access field rule such as
`access: { read: false, write: false }` denies the field, like
`Post.reviewNote`, but leaves it in the schema.

A disabled field is absent from the endpoint's schema, even for Master; a
document that selects it fails validation with `400`. Outside production the
error carries a hint naming the rule to set; GraphQL reads `NODE_ENV` when
created, as Access's `'development'` openings do, and in production the
error is GraphQL's own, naming no schema or rule:

<include cwd meta='title="tests/errors.test.ts"'>
	../../examples/graphql/tests/errors.test.ts#disabled-field
</include>

<include cwd meta='title="tests/errors.test.ts"'>
	../../examples/graphql/tests/errors.test.ts#disabled-field-answer
</include>

An enum field declared with a string array gets one enum type named from its
schema and field path, `PostStatus` here. Every field using the same shared
enum from `defineEnum('TaskPriority', [...])` uses one `TaskPriority` enum type
(ADR-0310); a name that collides with another generated type fails schema
compilation.

### Generated queries

| Field          | Rule key   | Arguments                                                                  | What it returns                          | Default |
| -------------- | ---------- | -------------------------------------------------------------------------- | ---------------------------------------- | ------- |
| `health`       | (always)   | none                                                                       | `HealthStatus!`: `OK` or `DEGRADED`      | On      |
| `getPost`      | `findOne`  | `id: ID!`                                                                  | One `Post`; a missing target is an error | On      |
| `findOnePost`  | `findOne`  | `where: PostWhere`, `orderBy: [PostOrder!]`                                | First match or `null`                    | On      |
| `findManyPost` | `findMany` | `where: PostWhere`, `orderBy: [PostOrder!]`, `first: Int`, `after: String` | A `PostConnection!` page                 | On      |
| `countPost`    | `count`    | `where: PostWhere`                                                         | Matching-row count as `SafeInt!`         | Off     |
| `existsPost`   | `exists`   | `where: PostWhere`                                                         | Whether a match exists as `Boolean!`     | On      |

detail; it is always present, so an application without any exposed schema

| Field            | Rule key     | Required argument             | What it returns                     | Default |
| ---------------- | ------------ | ----------------------------- | ----------------------------------- | ------- |
| `createPost`     | `createOne`  | `input: PostCreateInput!`     | Created `Post!`                     | On      |
| `updatePost`     | `updateOne`  | `input: PostUpdateOneInput!`  | Updated `Post`                      | On      |
| `deletePost`     | `deleteOne`  | `input: PostDeleteOneInput!`  | Deleted `Post` preimage             | On      |
| `upsertPost`     | `upsertOne`  | `input: PostUpsertOneInput!`  | Created or updated `Post!`          | Off     |
| `createManyPost` | `createMany` | `input: PostCreateManyInput!` | Created `[Post!]!` items            | Off     |
| `updateManyPost` | `updateMany` | `input: PostUpdateManyInput!` | Updated `[Post!]!` items            | Off     |

### Plugin and custom root fields

The tables cover generated schema operations, not a universal list for every
application. A plugin-owned schema does not receive generated CRUD fields.
An operation its owner declared public appears in every installed transport
(ADR-0324): [authentication](./password-authentication) contributes
`signUp`, `login`, `current`, `refresh`, `logout`, `changePassword` and the
account fields, with typed GraphQL bindings whose `user` is the application's
User type. `graphqlPlugin({ hide: [authOperations.refresh] })` hides one; an
operation not declared public never appears.

A public operation without a GraphQL binding, such as one declared with
`defineOperation()`, becomes a mutation named after it whose types derive
from its validators, as REST's OpenAPI document does:

<include cwd meta='title="src/operations.ts"'>
	../../examples/graphql/src/operations.ts#operation
</include>

The schema then has
`readingTime(input: ReadingTimeInput!): ReadingTimeResult!`, nested objects
named `<Parent><Property>` (`ReadingTimeInputOptions`), string enums as enums
(`ReadingTimeInputPace` with `slow`, `normal` and `fast`), lists and
nullability; a field with a default is optional. Any part GraphQL cannot
describe, such as an open record, is `JSON`; the operation's own validator
still checks the input:

<include cwd meta='title="tests/operations.test.ts"'>
	../../examples/graphql/tests/operations.test.ts#call-operation
</include>

The answer is `{ "data": { "readingTime": { "minutes": 2, "words": 2 } } }`.
An empty `text` fails the validator with `VALIDATION_ERROR` and its issues in
`extensions.details.issues`.

[Soft Delete](./soft-delete) contributes schema-specific `softDeleteOnePost`
and `restoreOnePost` mutations when the rule names them
(`graphql: { softDeleteOne: true }`). Custom GraphQL schemas add other root
fields: pass completed `GraphQLSchema` values, from the reference `graphql`
package, Pothos, Nexus or GraphQL Tools, through `graphqlPlugin({ schemas })`:

<include cwd meta='title="src/custom-schema.ts"'>
	../../examples/graphql/src/custom-schema.ts#custom-schema
</include>

<include cwd meta='title="tests/queries.test.ts"'>
	../../examples/graphql/tests/queries.test.ts#version

The answer is `{ "data": { "health": "OK", "version": "1.0.0" } }`. A

To inspect what **your** application exposes, run this standalone script
instead of the server entry point. It starts the same configuration, prints

<include cwd meta='title="src/print-schema.ts"'>

### GraphQL without HTTP

`@ultimabase/graphql-plugin` compiles one executable `GraphQLSchema` from the final
application graph. It imports no HTTP, Yoga, REST, authentication, policy, or
database provider. The setup export exposes `schema`, `execute()`, and
deterministic `printSchema()`. `execute()` needs a real request context bound
to the same started application; request contexts are plugin-author
machinery from `@ultimabase/core/plugin` (ADR-0311). Foreign, forged, stale,
cancelled, and disposed contexts fail before resolver work:

<include cwd meta='title="tests/schema.test.ts"'>
	../../examples/graphql/tests/schema.test.ts#execute
</include>

`result.data` holds the first two posts, as over HTTP. Direct execution needs
no HTTP server, but it still passes generated operations through the same
Core request executor as an HTTP call. A standalone script owns startup and
cleanup, like `src/print-schema.ts`; run it in its own process, not alongside
another initialized application in the same realm.

To run a document as a given user, pass `principal` (a pointer, or
`undefined` for an anonymous caller): it replaces the authentication
provider's answer for that context, so `graphql.execute({ context, document,
principal: TodoUser.pointer(userId) })` evaluates every policy as that user.

Generated reads, mutations, nested writes, virtual fields, and public
plugin operations all delegate through Core's narrow application request executor.
Custom schema resolvers receive only `{ request: RequestContext }`, never the
application, executor, adapter, grant, transaction, or lifecycle control.

### Pagination and protection

Collections use Relay-style `edges`, `nodes`, and `pageInfo`, plus
`totalCount` on root connections when `count` is enabled; a relation
connection has no count. `first` defaults to 100 and is capped at 1000, 20 and
100 in the example; a `first` outside that window fails with
`VALIDATION_ERROR`, shown below.
`graphqlPlugin({ pagination: { defaultTake: 20, maxTake: 100 } })` sets other
values, with the same option and defaults as REST. A root collection maps
`first` and `after` to Core's `take` and `after`: each edge cursor is the
opaque position of its node in the order completed by `id`, the same cursor
REST returns as `nextCursor`, and `hasNextPage` comes from one extra row.
Pass `pageInfo.endCursor` as `after`, with the same `orderBy`, for the next
page:

<include cwd meta='title="tests/queries.test.ts"'>
	../../examples/graphql/tests/queries.test.ts#next-page
</include>

The second page holds `Gamma` and `Beta`, with `hasNextPage: false` and
`hasPreviousPage: true`, which is `true` exactly when `after` was given.
Cursors are unsigned, because a position grants nothing the caller could not
request as a filter, so they stay valid across restarts and instances.
Inserts and deletes between pages never repeat or skip an unchanged node. A
malformed cursor, or one for another type or ordering, fails with
`VALIDATION_ERROR` and `details: { parameter: "after" }`:

<include cwd meta='title="tests/errors.test.ts"'>
	../../examples/graphql/tests/errors.test.ts#bad-cursor
</include>

A negative `first`, or one above `maxTake`, fails the same way at the root
and on a relation connection, as REST rejects a `take` above `maxTake`. The
message gives the accepted window:

<include cwd meta='title="tests/errors.test.ts"'>
	../../examples/graphql/tests/errors.test.ts#first-too-large
</include>

<include cwd meta='title="tests/errors.test.ts"'>
	../../examples/graphql/tests/errors.test.ts#first-too-large-answer
</include>

A relation connection inside a node accepts the same `first`, `after`,
`orderBy`, and `where`: its edge cursors are positions of the target schema
and `after` continues every parent's collection after that position.

REST returns the same pages as a `{ results, nextCursor }` envelope; the visible
objects pass through the same Query normalization, policies, Runtime, and
database capability.

A selection of relations is one SQL statement: GraphQL turns it into a Core
`include`, and PostgreSQL reads every level in the same query. A virtual
field on included rows runs once per parent; declare `resolveMany` to resolve
all the rows of a read in one call (see
[Virtual Fields](/docs/1.0.0/core/data-modeling/virtual-fields)). In the
example, `readingMinutes` calls its estimating service once for every post of
this read:

<include cwd meta='title="tests/queries.test.ts"'>
	../../examples/graphql/tests/queries.test.ts#relations
</include>

Each post carries its author (`null` when unset) and its last comment, with
`hasNextPage: true` for `Hello`, which has two. Reading a relation row by row
in application code, for example `todo.relation('tags').findMany()` in a
loop, stays one query per row.

### Serve GraphQL over HTTP with Yoga

`@ultimabase/graphql-yoga-plugin` mounts the final schema through the shared
[HTTP application](./http). These remain separate plugins: GraphQL owns the schema,
Yoga owns the HTTP GraphQL route, HTTP selects the application, and a server
provider such as [Hono Server](./hono-server) opens the listener.
Install and configure each package you use; none is installed by its sibling.

By default, Yoga mounts `POST /graphql`, accepts UTF-8 JSON GraphQL requests,
answers `application/graphql-response+json`, and limits streamed bodies to
the HTTP plugin's `bodyLimit` (1 MiB). It rejects other methods with `405`,
batching, uploads, subscriptions, SSE, and its built-in GraphiQL UI. HTTP
introspection is on in development and off when `NODE_ENV=production`; an
explicit `introspection` value always wins. With introspection off,
validation errors carry no "Did you mean …" suggestions, which would name
fields. The `notes` application above sets `path: '/api/graphql'`, a 512 KiB
`bodyLimit` (a larger body answers `413` `HTTP_PAYLOAD_TOO_LARGE`) and
explicit introspection:

<include cwd meta='title="tests/notes.test.ts"'>
	../../examples/graphql/tests/notes.test.ts#notes-query
</include>

HTTP selects the application and resolves its request context before Yoga
begins: here `requireApplicationId` makes a request without the header answer
`401` `HTTP_APPLICATION_REJECTED`, and in the blog an
`X-UltimaBase-Application-Id` header that names another application answers
`404` `HTTP_APPLICATION_UNKNOWN`, both with the HTTP envelope. Yoga validates
documents with the application's rules, so a disabled feature answers with the
same hint outside production, and forwards that context to the same GraphQL
execution capability as direct calls. It does not reimplement policies, virtual fields, contextual
relations, transactions, cancellation, or safe errors.

A successful HTTP status is not enough to decide whether a GraphQL operation
succeeded: inspect `errors` as well as `data`. GraphQL errors carry safe
`extensions.code`, `requestId`, and `retryable` values, plus approved details
when available. A [`PublicError`](/docs/1.0.0/core/runtime/api-errors#publicerror)
from application code reaches the client with its code; other errors are
masked as `INTERNAL_SERVER_ERROR` and logged with their stack. The example's
operation throws one for a text above 10,000 words:

### Choose a development explorer

`@ultimabase/graphql-explorer-plugin` serves one browser explorer for the
installed GraphQL HTTP endpoint (ADR-0325); it installs neither GraphQL, Yoga,
HTTP nor a server. `apiServer({ graphql: { explorer: 'graphiql' } })` adds it.

| Explorer       | Option                                            | Route             |
| -------------- | ------------------------------------------------- | ----------------- |
| GraphiQL       | `graphqlExplorerPlugin()` (default)               | `/graphiql`       |
| Apollo Sandbox | `graphqlExplorerPlugin({ ui: 'apollo-sandbox' })` | `/apollo-sandbox` |

The blog serves GraphiQL; open `http://127.0.0.1:1337/graphiql` while
`src/main.ts` runs:

<include cwd meta='title="tests/schema.test.ts"'>
	../../examples/graphql/tests/schema.test.ts#explorer
</include>

The explorer derives its environment from `NODE_ENV` when created: it serves
its route in development and, in production, only with
`allowInProduction: true`. An explorer served while Yoga introspection is off
cannot be installed: creating the application fails with
`PLUGIN_CAPABILITY_MISSING`, naming `graphqlYogaPlugin({ introspection: true })`.
An application that requires the application header (several applications
behind one server) serves the same page at `/__ultimabase/apps/{appId}/graphiql`,
or `apollo-sandbox`, and the page then sends the header with its requests:

<include cwd meta='title="tests/notes.test.ts"'>
	../../examples/graphql/tests/notes.test.ts#notes-sandbox
</include>

GraphiQL has no application or endpoint switcher. Apollo Sandbox fixes the
endpoint and disables endpoint editing and cookie controls. Neither embeds
credentials or authority. GraphiQL loads pinned esm.sh modules, each checked
against its integrity hash, so a changed file blocks the page; its editor
workers load their own modules without that check. Apollo Sandbox loads an
unpinned script Apollo publishes without a version, so whatever Apollo serves
runs in the page: a documented risk, limited by serving explorers in
development only. Both need network access to their CDN.

## Troubleshooting

If startup warns that GraphQL exposes no schema or operation, expose at least
one schema or a public operation; only the `health` field answers meanwhile.
If startup refuses public writes, install a policy plugin such as Access or
pass `graphqlPlugin({ publicWrites: true })`. Outside production, a
validation error with a `hint:` names the rule that enables the field. If a
type you expected is missing from the schema, check that an exposed root,
command, pointer or relation reaches its schema. If direct execution rejects
a context, create it from the same started application and do not retain it
after cancellation or disposal.

For HTTP selection errors, first check that an
`X-UltimaBase-Application-Id` header, when sent, matches the configured
`appId`. If creating the application fails with `PLUGIN_CAPABILITY_MISSING`
for `ultimabase.graphql.introspection`, enable Yoga introspection or stop
serving the explorer in that environment. A missing explorer route in
production is expected unless `allowInProduction: true` is set. A cursor
rejected with `VALIDATION_ERROR` was produced for another type or `orderBy`:
send the same ordering as the read that returned it.
