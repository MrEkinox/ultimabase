## Overview

`@ultimabase/password-auth-plugin` adds local username-and-password identity
to one UltimaBase application. It owns a public `User` schema, Argon2id
password verifiers, and opaque, revocable sessions. Credentials and session
records live in owner-private storage: they are not application schemas and
cannot be queried through User, Typegen, REST, GraphQL, Hooks, or Access.
Importing the package alone installs nothing.

A valid session adds a typed principal and session value to the request, but
Core authority remains `anonymous`. Authentication does **not** grant schema
access, roles, ACL rights, or Master authority. Configure [Access](./access)
or [Object ACLs](./acl-permissions) separately for authorization.

## Installation

You need a database provider and a configured, audited
[Master Authority](/docs/1.0.0/core/security-foundations/master-authority).
Sign-up briefly uses Master to create the User and aborts if its audit fails.
Keep `ULTIMABASE_MASTER_KEY` server-side. Password Authentication uses that
authority internally for sign-up; clients need neither the key nor an HTTP
Master header.
Install the optional package:

```bash tab="npm" tab-group="package-manager"
npm install @ultimabase/password-auth-plugin
```

```bash tab="yarn"
yarn add @ultimabase/password-auth-plugin
```

```bash tab="pnpm"
pnpm add @ultimabase/password-auth-plugin
```

Direct server operations need no HTTP plugin. For network requests, add
[HTTP](./http) and explicitly expose the authentication operations through
[REST](./rest) or [GraphQL](./graphql), or enable the plugin's cookie routes.

## Configuration

The plugin supplies a default `User` schema. Define a custom one only when
you need additional public fields. This example uses a **disposable development
database**: PostgreSQL's `override` policy may create or alter application
and owner-private tables. Keep both credentials in a secret store or process
environment, never in source code.

```ts title="src/ultimabase.ts"
import { MasterAuthority, UltimaBase } from '@ultimabase/core'
import {
	PasswordUserSchema,
	passwordAuthPlugin,
} from '@ultimabase/password-auth-plugin'
import { postgresPlugin } from '@ultimabase/postgres-plugin'

const databaseUrl = process.env.DATABASE_URL
const masterKey = process.env.ULTIMABASE_MASTER_KEY
if (!databaseUrl || !masterKey) {
	throw new Error('DATABASE_URL and ULTIMABASE_MASTER_KEY are required')
}

export const AppUser = PasswordUserSchema.define({
	className: 'User',
	fields: (f) => ({
		displayName: f.string(),
	}),
})

export const ultimabase = new UltimaBase({
	masterAuthority: new MasterAuthority({
		keys: [{ id: 'server', value: masterKey }],
		onUse: (event) => {
			console.info('Master use', event.reason)
		},
	}),
	plugins: [
		postgresPlugin({ schemaPolicy: 'override', url: databaseUrl }),
		passwordAuthPlugin({ user: AppUser }),
	],
	schemas: [],
})

await ultimabase.start()
```

`schemas: []` is intentional: Password Authentication contributes its own
`User` schema. `PasswordUserSchema.define()` adds an immutable, required,
unique `username` field. Do not redeclare it or add `password`,
`passwordHash`, `credential`, or `session` fields. Only sign-up creates a login
credential; directly creating a User does not. Replace the console audit with
a reliable production audit sink before deployment. See [PostgreSQL](./postgresql)
for schema policies. V1 supports one Password Authentication instance per
application; a second instance is rejected during compilation.

The factory accepts these optional settings:

| Option        | What it controls                                                                                         |
| ------------- | -------------------------------------------------------------------------------------------------------- |
| `user`        | The exact custom `PasswordUserSchema`; omission uses the built-in User schema                            |
| `password`    | Argon2id `memoryCostKiB`, `timeCost`, `parallelism`, and monotonic `policyVersion`                       |
| `session`     | Rolling `expiresInMs` and absolute `absoluteExpiresInMs` lifetimes                                       |
| `http.cookie` | Secure browser-cookie routes in addition to Bearer; requires a compatible HTTP plugin and browser policy |

The default password hash uses Argon2id v19, 65,536 KiB memory, three passes,
and four lanes with a fresh salt. Raise `policyVersion` whenever a hash
parameter changes; a successful login upgrades an older verifier without
downgrading a newer one. Budget memory for concurrent login attempts. The
default session lasts up to seven rolling days, capped at thirty days from
creation. Both lifetime options are integer milliseconds; the absolute
lifetime must be at least the rolling lifetime.

### Optional secure cookies

Bearer sessions work without cookie configuration. For browser cookies, add
the configured Password Authentication and HTTP plugins to the same
application, along with a server provider as shown on the [HTTP](./http) page:

```ts title="src/cookie-auth.ts"
import { httpPlugin } from '@ultimabase/http-plugin'
import { passwordAuthPlugin } from '@ultimabase/password-auth-plugin'

export const cookieAuth = passwordAuthPlugin({
	http: { cookie: { name: '__Host-notes-session', sameSite: 'lax' } },
})

export const cookieHttp = httpPlugin({
	appId: 'notes',
	browser: {
		allowedHeaders: [
			'Authorization',
			'Content-Type',
			'X-UltimaBase-Application-Id',
		],
		allowedMethods: ['GET', 'POST'],
		allowedOrigins: ['https://app.example.com'],
		credentials: true,
	},
})
```

Use `cookieAuth` in place of the bare `passwordAuthPlugin()` call in your
application; if you use a custom User, pass `user: AppUser` to this configured
factory too. Add `cookieHttp` alongside it. The browser policy must use exact
origins, allow credentials, and include `POST`, `Content-Type`, and
`X-UltimaBase-Application-Id`; an incompatible policy fails startup. Cookie
mode uses `Secure`, `HttpOnly`, host-only `__Host-` cookies. Test it over HTTPS,
not a local HTTP preview.

## Behavior and limitations

### Usernames and passwords

Usernames are trimmed, Unicode-normalized, and lowercased before storage and
lookup. The canonical username must contain 3–64 Unicode code points, start
and end with a letter or number, and use only letters, numbers, `.`, `_`, or
`-` between them. An email address is not a v1 username. Passwords are
Unicode-normalized but never trimmed or case-changed; they must contain
15–256 code points. Do not pre-trim a password in your application.

The public User can be used by trusted server Query and Typegen, but its
plugin-owned provenance excludes automatic generated User CRUD routes.
Private credential and session records never appear in those surfaces.

### Direct operations and session scope

The plugin publishes four transport-neutral operations. They are available to
server code after `await ultimabase.start()` but are not public HTTP routes
until explicitly exposed.

| Operation | Input                              | Result or effect                                                           |
| --------- | ---------------------------------- | -------------------------------------------------------------------------- |
| `signUp`  | `{ username, password }`           | Creates User, credential, and session; returns principal and one raw token |
| `login`   | `{ username, password }`           | Returns a new independent session; may upgrade an older password verifier  |
| `refresh` | `null`, inside a validated session | Rotates the token and invalidates the old one atomically                   |
| `logout`  | `null`, inside a validated session | Revokes only that session; other sessions remain valid                     |

Use the application-bound helper to validate a token and run direct server
work in its authenticated request scope:

```ts title="src/auth-flow.ts"
import { passwordAuthOperations } from '@ultimabase/password-auth-plugin'
import { ultimabase } from './ultimabase.js'

const signedUp = await ultimabase
	.operation(passwordAuthOperations.signUp)
	.execute({
		username: 'Ada',
		password: 'correct horse battery staple',
	})

const auth = ultimabase.application.getPlugin(
	'@ultimabase/password-auth-plugin',
)

const refreshed = await auth.runWithSession(signedUp.session.token, () =>
	ultimabase.operation(passwordAuthOperations.refresh).execute(null),
)

await auth.runWithSession(refreshed.session.token, () =>
	ultimabase.operation(passwordAuthOperations.logout).execute(null),
)
```

`runWithSession()` validates the token before invoking its callback. It adds
typed `passwordPrincipal` and `passwordSession` request values, not the raw
token or a permission grant. The old token stops working after refresh; logout
invalidates the new one. Treat every returned token as a secret: never log it,
put it in a URL, or persist it as a User field. Multiple independent sessions
per User are allowed.

### Explicit REST or GraphQL exposure

Password Authentication does not publish its operations automatically. Pass
the exact tokens to the transport you choose:

```ts title="src/auth-operations.ts"
import { graphqlPlugin } from '@ultimabase/graphql-plugin'
import { passwordAuthOperations } from '@ultimabase/password-auth-plugin'
import { restPlugin } from '@ultimabase/rest-plugin'

export const authOperations = [
	passwordAuthOperations.signUp,
	passwordAuthOperations.login,
	passwordAuthOperations.refresh,
	passwordAuthOperations.logout,
] as const

export const authRest = restPlugin({ operations: authOperations })
export const authGraphql = graphqlPlugin({ operations: authOperations })
```

Add `authRest`, `authGraphql`, or both to the same application's plugins with
the required transport infrastructure. REST uses
`POST /api/v1/operations/ultimabase.password-auth.login` and wraps credentials
as `{ "input": { "username": "Ada", "password": "..." } }`. GraphQL uses its
own operation bindings. Neither transport exposes credential storage or
automatically generates User CRUD. See [REST](./rest) and [GraphQL](./graphql)
for their full setup, public-protection review, and response formats.
If the application has no verified public policy, these transports report
`UNVERIFIED_PUBLIC_TRANSPORT_PROTECTION`. Review the exposed surface and its
Access or ACL rules before acknowledging that diagnostic; a session alone is
not protection.

### Bearer and cookie requests

With HTTP installed, Bearer is the default credential transport: send exactly
one `Authorization: Bearer <token>` plus the selected application's
`X-UltimaBase-Application-Id` header. A validated token adds identity while
Core authority stays `anonymous`. Missing credentials leave the request
anonymous; malformed, expired, revoked, unknown, or foreign-application
tokens fail before route dispatch. A separate valid Master key can coexist
with a session, but the session itself cannot elevate authority.
Pre-dispatch HTTP credential failures use the safe
`HTTP_APPLICATION_REJECTED` boundary; `PASSWORD_AUTH_INVALID_SESSION` is the
failure of an executed refresh or logout operation.

Cookie mode adds `POST /auth/v1/sign-up`, `/auth/v1/login`,
`/auth/v1/refresh`, and `/auth/v1/logout`. Sign-up and login accept a direct
`{ username, password }` JSON body—not REST's `{ input: ... }` envelope.
Successful sign-up, login, and refresh set or rotate the `HttpOnly` cookie;
their JSON omits the raw token. Logout revokes the current session and expires
the cookie. Refresh and logout need no JSON body, but still require the exact
`Content-Type: application/json` header. A browser login looks like this:

```ts title="src/login.ts"
export const loginWithCookie = (username: string, password: string) =>
	fetch('https://api.example.com/auth/v1/login', {
		method: 'POST',
		credentials: 'include',
		headers: {
			'Content-Type': 'application/json',
			'X-UltimaBase-Application-Id': 'notes',
		},
		body: JSON.stringify({ username, password }),
	})
```

The browser supplies `Origin`; do not invent or override it in application
code. Every cookie route requires an exact allowed origin and exact
`application/json` content type. Unsafe application requests authenticated
by the cookie require the same proof. Sending Bearer and the configured cookie
together is rejected as ambiguous.

A stale cookie is ignored **only** on cookie sign-up and login so the browser
can replace an expired or revoked `HttpOnly` cookie. Bearer remains strict on
those routes; refresh, logout, and application routes still reject invalid
cookies. This is session-cookie recovery, not password recovery.

### Public failures and missing protections

| Code                                | Meaning                                            | REST status |
| ----------------------------------- | -------------------------------------------------- | ----------- |
| `PASSWORD_AUTH_SIGN_UP_REJECTED`    | Invalid or unavailable sign-up identity            | 400         |
| `PASSWORD_AUTH_INVALID_CREDENTIALS` | Invalid login credentials without user enumeration | 401         |
| `PASSWORD_AUTH_INVALID_SESSION`     | Invalid session or session transition              | 401         |

Password Authentication v1 has no password recovery, password change, MFA,
logout-all, automatic refresh, or built-in rate limiter. Put a suitable
online-attempt defense in front of any public login route before deployment;
do not mistake the plugin for a complete account-security product.

## Troubleshooting

- **Sign-up fails before User creation:** confirm that this application has
  `MasterAuthority` and a working audit callback. Audit failure aborts the
  operation. Check database preparation and permissions, but do not retry
  PostgreSQL `override` against shared data without a recovery plan.
- **Login fails for an apparently valid username:** use the canonical username
  rules above and check the password without trimming it. Unknown users,
  credential-less Users, and wrong passwords intentionally share
  `PASSWORD_AUTH_INVALID_CREDENTIALS`.
- **A session is rejected:** check expiry, revocation, rotation, and exact
  application ownership. Refresh invalidates the previous token immediately;
  `runWithSession()` and HTTP do not accept a token from another application.
- **A valid session cannot read or mutate a schema:** inspect [Access](./access)
  and [Object ACLs](./acl-permissions). Authentication adds identity, not
  permission; do not use Master to hide a broken policy.
- **Cookie login or refresh fails:** verify HTTPS, the credentialed exact-origin
  browser policy, application ID, exact JSON media type, and the request's
  `Origin`. Remove an accidental Bearer-plus-cookie combination. Login may
  replace a stale cookie; refresh cannot.
