## Overview

`@ultimabase/auth-plugin` is the authentication foundation: it adds
`App.UserSchema`, sessions shared by every sign-in method, the current
principal, linked accounts, attempt limiting, account events, and the
authentication routes under one HTTP prefix. Sign-in methods are separate
packages; `@ultimabase/auth-password` is the password method. Register with
`TodoUser.signUp()`, log in with `TodoUser.login()`, and use the returned
session for authenticated requests.

Authentication establishes identity and grants no
authorization. Configure [Access](./access) or [Object ACLs](./acl-permissions)
for authorization; Core authority remains `anonymous` in an authenticated
request.

## Installation

Start from a working UltimaBase application with a database provider. Packages
are pre-release; follow [Manual Installation](/docs/1.0.0/manual-installation)
for the project layout. These are the intended registry commands once the
packages are published:

```bash tab="npm" tab-group="package-manager"
npm install @ultimabase/auth-plugin @ultimabase/auth-password
```

```bash tab="yarn"
yarn add @ultimabase/auth-plugin @ultimabase/auth-password
```

```bash tab="pnpm"
pnpm add @ultimabase/auth-plugin @ultimabase/auth-password
```

Sign-up needs no Master key: the plugin creates the User with its own audited
`authority:elevate` privilege. An application may still configure
[Master Authority](/docs/1.0.0/core/security-foundations/master-authority) for
other trusted work. Keep `ULTIMABASE_MASTER_KEY` server-side. Clients never
supply it. Importing the packages alone installs no behavior.

## Configuration

Install `authPlugin` with its methods in the application's plugin list, then
declare the User through `App.UserSchema`, like any schema:

```ts title="src/app.ts"
import { password } from '@ultimabase/auth-password'
import { authPlugin } from '@ultimabase/auth-plugin'
import { UltimaBase } from '@ultimabase/core'
import { postgresPlugin } from '@ultimabase/postgres-plugin'

export const App = UltimaBase.use(
	postgresPlugin(),
	authPlugin({ methods: [password({ identifier: 'email' })] }),
)
```

```ts title="src/todo-user.ts"
import { App } from './app.js'

export const TodoUser = App.UserSchema.define({
	className: 'TodoUser',
	fields: (field) => ({
		displayName: field.string({ required: true }),
	}),
}).with({})
```

```ts title="src/ultimabase.ts"
import { App } from './app.js'
import { TodoUser } from './todo-user.js'

export const ultimabase = new App({ schemas: [TodoUser] })
```

The class name is yours. `password({ identifier: 'email' })` adds a required,
unique, immutable `email`; `identifier: 'username'` (the default) adds
`username` instead. Do not declare that field or `password` yourself. The User
stays an application schema: its `.with({ access, hooks, … })` rules apply
like any other. One `authPlugin` instance owns one User schema; install that
instance in every application registering the User.

Options of `authPlugin({ methods, session, linking, http, events })`:

- `methods`: the sign-in methods, such as `password()`.
- `session.expiresInMs` and `session.absoluteExpiresInMs`: rolling (seven
  days) and absolute (thirty days) lifetimes.
- `session.revokeOnPasswordChange`: revokes the other sessions after a
  password change; `true` by default.
- `session.recentAuthenticationMs`: how long a login allows sensitive
  operations; five minutes by default.
- `linking`: `'verified-email'` (default) or `'manual'`.
- `http.basePath` (`/auth`) and `http.cookie` (`{ name: '__Host-…', sameSite }`).
- `events`: application handlers such as `afterLogin`.

`password({ identifier, policy })` takes Argon2id `memoryCostKiB`, `timeCost`,
`parallelism` and `policyVersion`. Raise `policyVersion` when changing hash
parameters; a successful login upgrades an older verifier.

## Behavior and limitations

### Register and log in

```ts
await ultimabase.start()

const { user, session } = await TodoUser.signUp({
	displayName: 'Ada',
	email: 'ada@example.com',
	password: 'correct horse battery staple',
})
const login = await TodoUser.login({
	email: 'ada@example.com',
	password: 'correct horse battery staple',
})
```

`user` is the readable profile, typed as `Model<'TodoUser'>`;
`session.token` is returned exactly once and only its SHA-256 digest is
stored. A missing or invalid field fails with `AUTH_SIGN_UP_REJECTED`, whose
details name the fields; a duplicate email is rejected without naming it.
Every login failure is the same `AUTH_INVALID_CREDENTIALS`, and an unknown
email pays for a full verification. The authenticated User must be able to
read its own profile:

```ts
export const TodoUser = App.UserSchema.define({ className: 'TodoUser' }).with({
	access: {
		read: ({ principal, where }) =>
			where.in('id', principal === undefined ? [] : [principal.id]),
	},
})
```

Emails are trimmed, normalized and lowercased, then checked as addresses;
usernames have 3–64 letters, numbers, `.`, `_` or `-`. Passwords are
Unicode-normalized, never trimmed, and have 15–256 code points.

### Use and manage sessions

```ts
import { authPlugin } from '@ultimabase/auth-plugin'

const auth = ultimabase.plugin(authPlugin)
await auth.runWithSession(login.session.token, async () => {
	const me = await TodoUser.current()
	const { sessions } = await TodoUser.listSessions()
	await TodoUser.revokeSession(sessions[1].id)
	await TodoUser.changePassword({
		currentPassword: 'correct horse battery staple',
		newPassword: 'another correct horse battery staple',
	})
})
const rotated = await TodoUser.refresh(login.session.token)
await TodoUser.logout(rotated.session.token)
```

The plugin provides Core's current principal: Access rules, Hooks, ACL and
Roles receive the User pointer as `principal`. `listSessions()` reports each
live session's method, creation, last use, expiry, address and device, never
its token. `logoutEverywhere()` revokes every session of the user; a password
change keeps the current session and revokes the others. On the server,
`auth.listSessions(user)` and `auth.revokeSessions(user)` serve
administration.

`deleteAccount()` and `unlinkMethod(id)` need a recent authentication: a login
younger than five minutes, or `reauthenticate({ password })` first. Deleting
the account removes the User, its sessions, linked methods and password.

### Attempt limiting

Failures are counted in the database and shared by every server. Per account
and client address, five failures are free, then each one locks that pair for
a delay doubling from one second up to fifteen minutes; per account, twenty
failures are free with the same growth. A success resets both. A locked
attempt fails with `AUTH_TOO_MANY_ATTEMPTS` (HTTP 429 and `Retry-After`)
before any password work. Configure the HTTP plugin's `rateLimit` and
`trustProxy` for a global per-address limit.

### Linked accounts and events

A user's sign-in methods are private linked accounts, unique per method and
provider identifier; `listMethods()` lists them and a user can never remove
the last one. With `linking: 'verified-email'`, a future provider method links
a new account to the user who verified the same email.

```ts
authPlugin({
	methods: [password({ identifier: 'email' })],
	events: { afterLoginFailed: (event) => alert(event.address) },
})
```

`afterSignUp`, `afterLogin`, `afterLoginFailed` and `afterLogout` run after
commit, best effort, and never carry a password or token. Events carry the
client address, and `afterLoginFailed` also carries the normalized identifier
the attempt targeted (an email or username, even for an unknown account): both
are personal data, so store, retain and forward them under your privacy
policy. Password reset and email verification arrive in a later step;
UltimaBase sends no email itself.

### HTTP, GraphQL and REST

With the HTTP plugin, every operation is served under one prefix, for Bearer
and cookie alike:

| Route                          | JSON body                          | Result                               | Session      |
| ------------------------------ | ---------------------------------- | ------------------------------------ | ------------ |
| `POST /auth/sign-up`           | `{ email, password, displayName }` | `{ user, session }`                  | Issued       |
| `POST /auth/login`             | `{ email, password }`              | `{ user, session }`                  | Issued       |
| `POST /auth/current`           | none                               | The User                             | Required     |
| `POST /auth/refresh`           | none                               | `{ user, session }` with a new token | Rotated      |
| `POST /auth/logout`            | none                               | `{ revoked: true }`                  | Ended        |
| `POST /auth/logout-everywhere` | none                               | `{ revoked: true }`                  | All ended    |
| `POST /auth/list-sessions`     | none                               | `{ sessions }`                       | Required     |
| `POST /auth/revoke-session`    | `{ id }`                           | `{ revoked: true }`                  | Required     |
| `POST /auth/change-password`   | `{ currentPassword, newPassword }` | `{ changed: true }`                  | Kept         |
| `POST /auth/reauthenticate`    | `{ password }`                     | `{ reauthenticated: true }`          | Required     |
| `POST /auth/delete-account`    | none                               | `{ deleted: true }`                  | Recent login |

Responses are `{ "result": … }`. Send the token as
`Authorization: Bearer <token>`. With `http: { cookie: { name: '__Host-todo-session' } }`,
the same routes answer browser requests (they send `Origin`) with a `Secure`,
`HttpOnly`, host-only cookie instead of the token; enable
`httpPlugin({ browser: { origins: ['https://app.example.com'], credentials: true } })`.
Browser requests need JSON and an allowed origin; Bearer and the cookie
together are rejected.

Every operation is also public (ADR-0324): GraphQL exposes `signUp`, `login`,
`current`, `refresh`, `logout` and the account fields, the payload's `user`
being your User type; REST exposes them under `/api/operations/<name>`. Hide
them per transport, for example
`restPlugin({ hide: [...Object.values(authOperations), ...Object.values(passwordOperations)] })`.

## Troubleshooting

- **Sign-up rejects the input:** read `details.fields`; include required User
  fields such as `displayName` and check the email and password rules.
- **Valid credentials fail with a profile error:** allow the authenticated User
  to read its own profile, and inspect Access and ACL filters.
- **Login answers 429:** attempt limiting locked the account or address; retry
  after `Retry-After`.
- **`deleteAccount` fails with `AUTH_REAUTHENTICATION_REQUIRED`:** call
  `reauthenticate({ password })` first.
- **A token stops working after refresh or a password change:** use the new
  token; refresh and `revokeOnPasswordChange` invalidate the old sessions.
- **Cookie login fails:** check HTTPS, the exact origin, the credentialed
  browser policy, the JSON content type, and the absence of a Bearer header.
- **`authPlugin needs one User schema`:** declare it with
  `App.UserSchema.define()` and register it in `schemas`.

The `/auth` routes map `AUTH_SIGN_UP_REJECTED` to **400**,
`AUTH_INVALID_CREDENTIALS` and `AUTH_INVALID_SESSION` to **401**,
`AUTH_REAUTHENTICATION_REQUIRED` to **403**, `AUTH_NOT_FOUND` to **404**,
`AUTH_LAST_METHOD` to **409** and `AUTH_TOO_MANY_ATTEMPTS` to **429**; REST
answers **400** for these declared errors and GraphQL returns their codes. An
invalid, expired or revoked token is rejected by HTTP before dispatch as
`HTTP_APPLICATION_REJECTED`; missing credentials leave a request anonymous. A
session never grants permission or elevates authority.
