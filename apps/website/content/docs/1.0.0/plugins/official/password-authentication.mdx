## Overview

`@ultimabase/password-auth-plugin` owns one local User identity domain,
Argon2id password verifiers, and revocable sessions per application. The User
schema is public to server Query and Typegen; credential and session records
stay in owner-private storage. Importing the package alone installs nothing.

A valid session adds a principal and session to the request. It does **not**
grant schema access, roles, ACL rights, or Master authority; configure
[Access](./access) or [Object ACLs](./acl-permissions) separately.

## Installation

You need a database provider and a configured, audited
[Master Authority](/docs/1.0.0/core/security-foundations/master-authority).
Sign-up uses that authority temporarily to create a User. Install Password
Authentication in the application project:

```bash tab="npm" tab-group="package-manager"
npm install @ultimabase/password-auth-plugin
```

```bash tab="yarn"
yarn add @ultimabase/password-auth-plugin
```

```bash tab="pnpm"
pnpm add @ultimabase/password-auth-plugin
```

[HTTP](./http) is optional for direct server operations, but required when
you enable cookie routes. REST or GraphQL exposure is configured separately.

## Configuration

The plugin supplies a default User schema. Define a custom one only when you
need extra public fields, as this example does. Use a **disposable development
database** here: PostgreSQL's `override` policy can create or alter both
application and owner-private tables. Do not use it on shared or production
data without a reviewed schema and recovery plan. Keep the database URL and
Master key in a secret store or process environment, never in source code.

```ts title="src/ultimabase.ts"
import { MasterAuthority, UltimaBase } from '@ultimabase/core'
import {
	PasswordUserSchema,
	passwordAuthPlugin,
} from '@ultimabase/password-auth-plugin'
import { postgresPlugin } from '@ultimabase/postgres-plugin'

const databaseUrl = process.env.DATABASE_URL
const masterKey = process.env.ULTIMABASE_MASTER_KEY
if (databaseUrl === undefined || masterKey === undefined) {
	throw new TypeError('Database URL and Master key are required')
}

const AppUser = PasswordUserSchema.define({
	className: 'User',
	fields: (field) => ({
		displayName: field.string(),
	}),
})

export const ultimabase = new UltimaBase({
	masterAuthority: new MasterAuthority({
		keys: [{ id: 'server', value: masterKey }],
		onUse: (event) => {
			console.info('Master use', event.reason)
		},
	}),
	plugins: [
		postgresPlugin({ schemaPolicy: 'override', url: databaseUrl }),
		passwordAuthPlugin({ user: AppUser }),
	],
	schemas: [],
})
```

| Option        | Purpose                                                                                                         |
| ------------- | --------------------------------------------------------------------------------------------------------------- |
| `user`        | Selects a custom `PasswordUserSchema`; omit it for the built-in User schema.                                    |
| `password`    | Bounds Argon2id memory, passes, lanes, and policy version; raise `policyVersion` when changing hash parameters. |
| `session`     | Configures rolling expiry (seven days by default) and absolute expiry (thirty days by default).                 |
| `http.cookie` | Adds secure cookie routes; requires a compatible HTTP plugin and browser policy.                                |

Do not add password or session fields to the public User schema. The default
Argon2id policy uses 65,536 KiB memory, three passes, four lanes, and a
fresh salt. Changes to these values need a reviewed resource budget and
an increased `policyVersion`. See [PostgreSQL](./postgresql) for schema policies.

### Optional secure cookies

Bearer sessions need no cookie routes. To opt in, configure a host-only
`__Host-` cookie and install the [HTTP](./http) plugin in the same application:

```ts title="src/ultimabase.ts"
passwordAuthPlugin({
	user: AppUser,
	http: { cookie: { name: '__Host-notes-session', sameSite: 'lax' } },
})
```

The HTTP browser policy must allow credentials from exact origins and include
`POST`, `Content-Type`, and `X-UltimaBase-Application-Id`. Cookie routes reject
requests without a matching `Origin` and exact `application/json` content type.
They require HTTPS for a `Secure` cookie; do not treat a local HTTP preview as
proof that browser cookies work.

## Behavior and limitations

### Operations and sessions

After `await ultimabase.start()`, the four transport-neutral operations are
`signUp`, `login`, `logout`, and `refresh`. They remain private until their
exact operation tokens are selected by REST or GraphQL. Sign-up performs one
audited temporary Master elevation; the resulting session still has anonymous
Core authority.

```ts title="src/sign-up.ts"
import { passwordAuthOperations } from '@ultimabase/password-auth-plugin'

import { ultimabase } from './ultimabase.js'

export const signUp = (username: string, password: string) =>
	ultimabase.operation(passwordAuthOperations.signUp).execute({
		username,
		password,
	})
```

Tokens start with `ub_s1.`, contain 32 random bytes, and are stored only as
SHA-256 digests. Rolling expiry defaults to seven days with a thirty-day
absolute ceiling. Refresh rotates the token atomically; logout revokes the
current session.

### HTTP credentials

Over HTTP, send exactly one `Authorization: Bearer <token>` by default.
Invalid, expired, revoked, or foreign-application tokens fail before route
dispatch. Cookie mode is opt-in, requires exact allowed origins with
credentials, and provides `Secure`, `HttpOnly`, host-only `__Host-` cookies.
Bearer and cookie credentials on one request are rejected as ambiguous.
V1 has no recovery, MFA, device list, logout-all, automatic refresh, or rate
limiter.

## Troubleshooting

If sign-up fails before User creation, verify that the selected application
has a configured Master key and an audit callback, then inspect sanitized
server diagnostics. If startup reports schema preparation failure, review
the proposed change and database permissions; do not retry `override`
against shared data without a recovery plan.

If a session is rejected, check that it belongs to the same application and
has not expired or been revoked. Do not log raw tokens or passwords. If a
valid session still cannot read or write a schema, inspect Access or ACL:
authentication adds identity, not permission. For cookie failures, check the
HTTP browser policy, exact `Origin`, JSON content type, and whether the
request accidentally sends both cookie and Bearer credentials.
