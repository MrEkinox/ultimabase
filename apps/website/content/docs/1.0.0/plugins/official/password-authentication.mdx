## Overview

`@ultimabase/auth-plugin` is the authentication foundation: it adds
`App.UserSchema`, sessions shared by every sign-in method, the current
principal, linked accounts, attempt limiting, account events, and the
authentication routes under one HTTP prefix. Sign-in methods are separate
packages; `@ultimabase/auth-password` is the password method. Register with
`Member.signUp()`, log in with `Member.login()`, and use the returned
session for authenticated requests.

Authentication establishes identity and grants no
authorization. Configure [Access](./access) or [Object ACLs](./acl-permissions)
for authorization; Core authority remains `anonymous` in an authenticated
request.

Every TypeScript block on this page is copied from the
[auth example](https://github.com/MrEkinox/ultimadatabase/tree/main/examples/auth),
a small notes backend whose tests check each result described here.

## Installation

Start from a working UltimaBase application with a database provider. Packages
are pre-release; follow [Manual Installation](/docs/1.0.0/manual-installation)
for the project layout. These are the intended registry commands once the
packages are published:

```bash tab="npm" tab-group="package-manager"
npm install @ultimabase/auth-plugin @ultimabase/auth-password
```

```bash tab="yarn"
yarn add @ultimabase/auth-plugin @ultimabase/auth-password
```

```bash tab="pnpm"
pnpm add @ultimabase/auth-plugin @ultimabase/auth-password
```

Sign-up needs no Master key: the plugin creates the User with its own audited
`authority:elevate` privilege. An application may still configure
[Master Authority](/docs/1.0.0/core/security-foundations/master-authority) for
other trusted work. Keep `ULTIMABASE_MASTER_KEY` server-side. Clients never
supply it. Importing the packages alone installs no behavior.

The class name is yours. `password({ identifier: 'email' })` adds a required,
unique `email`, plus `emailVerified` and `emailVerifiedAt`, which no create
or update input accepts (sign-up takes the email beside the create fields);
`identifier: 'username'` (the default) adds `username` instead. Either
identifier is a unique target, so `User.deleteOne({ where: { email } })`
compiles. Do not
declare that field or `password` yourself. The User stays an application
schema: the `access`, `hooks` and other rules of
its `.with` apply like any other, and `App.UserSchema.define` accepts
`indexes` and feature keys (see [Where each declaration goes](/docs/1.0.0/core/data-modeling/schemas#where-each-declaration-goes)). One
`authPlugin` instance owns one User schema; install that instance in every
application registering the User.

Options of `authPlugin({ methods, session, linking, http, events })`:

- `methods`: the sign-in methods, such as `password()`.
- `session.expiresInMs` (seven days by default, from five minutes to thirty
  days): a session expires that long after it is issued or last refreshed;
  using it does not extend it, `refresh()` does.
- `session.absoluteExpiresInMs` (thirty days by default, from one to 365
  days): no refresh extends a session beyond that time after its login.
- `session.revokeOnPasswordChange`: revokes the other sessions after a
  password change; `true` by default.
- `session.recentAuthenticationMs`: how long a login allows sensitive
  operations; five minutes by default.
- `linking`: `'verified-email'` (default) or `'manual'`.
- `http.basePath` (`/api/auth`) and `http.cookie` (`{ name: '__Host-…', sameSite }`).
- `events`: application handlers such as `afterLogin`.

`password({ identifier, policy })` takes Argon2id `memoryCostKiB`, `timeCost`,
`parallelism` and `policyVersion`. Raise `policyVersion` when changing hash
parameters; a successful login upgrades an older verifier. With
`identifier: 'email'`, `reset`, `verification` and `emailChange` enable the
email flows below with your delivery callbacks; the example gives them
`sendEmail`, a test sender that keeps every message in an outbox.

owner recovers the account.

### Security notes

- **Identical answers.** Reset and verification requests answer the same for
  known and unknown addresses: the same limiting (five requests per address
  and email, twenty per email, then growing delays), the same reads, and the
  callback runs after commit, outside the request, so its duration and
  failure never reach the client.
- **Tokens.** 32 random bytes, prefixed by purpose (`ub_r1.`, `ub_v1.`,
  `ub_c1.`); only their SHA-256 digest is stored. A token is single use, a new
  one cancels the previous one of the same purpose, and an expired, used,
  replaced or foreign token fails with `AUTH_INVALID_TOKEN`; failures are
  counted per client address, when one is known. Never log tokens; prefer the
  URL fragment (`#token`), which browsers do not send to servers.
- **Protected fields.** `email`, `emailVerified` and `emailVerifiedAt` appear
  in no create or update input (TypeScript, REST, OpenAPI, GraphQL); only
  these flows write them, Master included. Users are created by sign-up, or
  on the server by `auth.createUser({ data, email })` for seeding.
- **Personal data.** Callbacks receive the User row and the email addresses;
  `afterEmailVerified` and `afterEmailChanged` carry emails. Keep them under
  your privacy policy.

### Attempt limiting

Failures are counted in the database and shared by every server. Per account
and client address, five failures are free, then each one locks that pair for
a delay doubling from one second up to fifteen minutes; per account, twenty
failures are free with the same growth. A success resets both. A locked
attempt fails with `AUTH_TOO_MANY_ATTEMPTS` (HTTP 429 and `Retry-After`)
before any password work. The client address comes from HTTP; outside HTTP,
or when HTTP knows no address (no socket peer and no trusted `X-Forwarded-For`
entry), only the account limit applies. Configure the HTTP plugin's
`trustProxy` behind a proxy, as the example does, and `rateLimit` for a global
per-address limit.

### Linked accounts and events

A user's sign-in methods are private linked accounts, unique per method and
provider identifier; `listMethods()` lists them and a user can never remove
the last one (`unlinkMethod` fails with `AUTH_LAST_METHOD`). With
`linking: 'verified-email'`, a future provider method links a new account to
the user who verified the same email.

<include cwd meta='title="tests/account.test.ts"'>

</include>

The example's `authEvents` write to a security log:

<include cwd meta='title="src/events.ts"'>

</include>

`afterSignUp`, `afterLogin`, `afterLoginFailed`, `afterLogout`,
`afterPasswordReset`, `afterEmailVerified` and `afterEmailChanged` run after
commit, best effort, and never carry a password or token. Events carry the
client address (`null` outside HTTP or when unknown), and `afterLoginFailed`
also carries the normalized identifier the attempt targeted (an email or
username, even for an unknown account) and `limited` when attempt limiting
refused it; email events carry the emails: all are personal data, so store,
retain and forward them under your privacy policy. UltimaBase sends no email
itself.

With the HTTP plugin, every operation is served under one prefix, for Bearer
and cookie alike:

| `POST /api/auth/login`             | `{ email, password }`              | `{ user, session }`                  | Issued       |
| `POST /api/auth/current`           | none                               | The User                             | Required     |
| `POST /api/auth/refresh`           | none                               | `{ user, session }` with a new token | Rotated      |
| `POST /api/auth/logout`            | none                               | `{ revoked: true }`                  | Ended        |
| `POST /api/auth/logout-everywhere` | none                               | `{ revoked: true }`                  | All ended    |
| `POST /api/auth/list-sessions`     | none                               | `{ sessions }`                       | Required     |
| `POST /api/auth/revoke-session`    | `{ id }`                           | `{ revoked: true }`                  | Required     |
| `POST /api/auth/change-password`   | `{ currentPassword, newPassword }` | `{ changed: true }`                  | Kept         |
| `POST /api/auth/reauthenticate`    | `{ password }`                     | `{ reauthenticated: true }`          | Required     |
| `POST /api/auth/delete-account`    | none                               | `{ deleted: true }`                  | Recent login |

`/api/operations/login` then answers 404.

## Troubleshooting

- **Sign-up rejects the input:** read `details.fields`; include required User
  fields such as `displayName` and check the email and password rules. Over
  HTTP, a body without the credentials answers `AUTH_INVALID_REQUEST`.
- **Valid credentials fail with a profile error:** allow the authenticated User
  to read its own profile, and inspect Access and ACL filters.
- **Login answers 429:** attempt limiting locked the account or address; retry
  after `Retry-After`.
- **`deleteAccount` fails with `AUTH_REAUTHENTICATION_REQUIRED`:** call
  `reauthenticate({ password })` first, then retry within
  `session.recentAuthenticationMs`.
- **A token stops working after refresh or a password change:** use the new
  token; refresh and `revokeOnPasswordChange` invalidate the old sessions.
- **A session expires while in use:** using a session does not extend it;
  call `refresh()` before `expiresAt`.
- **Cookie login fails:** check HTTPS, the exact origin, the credentialed
  browser policy, the JSON content type, and the absence of a Bearer header.
- **`authPlugin needs one User schema`:** declare it with
  `App.UserSchema.define()` and register it in `schemas`.
- **A reset or verification request answers 501 `AUTH_NOT_CONFIGURED`:** give
  `password()` the `reset`, `verification` or `emailChange` callbacks.
- **No email arrives:** callbacks run after commit; a failing callback is
  logged by the server and never reaches the client. The address may also
  have no account, or be verified already.
- **`AUTH_INVALID_TOKEN`:** the token expired, was used, was replaced by a
  newer request, or was issued for an email that has changed since.
- **Login answers `AUTH_EMAIL_NOT_VERIFIED`:** `requireVerifiedEmail` is on;
  verify the email or request a new verification token.
- **Writing `email` or `emailVerified` fails:** use the email change flow;
  these fields are written only by authentication.
- **Creating a User fails with `auth.user-creation`:** with an email
  identifier, Users come from sign-up; seed them with
  `ultimabase.plugin(authPlugin).createUser({ data, email })`.

The `/api/auth` routes map `AUTH_INVALID_REQUEST`, `AUTH_SIGN_UP_REJECTED`,
`AUTH_INVALID_TOKEN`, `AUTH_PASSWORD_CHANGE_REJECTED` and
`AUTH_EMAIL_CHANGE_REJECTED` to **400**, `AUTH_INVALID_CREDENTIALS` and
`AUTH_INVALID_SESSION` to **401**, `AUTH_REAUTHENTICATION_REQUIRED` and
`AUTH_EMAIL_NOT_VERIFIED` to **403**, `AUTH_NOT_FOUND` to **404**,
`AUTH_LAST_METHOD` to **409**, `AUTH_TOO_MANY_ATTEMPTS` to **429** and
`AUTH_NOT_CONFIGURED` to **501**; REST answers **400** for these declared
errors and GraphQL returns their codes. An invalid, expired or revoked token
is rejected by HTTP before dispatch as `HTTP_APPLICATION_REJECTED`; missing
credentials leave a request anonymous. A session never grants permission or
elevates authority.
