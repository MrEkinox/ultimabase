## Overview

`@ultimabase/password-auth-plugin` lets you register and authenticate a User
with `AppUser.signUp()` and `AppUser.login()`. Both return a readable User
profile and a session. Use that session for authenticated requests, rotate its
token with `refresh()`, and revoke it with `logout()`.

Authentication identifies the caller; it grants no schema permissions, roles,
ACL rights, or Master authority. Configure [Access](./access) or
[Object ACLs](./acl-permissions) for authorization. Core authority remains
`anonymous` in an authenticated request.

Start with the server-side flow below, then choose [REST](#rest),
[GraphQL](#graphql), or [browser cookies](#browser-cookies) for your client.
Every example uses the same User with a required `displayName`.

## Installation

Start from a working UltimaBase application with a database provider. Packages
are pre-release; follow [Manual Installation](/docs/1.0.0/manual-installation)
for the project layout and the linked repository example. These are the intended registry commands
once the package is published:

```bash tab="npm" tab-group="package-manager"
npm install @ultimabase/password-auth-plugin
```

```bash tab="yarn"
yarn add @ultimabase/password-auth-plugin
```

```bash tab="pnpm"
pnpm add @ultimabase/password-auth-plugin
```

Sign-up also requires configured, audited
[Master Authority](/docs/1.0.0/core/security-foundations/master-authority).
Keep `ULTIMABASE_MASTER_KEY` server-side. The plugin briefly uses it internally
to create the User; clients do not supply it. A failed audit aborts sign-up.
Importing the package alone installs no behavior.

## Configuration

Define your User, install the plugin, and start the application. This example
uses a **disposable development database**: PostgreSQL's `override` policy may
create or alter application and private tables. Keep the database URL and
Master key in your environment.

```ts title="src/user.ts"
import { PasswordUserSchema } from '@ultimabase/password-auth-plugin'

export const AppUser = PasswordUserSchema.define({
	className: 'User',
	fields: (f) => ({
		displayName: f.string({ required: true }),
	}),
})
```

```ts title="src/ultimabase.ts"
import { MasterAuthority, UltimaBase } from '@ultimabase/core'
import { passwordAuthPlugin } from '@ultimabase/password-auth-plugin'
import { postgresPlugin } from '@ultimabase/postgres-plugin'
import { AppUser } from './user.js'

const databaseUrl = process.env.DATABASE_URL
const masterKey = process.env.ULTIMABASE_MASTER_KEY
if (!databaseUrl || !masterKey) {
	throw new Error('DATABASE_URL and ULTIMABASE_MASTER_KEY are required')
}

export const authPlugin = passwordAuthPlugin({ user: AppUser })

export const ultimabase = new UltimaBase({
	masterAuthority: new MasterAuthority({
		keys: [{ id: 'server', value: masterKey }],
		onUse: (event) => {
			// Replace this development sink with your production audit sink.
			console.info('Master use', event.reason)
		},
	}),
	plugins: [
		postgresPlugin({ schemaPolicy: 'override', url: databaseUrl }),
		authPlugin,
	],
	schemas: [AppUser],
})
```

Keep this configuration safe for Typegen to load. For a running HTTP API, use
[Hono's server entry point](./hono-server#start-and-stop-the-managed-listener)
after adding the transport plugins below. For direct server-side scripts, use
the [Manual Installation lifecycle](/docs/1.0.0/manual-installation#start-and-verify):
place the following authentication calls after `await ultimabase.start()`. Use
`await using ultimabase = new UltimaBase(...)` when the application belongs to
one script scope; otherwise always await `ultimabase.dispose()` in `finally`.

The custom `AppUser` stays visible in the root schema list. Password Auth claims
that exact class as plugin-owned and adds a required, unique, immutable
`username`; do not declare that field yourself.
The reserved names `password`, `passwordHash`, `credential`, and `session`
cannot become User fields. Only sign-up creates a login credential; ordinary
User creation does not.

If you need no custom fields, use `passwordAuthPlugin()` and import the built-in
`PasswordUser` for the same account and authentication methods. V1 supports one
Password Authentication instance per application. See [PostgreSQL](./postgresql)
for schema policies and [configuration reference](#configuration-reference)
for password and session options.

## Behavior and limitations

### Register and log in

Call your User class directly in server code. In a script, pass the started
application through `{ ultimabase }`:

```ts title="src/auth-flow.ts"
import { AppUser } from './user.js'
import { ultimabase } from './ultimabase.js'

const signedUp = await AppUser.signUp(
	{
		username: 'Ada',
		password: 'YOUR_PASSWORD_AT_LEAST_15_CHARS',
		displayName: 'Ada Lovelace',
	},
	{ ultimabase },
)

const loggedIn = await AppUser.login(
	{ username: 'Ada', password: 'YOUR_PASSWORD_AT_LEAST_15_CHARS' },
	{ ultimabase },
)
```

Replace the password placeholder with your chosen password. Use a fresh
username when repeating sign-up. Verify that `signedUp.user.username` is `ada`,
that the profile contains `displayName: 'Ada Lovelace'`, and that login returns
the same User ID with a different session token. Never log those tokens.

| Method                       | Input                                          | Successful result                                       |
| ---------------------------- | ---------------------------------------------- | ------------------------------------------------------- |
| `AppUser.signUp()`           | `username`, `password`, and User create fields | `{ user, session, principal }`                          |
| `AppUser.login()`            | Only `username` and `password`                 | `{ user, session, principal }`                          |
| `AppUser.refresh()`          | The current session token                      | `{ user, session, principal }` with a replacement token |
| `AppUser.logout()`           | The current session token                      | `{ revoked: true }`                                     |
| `AppUser.current()`          | Active authenticated request                   | The ordinarily readable User                            |
| `AppUser.changePassword()`   | Current and new passwords                      | `{ changed: true }`                                     |
| `AppUser.logoutEverywhere()` | Active authenticated request                   | `{ revoked: true }`                                     |

Sign-up uses a flat object. Required User fields without defaults must be
provided; optional, defaulted, and generated fields may be omitted. TypeScript
infers these requirements from your declaration without Typegen. The ordinary
creation pipeline validates values and applies defaults and Hooks. The password
never enters User data. Login rejects additional profile fields.

`user` is the current readable User model. `session` contains `id`, `token`,
`expiresAt`, and `absoluteExpiresAt`. Server results also include the typed
`principal`; use `user.id` when you just need the authenticated User ID.

Inside an active request, omit `{ ultimabase }` to use that request's application.
Outside a request, it is required. A foreign User class, conflicting active
application, or application that has not started is rejected. These methods
keep no current user or token on the class and accept no caller Master override.

### Use and manage the session

Sign-up and login each create an independent session. Refresh rotates one
session's token; logout revokes one session. There is no automatic refresh.

Continue the server-side example with the login session:

```ts title="src/auth-flow.ts (continued)"
import { authPlugin } from './ultimabase.js'

const auth = ultimabase.plugin(authPlugin)

const profile = await auth.runWithSession(loggedIn.session.token, () =>
	AppUser.current(),
)

const refreshed = await AppUser.refresh(loggedIn.session.token, { ultimabase })
await AppUser.logout(refreshed.session.token, { ultimabase })
```

`runWithSession()` validates the token and scopes the callback to its application
and identity. It supplies typed `passwordPrincipal` and `passwordSession`
request values. Reads and writes in that callback still obey authorization.
`refresh(token)` and `logout(token)` establish their own session scope.

After refresh, the old token is invalid. Keep the new token for subsequent
requests; the session ID and absolute expiry stay unchanged. After logout,
that session is unusable. The separate sign-up session above remains valid.
Treat tokens as secrets: never put them in URLs or persist them as User fields.

### Change the password or log out everywhere

`current()`, `changePassword()`, and `logoutEverywhere()` identify the User
from the active Password Auth request. They deliberately accept no User ID. In
a direct script, establish that request with `runWithSession()`:

```ts title="src/account-security.ts"
await auth.runWithSession(loggedIn.session.token, async () => {
	const me = await AppUser.current()
	await AppUser.changePassword({
		currentPassword: 'YOUR_PASSWORD_AT_LEAST_15_CHARS',
		newPassword: 'YOUR_NEW_PASSWORD_AT_LEAST_15_CHARS',
	})
	console.info(me.id)
})
```

Password change preserves the session that performs it and invalidates every
other session. The old password can no longer log in. To invalidate the current
session as well as every other device:

```ts
await auth.runWithSession(loggedIn.session.token, () =>
	AppUser.logoutEverywhere(),
)
```

Both transitions are atomic. A concurrent refresh cannot create a usable token
from the invalidated session generation. Password Auth exposes no arbitrary
User target or administrative revocation method.

### Allow the authenticated User to read its profile

A readable User is required for sign-up, login, and refresh to succeed. If you
install Access or ACL policies, allow the authenticated user to read their own
profile. Individual fields can remain restricted. Authentication itself grants
no read permission; see [Access](./access) for policy configuration.

The profile read uses the newly issued identity, never sign-up's temporary
Master elevation or a caller's Master authority. A denied, filtered-out, or
missing profile rolls back the authentication transaction: sign-up leaves no
User or credential, login issues no session, and a failed refresh preserves the
previous token. Refresh reads the profile again, so later changes appear in its
result. Read policy and output restrictions apply normally; the official Hooks
plugin has no read callbacks.

### Choose a client interface

Server-side authentication needs no HTTP plugin. For network requests, install
[HTTP](./http) and a server provider such as [Hono](./hono-server) in the same
application. Then configure the interface your client uses:

| Interface                           | Endpoints                           | How the client sends its session  |
| ----------------------------------- | ----------------------------------- | --------------------------------- |
| [REST](#rest)                       | `/api/v1/auth/*`                    | `Authorization: Bearer <token>`   |
| [GraphQL](#graphql)                 | `/graphql` with Yoga's default path | `Authorization: Bearer <token>`   |
| [Browser cookies](#browser-cookies) | `/auth/v1/*`                        | Browser-managed `HttpOnly` cookie |

For REST and GraphQL, explicitly select the operations you intend to expose:

```ts title="src/auth-operations.ts"
import { passwordAuthOperationList } from '@ultimabase/password-auth-plugin'

export const authOperations = passwordAuthOperationList
```

These tokens configure transports; use `AppUser` methods for ordinary server
calls. Advanced operation handles remain available: their `refresh`, `logout`,
and `logoutEverywhere` inputs are `null` inside a validated session scope.

Before public exposure, configure authorization and review
[public transport protection](/docs/1.0.0/operations/before-exposing-your-application).
REST and GraphQL report `UNVERIFIED_PUBLIC_TRANSPORT_PROTECTION` when protection
is unverified. A session alone does not protect your data. The plugin-owned User
has no automatic generated CRUD routes; private credentials and session records
are never queryable through application schemas, Typegen, REST, GraphQL, Hooks,
or Access.

### REST

Add `restPlugin({ operations: authOperations })` and
`httpPlugin({ appId: 'notes' })` to the application's plugins before starting
it. Import them from `@ultimabase/rest-plugin` and `@ultimabase/http-plugin`;
import `authOperations` from `./auth-operations.js`. Follow the [REST setup](./rest)
for the server and protection configuration.

The following requests assume `http://127.0.0.1:1337` and REST's default `/api`
base path. Use HTTPS for remote credentials. All six actions use `POST`, an
`{ "input": ... }` envelope, and return `200` on success.

```bash title="sign-up.sh"
curl --request POST \
  http://127.0.0.1:1337/api/v1/auth/sign-up \
  --header 'Content-Type: application/json' \
  --header 'X-UltimaBase-Application-Id: notes' \
  --data '{"input":{"username":"Ada","password":"YOUR_PASSWORD_AT_LEAST_15_CHARS","displayName":"Ada Lovelace"}}'
```

Sign-up, login, and refresh share this response shape. IDs, tokens, and dates
below are illustrative placeholders; use values from your actual responses.

```json title="sign-up.response.json"
{
	"result": {
		"user": {
			"id": "USER_ID",
			"username": "ada",
			"displayName": "Ada Lovelace",
			"createdAt": "2026-09-20T12:00:00.000Z",
			"updatedAt": "2026-09-20T12:00:00.000Z"
		},
		"session": {
			"id": "SESSION_ID",
			"token": "SESSION_TOKEN",
			"expiresAt": "2026-09-27T12:00:00.000Z",
			"absoluteExpiresAt": "2026-10-20T12:00:00.000Z"
		}
	}
}
```

REST returns `user` and `session`. It omits restricted profile fields and uses
ordinary schema encodings, including decimal strings for bigint and binary
objects for bytes. Actual session tokens begin with `ub_s1.`.

```bash title="login.sh"
curl --request POST \
  http://127.0.0.1:1337/api/v1/auth/login \
  --header 'Content-Type: application/json' \
  --header 'X-UltimaBase-Application-Id: notes' \
  --data '{"input":{"username":"Ada","password":"YOUR_PASSWORD_AT_LEAST_15_CHARS"}}'
```

Login returns a new session. Copy its token into `LOGIN_SESSION_TOKEN` below.

```bash title="refresh.sh"
curl --request POST \
  http://127.0.0.1:1337/api/v1/auth/refresh \
  --header 'Content-Type: application/json' \
  --header 'X-UltimaBase-Application-Id: notes' \
  --header 'Authorization: Bearer LOGIN_SESSION_TOKEN' \
  --data '{"input":null}'
```

Refresh returns the same shape with a new token and current User profile.
Replace the old token with this returned `REFRESHED_SESSION_TOKEN`:

```bash title="logout.sh"
curl --request POST \
  http://127.0.0.1:1337/api/v1/auth/logout \
  --header 'Content-Type: application/json' \
  --header 'X-UltimaBase-Application-Id: notes' \
  --header 'Authorization: Bearer REFRESHED_SESSION_TOKEN' \
  --data '{"input":null}'
```

Logout returns `{ "result": { "revoked": true } }`. Only that session is revoked.
Send the same application header and Bearer token on other authenticated REST
requests. A custom REST `basePath` changes the `/api` prefix of these auth paths.

Password change and account-wide logout use the authenticated Bearer session:

```bash title="change-password.sh"
curl --request POST \
  http://127.0.0.1:1337/api/v1/auth/change-password \
  --header 'Content-Type: application/json' \
  --header 'X-UltimaBase-Application-Id: notes' \
  --header 'Authorization: Bearer LOGIN_SESSION_TOKEN' \
  --data '{"input":{"currentPassword":"YOUR_PASSWORD_AT_LEAST_15_CHARS","newPassword":"YOUR_NEW_PASSWORD_AT_LEAST_15_CHARS"}}'
```

The response is `{ "result": { "changed": true } }`. The supplied session
remains valid; every other session becomes invalid.

```bash title="logout-everywhere.sh"
curl --request POST \
  http://127.0.0.1:1337/api/v1/auth/logout-everywhere \
  --header 'Content-Type: application/json' \
  --header 'X-UltimaBase-Application-Id: notes' \
  --header 'Authorization: Bearer LOGIN_SESSION_TOKEN' \
  --data '{"input":null}'
```

This returns `{ "result": { "revoked": true } }` and invalidates the supplied
session together with every other session for the same User.

### GraphQL

Add `graphqlPlugin({ operations: authOperations })` to the application's plugins
before startup. Import it from `@ultimabase/graphql-plugin` and use the same
`authOperations` list above. Follow [GraphQL with Yoga](./graphql#serve-graphql-over-http-with-yoga)
for HTTP and server setup. The default endpoint is `POST /graphql`.

Your GraphQL application must expose at least one query field through an
application schema or custom GraphQL schema; Password Authentication contributes
mutations only. Set these headers in your explorer:

```json title="graphql-headers.json"
{
	"Content-Type": "application/json",
	"X-UltimaBase-Application-Id": "notes"
}
```

For an HTTP client, send each document in `query` and its variables in
`variables`. Use a fresh username if you already completed REST sign-up.

```graphql title="sign-up.graphql"
mutation SignUp($input: PasswordAuthSignUpInput!) {
	signUp(input: $input) {
		user {
			id
			username
			displayName
		}
		session {
			id
			token
			expiresAt
			absoluteExpiresAt
		}
	}
}
```

```json title="sign-up.variables.json"
{
	"input": {
		"username": "Ada",
		"password": "YOUR_PASSWORD_AT_LEAST_15_CHARS",
		"displayName": "Ada Lovelace"
	}
}
```

`PasswordAuthSignUpInput` derives the User's create fields and adds `password`.
With this User, omitting `displayName` is a GraphQL input error.

```json title="sign-up.graphql.response.json"
{
	"data": {
		"signUp": {
			"user": {
				"id": "USER_ID",
				"username": "ada",
				"displayName": "Ada Lovelace"
			},
			"session": {
				"id": "SESSION_ID",
				"token": "SESSION_TOKEN",
				"expiresAt": "2026-09-27T12:00:00.000Z",
				"absoluteExpiresAt": "2026-10-20T12:00:00.000Z"
			}
		}
	}
}
```

Login uses a separate credentials-only input and returns the selected fields
under `data.login`:

```graphql title="login.graphql"
mutation Login($input: PasswordAuthCredentialsInput!) {
	login(input: $input) {
		user {
			id
			username
			displayName
		}
		session {
			id
			token
			expiresAt
			absoluteExpiresAt
		}
	}
}
```

```json title="login.variables.json"
{
	"input": {
		"username": "Ada",
		"password": "YOUR_PASSWORD_AT_LEAST_15_CHARS"
	}
}
```

For refresh, add `Authorization: Bearer LOGIN_SESSION_TOKEN` to your headers,
using the token returned by login. Refresh has no input argument:

```graphql title="refresh.graphql"
mutation Refresh {
	refresh {
		user {
			id
			username
			displayName
		}
		session {
			id
			token
			expiresAt
			absoluteExpiresAt
		}
	}
}
```

Read the replacement token from `data.refresh.session.token`, update your
Authorization header to that token, and then run logout:

```graphql title="logout.graphql"
mutation Logout {
	logout {
		revoked
	}
}
```

Logout returns `{ "data": { "logout": { "revoked": true } } }`.
`PasswordAuthPayload` exposes `user` and `session`. Its `user` is non-null;
restricted nullable fields resolve to `null`, and GraphQL's ordinary non-null
propagation applies to denied required fields. Select readable fields. The
profile is an ordinary User read; selections do not eagerly load relationships.
These mutations return tokens in JSON; they do not issue or rotate a cookie.

The account mutations use the same Authorization header:

```graphql title="change-password.graphql"
mutation ChangePassword($input: PasswordAuthChangePasswordInput!) {
	changePassword(input: $input) {
		changed
	}
}
```

```graphql title="logout-everywhere.graphql"
mutation LogoutEverywhere {
	logoutEverywhere {
		revoked
	}
}
```

### Browser cookies

Cookie mode provides dedicated `/auth/v1/*` endpoints and stores the token in a
`Secure`, `HttpOnly`, host-only `__Host-` cookie. It requires HTTPS and an explicit
credentialed browser-origin policy. You do not need REST or GraphQL to use these
endpoints.

Replace the Password Authentication entry in your application with the
configured one below and add the HTTP entry. Retain the same `AppUser`, database,
Master authority, and server provider:

```ts title="src/cookie-auth.ts"
import { httpPlugin } from '@ultimabase/http-plugin'
import { passwordAuthPlugin } from '@ultimabase/password-auth-plugin'
import { AppUser } from './user.js'

export const cookieAuth = passwordAuthPlugin({
	user: AppUser,
	http: { cookie: { name: '__Host-notes-session', sameSite: 'lax' } },
})

export const cookieHttp = httpPlugin({
	appId: 'notes',
	browser: {
		allowedHeaders: ['Content-Type', 'X-UltimaBase-Application-Id'],
		allowedMethods: ['GET', 'POST'],
		allowedOrigins: ['https://app.example.com'],
		credentials: true,
		maxAgeSeconds: 600,
	},
})
```

Keep one Password Authentication instance and one matching HTTP configuration.
The browser policy must allow exact origins, credentials, `POST`, and the two
headers above; incompatible configuration fails startup. See [HTTP](./http)
for mounting the HTTPS application.

| Endpoint                          | JSON body                                           | Successful effect                          |
| --------------------------------- | --------------------------------------------------- | ------------------------------------------ |
| `POST /auth/v1/sign-up`           | `{ username, password, displayName }` for this User | Creates User and session; sets the cookie  |
| `POST /auth/v1/login`             | `{ username, password }`                            | Creates a new session; sets the cookie     |
| `POST /auth/v1/refresh`           | No body                                             | Rotates the session and cookie             |
| `POST /auth/v1/logout`            | No body                                             | Revokes the session and expires the cookie |
| `POST /auth/v1/change-password`   | `{ currentPassword, newPassword }`                  | Changes the password; keeps this cookie    |
| `POST /auth/v1/logout-everywhere` | No body                                             | Revokes all sessions; expires the cookie   |

Use a direct JSON object for sign-up, login, and password change. Refresh,
logout, and logout everywhere still require `Content-Type: application/json`,
even with no body. For example:

```ts title="src/client-auth.ts"
const authUrl = 'https://api.example.com/auth/v1'
const headers = {
	'Content-Type': 'application/json',
	'X-UltimaBase-Application-Id': 'notes',
}

export const signUp = (
	username: string,
	password: string,
	displayName: string,
) =>
	fetch(`${authUrl}/sign-up`, {
		method: 'POST',
		credentials: 'include',
		headers,
		body: JSON.stringify({ username, password, displayName }),
	})

export const login = (username: string, password: string) =>
	fetch(`${authUrl}/login`, {
		method: 'POST',
		credentials: 'include',
		headers,
		body: JSON.stringify({ username, password }),
	})

export const logout = () =>
	fetch(`${authUrl}/logout`, {
		method: 'POST',
		credentials: 'include',
		headers,
	})

export const changePassword = (currentPassword: string, newPassword: string) =>
	fetch(`${authUrl}/change-password`, {
		method: 'POST',
		credentials: 'include',
		headers,
		body: JSON.stringify({ currentPassword, newPassword }),
	})

export const logoutEverywhere = () =>
	fetch(`${authUrl}/logout-everywhere`, {
		method: 'POST',
		credentials: 'include',
		headers,
	})
```

Sign-up, login, and refresh set the cookie and return the following **cookie
response**, which differs from the REST and GraphQL payloads:

```json title="cookie-auth.response.json"
{
	"result": {
		"principal": {
			"user": { "type": "pointer", "className": "User", "id": "USER_ID" }
		},
		"session": {
			"id": "SESSION_ID",
			"expiresAt": "2026-09-27T12:00:00.000Z",
			"absoluteExpiresAt": "2026-10-20T12:00:00.000Z"
		}
	}
}
```

There is no raw token or User profile in this JSON. The browser sends the cookie
on later requests with `credentials: 'include'`. Password change returns
`{ "result": { "changed": true } }` without replacing the current cookie.
Logout and logout everywhere return `{ "result": { "revoked": true } }` and
expire the cookie.

The browser supplies `Origin`. Every cookie endpoint and unsafe application
request authenticated by the cookie requires an allowed origin and exact
`application/json` content type. Sending both Bearer and the configured cookie
is rejected as ambiguous.

A stale cookie is ignored only on cookie sign-up and login, allowing a browser
to replace an expired or revoked cookie. Refresh, logout, and other application
routes still reject invalid cookies. Bearer remains strict on every route.
This is session-cookie recovery, not password recovery.

### Configuration reference

- `user`: your exact `PasswordUserSchema`; defaults to the built-in
  `PasswordUser`.
- `password`: Argon2id `memoryCostKiB`, `timeCost`, `parallelism`, and
  `policyVersion`.
- `session.expiresInMs`: rolling lifetime; seven days by default.
- `session.absoluteExpiresInMs`: absolute lifetime; thirty days by default and
  at least the rolling lifetime.
- `http.cookie`: enables the dedicated secure-cookie endpoints.

Session lifetimes are integer milliseconds. The default password hash uses
Argon2id v19 with 65,536 KiB memory, three passes, four lanes, and a fresh salt.
Raise `policyVersion` when changing hash parameters. Successful login upgrades
an older verifier without downgrading a newer one. Budget memory for concurrent
login attempts.

Usernames are trimmed, Unicode-normalized, and lowercased. Their canonical form
must have 3–64 Unicode code points, start and end with a letter or number, and
contain only letters, numbers, `.`, `_`, or `-`. Email addresses are not v1
usernames. Passwords are Unicode-normalized but never trimmed or case-changed;
they must have 15–256 code points. Do not pre-trim them in your application.

V1 has no password recovery, MFA, administrative session revocation, automatic
refresh, or built-in rate limiter. Configure online-attempt protection before
exposing login publicly.

### Migrating earlier authentication examples

- **Class methods:** prefer `AppUser.signUp()`, `login()`, `refresh(token)`,
  `logout(token)`, `current()`, `changePassword()`, and `logoutEverywhere()`.
  Low-level operation handles remain available for advanced use.
- **Sign-up input:** supply required User create fields beside credentials.
  GraphQL sign-up now uses `PasswordAuthSignUpInput`; login retains
  `PasswordAuthCredentialsInput`.
- **REST paths:** replace `/api/v1/operations/ultimabase.password-auth.*` with
  `/api/v1/auth/sign-up`, `/login`, `/refresh`, `/logout`, `/change-password`,
  or `/logout-everywhere` under the auth prefix.
  The old routes are no longer registered.
- **REST/GraphQL results:** use `user.id` instead of `principal.user` or
  `principal { userId }`. `PasswordAuthPrincipal` was removed from GraphQL.
  Server-side results still include `principal`; cookie endpoints retain the
  separate response documented above.

## Troubleshooting

- **Sign-up rejects the input:** include required User fields such as
  `displayName`, and check username and password rules.
- **Sign-up fails before User creation:** check this application's Master
  authority, audit callback, and database setup.
- **Valid credentials fail with a profile error:** allow the authenticated User
  to read its own profile, and inspect Access/ACL filters.
- **Login rejects apparently valid credentials:** check the normalized username,
  untrimmed password, and that the User was created through sign-up.
- **A token stops working after refresh:** replace it with the new token; the
  old one is invalid.
- **An auth route is missing:** select its operation in REST/GraphQL, or enable
  the dedicated cookie routes.
- **Cookie login or refresh fails:** check HTTPS, exact origin, browser policy,
  application ID, JSON content type, and absence of a Bearer header.

REST maps `PASSWORD_AUTH_SIGN_UP_REJECTED` to **400**,
`PASSWORD_AUTH_PASSWORD_CHANGE_REJECTED` to **400**, and
`PASSWORD_AUTH_INVALID_CREDENTIALS` and `PASSWORD_AUTH_INVALID_SESSION` to **401**.
Unknown users, credential-less Users, and wrong passwords share the same login
error to prevent enumeration. Profile failures can return `PERMISSION_DENIED`
(**403**) or `NOT_FOUND` (**404**); they issue no session or committed rotation.

An invalid, expired, revoked, or foreign-application token is normally rejected
by HTTP before dispatch as `HTTP_APPLICATION_REJECTED`. The plugin's
`PASSWORD_AUTH_INVALID_SESSION` describes a failure during refresh, logout,
password change, or logout-everywhere execution. Missing credentials leave a request anonymous. A session never grants
permission or elevates authority; inspect [Access](./access) and
[Object ACLs](./acl-permissions) when authenticated application requests are denied.
