## Overview

`@ultimabase/hono-server-plugin` connects an UltimaBase HTTP application to
Hono on Node.js. It can own a listener or mount onto an existing Hono app. The
[HTTP plugin](./http) owns application identity, request boundaries, and
browser policy; Hono supplies the server. Neither plugin creates REST or
GraphQL routes. Install a [REST](./rest) or [GraphQL](./graphql) transport when
you need one.

The code on this page comes from the tested
[HTTP example](https://github.com/MrEkinox/ultimadatabase/tree/main/examples/http),
whose tests run both listener modes over real sockets.

## Installation

These packages are pre-release. Use the locally built repository example linked
from [Manual Installation](/docs/1.0.0/manual-installation) to evaluate the
current code; the registry commands below describe installation after publication.

Install the Hono server provider alongside the [HTTP plugin](./http):

```bash tab="npm" tab-group="package-manager"
npm install @ultimabase/hono-server-plugin
```

```bash tab="yarn"
yarn add @ultimabase/hono-server-plugin
```

```bash tab="pnpm"
pnpm add @ultimabase/hono-server-plugin
```

If you supply your own Hono app and start its listener yourself, also install
the packages you import directly:

```bash tab="npm" tab-group="package-manager"
npm install hono @hono/node-server
```

```bash tab="yarn"
yarn add hono @hono/node-server
```

```bash tab="pnpm"
pnpm add hono @hono/node-server
```

## Configuration

Start from the database setup in [Manual Installation](/docs/1.0.0/manual-installation).
`UltimaBase.start()` requires a database provider even when `schemas` is empty;
the examples below use PostgreSQL and `DATABASE_URL`.

Choose one listener owner. With no `app`, UltimaBase creates and starts a Node
listener after the application graph validates. The `apiServer()` preset passes
its `server` options to `honoServerPlugin(server)`:

This serves `/health`, the application and plugin routes, and REST; the
server plugin itself adds no REST or GraphQL route. Without `port`, the managed listener uses the `PORT` environment variable that
most hosting platforms set, then `1337`. Without `host`, it uses the `HOST`
environment variable, then `127.0.0.1` in development and every interface
when `NODE_ENV=production`; the plugin reads these when it is created and an
explicit option always wins. `logLevel: 'debug'` logs the derived address and
its source. Port `0` lets the operating system choose
an ephemeral port for tests; the `ultimabaseTesting()` Vitest preset sets
`PORT=0`. Once started, read the bound address through the
plugin exports; it is `undefined` before start, after stop, and when you pass
your own `app`:

### Start and stop the managed listener

Keep the exported configuration free of startup effects so other modules can
import it. The entry point starts the application, waits for a stop signal and
awaits disposal:

<include cwd meta='title="src/main.ts"'>
	../../examples/http/src/main.ts#main
</include>

The REST and GraphQL guides start from the same kind of entry point. Run the
project's typecheck, build and start scripts after configuring `DATABASE_URL`
and the example's secrets. The process keeps serving until Ctrl+C;
then it awaits application cleanup, including the managed listener and database.
The same disposal runs on SIGTERM, the signal most hosts send before stopping
a process. Do not start another application before that cleanup completes.

`stop()` and `dispose()` refuse new requests, wait at most `shutdownTimeoutMs`
(10 seconds by default; 5 in the example) for in-flight ones, then close the
remaining connections. `compression: true` compresses responses with gzip or
deflate; it is off by default because proxies and CDNs usually compress.

To join an existing Hono app instead, pass that `app`. You start and stop the
listener yourself. The example's second application installs the plugins one

`shutdownTimeoutMs` are not Hono plugin options; configure them on your own

## Behavior and limitations

### Run one active application

One JavaScript realm may initialize one UltimaBase application. After UltimaBase stops, its routes reject requests
through the safe HTTP boundary while ordinary Hono routes and the external
listener remain available. A second
application fails before opening a listener, even if it reuses the same
`honoServerPlugin()` value. Await complete disposal before replacement.
Run simultaneous applications in separate processes, workers, or containers.
An existing Hono app can keep its ordinary routes alongside its single
UltimaBase application.

### Choose one browser-policy owner

With an existing app, `browserPolicyOwner` is required only when
`httpPlugin({ browser })` enables CORS. Choose `'ultimabase'` to use the
[HTTP browser policy](./http#browser-policy). Choose `'external'` when existing
middleware already owns CORS, and leave the HTTP `browser` policy disabled.
UltimaBase rejects conflicting ownership rather than combining CORS headers.
Browser preflight selects no application.

### Keep the boundary intact

The existing-app Node integration must expose Hono's standard
`incoming.rawHeaders` binding. UltimaBase uses that evidence to reject
duplicate sensitive headers before application identity and fails closed if
the evidence is missing, with a message naming the fix. CORS is not
authentication, authorization, or CSRF protection. TLS and HTTP/2 come from
the proxy or platform; proxy trust, rate limits and security headers are
[HTTP plugin](./http) options; REST, GraphQL and authentication are separate
plugins. Servers for Bun, Deno and Workers are not provided yet.

## Troubleshooting

If startup reports an address conflict, check whether another listener owns
the fixed host and port. For another simultaneous application, use a separate process and address;
two independently created managed providers do not share a socket.

If initialization reports another active application, await that application’s
`dispose()` before starting its replacement. Use a separate worker or process
when both applications must run at the same time.
If an existing Hono app rejects requests before routing, verify its Node
integration supplies `incoming.rawHeaders` and that CORS has exactly one
owner. For application identity, credentials, or `HTTP_*` errors, continue at
[HTTP troubleshooting](./http#troubleshooting). A 404 with no REST or GraphQL
transport installed is expected: the server plugin does not add API routes.
