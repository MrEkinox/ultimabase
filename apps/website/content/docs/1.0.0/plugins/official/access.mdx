## Overview

`@ultimabase/access-plugin` adds the official authorization engine to an
application. It owns schema and field `access` rules: which operations may run,
which rows they may reach, which prepared items pass, and how fields may be read
or written. Importing the package alone does nothing; install `accessPlugin()`
in each application that uses these rules.

Access does not authenticate callers. [Password Authentication](./password-authentication)
can provide an identity, and [Roles](./roles) can resolve membership, but
neither grants access on its own. [Object ACLs](./acl-permissions) are a separate,
persisted per-object policy that works with or without this plugin.

## Installation

Start with an UltimaBase application and a database provider. Install the
optional Access package:

```bash tab="npm" tab-group="package-manager"
npm install @ultimabase/access-plugin
```

```bash tab="yarn"
yarn add @ultimabase/access-plugin
```

```bash tab="pnpm"
pnpm add @ultimabase/access-plugin
```

## Configuration

Declare a policy on the schema it protects. This example permits reads of
published articles, hides `internalNote`, and denies every mutation to ordinary
callers:

```ts title="src/application.ts"
import { accessPlugin } from '@ultimabase/access-plugin'
import { UltimaBase } from '@ultimabase/core'
import { postgresPlugin } from '@ultimabase/postgres-plugin'

const databaseUrl = process.env.DATABASE_URL
if (!databaseUrl) throw new Error('DATABASE_URL is required')

export const Application = UltimaBase.use(
	postgresPlugin({ url: databaseUrl }),
).use(accessPlugin())
```

```ts title="src/article.ts"
import { Application } from './application.js'

export const Article = Application.Schema.define({
	className: 'Article',
	fields: (f) => ({
		internalNote: f.string({
			access: { read: false, write: false },
		}),
		published: f.boolean({ default: false }),
		title: f.string({ required: true }),
	}),
	access: {
		read: ({ where }) => where.eq('published', true),
	},
})
```

Install the plugin alongside the database provider and register the schema:

```ts title="src/ultimabase.ts"
import { Application } from './application.js'
import { Article } from './article.js'

export const ultimabase = new Application({
	schemas: [Article],
})
```

Keep startup in the existing entry point from
[Manual Installation](/docs/1.0.0/manual-installation#start-and-verify): await
`ultimabase.start()` there and always await `dispose()` when the process finishes.
This configuration module stays safe to load for static Typegen generation.

The installed engine denies every operation that has no schema rule. In this
example, the `read` rule covers all four read operations and returns a private
row filter that limits them to published rows. Create, update, upsert, and
delete have no rule, so they remain denied. A normal result omits `internalNote`, while
an explicit selection, filter, or sort using it is rejected. Audited Master
requests bypass these Access restrictions.

The configured factory exposes field `access` directly from source. Schema
`access` callbacks use the retained Typegen graph so items, row filters,
relationships, and plugin mutation keys stay exact; regenerate after changing
that application graph. JavaScript uses the same compiled policy without
loading generated declarations.

## Behavior and limitations

### One rule per operation

Each operation has at most one schema rule, evaluated before any row is
loaded (ADR-0317). It is `true` (every row), `false` (no row), or a function
that returns one of them or a row filter built with the typed `where` builder.
A function that may return nothing is a type error, so a forgotten branch can
never open every row.

| Schema key  | Applies to                                                                         | Rule                                                         |
| ----------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| `read`      | `one` (`findOne` and `findOneOrThrow`), `many` (`findMany`), `count`, and `exists` | `true`, `false`, a filter, or `{ one, many, … }`             |
| `create`    | Singular and itemized bulk creates                                                 | `true`, `false`, a predicate, or `{ where, item }`           |
| `update`    | Singular and itemized bulk updates                                                 | `true`, `false`, a filter, or `{ where, item }`              |
| `upsert`    | Singular and itemized bulk upserts                                                 | `true`, `false`, a filter, or `{ where, item }`              |
| `delete`    | Singular and itemized bulk deletes                                                 | `true`, `false`, a filter, or `{ where, item }`              |
| plugin keys | Request commands such as `softDeleteOne`, permissions such as `readDeleted`        | Commands like `update`; permissions `true`/`false`/predicate |

`read` takes one rule for its four operations, or an object whose members
`one`, `many`, `count` and `exists` are each optional:

```ts title="src/count-only-article.ts"
import { Application } from './application.js'

export const CountOnlyArticle = Application.Schema.define({
	className: 'CountOnlyArticle',
	fields: (f) => ({ title: f.string({ required: true }) }),
	access: { read: { count: true } },
})
```

With plain `accessPlugin()`, `count` is allowed while `one`, `many`, and
`exists` stay denied: an omitted member has no schema rule.

### Operations without a rule: `allowWithoutRule`

Without a schema rule an operation is denied, unless the plugin's
`allowWithoutRule` option opens it for every schema that has no rule for it:

```ts
accessPlugin({ allowWithoutRule: { all: true, write: false } })
accessPlugin({
	allowWithoutRule: { read: true, count: false, write: isAuthenticated },
})
accessPlugin({ allowWithoutRule: { all: 'development' } })
```

- **Keys:** `all`; the groups `read` (`one`, `many`, `count`, `exists`) and
  `write` (`create`, `update`, `upsert`, `delete` and request plugin commands);
  each operation or plugin command key alone (`softDeleteOne`). An operation
  key wins over its group, a group over `all`, and a schema rule always wins.
  A plugin permission (`readDeleted`) is opened only by its own key, never by
  `all`, `read` or `write`.
- **Values:** `true` opens everywhere, production included; `'development'`
  opens outside production, and in production `start()` fails with a message
  naming the operations; a `PolicyPredicate` such as `isAuthenticated` opens
  when it allows (it receives the principal, operation and schema, never a
  row filter, since it applies to every schema); `false` or an absent key
  keeps the operation denied.

After `start()`, Access logs one `warn` line per opening, production
included, naming predicates, and one `info` line listing the schemas that have
no Access rule at all (they are fully denied unless an opening applies). An
opening of `write` is an explicit policy: Access is installed, so public
transports never ask for a separate acknowledgment of public writes.

### Detailed mutations: `where` and `item`

A mutation can also take `{ where, item }`. `where` is the same operation
rule (for `create`, a boolean decision, since nothing is loaded); `item` runs
on stable, prepared values and returns a boolean:

| Member  | Available on                             | Checks                                                                           |
| ------- | ---------------------------------------- | -------------------------------------------------------------------------------- |
| `where` | Create, update, upsert, delete, commands | The operation rule: every row, no row, or a private row filter combined by `AND` |
| `item`  | Create, update, upsert, delete, commands | A prepared draft, locked original, or final candidate according to the operation |

For example, an update can reach only unlocked rows and can keep a published
article's title unchanged:

```ts title="src/editable-article.ts"
import { Application } from './application.js'

export const EditableArticle = Application.Schema.define({
	className: 'EditableArticle',
	fields: (f) => ({
		locked: f.boolean({ default: false }),
		published: f.boolean({ default: false }),
		title: f.string({ required: true }),
	}),
	access: {
		update: {
			where: ({ where }) => where.eq('locked', false),
			item: ({ item, originalItem }) =>
				!originalItem.published || item.title === originalItem.title,
		},
	},
})
```

A filter object takes the same equality shorthand as a query
(`({ where }) => where.eq('locked', false)` or `() => ({ locked: false })`).
Row rules also constrain mutation targets; a target outside the visible row
universe cannot be reached by changing the caller's predicate. For upsert,
`item` also receives `mode` (`create` or `update`); update and upsert-update
receive `originalItem`.

### Request-aware decisions

Every rule callback receives the request `principal` resolved by Core (a
pointer to the authenticated identity, `undefined` when anonymous), the policy
`operation` key, the `schema` class name and the request `context`. Because a
rule receives that policy context, a Core
[`PolicyPredicate`](/docs/1.0.0/core/security-foundations/request-identity#policy-predicates)
such as `isAuthenticated` is accepted wherever a rule returns a decision:

```ts title="src/private-note.ts"
import { isAuthenticated } from '@ultimabase/core'
import { Application } from './application.js'

export const PrivateNote = Application.Schema.define({
	className: 'PrivateNote',
	fields: (f) => ({
		author: f.string({ required: true }),
		body: f.string({ required: true }),
	}),
	access: {
		create: isAuthenticated,
		read: ({ principal, where }) =>
			principal === undefined ? false : where.eq('author', principal.id),
	},
})
```

`isAuthenticated` alone allows any authenticated caller; the `read` rule
denies anonymous callers and makes notes private to their author. A rule never imports the authentication
plugin: the [Password Authentication](./password-authentication) page explains
how a session becomes the principal, and [Roles](./roles) documents the
`hasRole()` predicate. A rule or predicate that throws rejects the operation;
throw a [`PublicError`](/docs/1.0.0/core/runtime/api-errors#publicerror) to
tell the client why.

If you also expose a `find` route for this schema through [REST](./rest),
verify the boundary with three requests: an anonymous read returns `403`
`PERMISSION_DENIED`, a valid Password Authentication Bearer session returns
`200` with a `results` collection, and a revoked session returns `401`
`HTTP_APPLICATION_REJECTED` before Access runs. The Bearer token establishes
identity; this Access rule grants the read. A successful read does not imply
per-user row isolation.

### Field read and write rules

An undeclared field is available unless an exact field rule or compatible
provider narrows it. Put `access` on a stored field, embedded property, or
virtual field. For a virtual field, the rule protects the logical field as a
whole, not individual properties inside its output descriptor.

| Field rule                         | Effect                                                                                                     |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `read: false`                      | Denies output, `where`, and `orderBy` together                                                             |
| `read: { output, where, orderBy }` | Controls those three disclosure paths separately; an omitted member restricts nothing                      |
| `write: false`                     | Denies fills, replacements, and clears together                                                            |
| `write: { fill, replace, clear }`  | Controls null-to-value, value-to-value, and value-to-null transitions; an omitted member restricts nothing |

For example, `read: { where: false, orderBy: false }` permits displaying a
field but not using it to infer information through filtering or ordering.
`write: { replace: false, clear: false }` permits its first non-null value but
prevents later replacement or clearing. Field callbacks
receive the request `principal` and `context`; value-aware callbacks receive
the relevant `value` or `originalValue`.

A denied output field is omitted from ordinary results. Explicitly selecting
it fails with `PERMISSION_DENIED`, as does an unauthorized filter, order, or
write. Relation fields use `access.read` for traversal and `access.write` for
logical edge changes; nested writes check the source relation before running
each child's own Access policy. See [Related Data](/docs/1.0.0/core/reading-data/related-data)
and [Nested Writes](/docs/1.0.0/core/writing-data/nested-writes) for those
operations.

### Plugin commands, plugin permissions and policy composition

A plugin-owned request command, such as [Soft Delete](./soft-delete)'s
`softDeleteOne`, has its own exact schema `access` key with the same forms as
`update`; its `input` is available to the rule. It does not inherit `update`
or `delete` permission merely because its physical effect is an update or
delete. Without a rule, its own `allowWithoutRule` key, then `write`, then
`all` decide. Master-only commands have no Access key and never become public.

A plugin can also declare a named schema permission, such as Soft Delete's
`readDeleted`. Access grants it through a rule of the same name (`true`,
`false` or a predicate: `readDeleted: hasRole(Admin)`) or through its own
`allowWithoutRule` key; `all`, `read` and `write` never include it. Core asks
every installed policy, holds the permission only when one grants it and none
refuses it, and Master always holds it. Neither Access nor the declaring
plugin imports the other.

Compatible provider contributions join schema decisions through logical
`AND`; private row filters also join through `AND`, and field restrictions
intersect. A provider cannot turn a denial into a grant. [Object ACLs](./acl-permissions)
use Core's independent protected-policy boundary and compose with Access
without depending on it. Authentication and role membership supply facts for
rules; they do not authorize an operation by themselves.

### Mutation results obey read rules

The result of a create, update, upsert or delete obeys the row `read` rules,
like PostgreSQL's `RETURNING` under row-level security: before commit, Core
checks each resulting row (the locked pre-image for a delete) against every
installed read policy. When a row is not readable and the call selects
anything beyond `id` (no `select`, another field, or any `include`), it fails
with `PERMISSION_DENIED` and nothing is written. `select: { id: true }` is
always allowed, so a write-only client (for example `read: false`) asks for
the identifier alone:

```ts title="src/audit.ts"
await AuditEntry.createOne({
	data: { action: 'login' },
	select: { id: true },
})
```

Collection commands are atomic, Master skips the check, and field rules keep
their behavior.

### Links obey read rules

Linking a row is reading it: each target named by `connect` or `set`, in a
singular, nested or collection command, must be visible to the caller as a
single-row (`one`) read under every installed policy, and `disconnect` names
only visible linked targets. A hidden target fails with the same `NOT_FOUND`
as a missing one, naming the field and target schema, so a link never reveals
that a row exists (ADR-0308). Master skips visibility but still fails on a
missing target. Use `ultimabase.can({ operation, schema, item })` to ask
whether an operation would be permitted without executing it.

Access checks run around Core's prepared mutation pipeline, including a
reevaluation after input resolution. A Hook cannot remove accumulated Access
restrictions. Trusted, audited Master authority bypasses the complete official
Access policy, including field rules and compatible-provider callbacks; it
still runs validation, Hooks, transactions, database constraints, and integrity
work. Never expose Master as a substitute for a public policy.

### Denial diagnostics

When Access denies a request, the server logs one line naming the schema, the
operation, the step (`operation`, `row filter`, `item` or `field`) and the
rule that denied, for example
`denied update on Article at the item step (Article.access.update.item)`. The
line is `info` outside production and `debug` in production; clients receive
the same `PERMISSION_DENIED` as before. `ultimabase.can()` answers are not
logged.

## Troubleshooting

- **Every request is denied:** confirm `accessPlugin()` is installed, read the
  denial line in the server log, and check the schema rule or the
  `allowWithoutRule` key that should open the operation. The startup `info`
  line lists the schemas without any rule.
- **`count` works but `findMany` fails:** inspect `read`. A declaration such as
  `{ count: true }` leaves `many`, `one`, and `exists` without a rule, so only
  `allowWithoutRule` can open them.
- **`start()` fails in production:** an `allowWithoutRule` value is
  `'development'`. Write schema rules for those operations, or use `true` to
  open them in production too.
- **A row cannot be found or updated:** check the caller's query together with
  the private `where` restrictions on the relevant operation. Check `item`
  separately if a prepared target is rejected.
- **A field is missing or a query fails with `PERMISSION_DENIED`:** check the
  declared read channels (`output`, `where`, `orderBy`) and the write
  transition that the operation performs. Explicit selection of a denied field fails;
  ordinary output omits it.
- **An `access` option is rejected during compilation:** install
  `accessPlugin()` on the configured factory used to declare that schema and
  check the exact rule shape. A detailed mutation rule needs both `where` and
  `item`; a permission rule is `true`, `false` or a predicate.
- **A role-dependent rule denies unexpectedly:** verify that [Roles](./roles)
  and its subject resolver are configured in the same application. Do not use
  Master to hide a broken caller policy.
