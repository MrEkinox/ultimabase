## Outcome

Add Hooks and Validation to the `Task` application from
[Manual Installation](/docs/1.0.0/manual-installation). The field Hook trims a
title; Validation rejects it if the result is empty. Both behaviors belong to
the application that installs these plugins.

## Prerequisites

- Complete Manual Installation with its disposable PostgreSQL database and
  its `src/app.ts`, `src/schemas/task.ts`, `src/ultimabase.ts`, and
  `src/main.ts` files.
- Field Hooks and Validation options are typed directly from the configured
  application factory: no generation step or generated declaration is needed,
  and JavaScript applications run the same plugins.

## Steps

### Choose the plugin set

Start with the capability you need. Before adding any plugin, check its
supported UltimaBase and capability versions, stable identity, requested
privileges and reasons, and direct filesystem, network, process, or native
claims. For a community package, also check its maintainer, source, license,
and support channel. A community listing does not imply official maintenance
or a security audit.

This task needs [Hooks](./official/hooks) to normalize input and
[Validation](./official/validation) to reject the final value. Keep the
PostgreSQL provider from Manual Installation. Its `override` schema policy can
change physical tables, so use only the disposable development database here.

### Install the packages

Install the two plugins and Zod, which supplies the field validator:

```bash tab="npm" tab-group="package-manager"
npm install @ultimabase/hooks-plugin @ultimabase/validation-plugin zod
```

```bash tab="yarn"
yarn add @ultimabase/hooks-plugin @ultimabase/validation-plugin zod
```

```bash tab="pnpm"
pnpm add @ultimabase/hooks-plugin @ultimabase/validation-plugin zod
```

### Add the plugins to the factory

Add Hooks and Validation to the one plugin list in `app.ts`, beside the
PostgreSQL provider from Manual Installation. The factory stays in this one
module, which still imports no schema (see [Project Layout](/docs/1.0.0/project-layout)):

```ts twoslash title="src/app.ts"
import { UltimaBase } from '@ultimabase/core'
import { hooksPlugin } from '@ultimabase/hooks-plugin'
import { postgresPlugin } from '@ultimabase/postgres-plugin'
import { validationPlugin } from '@ultimabase/validation-plugin'

export const App = UltimaBase.use(
	hooksPlugin(),
	validationPlugin(),
	postgresPlugin(),
)
```

Importing either package or calling its factory alone installs no behavior;
the returned definition must enter this application's graph. The order inside
`use()` does not matter: Core starts each plugin after the plugins it depends
on. You can also spread a plugin list; each `.use()` call returns a new
factory and leaves its parent unchanged, and the application constructor
takes no `plugins` option.

### Use the plugin options

`Task` is declared from `App`, so the field options of the installed plugins
are available directly. The Hook trims the title before the final field
validator runs, so Zod receives the trimmed title:

```ts twoslash title="src/schemas/task.ts"
// @filename: app.ts
import { UltimaBase } from '@ultimabase/core'
import { hooksPlugin } from '@ultimabase/hooks-plugin'
import { postgresPlugin } from '@ultimabase/postgres-plugin'
import { validationPlugin } from '@ultimabase/validation-plugin'

export const App = UltimaBase.use(
	hooksPlugin(),
	validationPlugin(),
	postgresPlugin(),
)
// @filename: schemas/task.ts
// ---cut---
import { z } from 'zod'

import { App } from '../app.ts'

export const Task = App.Schema.define({
	className: 'Task',
	fields: (f) => ({
		done: f.boolean({ default: false }),
		title: f.string({
			required: true,
			hooks: { resolveInput: ({ value }) => value.trim() },
			validation: z.string().min(1),
		}),
	}),
})
```

`src/ultimabase.ts` does not change: it still creates the application from
`App` with `schemas: [Task]`.

Each plugin option has one place. Options about one field, such as these
`hooks` and `validation`, stay on the field; a plugin feature that changes
what the schema is, such as `softDelete: true`, is a key of `define`; how a
plugin treats the whole schema, such as an Access rule or a schema Hook, is a
key of `.with({ ... })`; and an option for the whole application
goes to the plugin factory in `.use()`. The
[Where each declaration goes](/docs/1.0.0/core/data-modeling/schemas#where-each-declaration-goes)
table lists every case.

Use `dependencies` when another plugin must exist and start first,
`optionalDependencies` for that order only when it is installed, `peers` for
compatible identity without ordering, and a versioned capability when several
providers can supply the required behavior.

The Hook may normalize input, and Validation then accepts or rejects the
result. A Standard Schema validator's output is what gets stored, so a
transforming validator such as `z.string().trim()` changes the stored value
too; `z.string().min(1)` returns its input unchanged. Core still enforces
required presence and field structure even if Validation is absent.

## Verify

Replace the manual tutorial's `main.ts` with one successful and one rejected
write:

```ts twoslash title="src/main.ts"
// @filename: app.ts
import { UltimaBase } from '@ultimabase/core'
import { hooksPlugin } from '@ultimabase/hooks-plugin'
import { postgresPlugin } from '@ultimabase/postgres-plugin'
import { validationPlugin } from '@ultimabase/validation-plugin'

export const App = UltimaBase.use(
	hooksPlugin(),
	validationPlugin(),
	postgresPlugin(),
)
// @filename: schemas/task.ts
import { z } from 'zod'

import { App } from '../app.ts'

export const Task = App.Schema.define({
	className: 'Task',
	fields: (f) => ({
		done: f.boolean({ default: false }),
		title: f.string({
			required: true,
			hooks: { resolveInput: ({ value }) => value.trim() },
			validation: z.string().min(1),
		}),
	}),
})
// @filename: ultimabase.ts
import { App } from './app.ts'
import { Task } from './schemas/task.ts'

export const ultimabase = new App({
	schemas: [Task],
})

// Required once per application: it gives name-keyed editor types.
declare module '@ultimabase/core' {
	interface Register {
		readonly app: typeof ultimabase
	}
}
// @filename: main.ts
// ---cut---
import { FrameworkError } from '@ultimabase/core'

import { Task } from './schemas/task.ts'
import { ultimabase } from './ultimabase.ts'

try {
	await ultimabase.start()
	const task = await Task.createOne({
		data: { title: '  Write the documentation  ' },
	})
	console.log(task.title) // 'Write the documentation'

	let rejected = false
	try {
		await Task.createOne({ data: { title: '   ' } })
	} catch (error) {
		if (
			!(error instanceof FrameworkError) ||
			error.code !== 'VALIDATION_ERROR'
		) {
			throw error
		}
		rejected = true
	}
	if (!rejected) throw new Error('Expected an empty title to be rejected')
	console.log('VALIDATION_ERROR')
} finally {
	await ultimabase.dispose()
}
```

Run the updated scripts. The configured factory already supplies the new
field options, so there is nothing to regenerate:

```bash tab="npm" tab-group="package-manager"
npm run typecheck
npm run build
npm start
```

```bash tab="yarn"
yarn typecheck
yarn build
yarn start
```

```bash tab="pnpm"
pnpm typecheck
pnpm build
pnpm start
```

Expect the trimmed title and then `VALIDATION_ERROR`. The second write is
rejected before persistence. If TypeScript does not recognize `hooks` or
`validation`, check that Task is declared from `App`, on which Hooks and
Validation are installed, not from the zero-plugin `UltimaBase.Schema`. If startup fails instead, inspect the default
plugin report and compatibility diagnostics before changing privileges or
infrastructure settings.

## Register schemas

No schema is registered by being declared: keep `new App({ schemas: [...] })`.
Advanced dynamically named handles remain for capabilities that need them; they
are not the ordinary CRUD journey. Plugins may add schema factories to the
configured application: installing Roles adds `App.RoleSchema.define(...)`,
whose declarations end with `.with({ ... })` like any schema and inherit the same
plugin configuration; installing `authPlugin` adds `App.UserSchema.define(...)`
for the User. No additional plugin installation is required per schema.

## Next steps

When removing a plugin, remove its factory, its feature keys in `define`, its
`.with` keys and its commands, then verify typechecking, startup and stored-data
compatibility.
Removing a plugin does not automatically migrate its data. Core checks
required providers, protocol compatibility, privileges, and duplicate
identities during application assembly; it cannot replace your review of a
package's maintenance or direct Node.js behavior.
