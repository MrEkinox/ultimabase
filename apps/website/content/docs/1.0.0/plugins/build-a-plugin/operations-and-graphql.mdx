## Outcome

Give a plugin its own executable command, then choose whether that command is
private to TypeScript callers or explicitly reachable through GraphQL or REST.
You can also provide independent GraphQL fields. Declaring behavior, generating
its TypeScript types, and publishing it on a transport are separate decisions.

## Prerequisites

- Complete [Build a Plugin](/docs/1.0.0/plugins/build-a-plugin) and start from an existing application.
- Read [Application](/docs/1.0.0/core/application) for application-owned
  handles and [GraphQL](/docs/1.0.0/plugins/official/graphql) for the consumer-facing endpoint.
- For GraphQL integration, install `@ultimabase/graphql-plugin` in the
  application. An HTTP endpoint additionally needs Yoga, HTTP, and a server
  provider; the GraphQL package itself is network-independent.

## Pick the executable surface

| Requirement            | Declare                                                            | Implement                    | Expose                                                           |
| ---------------------- | ------------------------------------------------------------------ | ---------------------------- | ---------------------------------------------------------------- |
| App-wide command       | `defineOperation({ target: 'application' })`                       | `contributeOperation()`      | Optional exact GraphQL or REST binding and application allowlist |
| Item-oriented mutation | `defineSchemaMutation()` plus `models.extend({ schemaMutations })` | `contributeSchemaMutation()` | Optional exact REST or GraphQL binding                           |

`operation:declare` covers both token kinds. `model:extend` attaches
schema-mutation methods to schema and model handles. Every command uses an exact namespaced name and semantic version.
Input and result snapshotters validate untrusted values; declaring an error
code makes only that `PluginError` safe to publish. Unknown exceptions remain
internal diagnostics.

Pure schema compilation does not call a resource-backed handler's
`create` factory. It runs once during application initialization under the exact
plugin owner; transport bindings themselves remain inert declarations. Core
rejects duplicate active handlers or protocol bindings and foreign ownership
before plugin setup or transport planning. If initialization fails, it disposes
the resources already created. Return resource cleanup from `create` as
`dispose`.

## Declare and implement an operation

Here is one complete, intentionally simple app-wide operation. It has no
database work, so it forbids a transaction. The token stays independently
exportable; its Core contribution correlates declaration and execution:

<include cwd meta='title="src/workflow/operations.ts"'>
	../../examples/plugin-authoring/src/workflow/operations.ts#operations
</include>

Install the token and its handler under one plugin owner. The contribution is
the single source for the static declaration, executable handler, owner-local
identifier, optional wire bindings, and lifecycle resource boundary:

```ts twoslash title="src/workflow/plugin.ts"
// @filename: operations.ts
export { formatWorkflow } from '../../examples/plugin-authoring/src/workflow/operations.ts'
// @filename: plugin.ts
// ---cut---
import { contributeOperation, plugin } from '@ultimabase/core/plugin'

import { formatWorkflow } from './operations.ts'

export const workflowPlugin = () =>
	plugin({
		id: 'community.workflow',
		core: '^0.0.0',
		version: '1.0.0',
		contributions: [
			contributeOperation({
				execute: ({ input }) => input.trim(),
				operation: formatWorkflow,
			}),
		],
	})
```

Export both `workflowPlugin` and `formatWorkflow` from the package root. A
started application that installs the plugin executes the token directly:

<include cwd meta='title="tests/operations.test.ts"'>
	../../examples/plugin-authoring/tests/operations.test.ts#execute-operation
</include>

`result` is `'ready'`. The same application without the plugin rejects that
token. The
installed operation's source definition gives TypeScript its input and result
types without a generated plugin declaration. The operation remains private
from every network transport at this point.

## Reuse queries and mutate one item

For a reusable query, export an ordinary function that builds an immutable
`QueryBuilder` or calls the schema's query methods. Query helpers need no plugin
registrar or privilege.

Use a [schema mutation](#expose-a-schema-mutation) when a command updates or
deletes one item and needs Core's locked target, policy checks, and transaction.
`models.extend()` attaches its `schemaMutations` to the selected schemas at
Runtime; it does not type them. A statics slot types the methods on the
schemas that set your feature, as
[Schema Contributions](/docs/1.0.0/plugins/build-a-plugin/schema-contributions#add-commands-to-the-schema-class)
explains, and `definePlugin` writes it for you. JavaScript uses the same
compiled surfaces.

A mutation handler or transport binding with no selected schema/model alias
stays dormant. It contributes no method or route and does not cause an
unused-binding startup error. Declaring a provider alone never exposes a command.

For transport authors, the Core planner and late execution facade share the
same frozen descriptors from the compiled command. Keep those descriptors when
binding execution; a reconstructed object does not identify an exposed mutation.
The plan contains no codec or handler and cannot authorize a request.

### Decode a Core-shaped filter without rebuilding its traversal

If a transport exposes Core's `where` shape but uses different wire values, use
`transformQueryFilterInput()` before canonical read normalization. Here
`wireWhere` and `decodeTransportOperand` stand for the transport's own input
and scalar decoder:

```ts twoslash
import type { QueryFilterOperandInput } from '@ultimabase/core'
import { Post } from '../../examples/plugin-authoring/src/schema.ts'
const schema = Post
declare const wireWhere: unknown
declare const decodeTransportOperand: (
	operand: Omit<QueryFilterOperandInput, 'path'>,
) => unknown
// ---cut---
import {
	normalizeReadOperation,
	transformQueryFilterInput,
	transformSchemaMutationDataInput,
} from '@ultimabase/core'

const where = transformQueryFilterInput(
	schema,
	wireWhere,
	({ field, operator, source, value }) =>
		decodeTransportOperand({ field, operator, source, value }),
)

const operation = normalizeReadOperation(schema, 'find-many', { where })
```

Core traverses `AND`, `OR`, `NOT`, relationship predicates, filtered relation
counts, and structured `at` paths. The callback receives only the terminal
field operand, so the transport keeps its scalar codecs and error contract in
one place. The helper transforms values; it does not validate operators or
authorize execution. Always pass its result through the ordinary Core
normalizer and application request executor.

For mutation data, the matching helper avoids rebuilding schema and nested-write
recursion:

```ts twoslash
import {
	transformSchemaMutationDataInput,
	type SchemaMutationDataFieldInput,
} from '@ultimabase/core'
import { Post } from '../../examples/plugin-authoring/src/schema.ts'
const schema = Post
declare const wireData: unknown
declare const decodeMutationField: (
	input: SchemaMutationDataFieldInput,
) => unknown
// ---cut---
const data = transformSchemaMutationDataInput(schema, wireData, {
	mode: 'create',
	relationships: 'nested',
	transformField: (input) => decodeMutationField(input),
})
```

Core classifies persisted, virtual, and unknown fields and follows nested
pointer/relation `create` and `update` data into the target schema. Your callback
still owns scalar wrappers, IDs, command allowlists, and transport errors. Pass
the result to the ordinary schema-mutation normalizer; this helper neither
validates the complete command nor executes it.

## Expose behavior through GraphQL

### Bind an existing operation

An operation the owner declares public (`public: { name }`) appears in every
installed transport (ADR-0325). For typed GraphQL fields, the owner also
supplies an exact wire codec and inert GraphQL metadata and requests
`transport:expose`; without that binding, GraphQL exposes the operation as a
mutation whose types derive from `public.input` and `public.output` (JSON
Schema), with `JSON` for what GraphQL cannot describe. The owner can name the canonical
protocol through Core without importing the GraphQL package:

<include cwd meta='title="src/workflow/graphql-binding.ts"'>
	../../examples/plugin-authoring/src/workflow/graphql-binding.ts#graphql-binding
</include>

Replace the previous plugin definition with the version that installs both
providers under the same owner and requests the additional privilege:

<include cwd meta='title="src/workflow/plugin.ts"'>
	../../examples/plugin-authoring/src/workflow/plugin.ts#workflow-plugin
</include>

The operation owner can instead add
`contributeOperationBinding(formatGraphqlBinding)` separately to the same
plugin's `contributions` list. This keeps handler and transport modules separate
without weakening exact ownership; a foreign plugin cannot publish the
operation. The binding still requires `transport:expose`.

The package root should re-export `workflowPlugin` and `formatWorkflow`.
In the application, install GraphQL (here through `apiServer({ graphql })` in
the [schema factory](/docs/1.0.0/plugins/build-a-plugin/schema-contributions#start-with-defineplugin))
and the plugin:

<include cwd meta='title="src/ultimabase.ts"'>
	../../examples/plugin-authoring/src/ultimabase.ts#application
</include>

After startup, `ultimabase.plugin('@ultimabase/graphql-plugin').printSchema()`
shows `formatWorkflow(input: String!): String!` under `Query`, and the public
name also exposes `POST /api/operations/formatWorkflow` over REST. `graphqlPlugin({ hide: [formatWorkflow] })` hides it;
an operation its owner does not declare public stays absent. GraphQL checks owner, protocol, types, names, and collisions
before serving requests. Its resolver passes a real application-bound request
context to Core; neither GraphQL variables nor a custom resolver can create
Master authority.

### Provide an independent GraphQL field

Use this path when you have a completed `GraphQLSchema` from `graphql`, Nexus,
Pothos, or GraphQL Tools rather than an UltimaBase operation token. Install
`graphql` and `@ultimabase/graphql-plugin` in the plugin package only when
this integration is needed:

```bash tab="npm" tab-group="package-manager"
npm install graphql @ultimabase/graphql-plugin
```

```bash tab="yarn"
yarn add graphql @ultimabase/graphql-plugin
```

```bash tab="pnpm"
pnpm add graphql @ultimabase/graphql-plugin
```

<include cwd meta='title="src/graphql-addon.ts"'>
	../../examples/plugin-authoring/src/graphql-addon.ts#graphql-addon
</include>

This provider contributes one schema to the installed GraphQL plugin; it does
not install GraphQL, Yoga, HTTP, or a listener. A custom resolver receives only
`{ request: RequestContext }`, not an UltimaBase application, adapter, or
authority facade. Root-field and type collisions fail startup rather than
overwriting another contribution. For data operations, prefer the owned
operation and binding path above instead of reaching into Core Runtime from a
resolver.

### Expose a schema mutation

Use `defineSchemaMutation()` when the command acts on one persisted schema
item and should participate in Core's locked-target, policy, hook, and
transaction semantics. The owner adds one `contributeSchemaMutation()` entry
to the plugin's `contributions` list; that one entry owns the token declaration,
handler, optional bindings, and lifecycle. `models.extend({ schemaMutations: { ... } })` selects the
schema surface; results have no methods, so `'schema'` is the only surface
(ADR-0310). Optional GraphQL exposure adds a
`schemaMutationWireCodec()` binding to that same contribution. It uses the separate
canonical `ultimabase.graphql@1.0.0` protocol and is not an application
operation.

GraphQL derives the root field from the installed schema and command. The
owner may describe only the optional payload's closed input types, not choose
its own root name, target ID, result type, resolver, or authority. A
Master-only mutation never enters the public SDL. The official
[Soft Delete](/docs/1.0.0/plugins/official/soft-delete) plugin is a concrete example of schema
mutations: REST exposes a one-row request command when the application names
it with `plugins.rest({ softDeleteOne: true })` in `.with`, and GraphQL when it
names it with `plugins.graphql({ softDeleteOne: true })`, without any binding: the
GraphQL field then takes only the row `id`. The `archivePlugin` of
[Schema Contributions](/docs/1.0.0/plugins/build-a-plugin/schema-contributions#start-with-defineplugin)
works the same way once `Post` names `archiveOne` for both transports:

<include cwd meta='title="tests/schema-contributions.test.ts"'>
	../../examples/plugin-authoring/tests/schema-contributions.test.ts#archive-over-http
</include>

REST answers `200` with the archived row in `result`, GraphQL with
`{ archiveOnePost: { id } }`; `archiveMany` stays off both transports.

## REST and HTTP are separate choices

- An operation is public only when its owner declares it:
  `contributeOperation({ operation, execute, public: { name: 'login' } })`.
  Every installed transport then exposes it; REST at
  `POST /api/operations/{public name}`, unless the application hides it with
  `restPlugin({ hide: [token] })`. An optional REST binding for canonical
  `ultimabase.rest@1.0.0` adapts the wire format with a codec and
  `{ errors: { ... }, path?: string }` metadata; without one, REST passes the
  wire input to the operation's own input contract and maps each declared
  public error to `400`. `public.input` and `public.output` may carry JSON
  Schemas that the OpenAPI document shows. A static `path: '/reports/daily'`
  replaces the route with `POST /api/reports/daily`, respecting the configured
  REST base path. Paths contain slash-separated ASCII letters,
  digits, underscores, or hyphens, start with `/`, and have no trailing slash.
  The `classes` and `operations` roots are reserved. Dynamic or encoded paths
  and unknown metadata keys are rejected; duplicate routes fail before startup.
- Plugin schema mutations use a separate REST schema-mutation binding and
  schema-local route. They are not REST application operations.
- An independent Fetch route or mount uses the HTTP package's
  `provideHttpEndpoints()` and `transport:expose`. HTTP selects the exact
  application and context before the handler; Hono is only a server provider.
- A custom transport must use Core's narrow application request-execution
  capability. It never receives the private Runtime engine, an adapter, or a Master
  grant from an HTTP header or shaped object.

For a standalone Fetch route, provide the HTTP endpoint capability. This
example reads no application data; it still belongs to the selected HTTP
application and requires its identity header:

<include cwd meta='title="src/status-route.ts"'>
	../../examples/plugin-authoring/src/status-route.ts#status-route
</include>

The application must also install the HTTP plugin and a server provider to
listen on a socket. Route collisions fail during application materialization.
Like every route, it accepts requests without `X-UltimaBase-Application-Id`
unless the application sets `requireApplicationId: true`, and every handler
receives `(request, { context })`. Applications declare their own routes
without a plugin through `httpPlugin({ routes })`. If a route handles application data, it must use the selected request context
and Core's public request-execution facade rather than bypassing Runtime.

A plugin that exposes a browser bootstrap UI can validate a configurable route
suffix with `normalizeHttpBrowserBootstrapPath(value, label)` and pass the
result to `httpBrowserBootstrapRoute()`. This keeps absolute-path, reserved
namespace, decoded-segment, and non-root checks consistent with the official
GraphQL explorer plugin.

Transport exposure is not authorization. Check Access, ACL, request identity
and browser policy for the actual public route; REST and GraphQL refuse to
start with public writes and no policy plugin unless `publicWrites` opts in. See the official [REST](/docs/1.0.0/plugins/official/rest)
and [HTTP](/docs/1.0.0/plugins/official/http) guides for complete application configuration.

## Schema-derived operation inputs

For an operation that creates a plugin-owned schema, REST binding metadata can
set `inputSchema` to its class name. REST applies the ordinary nested-create
field codecs before the operation owner's decoder runs. The schema must belong
to that exact plugin owner; declaring it exposes no CRUD routes.

A GraphQL supporting input-object can similarly declare `createFieldsFrom`.
Its fields inherit the schema's create types, requiredness, and codecs. Explicit
supporting fields may add operation-only values, but cannot replace inherited
fields. The password method uses this for `PasswordSignUpInput`, adding
`password` to the User create fields; a plugin whose schema class name the
application chooses names it `{ kind: 'owned-schema' }`, the one schema it adds,
claims or designates with a schema option it defines. Login retains a separate
credentials-only input.
Defaults and validation still run once through the ordinary Runtime creation.

## Verify

Test direct TypeScript execution first. For every selected public operation,
inspect the generated GraphQL SDL or REST route graph and exercise one valid
request, one invalid input, one undeclared error, and a context from another
application. Confirm unselected operations stay private and that teardown
revokes their handles. Use `@ultimabase/testing/plugins`' `operation`,
`schema-mutation`, `transport`, and `javascript-operation` optional checks
where they match the feature; add real protocol-level tests for the wire
representation and safe errors.
