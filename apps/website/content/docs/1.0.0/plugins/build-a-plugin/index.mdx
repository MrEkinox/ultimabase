## Outcome

Build a plugin with one public factory and a typed setup result. Verify that
the result belongs to the application that installs it. Then choose the
specific extension boundary for the behavior you want to add. The starter
plugin does not add schema fields, operations, or Runtime behavior yet.

## Prerequisites

- Read [Plugin System](/docs/1.0.0/plugins/overview) and
  [Using Plugins](/docs/1.0.0/plugins/using-plugins) so
  application-local installation is familiar.
- Have a Node.js 24+, ESM TypeScript library package with a build and a
  package-root export. Name publishable plugins with the `-plugin` suffix,
  such as `@your-scope/workflow-plugin`.
- Use the Core compatibility range you actually test. The snippets target
  this `1.0.0` documentation line; packages are still pre-release.

## Steps

### Install Core

Install Core in your plugin package:

```bash tab="npm" tab-group="package-manager"
npm install @ultimabase/core
```

```bash tab="yarn"
yarn add @ultimabase/core
```

```bash tab="pnpm"
pnpm add @ultimabase/core
```

Plugin Kit is optional. Install it later only when an event, option parser,
contextual-field helper, or immutable patch builder helps the plugin. Package
identity and configured plugin definitions belong directly to Core.
It provides no generic registry, service locator, privilege shortcut, or
alternate plugin-registration path.

### Export a static factory

Export the factory at the package root so consumers never need a `src/`
deep import:

```ts title="src/index.ts"
import { contributeApplication, plugin } from '@ultimabase/core'

export const workflowPlugin = (instanceId?: string) =>
	plugin({
		id: 'community.workflow',
		core: '^1.0.0',
		version: '1.0.0',
		...(instanceId === undefined ? {} : { instanceId }),
		contributions: [
			contributeApplication(() => ({
				exports: { ready: true as const },
			})),
		],
	})

export type WorkflowPlugin = ReturnType<typeof workflowPlugin>
```

The factory returns an inert, typed definition. Constructing it must not
connect to a database, read files, or start a listener. Its `ready` export is
only a learning example, not workflow functionality. Importing a plugin
package or calling its factory does not install behavior: the definition must
enter one application's `.use()` chain.

Every capability, operation, static declaration, and application resource goes
into `contributions`. Core compiles that list once into its native plugin plan
and derives the required privilege names. Authors add only the corresponding
human-readable `permissions` reasons; missing and unused reasons fail while the
definition is still inert. There is no separate setup/hooks authoring model
behind this API.

### Install test tooling

Add the conformance harness and Vitest as development dependencies:

```bash tab="npm" tab-group="package-manager"
npm install --save-dev @ultimabase/testing vitest typescript
```

```bash tab="yarn"
yarn add --dev @ultimabase/testing vitest typescript
```

```bash tab="pnpm"
pnpm add --save-dev @ultimabase/testing vitest typescript
```

## Verify

Build your package so its root export resolves, then test the same public
import an application will use. This plugin needs no database:

```ts title="tests/workflow-plugin.test.ts"
import { UltimaBase } from '@ultimabase/core'
import {
	createPluginConformanceFixture,
	definePluginConformanceSuite,
	runPluginConformance,
} from '@ultimabase/testing'
import { expect, it } from 'vitest'

import { workflowPlugin } from '@your-scope/workflow-plugin'

it('exposes setup only through its installed application', async () => {
	const Application = UltimaBase.use(workflowPlugin())
	const application = await new Application({
		schemas: [],
	}).initialize()

	try {
		expect(application.plugin('community.workflow')).toStrictEqual({
			ready: true,
		})
	} finally {
		await application.dispose()
	}
})

const suite = definePluginConformanceSuite({
	createFixture: () =>
		createPluginConformanceFixture({ subject: workflowPlugin() }),
	expected: {
		core: '^1.0.0',
		pluginId: 'community.workflow',
		version: '1.0.0',
	},
})

it('conforms to the public plugin kernel', async () => {
	const report = await runPluginConformance(suite)
	expect(report.checks.every(({ status }) => status === 'passed')).toBe(true)
})
```

`initialize()` compiles the graph, materializes application
capabilities, and runs setup. This particular plugin opens no resources. Only
one application may initialize per JavaScript realm; these tests run
sequentially and dispose their applications even after an assertion failure.
Run your Vitest command and confirm that both tests pass. Conformance covers
static determinism, provenance, lifecycle cleanup, and application isolation;
it does not prove the domain behavior you will add next.

## Choose an extension boundary

Start with the reader-visible behavior, then use the smallest owning contract.
One feature may cross several boundaries; none is automatic merely because its
neighbor exists.

| You want to add                                                                 | Start with                                                                                                                     | Exact additional power                               |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| A schema, field, direct option, index, or additive patch                        | [Schemas and Typegen](/docs/1.0.0/plugins/build-a-plugin/schemas-and-typegen)                                                  | `schema:declare`                                     |
| A public type reference used by the compiled graph                              | [Schemas and Typegen](/docs/1.0.0/plugins/build-a-plugin/schemas-and-typegen#contribute-to-typegen)                            | `typegen:reference`                                  |
| An app-wide operation or item-oriented schema mutation                          | [Operations and GraphQL](/docs/1.0.0/plugins/build-a-plugin/operations-and-graphql)                                            | `operation:declare`, often `model:extend`            |
| A GraphQL field or selected operation                                           | [Operations and GraphQL](/docs/1.0.0/plugins/build-a-plugin/operations-and-graphql#expose-behavior-through-graphql)            | `transport:expose` for an owner contribution         |
| A shared protocol, lifecycle resource, observer, policy, or persistence rewrite | [Runtime and Infrastructure](/docs/1.0.0/plugins/build-a-plugin/runtime-and-infrastructure)                                    | Depends on the exact Core facade                     |
| A database adapter, physical contribution, or owner-private record              | [Runtime and Infrastructure](/docs/1.0.0/plugins/build-a-plugin/runtime-and-infrastructure#data-and-infrastructure-boundaries) | `adapter:consume` or `storage:private` as applicable |

The full current privilege and environment-claim map is in
[Runtime and Infrastructure](/docs/1.0.0/plugins/build-a-plugin/runtime-and-infrastructure#privilege-and-claim-reference).
It distinguishes enforceable Core powers from direct Node.js behavior.

## Identity and ordering

`pluginId` is the stable namespaced package identity. Use a distinct,
explicit `instanceId` only when one application configures that plugin more
than once; Core never derives it from options, URLs, or secrets. Read repeated
setup exports through the structured `{ pluginId, instanceId }` identity
because the bare ID is ambiguous.

A declared dependency supplies provider-first ordering. Configuration order
only breaks ties between otherwise ready plugins. A `peer` checks presence
and version without promising lifecycle order. A required capability is
preferable to naming a concrete provider when implementations can vary.
