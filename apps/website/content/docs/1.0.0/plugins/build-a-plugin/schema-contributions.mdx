## Outcome

Extend a schema without changing Core or patching an exported schema class.
An application declares each schema in two blocks: what the schema is in
`App.Schema.define({ className, fields, indexes, ... })`, including the
feature keys of the installed plugins such as `softDelete: true`, then how
each plugin treats it in one optional `.with({ ... })` holding their
rules. Your plugin types both blocks from its own source
through Core's projection slots.
There is no generation step and no generated file, and the same declarations
compile at Runtime, so JavaScript applications get the same behavior.

## Prerequisites

- Complete [Build a Plugin](/docs/1.0.0/plugins/build-a-plugin) and know its stable plugin identity.
- Read [Schemas](/docs/1.0.0/core/data-modeling/schemas#plugin-features-and-rules)
  and [Fields](/docs/1.0.0/core/data-modeling/fields) for the declaration
  your plugin extends, and [Features and Rules](/docs/1.0.0/plugins/build-a-plugin/features-and-rules)
  to decide whether an option is a feature or a rule.

## Choose the schema contribution

| Requirement                                      | Public declaration boundary                                                       | Typed for the application by                      |
| ------------------------------------------------ | --------------------------------------------------------------------------------- | ------------------------------------------------- |
| A feature with fields and commands, or a rule    | `definePlugin()` with `features`, `feature()` and `rules`                         | `definePlugin`, from the same object              |
| A `.with` rule in a raw plugin                   | `schemas.defineOptions()` with `defineSchemaOption()`, `provideSchemaRules()`     | A rules slot: `SchemaRulesHKT`                    |
| A feature in a raw plugin                        | `provideSchemaFeatures()`, plus `schemas.select()` and `schemas.patch()`          | `PluginSchemaFeatureSource` and `SchemaFieldsHKT` |
| Commands added to the schema class               | `defineSchemaMutation()` and `contributeSchemaMutation()`                         | A statics slot: `SchemaStaticsHKT`                |
| A field option                                   | `schemas.defineOptions()` with `definePluginFieldOption()` or `defineFieldOption` | The installed option definition                   |
| A field kind or contextual builder method        | `definePluginField()`, `definePluginFieldFamily()` and `fields.register()`        | The registered family                             |
| A schema factory such as `App.RoleSchema`        | `provideSchemaFactories()`                                                        | `SchemaFactoriesHKT`                              |
| An application-local schema, or an owned one     | `schemas.add()`, `schemas.claim()`                                                | The schema's own declaration                      |
| A field, index, or option value on selected rows | `schemas.select()` and `schemas.patch()`                                          | Nothing: patches change the Runtime schema only   |

Schema declarations need the `schema:declare` privilege, and schema commands
`operation:declare` and `model:extend`; Core derives each one from the
contribution that uses it. Every contribution needs a stable owner-local
`contributionId`; Core checks collisions and records provenance in the final
graph. Patches are additive: they cannot replace, rename, or remove existing
facts, and an option setter rejects an already present value. A patch or a
`models.extend()` selection changes the compiled schema at Runtime but adds
nothing to the application's types: when developers should see a field or a
command, offer it through a feature. Plugin-owned schemas are not
automatically public REST or GraphQL schemas.

Use `schemas.claim({ contributionId, schema })` when the developer owns the
class declaration and lists it in the root `schemas` array, but your plugin
must retain provenance and transport-visibility ownership. A claim never adds a
missing class implicitly and cannot duplicate the plugin's own `schemas.add()`.

## Start with `definePlugin`

Most schema contributions are a feature that adds server-written fields
and commands, or a rule read after commit. `definePlugin` from
`@ultimabase/plugin-kit` declares both from one object and writes every slot
below for you; [Start Here](/docs/1.0.0/plugins/build-a-plugin#declare-the-plugin-with-defineplugin)
shows the `archivePlugin` it builds. An application installs it once in its
factory, here with the `auditPlugin` of the same page and the raw
`flagPlugin` below:

<include cwd meta='title="tests/schema-contributions.test.ts"'>
	../../examples/plugin-authoring/tests/schema-contributions.test.ts#archive-one
</include>

`archived.archivedAt` is the time of the command. Keep a raw `plugin()` when a
rule or a command depends on the schema it applies to, or when a command takes
input.

Name each command `<operation>One` for a `'one'` target and `<operation>Many`
for a `'many'` target: `archiveOne` and `archiveMany` form the operation
`archive`. `definePlugin` refuses another name, an operation that is a native
operation or method, `read`, `write` or `all`, and two commands sharing a name.
The REST path (`/archive-one`) and the GraphQL field (`archiveOnePost`) follow
the method name, and `.with({ expose: { archive: true } })` opens the operation
on REST without a `rest` key, whose `archiveOne` entry above is the
per-transport form;
[Operations and GraphQL](/docs/1.0.0/plugins/build-a-plugin/operations-and-graphql#expose-a-schema-mutation)
details the rule.

## Type a rule with a rules slot

A rule is a schema option that the application sets with a key of
`.with({ ... })`. `define` rejects it as an unknown key, in TypeScript and at
runtime (`Unknown schema option: <name>`). Declare the option once with
`schemas.defineOptions()`, give its name to
`provideSchemaRules(instance, names)` so that `.with` accepts the key, then
type it through a rules slot: an interface extending `SchemaRulesHKT` whose
`rules` member is the `.with` entry. The slot reads `this['schema']`, the
configured schema, so a rule may be typed against its fields (as Access, Hooks
and Validation do), and `this['shape']`, the features `define` sets, so a rule
may appear only with its feature. A feature that needs a rule declares it as
required, as ACL's `acl: true` requires `.with({ acl: { default } })`;
see [Features and Rules](/docs/1.0.0/plugins/build-a-plugin/features-and-rules#a-feature-may-require-a-rule).

This raw plugin adds a `flaggable` feature that gives a schema a
server-written `flagged` field, and a `flagReason` rule offered only with it:

</include>

The application uses the feature and the rule like any official plugin's,
with `flagPlugin()` in the factory shown above:

`Comment` results carry `flagged`, `false` by default, and the patch also
indexes `flagged` with `createdAt`; create and update input reject it, because
`mutationInput: 'forbidden'` reserves the field for the plugin's own effects
while keeping it readable and persisted. It is not a permission rule for
reading the field. A patch can close a whole generic command the same way:
`closeSchemaCommand({ contributionId, command: 'create', reason })` from
`@ultimabase/core/plugin` closes `createOne`, `createMany`, `upsertOne` and
`upsertMany` on the targeted schemas. REST, OpenAPI and GraphQL then publish
nothing for them, and every call fails with `VALIDATION_ERROR` (issue
`command.closed`, carrying `reason`), Master included, except the closing
plugin's own calls, which provide the schema's creation path; Password
Authentication closes the User's create this way (ADR-0341).
`.with({ flagReason: … })` without `flaggable: true` is a
type error, and TypeScript flags a key given twice. At Runtime the plugin
reads a schema's rules with `readSchemaRules(schema, owner)` from
`@ultimabase/core/plugin`, which returns only the options that plugin declared.

The selector matches the presence of `flaggable`. Use
`{ option: { name, path, equals } }` to match portable JSON structurally;
object key order does not matter, array order does.
`{ option: { name, present: false } }` matches an omitted option. An option
containing a callback or another nonportable value supports presence and
absence, but equality and path selectors never invoke the callback or expose
an internal marker. Each plugin's selection targets are frozen before its own
additions and patches; later contributions cannot make that selection grow.

`present: true`, `present: false` combined with `equals` or `path`, and selector
negation are rejected, and the option name must resolve to exactly one
definition; an option set explicitly to `false` counts as present. A
`contributionId` only needs to be unique within one plugin instance, so two
explicit instances of the same plugin may reuse it.

An option definition may add `runtime: { requirement, compile }` when each use
must register with a capability your plugin owns. `ultimabase.compile()` only
records the uses. Initialization materializes capabilities, then calls `compile`
once per use, in plugin-declaration and schema order and before plugin `setup`,
with the capability, `className`, `fieldName`, `optionName`, `path`, `scope`,
`provenance` and normalized `value`. `compile` returns `undefined`; a throw
aborts initialization and disposes the capabilities already created. Set
`valueKind: 'opaque'` for values that are not portable JSON.

A forbidden field still receives its declared default on create. For a closed
command, `can()` answers `false` and nested writes fail the same way; read a
closure and its reason with `readSchemaCommandClosure(schema, 'createOne')`.

### Add commands to the schema class

A statics slot types the commands a feature adds: an interface
extending `SchemaStaticsHKT` whose `statics` member uses
`SchemaCommands<this['schema'], { archiveOne: typeof archive }>`, so each
command's `select` and result follow the configured schema. Declare the
command itself with `defineSchemaMutation()` and `contributeSchemaMutation()`,
and select its schemas with `models.extend()`, as
[Operations and GraphQL](/docs/1.0.0/plugins/build-a-plugin/operations-and-graphql#expose-a-schema-mutation)
shows. Without the statics slot the command still runs, but TypeScript does
not offer it. `definePlugin` writes this slot for every `command()`.

## Add field options and field kinds

A field option stays on the field, such as PostgreSQL's
`f.string({ postgres: { renamedFrom: 'headline' } })`. Declare it with
`definePluginFieldOption({ contexts, normalize, protocolVersion })` from
`@ultimabase/plugin-kit` and install it with
`schemas.defineOptions({ contributionId, field: { postgres: option } })`; the
configured factory then types the option from that definition.

Field value representation, builder availability, storage, and wire encoding
are independent decisions:

| Concern           | Owner decision                                                                                            |
| ----------------- | --------------------------------------------------------------------------------------------------------- |
| Logical value     | `definePluginField()` snapshots and validates one field kind.                                             |
| Builder placement | `definePluginFieldFamily()` names only supported `stored`, `embedded`, `virtual`, or `output` contexts.   |
| Direct option     | `definePluginFieldOption()` declares the exact contexts and normalization.                                |
| Persistence       | A portable JSON storage codec or an explicit adapter integration.                                         |
| Query predicates  | Portable codec grants complete-value equality/inclusion only; structural `contains` is a separate opt-in. |
| Transport value   | An exact protocol-specific wire codec; storage encoding is not automatically a wire format.               |

Register a family with `fields.register(family)` in the same `schema`
declaration callback; `UltimaBase.use()` then offers the builder method, such
as `f.vector()`, only in the contexts the family names. A stored field method
does not automatically work as a virtual output, and Core rejects unsupported
usage even when JavaScript bypasses autocomplete.

A field kind is a namespaced string such as `community.search.document`: a
non-empty namespace, a dot, and a name, never a Core kind.
`definePluginField(kind, options, { snapshotValue, storageCodec, wireCodecs, structuralContains })`
builds the field, and hand-built field objects are rejected.
`snapshotValue(value, path)` validates and freezes every logical value and
throws with `path` on invalid input; it must be pure, deterministic and
idempotent, because Core also applies it to static defaults. Validate an unknown
options container with `assertFieldOptions`, and report failures with
`PluginValidationIssueCode<'your.kind'>` codes. Compiling the application
rejects a kind no installed plugin claims, or that two plugins claim.

A `storageCodec` is `{ format: 'json', version, encode, decode }` with a
positive integer `version`; Core runs `snapshotValue` around both directions, so
the adapter stores one versioned JSON value and reads it with
`getPluginFieldStorageCodec()`. It gives a non-list field complete-value `eq`,
`ne`, `in` and `notIn` filters, and no ordering or other operator. Each entry of
`wireCodecs` is `{ format: 'json', protocol, encode, decode }` for one transport
protocol created with `definePluginFieldWireProtocol({ name, version })`, such
as `ultimabase.graphql.field@1.0.0`, without importing the transport; a field
gives each protocol once, and transports resolve it with
`getPluginFieldWireCodec(field, protocol)`. A storage codec is never used as a
wire codec.

To accept a partial `where: { field: { contains: … } }` operand, add
`structuralContains: { snapshotOperand }`: Core validates, detaches and freezes
the operand before the adapter sees it. It needs a JSON `storageCodec`, is
rejected on a list field, and a query using it fails unless the adapter
advertises `databasePluginFieldStructuralContainsCapability`, which the
PostgreSQL adapter does. A field may also declare `snapshotUpdateInput` for
extra update input (typed with `FieldUpdateInputCarrier`),
`existingRows(schema)` for rows that exist when storage adds the field, and
`storageDefault`; adapters read the last two with `readPluginFieldExistingRows`
and `readPluginFieldStorageDefault`. A plugin field may defer its required
create value until `resolveInput`, and a unique plugin field must carry
`UniqueFieldCarrier` in its type to be a `where` target.

`definePluginFieldFamily({ fieldKind, builder: { name, contexts } })` names a
non-empty subset of `stored`, `embedded`, `virtual` and `output`, with exactly
one factory per context; a context may override the family's kind. An
output-context factory returns
`definePluginOutputDescriptor(kind, { list, required }, snapshot)`, re-exported
as `defineOutputDescriptor` by `@ultimabase/plugin-kit`. Registration rejects a
Core kind, a duplicate, an unstable declaration, an unsupported context, and a
factory that returns another kind. Return the receipt of
`fields.register(family)` from the `schema` callback, or the configured factory
does not offer the method. A family without `builder` registers the kind for
fields your plugin adds through a schema patch, and offers developers no builder
method.

## Add a schema factory

A plugin that owns a kind of schema, such as Roles with `App.RoleSchema` or
authentication with `App.UserSchema`, adds a schema factory to the configured
application through `provideSchemaFactories()`, typed by a
`SchemaFactoriesHKT` slot. A factory receives
`define(options, statics)`: the same declaration as `App.Schema.define`,
with `statics` bound to every class it creates, so its declarations take the
same `indexes`, feature keys and `.with` rules as any schema. The factory's
own behaviour options are a rule too, as Roles offers `.with({ roles: … })`.

A plugin whose schema identifies callers, as `App.UserSchema` does, types the
request principal for applications: add Core's type-only
`PrincipalSchemaCarrier` to the statics of the schema it designates, and a key
such as `readonly 'community.accounts': true` to Core's
`PrincipalSchemaProviders` interface by declaration merging from the plugin
package. `Principal` then points to that schema once `Register` names the
application, and the `principal` key of `Register` still wins.

If the package must instead expose one final schema class of its own, use the
low-level Core boundary `Schema.defineSpecialized(options, createStatics)`.
The factory returns the static capabilities only; Core attaches them before
freezing the exact schema class. Results stay frozen plain data and never gain
methods. A specialization does not receive an application, adapter,
authority, or mutable prototype, and it does not register its class
automatically.

Type the schemas your factory creates as
`DeclaredSchemaShape<SchemaFactoryShape<'Name'>>`, with your factory's name, so
that your statics slot recognizes them and adds their commands.

## Inspect the compiled contracts

Tools can read `application.compile().operations` for the operations plugins
declared and `application.compile().schemaSurfaces` for the plugin commands
each schema gained. Both are descriptions without their executable parts:
operation entries omit the `input` and `result` contracts, and each surface
names its schema by `className`, not by constructor. Keep the original
operation or schema declaration for work that needs to execute it.

Each compiled schema exposes `schema.definition.provenance`, the inert owner and
`contributionId` of its schema, fields, options, indexes and applied patches.
Read it to verify which contribution added what.

## Verify

Compile the application graph with and without your plugin. With the plugin,
confirm the field or option appears only on the schemas that set the feature
and that its provenance names your contribution. Typecheck a consumer
of the packed package: the feature key, the `.with` rule, the added fields,
and the commands must offer the same completions, hovers, signatures, and
diagnostics as from source. Check the misuses too: a rule passed to `define`,
a rule without its feature, and a rule whose plugin is not installed must
each fail, as the example's `tests/schema-misuse.test.ts` checks.

Run the `@ultimabase/testing/plugins` conformance suite for the generic
repeatability check, then add a focused assertion for the field, rule, or
command your plugin promises. Finally start a JavaScript application: the
plugin's Runtime behavior must not depend on TypeScript.
