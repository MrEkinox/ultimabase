Master is trusted server-side authority for work that must bypass
authorization. It belongs to one exact application and requires a successful
audit before an elevated command runs. It is not a role, authenticated user,
transport flag, or substitute for an ordinary application policy.

## Configure a trusted server command

The example is the
[queries example](https://github.com/MrEkinox/ultimadatabase/tree/main/examples/queries),
whose tests check each result described here. `DATABASE_URL` is supplied by
the server environment. It uses
PostgreSQL for persistence and the optional Access plugin, and its
`Announcement` schema lets only signed-in authors create: an ordinary
anonymous create is denied with `PERMISSION_DENIED`. Keep the code on the
server, never in a browser bundle.

The application owns its `MasterAuthority`. In-process use needs no key,
only the mandatory `onUse` audit:

</include>

A trusted server command requests Master for one call:

<include cwd meta='title="src/maintenance.ts"'>

</include>

Run that command from an entry point that owns startup and cleanup:

<include cwd meta='title="src/run-maintenance.ts"'>
	../../examples/queries/src/run-maintenance.ts#run-maintenance
</include>

Calling `createMaintenanceAnnouncement('Rebuild complete')` from trusted
server code returns the created announcement and emits one audit event, with
the key ID `in-process`, before the write. If the audit callback throws,
elevation fails and no announcement is written. `console.info`
is only a local demonstration; use an audit sink with appropriate durability,
access controls, and failure handling for production.

## Choose the entry path

`useMasterKey: true` is the concise, trusted direct-server option. It never
verifies a raw key: the audit event carries the first configured key ID, or
`in-process` when the authority has no key. The option is a boolean, so a
conditional elevation stays one call:

<include cwd meta='title="tests/master.test.ts"'>
	../../examples/queries/tests/master.test.ts#conditional
</include>

With `isScheduledJob` false, `attempt` rejects with `PERMISSION_DENIED`:
`false` is identical to omitting the option. It inherits the current
authority and never downgrades a Master request. Any other value is rejected
before execution. Derive the value from server-side state only, never from
request input such as the body, query string, or headers. Plugin-initiated
elevation still requires the plugin's `authority:elevate` privilege. That
privilege suffices without a configured `masterAuthority`: sign-up
in [Password Authentication](/docs/1.0.0/plugins/official/password-authentication)
creates its User that way, each elevation being recorded as a `debug` line of
the application logger. Your own server code still needs a configured
authority.

Only a transport that accepts raw keys needs them, and it refuses to start
without one: `httpPlugin({ master: true })` names that option in its error.
Give the keys as `keys`, or as a function the application reads once, when it
starts, so importing the application reads no secret, as the
[HTTP example](https://github.com/MrEkinox/ultimadatabase/tree/main/examples/http)
does:

<include cwd meta='title="src/ultimabase.ts"'>
	../../examples/http/src/ultimabase.ts#application
</include>

When a trusted transport receives a raw key, `authorizeMasterKey(app, rawKey)`
from `@ultimabase/core/plugin` verifies it and returns an opaque grant;
`RequestEngine.useMasterKey(grant, reason)` then audits and binds the
elevation to its exact application. A
grant or Master context from another application is rejected, even if both
applications reuse the same `MasterAuthority` object in sequential lifetimes.
Disposing an application does not make its grants or contexts reusable: obtain
a fresh grant for its replacement. This does not revoke persisted user sessions.

The optional HTTP Master header works only when explicitly enabled. The
public application ID selects one application first; only that application's
authority may verify and audit the raw key. A client-supplied `useMasterKey`
flag, shaped context, foreign grant, or alternative header cannot select
Master. See [HTTP](/docs/1.0.0/plugins/official/http) for that
separate transport setup.

You can pass a trusted `context` together with `useMasterKey: true` in the same
options: the supplied context is elevated and keeps its typed request values and
principal; only its authority changes. Operations that run inside a request that
is already Master, such as nested writes, Hooks or a `transaction()` callback,
inherit that authority without a new elevation, so `onUse` runs once per
elevation.

## Know what Master bypasses

Master bypasses authorization owned by Access and ACL. It does **not** bypass:

- Core structural validation or installed application validation;
- Hooks, input resolution, or prepared-operation transforms;
- automatic transactions, database constraints, or rollback;
- reference maintenance, lifecycle work, or integrity checks.

<Callout type="warn" title="Keep credentials out of public output">
	Client `useMasterKey` flags, shaped contexts, metadata, grants, and
	alternative headers never create Master. Never log a raw key or place it in
	request metadata, a schema field, a browser bundle, or an error response.
</Callout>

A public application ID identifies the expected active application; it is public data,
not a secret or authorization proof. For ordinary user requests, use
[Access](/docs/1.0.0/plugins/official/access)
or [ACL](/docs/1.0.0/plugins/official/acl-permissions)
instead of Master.
