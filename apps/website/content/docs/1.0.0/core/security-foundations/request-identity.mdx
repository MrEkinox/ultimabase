A `RequestContextValue<T>` is a typed, validated slot for one request. An
identity plugin can use it to attach a principal after checking credentials;
another plugin might attach a tenant or API-client identity. The value is
information for installed policies, not permission by itself.

## Derive a typed context

```ts title="src/request-identity.ts"
import {
	RequestContext,
	RequestContextValue,
	requestSources,
} from '@ultimabase/core'

export const tenantId = new RequestContextValue<string>(
	'acme.identity.tenant-id',
	(value: unknown) => {
		if (typeof value !== 'string' || value.length === 0) {
			throw new TypeError('Tenant id must be a non-empty string')
		}
		return value
	},
)

const anonymous = RequestContext.anonymous({
	requestId: 'request-123',
	source: requestSources.internal,
})

export const scoped = anonymous.withValue(tenantId, 'tenant-42')
export const currentTenant = scoped.getValue(tenantId) // string | undefined
export const authorityMode = scoped.access.mode // 'anonymous'
```

`withValue()` validates and snapshots the value, then returns a new context.
`anonymous` remains unchanged. If the original context belongs to an
application, the derived one retains that ownership and its authority
provenance. Reading requires the exact token object: another token with the
same name is not interchangeable. Adding the same token twice fails instead
of silently replacing identity.

## Use a context in a direct operation

Outside an active request, pass the trusted context together with the started
application in the final operation options. This also lets a background job
carry its own cancellation signal:

```ts title="src/read-posts.ts"
import { RequestContext, requestSources } from '@ultimabase/core'

import { Post } from './post.js'

export const readPostsForJob = (requestId: string, signal: AbortSignal) => {
	const context = RequestContext.anonymous({
		requestId,
		source: requestSources.internal,
		signal,
		metadata: { job: 'daily-report' },
	})

	return Post.findMany({ limit: 20 }, { context })
}
```

The result contains only records visible to this anonymous request. The caller
can pass an `AbortController`'s signal and call `abort()` while the job is in
progress.
Core checks the signal at execution boundaries and reports
`OPERATION_CANCELLED`; this does not promise that an adapter can interrupt SQL
already in progress. `metadata` carries safe request-local information, not a
credential or permission grant; Core rejects credential-shaped metadata keys.
Inside an active request or transaction, omit these options to inherit its
context, signal, authority, and transaction instead. See
[Query Overview](/docs/1.0.0/core/reading-data/overview#execution-context).

## Identity is not a grant

Values can inform Access rules, ACL subject resolution, relation shaping,
Hooks, and audit metadata. An installed policy must explicitly consume the
value to make an authorization decision. Core authority still has only
`anonymous` and `master` modes; an authenticated user normally remains in
`anonymous` mode.

The optional Password Auth plugin exposes `passwordPrincipal` and
`passwordSession` tokens after it verifies a session; they read the session
itself. Policies read the principal from Core instead (next section). The
session context carries safe identifiers and dates, not the raw token,
password, verifier, Master grant, role, or authorization decision. See
[Password Authentication](/docs/1.0.0/plugins/official/password-authentication)
for the actual credential flow.

## The current principal

The principal is the authenticated identity of a request: a Core `Pointer` to
a row of the authentication provider's identity schema, or `undefined` when
the caller is anonymous. Core owns no user schema, session or credential. One
authentication plugin provides it (a second provider fails at startup;
without one, the principal is always `undefined`), and Core resolves it at
most once per request context. Nested, hook-issued and transactional
operations inherit it, and `useMasterKey` keeps it: Master changes authority,
not identity. Server code outside a request has no principal.

Access rules and predicates, the Hooks `context.principal`, ACL callbacks,
Roles and `ultimabase.can()` receive it as `principal`; plugins read it with
`getRequestPrincipal(context)` or `getCurrentPrincipal()`. Name the identity
schema once in `Register` to type it by name:

```ts title="src/ultimabase.ts"
declare module '@ultimabase/core' {
	interface Register {
		readonly app: typeof ultimabase
		readonly principal: 'TodoUser'
	}
}
// principal: Pointer<"TodoUser"> | undefined
```

Without it, `principal` is typed as `PointerValue`. Server code that runs on
behalf of a user names it explicitly: `context.withPrincipal(pointer)` returns
a context with that principal, `withPrincipal(undefined)` an anonymous one.

## Policy predicates

A `PolicyPredicate` is a boolean decision that needs no row filter. It
receives `{ principal, operation, schema }` and is accepted wherever a policy
rule returns a decision, for example in Access rules:

```ts title="src/policies.ts"
import { isAuthenticated, type PolicyPredicate } from '@ultimabase/core'

export const isStaff: PolicyPredicate = function isStaff({ principal }) {
	return principal !== undefined && staff.has(principal.id)
}
// access: { create: isAuthenticated, delete: isStaff }
```

Write predicates as named, side-effect-free functions: Core may call them
several times (retried transactions, `can()`). A predicate that throws
rejects the operation; the error stays masked unless it is a
[`PublicError`](/docs/1.0.0/core/runtime/api-errors#publicerror).

## Ask before acting

`ultimabase.can({ operation, schema, item, principal })` tells whether an
operation would be permitted, combining every installed policy as at
execution time, without executing it: no hook, input resolution, validation,
write or event runs.

```ts title="src/can-edit.ts"
const canEdit = await ultimabase.can({
	operation: 'update',
	schema: Todo,
	item: { id: todoId },
})
```

`principal` defaults to the current request's principal; pass one (or
`undefined` for an anonymous caller) to ask about another identity. Without
`item` the answer is `true` when no guard denies the operation, a row filter
counting as permitted for its rows. For `create`, `item` is candidate data.
For other operations `item.id` names a persisted row, read in a rolled-back
transaction: a missing or hidden row answers `false`. Field rules do not
apply. Master is always permitted. The answer can change before execution,
which remains the enforcement point.

<Callout type="warn" title="Never derive authority from request data">
	A header, JSON field, metadata flag, lookalike context, or caller-selected
	boolean cannot create Master authority. A credential-owning plugin validates
	untrusted input before attaching safe identity values; only Core can create
	the private provenance of a Master request.
</Callout>
