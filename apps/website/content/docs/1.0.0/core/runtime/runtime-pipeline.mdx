Direct TypeScript commands and the REST and GraphQL transports enter the same
Core Runtime. A transport converts its input into a logical operation; it does
not run its own database or authorization pipeline. Core fixes the execution
order, while installed plugins contribute behavior at declared boundaries.
Core owns normalization and transaction commit. Plugin authors can contribute
logical before/after-operation behavior and prepared-target transforms;
normalization and commit are not contribution points.

The shared policy, before/after behavior, result, and commit contracts use the
closed `RuntimeLogicalOperationAst` union. It contains native database
operations plus the existing product-neutral `plugin-schema-mutation`
identity, so callbacks can narrow that discriminant directly. This does not
make a schema mutation an adapter operation: normalization, prepared CRUD
transforms, `RuntimePipeline.execute()`, and database execution remain native
operation boundaries.

## Mutation path

<Mermaid
	description="A mutation is normalized, validated and checked against installed policy, then resolved and checked again before business behavior, persistence, result projection and commit. Post-commit events follow commit."
	chart="flowchart TB
    A[Normalize and structurally validate] --> B[Initial policy and visible target]
    B --> C[Resolve input, validate again, recheck policy]
    C --> D[Before behavior, write, after behavior]
    D --> E[Restrict and project result]
    E --> F[Commit]
    F --> G[Post-commit events]"
/>

Core first checks the input's basic structure. Installed policy may reject the
operation or narrow its target. For updates and deletes, Core then loads and
locks the visible target. Field and schema input resolution can use that
original item; target-aware transforms run before Core's mandatory final
structural validation. Defaults and generators are not replayed. The optional
Validation plugin then runs application validators as the last step before
storage: its issues and Core's structural issues form one `VALIDATION_ERROR`,
and a validator's output is checked structurally again before it is stored.

Core reevaluates value-dependent policy after the final candidate exists.
Optional business before-Hooks run next, followed by the database operation and
business after-Hooks. After-Hooks can still abort the transaction. Core applies
final output restrictions and the caller's `select` / `include` projection
before commit. After-commit work (Hooks `afterCommit` and events) runs only
after a successful commit, outside the transaction, without delaying the
response.

Policy contributions are monotonic: deny-only guards, row filters, adapter
constraints, field restrictions, and output subsets can narrow accumulated
access but never broaden it. Neither a later Hook nor a physical persistence
rewrite can remove a protected constraint.

## Reads and ownership

Reads use the same normalization, protected-policy, adapter, and result-shaping
boundaries, but they do not run mutation input resolution, mutation Hooks, or
an automatic transaction. An explicit transaction can contain reads. Included
pointer and relation targets pass through their own visibility checks; a
caller selection does not override policy.

Core owns structural validation, protected-policy accumulation, the logical
operation, transaction lifetime, and result boundary. Optional Validation,
Access, ACL, and Hooks plugins supply their own rules or callbacks; absent
plugins add no neutral substitute. The database plugin executes the protected
physical plan. Master authority bypasses authorization policy, not validation,
Hooks, transactions, database constraints, or integrity work.
