Core errors have transport-independent codes. A public HTTP request adds another
boundary: the layer that has accepted the request owns its response format.
Application selection and credential checks happen before REST or GraphQL can
handle the request.

## Find the owning boundary

| When the failure occurs        | Owner and representation                                       | Start here                                                                              |
| ------------------------------ | -------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Direct TypeScript command      | Core `FrameworkError` or the operation's declared plugin error | [Core errors](/docs/1.0.0/reference/core-api/errors)                                    |
| Before a protocol route begins | HTTP plugin's safe `HTTP_*` JSON envelope                      | [HTTP troubleshooting](/docs/1.0.0/plugins/official/http-and-apis/http#troubleshooting) |
| After REST begins              | REST plugin's JSON envelope and `REST_*` codes                 | [REST API](/docs/1.0.0/plugins/official/http-and-apis/rest)                             |
| After GraphQL begins           | GraphQL response errors and safe extensions                    | [GraphQL](/docs/1.0.0/plugins/official/http-and-apis/graphql)                           |

## Read only public error data

HTTP and REST both use an `error` object, but their codes and mappings remain
separate. For example, malformed REST read input can return:

```json
{
	"error": {
		"code": "REST_READ_INVALID_INPUT",
		"message": "The REST read request is malformed.",
		"retryable": false,
		"requestId": "request-123"
	}
}
```

The HTTP layer adds `X-UltimaBase-Request-Id` and
`Cache-Control: private, no-store` to its responses. The request ID helps
correlate a sanitized report with server diagnostics; it is not a credential.
Core's `FrameworkError.toJSON()` includes only the code, retryability, and
explicitly public message or details. Diagnostic messages, stacks, causes,
and internal details stay private.

Before route dispatch, malformed or ambiguous headers use `HTTP_BAD_REQUEST`;
application or credential rejection uses `HTTP_APPLICATION_REJECTED`. After
REST begins, unsupported versions, body limits, authorization, validation, and
missing targets use REST-owned codes. Unknown REST failures become the fixed
`REST_INTERNAL_ERROR`, not an exception string.

GraphQL follows its own response format. Explicitly public Core or plugin
failures may retain safe extensions such as code, retryability, request ID,
and optional JSON details. Unknown failures are masked as
`INTERNAL_SERVER_ERROR`.

## Handle a failure safely

Check the owner, stable code, and request ID first. Do not use the HTTP status
alone to infer whether a failure happened before or after dispatch. Never log
or attach a raw credential, password, session token, Master key, private
record, or stack trace to a public error report. For code lookup and safe
handling examples, see [Core Errors](/docs/1.0.0/reference/core-api/errors).
