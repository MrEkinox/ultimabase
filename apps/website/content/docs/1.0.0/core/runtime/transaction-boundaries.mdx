The [Transactions](/docs/1.0.0/core/writing-data/transactions) page shows how
application code groups commands. This page explains why a command cannot
silently escape the active database transaction.

## One active request scope

A root mutation with no active transaction opens one adapter transaction.
Runtime derives a transaction-bound request engine and installs it in the
current asynchronous scope before the mutation runs. Nested writes and
database operations started by optional Hooks inherit that exact engine; they
do not open sibling transactions. A root read does not open a transaction, but
it can join an explicit one.

<Mermaid
	description="A root mutation or explicit request transaction establishes one scoped engine. Every nested operation inherits it, then the outer transaction commits once or rolls back as a unit."
	chart="flowchart TB
    A[Root mutation or request.transaction] --> B[One scoped engine]
    B --> C[Root command]
    B --> D[Nested commands and Hook-started work]
    C --> E[Outer transaction finalization]
    D --> E
    E --> F[Commit once or roll back]"
/>

`request.transaction(callback)` creates the same kind of bound engine for
several commands. Its application, context, authority, and request metadata
remain unchanged. Schema terminals without an explicit engine use the current
scope. Runtime waits for operations started inside it, even if the callback
forgot to await one, before finalizing the transaction. A failed operation
makes the scope rollback-only even if user code catches its rejection.

Nested calls to `request.transaction()` fail with `TRANSACTION_ERROR`; there
are no public savepoints. A transaction-bound engine or query retained after
the callback closes also fails rather than running outside the transaction.

## Commit is the dividing line

Business after-Hooks, final output restriction, and result projection happen
before the outer commit and may still abort it. Named events emitted from an
optional Hook context are buffered with the transaction. Rollback discards
them; a successful commit releases them to matching consumers. A consumer
failure occurs after commit and cannot undo committed rows.

Automatic transactions are an application invariant, not a transport feature.
The same mutation has the same boundary whether it began in TypeScript, REST,
or GraphQL.
