Pass a `where` object to a read to match records. Its field names and available
operators follow the schema. Fields and operators at the same level combine with
`AND`; use `AND`, `OR`, and `NOT` for nested groups. A plain value on a scalar,
enum, or pointer field means equality, as in Prisma: `where: { id }` or
`where: { published: true }`.

The examples use the `Post` schema of the
[queries example](./overview): `published` is a boolean, `title` a string,
`views` an integer, and `tags` a string list.

<include cwd meta='title="src/reads.ts"'>
	../../examples/queries/src/reads.ts#discover
</include>

Every returned post is published, has 100–10,000 views inclusive, matches at
least one `OR` branch, and does not have a title starting with `Archive`. An
empty match returns `[]`. Core validates the filter before execution and
intersects it with installed access restrictions; a `where` clause never grants
access to otherwise hidden records.

## Equality shorthand

On a non-list scalar, enum, or pointer field, a value that is not a plain
object means `eq`, and `null` means `isNull: true`:

<include cwd meta='title="src/reads.ts"'>
	../../examples/queries/src/reads.ts#drafts
</include>

This is exactly `{ author: { eq: authorId }, published: { eq: false },
summary: { isNull: true } }`; Core normalizes both forms to the same filter.
An operand of a `uuid` field, or a pointer's target id, must be a UUID: a
malformed one throws a `TypeError` naming its path as soon as the read is
called, before any database work (`where.id must be a valid UUID` for the
shorthand, `where.id.eq must be a valid UUID` for the explicit form).
List, `json`, `object`, and relation fields keep explicit operators, because a
value there can look like an operator object (`{ tags: { eq: ['a'] } }`,
`{ metadata: { eq: { a: 1 } } }`). GraphQL filter inputs keep `{ eq }`, since a
GraphQL input value is either a scalar or an object. REST `where` JSON accepts
the shorthand; a pointer's shorthand is its target id there, because the
tagged pointer JSON object would read as operators.

## Scalar and list operators

Autocomplete shows only operators supported by the chosen field kind.

| Field kind            | Operators                                           | Operand and meaning                                                                                                          |
| --------------------- | --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Comparable scalar     | `eq`, `ne`, `in`, `notIn`                           | One value or an array of candidate values.                                                                                   |
| Ordered scalar        | `gt`, `gte`, `lt`, `lte`, `between`, `notBetween`   | Values of the field's type. A range uses `{ lower, upper }`, including both bounds for `between`.                            |
| String                | `contains`, `startsWith`, `endsWith`, `matches`     | Text; `matches` takes `{ source, flags }`, not a `RegExp` instance.                                                          |
| Nullable stored field | `isNull`, `isNotNull`                               | Only the literal `true`.                                                                                                     |
| One-dimensional list  | `eq`, `ne`, `has`, `hasSome`, `hasEvery`, `isEmpty` | `eq`/`ne` compare the whole list; `has` checks one element; `hasSome`/`hasEvery` take arrays; `isEmpty: true` excludes null. |

<include cwd meta='title="tests/filters.test.ts"'>
	../../examples/queries/tests/filters.test.ts#operators
</include>

Several operators on one field also combine with `AND`: `{ views: { gte: 100,
lt: 1_000 } }` includes 100 but excludes 1,000. `notBetween` matches values
strictly outside its inclusive bounds. Use `isNull: true` or `isNotNull: true`
to distinguish a nullable list from an empty one. Equality on a list or a JSON
array compares the whole value (length, elements and order); use `has`,
`hasSome` or `hasEvery` to test membership.

`matches` accepts one portable regular-expression subset that every database
runs identically: literals, `.`, bracket classes with ranges and negation,
`\d \w \s` and their negations, the anchors `^` and `$`, plain and `(?:...)`
groups, alternation, and the quantifiers `* + ? {m} {m,} {m,n}`, with the flags
`case-insensitive`, `dot-matches-newline` and `multiline`. Backreferences,
lookaround, named groups, Unicode properties, lazy quantifiers and other
escapes are rejected with `VALIDATION_ERROR` before the database runs.

## Operators the database runs

Each database adapter declares the operators it executes for each field kind.
Core checks a filter against that declaration before the database is reached:
an operator the adapter does not declare fails with `VALIDATION_ERROR`, whose
public details name the `field` and `operator`. The PostgreSQL adapter declares
every operator on this page.

## Structured values

`field.json()` and `field.object()` support structural `contains`, key checks
(`hasKey`, `hasAnyKeys`, `hasAllKeys`), and `at` path predicates. Here
`Post.metadata` is a JSON field and `Author.profile` is a typed embedded object
with `contact.email`:

Each `at` path is an array of segments, not a dotted string. Typed object
paths and operands follow the declared shape; JSON paths are dynamic. See [Embedded Objects](/docs/1.0.0/core/data-modeling/embedded-objects) for
how nested values are declared.

## Pointers and relations

A pointer stores one target ID. Its `eq`, `ne`, `in`, and `notIn` operators take
target IDs. The equality shorthand also accepts a `Pointer` of the declared
target already in hand, such as the current principal (`where: { author:
principal }`); a `Pointer` of another schema is a type error and a
`VALIDATION_ERROR`. `is` and `isNot` instead test a nested filter against the
visible target:

<include cwd meta='title="src/reads.ts"'>
	../../examples/queries/src/reads.ts#pointer-filter
</include>

`Post.author` is an optional pointer to an `Author` with a `verified` boolean.
`eq` checks stored identity without reading the target. `is` and
`isNot` apply target visibility and policy. `isNot` also matches a null pointer
or a target hidden by policy; add `isNotNull: true` if a null pointer must not
match. Use `null` or `isNull: true` to find null pointers, not `eq: null`.

A to-many relation is not a stored list. It supports `some`, `none`, and
`every` with a target-schema `where` object; `count` compares the number of
visible related records and can include its own target `where`. For a simple
existence check, use `isEmpty: true` or `isNotEmpty: true`. `every` is also true
when the visible relation is empty, so combine it with `isNotEmpty: true` when
at least one target is required. See [Related Data](./related-data) for
relation-filter examples and visibility rules.
