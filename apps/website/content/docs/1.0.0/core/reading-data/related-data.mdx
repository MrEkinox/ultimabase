## Include related models

Use `include` to load related records with their own selections. A root
`select` chooses fields on each `Post`; it does not load an author or comments
on its own.

Start with [Relationships](/docs/1.0.0/core/data-modeling/relationships) and
register the schemas in a started application. The example assumes `Post` has
an `author` pointer to a schema with `name`, and a `comments` relation to a
schema with `body` and `published`.

Include a to-one author and a filtered, ordered, bounded comment collection:

```ts title="src/post-context.ts"
import { Post } from './schemas.js'
import { ultimabase } from './ultimabase.js'

export const readPostsWithContext = () =>
	Post.findMany(
		{
			include: {
				author: { select: { name: true } },
				comments: {
					limit: 3,
					orderBy: { createdAt: 'desc', id: 'asc' },
					select: { body: true },
					where: { published: { eq: true } },
				},
			},
			select: { title: true },
		},
		{ ultimabase },
	)
```

Pointer and relation cardinality deliberately expose different nested clauses:

| Included field | Allowed shaping                                                   | Result                          |
| -------------- | ----------------------------------------------------------------- | ------------------------------- |
| Pointer        | `select`, nested `include`                                        | Selected target model or `null` |
| Relation       | `where`, `orderBy`, `offset`, `limit`, `select`, nested `include` | Readonly selected model array   |

A pointer already identifies at most one target. A nested `where` on its
inclusion would make an existing pointer appear missing merely because it
failed a projection filter, so Core rejects that clause. Filter parent posts by
their author with the pointer's `is` or `isNot` operator in the root `where`;
see [Filters](./filters).

Relation filtering runs before ordering, offset, and limit. Its offset applies
independently to each parent's comment collection, not across all comments.
The `id` tie-breaker makes a page deterministic when several comments share a
timestamp. An inclusion filter does not remove a parent post whose included
collection is empty.

## Choose where a filter applies

| Goal                               | Put the condition in                                                     | Effect                                                             |
| ---------------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| Return only matching parents       | Root `where` with a relation predicate such as `comments: { some: ... }` | Filters posts; does not load comments.                             |
| Load only matching targets         | `include.comments.where`                                                 | Filters each returned post's comment array; does not filter posts. |
| Define the relation's usual subset | `f.relation({ where })`                                                  | Narrows every read through that exact relation field.              |

These conditions intersect when used together. The declared relation filter
cannot be overridden by a caller and does not replace authorization.
If you already have one persisted parent and do not need to return it again,
read its collection through a [relation handle](/docs/1.0.0/core/data-modeling/relationships#read-through-a-relation-handle).

## Verify

The inferred root model contains `id`, `title`, included `author`, and included
`comments`. When present, the author contains `id` and `name`; each included
comment contains `id` and `body`. Unselected fields are absent from those
nested model types. Installed output policies can narrow the runtime result
further.

Missing or inaccessible pointer targets become `null`. Relations contain only
visible targets and therefore become an empty array when none remain. The
array may also be shorter than the complete visible relation because this
example requests at most three comments. Nested target reads still apply
installed policies, protected constraints, output restrictions, and the
relation's declared shaping filter.

## Relation predicates

Relation predicates match source records without loading the related
collection. This example assumes `Author.posts` is a to-many relation and
`Post` declares `published` and `score`:

```ts title="src/relation-filters.ts"
import { Author } from './schemas.js'
import { ultimabase } from './ultimabase.js'

export const readEstablishedAuthors = () =>
	Author.findMany(
		{
			where: {
				posts: {
					count: { gte: 3, where: { published: { eq: true } } },
					some: { published: { eq: true }, score: { gte: 80 } },
				},
			},
		},
		{ ultimabase },
	)
```

The result contains authors, not their posts. `some` requires a visible match,
`none` requires no visible match, and `every` requires no visible violation.
`every` is true for an empty visible relation; add `isNotEmpty: true` when at
least one target is required. Use `isEmpty: true` or `isNotEmpty: true` for
simple existence checks. `count` needs at least one comparison with a
non-negative safe-integer operand; its optional target `where` filters the
counted posts before the comparison. Here each returned author has at least
three visible published posts, including at least one with a score of 80 or
more.

Every predicate observes the same visible universe: physical membership, the
field's declared filter, target policies and constraints, then the caller's
predicate. Hidden targets are not counted.

## Declared relation filters

A relation may declare one static target filter, such as
`where: { published: { eq: true } }`. Use a synchronous contextual callback
when that subset depends on the request. Register both schemas below in the
same application:

```ts title="src/channel.ts"
import { UltimaBase } from '@ultimabase/core'

export const Message = UltimaBase.Schema.define({
	className: 'DocsMessage',
	fields: (f) => ({ published: f.boolean({ required: true }) }),
})

export const Channel = UltimaBase.Schema.define({
	className: 'DocsChannel',
	fields: (f) => ({
		messages: f.relation({
			target: () => Message,
			where: ({ context, where }) =>
				context.access.mode === 'master' ? where : where.eq('published', true),
		}),
	}),
})
```

The immutable `WhereBuilder` starts empty and targets the exact related schema.
The callback receives request context but no source item, adapter, transaction,
transport request, or authority grant. It must return a target `WhereInput` or
builder synchronously; an empty builder adds no restriction.

Master does not automatically bypass a declared relation filter. This example
deliberately returns the empty builder for Master; other requests see only
published messages. The filter intersects with caller filters, authorization
row filters, and protected constraints. It shapes reads but does not authorize
them, modify physical membership, or change `connect`, `disconnect`, `set`, or
`clear`.

For example, an authentication plugin can attach a validated principal to the
request context. A relation callback may use that value to choose the visible
subset for anonymous and authenticated readers. The same declared filter
applies to relation handles, eager inclusion, predicates, counts, and reads
through REST or GraphQL. Test both request contexts against those paths when
you use a contextual relation. Protect the target schema separately with an
authorization policy: a relation filter is not a permission check.
