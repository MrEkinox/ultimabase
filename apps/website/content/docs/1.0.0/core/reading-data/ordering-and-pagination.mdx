## Outcome

Combine explicit ordering, a positive `limit`, and a non-negative `offset` to
return a predictable page from a Core collection read. Core does not provide a
cursor or snapshot pagination API.

## Prerequisites

Start with [Query Overview](./overview) and a started application. The example
assumes `Post` declares `title` and has the built-in `createdAt` field. Choose
an order that uniquely positions matching records; a timestamp alone may
repeat.

## Steps

This function uses a zero-based `pageIndex`: `0` is the first page. Declare
ordering priority in object property order and add `id` to break timestamp
ties:

```ts title="src/post-page.ts"
import { Post } from './schemas.js'

const PAGE_SIZE = 25

export const readPostPage = (pageIndex: number) => {
	const offset = pageIndex * PAGE_SIZE

	if (
		!Number.isSafeInteger(pageIndex) ||
		pageIndex < 0 ||
		!Number.isSafeInteger(offset)
	) {
		throw new RangeError('pageIndex must produce a non-negative safe offset')
	}

	return Post.findMany({
		limit: PAGE_SIZE,
		offset,
		orderBy: { createdAt: 'desc', id: 'asc' },
		select: { createdAt: true, title: true },
	})
}
```

`limit` is the maximum number of rows returned and must be a positive safe
integer. `offset` skips matching rows and must be a non-negative safe integer;
omitting it is equivalent to zero. Core validates both values, but the example
also rejects invalid page indexes before executing a read.

`orderBy` accepts `asc`, `desc`, or `null` for each supported persisted field.
`null` skips that field. The first non-null property has highest priority.
Core adds neither default ordering nor an `id` tie-breaker: without a complete
order, two reads may return tied records in different positions. A field may be
used for ordering without being included in `select`. Every database adapter
sorts `null` last, in ascending and descending order alike.

## Verify

For `pageIndex = 2`, the function requests the third page: at most 25 rows
after skipping 50. Repeating it against unchanged data with the same order
produces the same page. A page may contain fewer than 25 rows or be empty.

Offset pagination is not a snapshot. Inserting, deleting, or changing records
between calls can shift later pages even with a unique order. Deep offsets may
also become expensive. Use focused filters when scanning a large collection;
do not treat an offset as a durable continuation token.

An included relation has its own per-parent pagination; continue with
[Related Data](./related-data). The optional [REST API](/docs/1.0.0/plugins/official/rest)
uses numeric pagination parameters, while [GraphQL](/docs/1.0.0/plugins/official/graphql)
exposes Relay connections and cursors.
