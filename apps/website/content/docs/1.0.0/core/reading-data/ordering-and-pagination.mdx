## Outcome

Read a collection page by page with `take` and `after`. Each page starts
strictly after the last row of the previous one, so rows that did not change are
never repeated or skipped, even when other rows are inserted or deleted between
calls.

## Prerequisites

Start with [Query Overview](./overview). The examples use the `Post` and
`Comment` schemas of the queries example; `Post` declares `title` and has the
built-in `createdAt` field.

## Steps

Pass the last row of a page as `after` to read the next one. Request one row
more than the page size to know whether another page exists:

<include cwd meta='title="src/reads.ts"'>
	../../examples/queries/src/reads.ts#post-page
</include>

`take` is the maximum number of rows returned and must be a positive safe
integer. `after` is a row received from a read of the same shape: Core reads
the ordered fields and `id` from it and returns the rows strictly after it. The
row must contain every ordered field and `id`, so select them; a missing field
fails with `VALIDATION_ERROR` naming the fields, with
`publicDetails: { parameter: 'after' }`.

`orderBy` accepts `asc`, `desc`, or `null` for each non-list scalar or enum
field; `null` skips that field. Any other key fails to compile: pointers,
relations, lists, `json`, `object`, and plugin field kinds (such as the ACL
field) have no order every adapter shares. An untyped caller that orders by
one fails with `query.orderBy.<field> must name a non-list scalar or enum
field`. The first non-null property has highest
priority. Core completes every collection order with `id` ascending unless `id`
is already ordered, so the order is total; without `orderBy` rows come in `id`
order. Every database adapter sorts `null` last, in ascending and descending
order alike, and positions follow the same rule.

Strings are ordered and compared (`gt`, `lt`, `between`) by the database
column's collation, so the order of letters, case and accents depends on how
the database was created.

A position is an ordinary filter of the caller: each ordered field counts as
filtered, so ordering by a field the caller may not read or filter fails with
`PERMISSION_DENIED`, and a hand-written position returns exactly the rows its
filter would.

Server-side reads have no default `take`: without `take`, `findMany` returns
every matching row. The REST and GraphQL limits
(`pagination: { defaultTake, maxTake }`, 100 and 1,000 by default) apply only to
their clients. Read a large table in batches with `after`, here every comment:

<include cwd meta='title="src/reads.ts"'>
	../../examples/queries/src/reads.ts#batches
</include>

`skip` skips a number of rows instead. It cannot be combined with `after`
(`VALIDATION_ERROR`); prefer `after`, because an offset shifts when rows are
inserted or deleted and becomes slower as it grows.

## Verify

Reading every page with `after` returns each unchanged row exactly once, in
the order of a single read without `take`. A row whose ordered values change
between two calls may move to another page.

An included relation has its own per-parent `take` and `skip`; continue with
[Related Data](./related-data). The optional [REST API](/docs/1.0.0/plugins/official/rest)
returns a `nextCursor` to pass as `after`, and [GraphQL](/docs/1.0.0/plugins/official/graphql)
maps Relay `first` and `after` to the same positions.
