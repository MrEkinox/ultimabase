Read from the schema class returned by `App.Schema.define()`. `findMany` accepts one
object for filtering, selection, related data, ordering, and pagination.
Execution options are a separate final argument, not part of that read input.

Every TypeScript block of the Reading Data and Writing Data pages is copied
from the
[queries example](https://github.com/MrEkinox/ultimadatabase/tree/main/examples/queries),
a small blog application whose tests check each result described here. Its
`Post` schema declares `published` and `title`, and the application is
started with PostgreSQL; see [Manual Installation](/docs/1.0.0/manual-installation)
for that setup.

The call returns at most 20 frozen `Post` results, ordered newest first with
`id` breaking equal-timestamp ties. Each result contains `id`, `createdAt`,
and `title`; `published` filters the rows but is not returned because the
selection does not request it. The types inferred from the schema check
fields and operators, with no generation step. Core still validates
JavaScript and untrusted transport input before executing a read.

## Read terminals

| Terminal                           | Result               | No visible match | Use it for                       |
| ---------------------------------- | -------------------- | ---------------- | -------------------------------- |
| `findMany(input?, options?)`       | Readonly model array | Empty array      | A filtered collection            |
| `findOne(input?, options?)`        | One model or `null`  | `null`           | One matching record              |
| `findOneOrThrow(input?, options?)` | One model            | `NOT_FOUND`      | One record that must exist       |
| `count({ where? }, options?)`      | `number`             | `0`              | Collection cardinality           |
| `exists({ where? }, options?)`     | `boolean`            | `false`          | Presence without loading a model |

`findOne` and `findOneOrThrow` take the same input (`where`, `orderBy`,
`select`, `include`) and communicate different expectations. Use
`findOneOrThrow({ where: { id } })` when absence is exceptional, for example a
known ID; it fails with `NOT_FOUND` where `findOne` returns `null`, including
when the record exists but is hidden from the caller. Use `findOne` when a
filter may legitimately match nothing. If several records may match, add
`orderBy` to define which is first; Core adds no implicit ordering. Access
treats both as its `one` read. `count` and `exists` accept `where`, not
selection, ordering, or pagination clauses.

## Execution context

Inside an active request, hook, or transaction, a read can omit the final
argument and inherit the exact application, request context, cancellation
signal, authority, and any active transaction. A read does not start a
transaction by itself. In a root script, worker, or test, a read runs on the
sole started application, as the first example does.
Execution options can also supply a trusted context when needed; they are
never serialized as query input by a transport. See
[Request Identity](/docs/1.0.0/core/security-foundations/request-identity#use-a-context-in-a-direct-operation)
for an explicit context and cancellation example.

## Reusable dynamic queries

Object input is the API. Compose reusable parts as typed objects and spread
them into one read:

<include cwd meta='title="src/reads.ts"'>
	../../examples/queries/src/reads.ts#reusable-parts
</include>

A `Where<typeof Post>` object can be annotated directly. A selection must stay
literal, so that the result type lists exactly its fields: declare it
`as const` and check it with `satisfies Select<typeof Post>`. A variable
annotated `Select<typeof Post>` is rejected by a read, because its flags are
`boolean` and cannot type an exact result.

These objects perform no I/O and retain no application or authority; the
read executes them. A root `findMany` always completes its order with `id`
ascending (see [Ordering and Pagination](./ordering-and-pagination)).

Applications receive a `QueryBuilder` or `WhereBuilder` only where Core passes
one: Access rules, relation `where` callbacks, and `QueryScope` functions. The
main entry exports both as types; plugin authors construct them from
`@ultimabase/core/plugin`. Every builder method returns a new frozen branch,
and `include(field, callback)` shapes a related target with its own typed
builder. See [Related Data](./related-data) for the corresponding object
input.

## Read failures

Core rejects unknown fields, invalid operators, negative pagination, and
invalid relation predicates before database work. Input it cannot build a
query from, such as a malformed UUID operand, rejects the read with a
`TypeError`. A read never throws from the call itself: every failure rejects
the promise it returns, so `.catch()` or `await` inside `try` handles them all.
An adapter can also reject a query capability it does not support. Installed
policy may hide a target, so `findOneOrThrow()` can report `NOT_FOUND` even
when the record exists physically.
See [API Error Boundaries](/docs/1.0.0/core/runtime/api-errors) for safe error
handling.
