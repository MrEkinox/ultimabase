Use a **pointer** when a record refers to one target. Use a **relation** when it
owns or exposes a collection of targets. Neither stores the related records
inside the source model. Declare both at the schema root, not inside an
[embedded object](./embedded-objects).

## Pointers

A pointer stores one immutable logical reference: the exact target schema plus
one record ID. It does not load the target and does not expose a mutable target
object.

```ts title="src/session.ts"
import { UltimaBase } from '@ultimabase/core'

export const Account = UltimaBase.Schema.define({
	className: 'DocsAccount',
	fields: (f) => ({
		email: f.string({ required: true }),
	}),
})

export const Session = UltimaBase.Schema.define({
	className: 'DocsSession',
	fields: (f) => ({
		account: f.pointer({
			required: true,
			target: 'DocsAccount',
		}),
		expiresAt: f.dateTime({ required: true }),
	}),
})
```

Register both schemas in the same application. During compilation, UltimaBase
resolves `target: 'DocsAccount'` to the exact registered `Account` schema;
an unknown target fails before database setup. Typegen can then expose the
exact target type for `Session.account`.

Link a session to an existing account with `{ connect: accountId }` in create
or update data; `connect` also accepts a `Pointer` of the declared target
already in hand, such as `{ connect: session.account }`. The target must be
visible to the caller (see [Nested Writes](/docs/1.0.0/core/writing-data/nested-writes#every-link-checks-visibility)),
and a `Pointer` or ID assigned directly to the field is rejected.
`Account.pointer(id)` is the only way to create a pointer value, for filters,
comparisons, and ACL entries: `new Pointer(...)` is not public, and the
exported `Pointer` serves type annotations and `instanceof Pointer` checks.
Creating a pointer performs no I/O and does not prove that the target exists. Its ordinary value is a `Pointer`, not
an `Account` row, and it does not read its target: use `Account.findOne` with
the pointer's `id`. `pointer.equals(other)` compares exact schema identity and
ID, while `pointer.toJSON()` returns the immutable logical shape
`{ type: 'pointer', className: 'DocsAccount', id }`.

A required pointer cannot be `null`. An optional pointer can be `null` in a
complete record, and `null` in update data unlinks it; pointers cannot be lists or have defaults. Use
[Defaults and Nullability](./defaults) for the general presence rules.

### Read a pointer's target

After registering both schemas and starting the application with a persistence
plugin, read a persisted session without including its account. Its selected
`account` field is still a `Pointer`, not a loaded `Account` row. A pointer does
not read its target (ADR-0310); read it through the target schema:

```ts title="src/read-account.ts"
import { Account, Session } from './session.js'

export const readSessionAccount = async (sessionId: string) => {
	const session = await Session.findOneOrThrow({
		where: { id: sessionId },
		select: { account: true },
	})

	return Account.findOne({
		where: { id: session.account.id },
		select: { email: true },
	})
}
```

`Account.findOne()` returns the selected row or `null` if the target is missing
or excluded by a row filter; `Account.exists()` answers with a boolean.
Explicit read-policy denials reject both operations and abort an active
transaction, just like other read errors. Neither changes the stored pointer or
grants access to its target.

If you already know that you need the account when reading the session, use
`include: { account: { select: { email: true } } }` on `Session.findOneOrThrow()`
instead. See [Related Data](/docs/1.0.0/core/reading-data/related-data) for
inclusion behavior.

### Pointer deletion behavior

`onDelete` controls how deleting a target affects its referencing records:

- `restrict` (the default) rejects target deletion while the pointer exists,
  with `REFERENCE_VIOLATION`, and rolls the transaction back;
- `cascade` deletes the referencing record in the same transaction,
  transitively; a `restrict` anywhere in the chain fails the whole deletion;
- `setNull` clears the pointer and therefore requires an optional field.

The database adapter enforces these actions inside the deletion's
transaction. Cascades are physical: deleted or cleared referencing records run
no Hooks, Access, ACL or Soft Delete rewrite, and emit no event. Delete
children explicitly from a Hook of the parent deletion when they need their own
lifecycle. Under concurrent writes, a write that references a record and the
deletion of that record never both commit with a dangling pointer: either the
write commits first and the deletion applies its action to it, or the deletion
commits first and the write fails with `REFERENCE_VIOLATION`. The error names
only the schema of the record being deleted or written. A soft deletion
triggers no referential action.

Use `indexed: 'unique'` on a pointer to express a one-to-one constraint. Use a
relation instead when one record owns a changing set of target members.

## Relations

A relation declares a typed to-many edge between two schemas. The source record
does not contain a target array. The database adapter stores membership, while
Runtime provides explicit reads and mutations through the relationship.

```ts title="src/post.ts"
import { UltimaBase } from '@ultimabase/core'

export const Author = UltimaBase.Schema.define({
	className: 'DocsAuthor',
	fields: (f) => ({
		name: f.string({ required: true }),
		posts: f.relation({ mappedBy: 'author', target: 'DocsPost' }),
	}),
})

export const Post = UltimaBase.Schema.define({
	className: 'DocsPost',
	fields: (f) => ({
		author: f.pointer({
			required: true,
			target: 'DocsAuthor',
		}),
		reviewers: f.relation({ target: 'DocsAuthor' }),
		title: f.string({ required: true }),
	}),
})
```

### Owning and inverse sides

`Post.reviewers` owns an independent membership set. `Author.posts` is inverse:
`mappedBy: 'author'` derives its members from `Post.author` instead of storing
a second edge. Static compilation resolves target names and verifies that the
inverse points to a compatible field. A one-to-one relationship uses a unique
pointer, not a one-item relation.

Relations do not appear as arrays in ordinary results unless they are
included, and create or update data changes them only through link commands.
Results have no relation handles (ADR-0310). Use an explicit
relationship schema with pointers when the edge itself needs fields such as
role, position, status, or creation time.

<Callout type="info" title="One source of membership truth">
	Choose either an owning relation or an inverse `mappedBy` relation for an
	edge. Do not mirror both sides with separately writable relation sets.
</Callout>

## Read through a relation

Use `include` to load pointer and relation targets with a parent result;
[Related Data](/docs/1.0.0/core/reading-data/related-data) owns the full
example, selection rules, and filtering behavior. The following examples assume
registered `Author` and `Post` schemas in a started application with a
persistence plugin.

```ts title="src/read-reviewers.ts"
import { Post } from './post.js'

export const readReviewers = async (postId: string) => {
	const post = await Post.findOneOrThrow({
		where: { id: postId },
		select: { id: true },
		include: { reviewers: { take: 10, select: { name: true } } },
	})

	return post.reviewers
}
```

To ask a question about membership without loading the collection, filter the
parent through the relation. For example, check whether a post has a particular
visible reviewer:

```ts title="src/read-reviewers.ts"
import { Post } from './post.js'

export const hasReviewer = (postId: string, reviewerId: string) =>
	Post.exists({
		where: { id: postId, reviewers: { some: { id: reviewerId } } },
	})
```

Included relations and relation filters apply the relation's declared filter and
target policies; their results describe visible membership, which can differ
from physical membership. Use `where` in the include or in the relation filter
to narrow it further.

## Change relation membership

Change membership through the relation field of `updateOne` data, with the
same `connect`, `disconnect`, and `set` commands as any link (see
[Nested Writes](/docs/1.0.0/core/writing-data/nested-writes)). For example,
add one reviewer and return the visible membership:

```ts title="src/add-reviewer.ts"
import { Post } from './post.js'

export const addReviewer = (postId: string, reviewerId: string) =>
	Post.updateOne({
		where: { id: postId },
		data: { reviewers: { connect: [reviewerId] } },
		include: { reviewers: { select: { name: true } } },
	})
```

`{ set: [] }` removes every membership visible under the installed policies,
including members the relation's declared `where` hides from reads. Results have no relation
handles (ADR-0310); the edge itself is not a result field:

| Method                     | Effect                                                                                    |
| -------------------------- | ----------------------------------------------------------------------------------------- |
| `connect(id, options?)`    | Add one target without removing existing edges; it also accepts a non-empty tuple of IDs. |
| `disconnect(id, options?)` | Remove one edge without deleting its target; it also accepts a non-empty tuple of IDs.    |
| `set(ids, options?)`       | Replace membership with the supplied IDs; `[]` is allowed.                                |
| `clear(options?)`          | Remove membership without supplying an empty array.                                       |

Each call has one automatic or inherited transaction and runs installed
source-field policy, target visibility checks, and mutation behavior. Missing
or inaccessible targets both report `NOT_FOUND`; duplicate IDs within one
call are rejected before the transaction. On an owning relation, direct-handle
`set` and `clear` change the complete physical edge set, not only the subset a
read currently shows. An inverse pointer relation instead updates its visible
targets through ordinary pointer mutations; an operation that would clear a
required inverse pointer fails. Use [Nested Writes](/docs/1.0.0/core/writing-data/nested-writes)
when the relation change must be part of the same atomic root create or update;
its `set` preserves policy-hidden memberships.

A relation may declare a static or request-contextual `where` to narrow every
read through that field, in the final `.with({ relations })` of its schema,
keyed by the relation field name. It intersects with caller filters and target
policies; it does not grant access or change membership. See
[Related Data](/docs/1.0.0/core/reading-data/related-data#declared-relation-filters).
