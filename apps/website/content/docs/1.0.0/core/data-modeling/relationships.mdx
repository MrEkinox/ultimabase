Use a **pointer** when a record refers to one target. Use a **relation** when it
owns or exposes a collection of targets. Neither stores the related records
inside the source model. Declare both at the schema root, not inside an
[embedded object](./embedded-objects).

## Pointers

A pointer stores one immutable logical reference: the exact target schema plus
one record ID. It does not load the target and does not expose a mutable target
object.

The `Order` schema of the
[modeling example](https://github.com/MrEkinox/ultimadatabase/tree/main/examples/modeling)
points to its customer, and `Book` points to its author the same way
(`author: field.pointer({ target: () => Author, required: true })`):

<include cwd meta='title="src/orders.ts"'>
	../../examples/modeling/src/orders.ts#order
</include>

Register both schemas in the same application. The target is a function that
returns the schema, so TypeScript types `Order.customer` from `Customer`
directly, and schemas in separate files, or a schema and itself, may reference
each other. During compilation, UltimaBase resolves the function to the
registered `Customer` schema; an unregistered target fails before database
setup. A target may also name the registered `className`
(`target: 'Customer'`), which the application's `Register` declaration
types.

Link an order to an existing customer with `{ connect: customerId }` in create
or update data; `connect` also accepts a `Pointer` of the declared target
already in hand, such as `{ connect: order.customer }`. The target must be
visible to the caller (see [Nested Writes](/docs/1.0.0/core/writing-data/nested-writes#every-link-checks-visibility)),
and a `Pointer` or ID assigned directly to the field is rejected.
`Customer.pointer(id)` is the only way to create a pointer value, for filters,
comparisons, and ACL entries: `new Pointer(...)` is not public, and the
exported `Pointer` serves type annotations and `instanceof Pointer` checks.
Creating a pointer performs no I/O and does not prove that the target exists. Its ordinary value is a `Pointer`, not
a `Customer` row, and it does not read its target: use `Customer.findOne` with
the pointer's `id`. `pointer.equals(other)` compares exact schema identity and
ID, while `pointer.toJSON()` returns the immutable logical shape
`{ type: 'pointer', className: 'Customer', id }`.

A required pointer cannot be `null`. An optional pointer can be `null` in a
complete record, and `null` in update data unlinks it; pointers cannot be lists or have defaults. Use
[Defaults and Nullability](./defaults) for the general presence rules.

### Read a pointer's target

In the started application of the example, read a book without including its
author. Its selected `author` field is still a `Pointer`, not a loaded `Author`
row. A pointer does not read its target (ADR-0310); read it through the target
schema:

<include cwd meta='title="tests/relationships.test.ts"'>
	../../examples/modeling/tests/relationships.test.ts#read-pointer
</include>

`Author.findOne()` returns the selected row, here `{ id, lastName: 'Lovelace' }`,
or `null` if the target is missing or excluded by a row filter;
`Author.exists()` answers with a boolean.
Explicit read-policy denials reject both operations and abort an active
transaction, just like other read errors. Neither changes the stored pointer or
grants access to its target.

If you already know that you need the author when reading the book, include it
instead:

<include cwd meta='title="tests/relationships.test.ts"'>
	../../examples/modeling/tests/relationships.test.ts#include-pointer
</include>

`withAuthor.author` is the plain object `{ id, lastName: 'Lovelace' }`. See
[Related Data](/docs/1.0.0/core/reading-data/related-data) for inclusion
behavior.

### Pointer deletion behavior

`onDelete` controls how deleting a target affects its referencing records:

- `restrict` (the default) rejects target deletion while the pointer exists,
  with `REFERENCE_VIOLATION`, and rolls the transaction back;
- `cascade` deletes the referencing record in the same transaction,
  transitively; a `restrict` anywhere in the chain fails the whole deletion;
- `setNull` clears the pointer and therefore requires an optional field.

`Book.author` keeps the default and `Order.customer` declares `cascade`:

<include cwd meta='title="tests/relationships.test.ts"'>
	../../examples/modeling/tests/relationships.test.ts#delete-target
</include>

`refused` is a `FrameworkError` with `code: 'REFERENCE_VIOLATION'` and
`publicDetails: { schema: 'Author' }`; the customer's orders are deleted with
it.

The database adapter enforces these actions inside the deletion's
transaction. Cascades are physical: deleted or cleared referencing records run
no Hooks, Access, ACL or Soft Delete rewrite, and emit no event. Delete
children explicitly from a Hook of the parent deletion when they need their own
lifecycle. Under concurrent writes, a write that references a record and the
deletion of that record never both commit with a dangling pointer: either the
write commits first and the deletion applies its action to it, or the deletion
commits first and the write fails with `REFERENCE_VIOLATION`. The error names
only the schema of the record being deleted or written. A soft deletion
triggers no referential action.

Use `indexed: 'unique'` on a pointer to express a one-to-one constraint. Use a
relation instead when one record owns a changing set of target members.

## Relations

A relation declares a typed to-many edge between two schemas. The source record
does not contain a target array. The database adapter stores membership, while
Runtime provides explicit reads and mutations through the relationship.

The example declares both kinds. `Author.books` is the inverse of the
`Book.author` pointer:

<include cwd meta='title="src/catalog.ts"'>
	../../examples/modeling/src/catalog.ts#author
</include>

`Customer.wishlist` owns its membership, and its final `.with` declares a
filter for every read through it:

<include cwd meta='title="src/customers.ts"'>
	../../examples/modeling/src/customers.ts#customer
</include>

### Owning and inverse sides

`Customer.wishlist` owns an independent membership set. `Author.books` is
inverse: `mappedBy: 'author'` derives its members from `Book.author` instead of
storing a second edge. Static compilation resolves targets and verifies that the
inverse points to a compatible field. A one-to-one relationship uses a unique
pointer, not a one-item relation.

Relations do not appear as arrays in ordinary results unless they are
included, and create or update data changes them only through link commands.
Results are plain data with no relation methods (ADR-0310). Use an explicit
relationship schema with pointers when the edge itself needs fields such as
role, position, status, or creation time.

<Callout type="info" title="One source of membership truth">
	Choose either an owning relation or an inverse `mappedBy` relation for an
	edge. Do not mirror both sides with separately writable relation sets.
</Callout>

## Read through a relation

Use `include` to load pointer and relation targets with a parent result;
[Related Data](/docs/1.0.0/core/reading-data/related-data) owns the full
example, selection rules, and filtering behavior. In the started application of
the example:

<include cwd meta='title="tests/relationships.test.ts"'>
	../../examples/modeling/tests/relationships.test.ts#include-inverse
</include>

`author.books` holds the author's two books, each `{ id, title }`, ordered by
title. To ask a question about membership without loading the collection,
filter the parent through the relation. For example, check whether a customer
wishes for a particular book:

<include cwd meta='title="tests/relationships.test.ts"'>
	../../examples/modeling/tests/relationships.test.ts#relation-filter
</include>

`wishesNotes` is `true`. The same question about an unpublished book in the
wishlist answers `false`: included relations and relation filters apply the
relation's declared filter and target policies; their results describe visible membership, which can differ
from physical membership. Use `where` in the include or in the relation filter
to narrow it further.

## Change relation membership

Change membership through the relation field of `updateOne` data, with the
same link commands as any nested write (see
[Nested Writes](/docs/1.0.0/core/writing-data/nested-writes)). For example,
add two books to a wishlist and return the visible membership:

<include cwd meta='title="tests/relationships.test.ts"'>
	../../examples/modeling/tests/relationships.test.ts#connect-wishlist
</include>

Both books are members, but `updated.wishlist` lists only the published one:
the declared filter of `.with({ relations })` hides the draft from every read,
`exists` included. Results have no relation handles (ADR-0310); the edge itself
is not a result field. A relation field takes these commands:

| Command      | Effect                                                                                      |
| ------------ | ------------------------------------------------------------------------------------------- |
| `connect`    | Add a non-empty list of targets, by ID or `Pointer`, without removing existing members.     |
| `disconnect` | Remove a non-empty list of members without deleting the targets.                            |
| `set`        | Replace the membership with the supplied list, alone in its object; `[]` removes every one. |
| `create`     | Create a non-empty list of targets and link them.                                           |
| `update`     | Update linked targets, each given as `{ id, data }`.                                        |

`connect`, `disconnect`, `create`, and `update` combine in one object; `set`
stands alone. A missing or inaccessible target reports `NOT_FOUND` and rolls
the update back. `{ set: [] }` removes every membership visible under the
installed policies, including members the relation's declared `where` hides
from reads. On an inverse relation whose pointer is required, such as
`Author.books`, `disconnect` and `set` are not offered: unlinking a book would
clear its required `author`.

A relation may declare a static or request-contextual `where` to narrow every
read through that field, in the final `.with({ relations })` of its schema,
keyed by the relation field name, as `Customer` does. It intersects with caller
filters and target policies; it does not grant access or change membership. See
[Related Data](/docs/1.0.0/core/reading-data/related-data#declared-relation-filters).
