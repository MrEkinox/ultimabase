Use a **pointer** when a record refers to one target. Use a **relation** when it
owns or exposes a collection of targets. Neither stores the related records
inside the source model. Declare both at the schema root, not inside an
[embedded object](./embedded-objects).

## Pointers

A pointer stores one immutable logical reference: the exact target schema plus
one record ID. It does not load the target and does not expose a mutable target
object.

```ts title="src/session.ts"
import { Schema } from '@ultimabase/core'

export const Account = Schema.define({
	className: 'DocsAccount',
	fields: (field) => ({
		email: field.string({ required: true }),
	}),
})

export const Session = Schema.define({
	className: 'DocsSession',
	fields: (field) => ({
		account: field.pointer({
			required: true,
			target: 'DocsAccount',
		}),
		expiresAt: field.dateTime({ required: true }),
	}),
})

export const accountReference = Account.pointer(
	'0198f090-2a50-7000-8000-000000000034',
)
```

Register both schemas in the same application. During compilation, UltimaBase
resolves `target: 'DocsAccount'` to the exact registered `Account` schema;
an unknown target fails before database setup. Typegen can then expose the
exact target type for `Session.account`.

Use `Account.pointer(id)` in a create or update input to reference an existing
account. The equivalent general form is `new Pointer(Account, id)`. Constructing
a pointer performs no I/O and does not prove that the target exists;
persistence enforces the relationship. Its ordinary value is a `Pointer`, not
an `Account` model. `pointer.equals(other)` compares exact schema identity and
ID, while `pointer.toJSON()` returns the immutable logical shape
`{ type: 'pointer', className: 'DocsAccount', id }`.

A required pointer cannot be `null`. An optional pointer can be `null` in a
complete record; pointers cannot be lists or have defaults. Use
[Defaults and Nullability](./defaults) for the general presence rules.

### Pointer deletion behavior

`onDelete` controls how deleting a target affects its referencing records:

- `restrict` (the default) rejects target deletion while the pointer exists;
- `cascade` deletes the referencing record;
- `setNull` clears the pointer and therefore requires an optional field.

Use `indexed: 'unique'` on a pointer to express a one-to-one constraint. Use a
relation instead when one record owns a changing set of target members.

## Relations

A relation declares a typed to-many edge between two schemas. The source record
does not contain a target array. The database adapter stores membership, while
Runtime provides explicit reads and mutations through the relationship.

```ts title="src/post.ts"
import { Schema } from '@ultimabase/core'

export const Author = Schema.define({
	className: 'DocsAuthor',
	fields: (field) => ({
		name: field.string({ required: true }),
		posts: field.relation({ mappedBy: 'author', target: 'DocsPost' }),
	}),
})

export const Post = Schema.define({
	className: 'DocsPost',
	fields: (field) => ({
		author: field.pointer({
			required: true,
			target: 'DocsAuthor',
		}),
		reviewers: field.relation({ target: 'DocsAuthor' }),
		title: field.string({ required: true }),
	}),
})
```

### Owning and inverse sides

`Post.reviewers` owns an independent membership set. `Author.posts` is inverse:
`mappedBy: 'author'` derives its members from `Post.author` instead of storing
a second edge. Static compilation resolves target names and verifies that the
inverse points to a compatible field. A one-to-one relationship uses a unique
pointer, not a one-item relation.

Relations do not appear as arrays in ordinary model values or create/update
data. A persisted model can create a relation handle through `relation(name)`
even when the collection was not included in its result. Use an explicit
relationship schema with pointers when the edge itself needs fields such as
role, position, status, or creation time.

<Callout type="info" title="One source of membership truth">
	Choose either an owning relation or an inverse `mappedBy` relation for an
	edge. Do not mirror both sides with separately writable relation sets.
</Callout>

## Read related records

After registering `Author` and `Post` in a started application with a
persistence plugin, as in
[Manual Installation](/docs/1.0.0/manual-installation), use `include` to load
related models explicitly:

```ts title="src/read-posts.ts"
import { Post } from './post.js'
import { ultimabase } from './ultimabase.js'

export const readPosts = () =>
	Post.findMany(
		{
			include: {
				author: { select: { name: true } },
				reviewers: { limit: 5, select: { name: true } },
			},
			select: { title: true },
		},
		{ ultimabase },
	)
```

Each returned post includes its `id` and `title`. Its included `author` is a
selected `Author` model or `null` if the target is missing or inaccessible;
that does not change the stored pointer's requiredness. `reviewers` is a
readonly array of up to five visible `Author` models, not a stored array on
`Post`. A relation with no visible targets yields `[]`.

For a collection you do not want to include in a parent result, read through
the persisted model's relation handle:

```ts title="src/read-reviewers.ts"
import { Post } from './post.js'
import { ultimabase } from './ultimabase.js'

export const readReviewers = async (postId: string) => {
	const post = await Post.get({ id: postId }, { ultimabase })
	const reviewers = post.relation('reviewers')

	return reviewers.findMany(
		{ limit: 10, select: { name: true } },
		{ ultimabase },
	)
}
```

## Change relation membership

A persisted model's relation handle can change an existing membership without
updating an array field or deleting a target record. For example, add one
reviewer and then read the visible membership:

```ts title="src/add-reviewer.ts"
import { Post } from './post.js'
import { ultimabase } from './ultimabase.js'

export const addReviewer = async (postId: string, reviewerId: string) => {
	const post = await Post.get({ id: postId }, { ultimabase })
	const reviewers = post.relation('reviewers')

	await reviewers.connect(reviewerId, { ultimabase })
	return reviewers.findMany({ select: { name: true } }, { ultimabase })
}
```

The returned models have `id` and `name`; the edge itself is not a model field.
Choose the mutation that describes the intended membership change:

| Method                     | Effect                                                                                    |
| -------------------------- | ----------------------------------------------------------------------------------------- |
| `connect(id, options?)`    | Add one target without removing existing edges; it also accepts a non-empty tuple of IDs. |
| `disconnect(id, options?)` | Remove one edge without deleting its target; it also accepts a non-empty tuple of IDs.    |
| `set(ids, options?)`       | Replace membership with the supplied IDs; `[]` is allowed.                                |
| `clear(options?)`          | Remove membership without supplying an empty array.                                       |

Each call has one automatic or inherited transaction and runs installed
source-field policy, target visibility checks, and mutation behavior. Missing
or inaccessible targets both report `NOT_FOUND`; duplicate IDs within one
call are rejected before the transaction. On an owning relation, direct-handle
`set` and `clear` change the complete physical edge set, not only the subset a
read currently shows. An inverse pointer relation instead updates its visible
targets through ordinary pointer mutations; an operation that would clear a
required inverse pointer fails. Use [Nested Writes](/docs/1.0.0/core/writing-data/nested-writes)
when the relation change must be part of the same atomic root create or update;
its `set` and `clear` preserve policy-hidden memberships.

A relation may declare a static or request-contextual `where` to narrow every
read through that field. It intersects with caller filters and target policies;
it does not grant access or change membership.
