Create input and persisted output answer different questions. You may omit a
field from create input, but a complete persisted record still has a value for
it: the supplied value, a default or generated value, or `null`. A narrowed
read selection can omit that field from the returned model; see
[Models](./models) for the difference between a complete record and a selected
snapshot.

## From create input to persisted value

The `Order` schema of the
[modeling example](https://github.com/MrEkinox/ultimadatabase/tree/main/examples/modeling)
has two required fields, defaulted, nullable defaulted, optional, generated,
and automatically dated fields:

<include cwd meta='title="src/orders.ts"'>
	../../examples/modeling/src/orders.ts#order
</include>

Create an order with only its required input:

<include cwd meta='title="tests/defaults.test.ts"'>
	../../examples/modeling/tests/defaults.test.ts#required-input
</include>

Without an output policy restricting fields, `order` contains the supplied
`customer` and `total`, `status: 'pending'`, `giftWrap: false` and
`coupon: 'WELCOME'` from their defaults, `note: null` and `pickupTime: null`, a fresh `reference` from its
factory, `number: 1n` from the database, an operation-time `placedAt` and
`placedOn`, and the generated `id`, `createdAt`, and `updatedAt` system fields.
The example requests no `select`, so it returns the complete result permitted
by installed output policy.

## Omitted input versus explicit null

These rules apply to stored value fields. Relations and virtual fields have
their own input and output contracts.

| Declaration                                  | Omitted on create          | Explicit `null`        | Complete value |
| -------------------------------------------- | -------------------------- | ---------------------- | -------------- |
| No option, such as `note`                    | Becomes `null`             | Accepted               | `T \| null`    |
| `required: true`, such as `total`            | Rejected                   | Rejected               | `T`            |
| `default: value`, such as `status`           | Uses the default           | Rejected               | `T`            |
| `default` with `nullable: true` (`coupon`)   | Uses the default           | Accepted; stays `null` | `T \| null`    |
| `autoNow: true`, such as `placedAt`          | Generates a temporal value | Rejected               | `T`            |
| `autoIncrement: true`, such as `number`      | Database assigns a value   | Rejected               | `T`            |
| System field: `id`, `createdAt`, `updatedAt` | Generated by UltimaBase    | Not accepted as input  | `T`            |

Here, `T` means the field's declared value type. TypeScript rejects a value the
table rejects, and Runtime does too. A plain optional field is optional in
create input, but its complete persisted value is `T | null`, not an absent
property. A default makes a field non-null: an order can never hold
`status: null`. Declare `nullable: true` beside a default when `null` is a
meaningful value; the default then fills an omitted value only:

<include cwd meta='title="tests/defaults.test.ts"'>
	../../examples/modeling/tests/defaults.test.ts#explicit-null
</include>

This order persists `coupon: null`, not `'WELCOME'`.

Each option has one meaning. `required: true` means create input must supply
the value; beside a default it adds nothing, since the field is already
non-null. `nullable: true` is accepted only beside a default, since a field
without one is already nullable unless it is `required`; it cannot be combined
with `required: true` or `autoIncrement: true`.

The same nullability rule applies to the whole value of a list or embedded
object, such as `favoriteGenres` or `previousAddresses` of `Customer`; list
elements themselves cannot be `null`. See
[Fields](./fields) and [Embedded Objects](./embedded-objects) for their shapes.

## Defaults and generators

A default can be a static value or a zero-argument factory, such as
`reference` of `Order`: `field.uuid({ default: () => crypto.randomUUID() })`.
The factory runs once for each record whose create input omits that field, not
when the schema is declared. Its result is validated like a supplied
value. Use a factory when each record needs a fresh value; a static default is
snapshotted so later changes to the original object or array cannot change it.

`autoNow: true` works on `date`, `time`, and `dateTime` fields. It fills an
omitted value from the operation's clock; a supplied valid value is used as-is.
It cannot be combined with `default` or `list: true`. `autoIncrement: true` is
available only for top-level `int` and `bigint` fields and relies on database
adapter support rather than a Core-generated sequence.

On PostgreSQL, a defaulted column is `NOT NULL` unless its field declares
`nullable: true`. Schema synchronization adds the constraint to an existing
column; when rows of a database created before this rule hold `null` there,
synchronization fails and names the column: fill those rows, or declare
`nullable: true`.

<Callout
	type="warn"
	title="Do not use database expressions as portable defaults"
>
	Schema defaults are application values or application factories. Database-side
	expressions belong to database-specific migration or adapter configuration.
</Callout>

## Updates and selections

Defaults, `autoNow`, and auto-increment generation fill missing **create**
values. They do not run again just because an update omits a field. In update
input, omission means “leave unchanged”; setting an optional field to `null`
clears it, while a required or defaulted field rejects `null`. System-generated fields are
not accepted in update input at all:

<include cwd meta='title="tests/defaults.test.ts"'>
	../../examples/modeling/tests/defaults.test.ts#update-null
</include>

The updated order keeps its `number`, `reference`, `placedAt`, and `giftWrap`,
has `status: 'paid'` and `note: null`, and a refreshed `updatedAt`.

The framework-owned `updatedAt` is a separate system rule: UltimaBase refreshes
it on persisted updates. Create and update input cannot set system fields
directly. See [Schemas](./schemas) for their definitions and
[Update Records](/docs/1.0.0/core/writing-data/update) for mutation commands.
