Create input and persisted output answer different questions. You may omit a
field from create input, but a complete persisted record still has a value for
it: the supplied value, a default or generated value, or `null`. A narrowed
read selection can omit that field from the returned model; see
[Models](./models) for the difference between a complete record and a selected
snapshot.

## From create input to persisted value

This schema has one required field, one defaulted field, one plain optional
field, and one automatically dated field:

```ts title="src/publication.ts"
import { UltimaBase } from '@ultimabase/core'

export const Publication = UltimaBase.Schema.define({
	className: 'DocsPublication',
	fields: (f) => ({
		publishedAt: f.dateTime({ autoNow: true }),
		status: f.string({ default: 'draft' }),
		summary: f.string(),
		title: f.string({ required: true }),
	}),
})
```

After `Publication` is registered and the application has started with a
persistence plugin, create a record with only its required input:

```ts title="src/publication-input.ts"
import { Publication } from './publication.js'

const created = await Publication.createOne({
	data: { title: 'Release notes' },
})
console.log(created)
```

Without an output policy restricting fields, `created` contains the supplied title, `status: 'draft'`, `summary: null`, an
operation-time `publishedAt`, and the generated `id`, `createdAt`, and
`updatedAt` system fields. The example requests no `select`, so it returns the
complete result permitted by installed output policy.

## Omitted input versus explicit null

These rules apply to stored value fields. Relations and virtual fields have
their own input and output contracts.

| Declaration                                  | Omitted on create          | Explicit `null`        | Complete value |
| -------------------------------------------- | -------------------------- | ---------------------- | -------------- |
| No option, such as `summary`                 | Becomes `null`             | Accepted               | `T \| null`    |
| `required: true`, such as `title`            | Rejected                   | Rejected               | `T`            |
| `default: value`, such as `status`           | Uses the default           | Accepted; stays `null` | `T \| null`    |
| `required: true` with a default              | Uses the default           | Rejected               | `T`            |
| `autoNow: true`, such as `publishedAt`       | Generates a temporal value | Rejected               | `T`            |
| `autoIncrement: true` on `int` or `bigint`   | Database assigns a value   | Rejected               | `T`            |
| System field: `id`, `createdAt`, `updatedAt` | Generated by UltimaBase    | Not accepted as input  | `T`            |

Here, `T` means the field's declared value type. A plain optional field is
optional in create input, but its complete persisted value is `T | null`, not
an absent property. For example, creating a `Publication` with `status: null`
persists `null`, not `'draft'`. Add `required: true` when a defaulted field must
never be cleared to `null`.

The same nullability rule applies to the whole value of a list or embedded
object; list elements themselves cannot be `null`. See
[Fields](./fields) and [Embedded Objects](./embedded-objects) for their shapes.

## Defaults and generators

A default can be a static value or a zero-argument factory:

`f.uuid({ default: () => crypto.randomUUID() })`.

The factory runs once for each record whose create input omits that field, not
when the schema is declared. Its result is validated like a supplied
value. Use a factory when each record needs a fresh value; a static default is
snapshotted so later changes to the original object or array cannot change it.

`autoNow: true` works on `date`, `time`, and `dateTime` fields. It fills an
omitted value from the operation's clock; a supplied valid value is used as-is.
It cannot be combined with `default` or `list: true`. `autoIncrement: true` is
available only for top-level `int` and `bigint` fields and relies on database
adapter support rather than a Core-generated sequence.

<Callout
	type="warn"
	title="Do not use database expressions as portable defaults"
>
	Schema defaults are application values or application factories. Database-side
	expressions belong to database-specific migration or adapter configuration.
</Callout>

## Updates and selections

Defaults, `autoNow`, and auto-increment generation fill missing **create**
values. They do not run again just because an update omits a field. In update
input, omission means “leave unchanged”; setting an optional field to `null`
clears it, while a required field rejects `null`. System-generated fields are
not accepted in update input at all.

The framework-owned `updatedAt` is a separate system rule: UltimaBase refreshes
it on persisted updates. Create and update input cannot set system fields
directly. See [Schemas](./schemas) for their definitions and
[Update Records](/docs/1.0.0/core/writing-data/update) for mutation commands.
