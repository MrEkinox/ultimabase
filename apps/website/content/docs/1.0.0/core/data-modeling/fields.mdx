Fields describe logical application values, not database columns. Choose a
field for the shape and behavior you need; the installed database plugin decides
how to store it. The `Book` schema of the
[modeling example](https://github.com/MrEkinox/ultimadatabase/tree/main/examples/modeling)
declares one field of each built-in value kind:

<include cwd meta='title="src/catalog.ts"'>
	../../examples/modeling/src/catalog.ts#book
</include>

`price` is an exact decimal string, not a JavaScript `number`. `tags` is a
one-dimensional list of strings; because it is not required, a complete record
may contain `null` when no value was supplied. See
[Defaults and Nullability](./defaults) for the create-input and persisted-value
rules.

## Choose a field family

| You need                                | Choose                                                                                               |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| A scalar, enum, or one-dimensional list | A built-in value field; use `list: true` for a list of that value.                                   |
| A nested value with known fields        | `f.object()`; it belongs to its parent record. See [Embedded Objects](./embedded-objects).           |
| An unstructured JSON document           | `f.json()`; its root must be an object or array, or `null` if optional.                              |
| One reference to another record         | `f.pointer()`; it stores target identity, not a loaded record. See [Relationships](./relationships). |
| A changing set of related records       | `f.relation()`; it represents membership, not a stored array. See [Relationships](./relationships).  |
| A computed, selectable result           | `f.virtual()`; output-only. See [Virtual Fields](./virtual-fields).                                  |
| A distinct value kind owned by a plugin | That plugin's field method, installed in the application.                                            |

Use `object` when the nested shape is part of your model, and `json` when it is
deliberately unstructured. A list of record IDs is not a substitute for a
`pointer` or `relation` when you need relationship behavior.

## Built-in field builders

The `fields` callback receives a field builder, named `field` in the example
and `f` in this table.
Each method returns an immutable declaration; it does not create or load a
record. Choose by the value your application uses, not by a database column type.

| Builder        | Application value           | Builder-specific options or behavior                                                                                          |
| -------------- | --------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `f.string()`   | `string`                    | Text; application formats such as email need the optional Validation plugin.                                                  |
| `f.boolean()`  | `boolean`                   | No builder-specific options.                                                                                                  |
| `f.int()`      | Safe integer `number`       | `autoIncrement` requests adapter-backed generation.                                                                           |
| `f.bigint()`   | Native JavaScript `bigint`  | `autoIncrement` requests adapter-backed generation; transports need an explicit codec.                                        |
| `f.float()`    | `number`                    | Use `decimal` for exact base-10 values.                                                                                       |
| `f.decimal()`  | Exact decimal `string`      | `precision` limits total digits; `scale` limits fractional digits.                                                            |
| `f.uuid()`     | UUID `string`               | UUID syntax is always checked; `default` can supply a generated value.                                                        |
| `f.date()`     | `YYYY-MM-DD` string         | `autoNow` can generate a calendar day.                                                                                        |
| `f.time()`     | Canonical time string       | `timezone` defaults to `false`; `autoNow` can generate a time.                                                                |
| `f.dateTime()` | Canonical date-time string  | `timezone` defaults to `true`; `autoNow` can generate a timestamp.                                                            |
| `f.binary()`   | `Uint8Array`                | Wire encoding belongs to the transport.                                                                                       |
| `f.json()`     | JSON object or array        | Optional fields may also be `null`; root scalars are rejected.                                                                |
| `f.enum()`     | Declared string union       | `values` is a string array or a shared enum from `defineEnum`; see [Enums](#enums).                                           |
| `f.object()`   | Typed nested value          | Declare child `fields`; see [Embedded Objects](./embedded-objects).                                                           |
| `f.pointer()`  | One target reference        | `target` is required; `onDelete` defaults to `restrict`. See [Relationships](./relationships).                                |
| `f.relation()` | To-many target membership   | `target` is required; `mappedBy` declares an inverse; `relations` in `.with` scopes it. See [Relationships](./relationships). |
| `f.virtual()`  | Selected, output-only value | Declare `output`, `select`, and `resolve`; see [Virtual Fields](./virtual-fields).                                            |

`int` and `float` use JavaScript `number`; `bigint` uses native `bigint`, and
`decimal` uses a string so its base-10 value stays exact. Stored value fields
can also use the common options below. Pointers have a narrower option set;
relations and virtual fields do not use stored-value options.

### Values to pass from TypeScript

Some built-in kinds have a stricter shape than their TypeScript type alone
expresses. These are direct application values, before a REST or GraphQL
transport applies its own wire encoding:

| Field      | Valid value                  | Important boundary                                                                                     |
| ---------- | ---------------------------- | ------------------------------------------------------------------------------------------------------ |
| `bigint`   | `42n`                        | A JavaScript `number` is not an exact bigint.                                                          |
| `decimal`  | `'19.99'`                    | Pass a plain decimal string, not `19.99`, exponent notation, or a leading `+`.                         |
| `date`     | `'2026-07-31'`               | A calendar day has no time or timezone.                                                                |
| `time`     | `'14:30:00.000'`             | Milliseconds are required; with `timezone: true`, use `Z` or an offset such as `'14:30:00.000+02:00'`. |
| `dateTime` | `'2026-07-31T14:30:00.000Z'` | An offset is required by default; `timezone: false` instead uses `'2026-07-31T14:30:00.000'`.          |
| `binary`   | `new Uint8Array([1, 2, 3])`  | Pass bytes directly; Base64 or multipart encoding belongs to the transport.                            |

The example creates a book and an order with such values; `order.number`, a
`bigint` generated by the database, is `1n` for the first order:

<include cwd meta='title="tests/fields.test.ts"'>
	../../examples/modeling/tests/fields.test.ts#values
</include>

Core checks these shapes during an operation: `'19.999'` for a decimal of
scale 2, `'2026-02-30'`, `'14:30'` for a time, or a date-time without an offset
fails with `VALIDATION_ERROR`. The application's timezone
controls automatic calendar and zone-less values; it does not relax a field's
required input format. See [Application](/docs/1.0.0/core/application#configure-core-validation-and-time)
for that setting and [Defaults and Nullability](./defaults) for `autoNow`.

## Common options and validation

Stored value fields share several options:

- `required: true` makes a complete value non-null. Create input must supply it
  unless a default or generator can provide it.
- `default` supplies a static value or a zero-argument factory when create input
  omits the field. A default makes the field required: explicit `null` is
  rejected unless the field also declares `required: false`.
- `list: true` creates one list level for a value field; nested arrays belong in
  a JSON document.
- `indexed: true` requests an index, while `indexed: 'unique'` requests a unique
  index from the database adapter. See [Indexes](./schemas#indexes) for choosing
  and preparing one.
- `immutable: true` allows a value on create but rejects developer updates;
  the field is absent from update input, as `isbn` of `Book` shows.
- `description` supplies text for tooling and generated surfaces.

Core validates requiredness, nullability, canonical value shapes, enum values,
and decimal precision and scale. It does not impose application rules such as
string length, email format, or a business-specific numeric range. Add those
through the optional [Validation plugin](/docs/1.0.0/plugins/official/validation).

`autoNow` cannot be combined with `default` or `list: true`. An invalid built-in
option or combination fails during declaration or application compilation;
invalid input values fail when an operation runs. For create-input and
persisted-value details, see [Defaults and Nullability](./defaults).

## Enums

`f.enum({ values })` declares a closed string union. `values` takes one of two
forms. A shared enum comes from `defineEnum(name, values)`:

<include cwd meta='title="src/genre.ts"'>
	../../examples/modeling/src/genre.ts#genre
</include>

`Book.format` passes a string array, a local enum: transports such as GraphQL
name its type from the schema and field path. A shared enum is an immutable
value used only to share one named type: `Book.genre` and the list
`Customer.favoriteGenres` both use the `Genre` type:

<include cwd meta='title="tests/fields.test.ts"'>
	../../examples/modeling/tests/fields.test.ts#enums
</include>

The book gets the default format `'paperback'`, and the customer's
`favoriteGenres` is `['poetry', 'essay']`. Both forms type the field as a
string union; hover the names:

```ts twoslash title="Enum types"
import '../../examples/modeling/src/ultimabase.ts'
import type { Model } from '@ultimabase/core'
// ---cut---
type Genre = Model<'Book'>['genre']
//   ^?
type Format = Model<'Book'>['format']
//   ^?
type FavoriteGenres = Model<'Customer'>['favoriteGenres']
//   ^?
```

Two different shared enums with the same name fail when the application is
constructed. The object-mapping form, TypeScript `enum` objects, and the
`typeName` option are not accepted.

## Virtual results

A `virtual` field declares an output shape, a `select` of persisted dependencies,
and a resolver. The resolver can use the request context and return a value or
a promise. Core loads dependency-only values privately and validates the
resolved output before returning it. Virtual fields are not stored, indexed,
filterable, orderable, or writable. [Virtual Fields](./virtual-fields) explains
dependencies, output typing, request context, and failure behavior.

## Plugin-owned field methods

Importing a plugin package alone does not add its field method. Install the
owning plugin in the application; compilation then adds the method only in the
contexts that plugin supports. TypeScript offers the method on the configured
factory's `App.Schema.define()` builder, with no generation step. See
[Using Plugins](/docs/1.0.0/plugins/using-plugins).
