Fields describe logical application values, not database columns. Choose a
field for the shape and behavior you need; the installed database plugin decides
how to store it.

```ts title="src/product.ts"
import { Schema } from '@ultimabase/core'

export const Product = Schema.define({
	className: 'DocsProduct',
	fields: (field) => ({
		name: field.string({ required: true }),
		price: field.decimal({ precision: 12, required: true, scale: 2 }),
		tags: field.string({ list: true }),
	}),
})
```

`price` is an exact decimal string, not a JavaScript `number`. `tags` is a
one-dimensional list of strings; because it is not required, a complete record
may contain `null` when no value was supplied. See
[Defaults and Nullability](./defaults) for the create-input and persisted-value
rules.

## Choose a field family

| You need                                | Choose                                                                                                   |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| A scalar, enum, or one-dimensional list | A built-in value field; use `list: true` for a list of that value.                                       |
| A nested value with known fields        | `field.object()`; it belongs to its parent record. See [Embedded Objects](./embedded-objects).           |
| An unstructured JSON document           | `field.json()`; its root must be an object or array, or `null` if optional.                              |
| One reference to another record         | `field.pointer()`; it stores target identity, not a loaded record. See [Relationships](./relationships). |
| A changing set of related records       | `field.relation()`; it represents membership, not a stored array. See [Relationships](./relationships).  |
| A computed, selectable result           | `field.virtual()`; output-only. See [Virtual Fields](./virtual-fields).                                  |
| A distinct value kind owned by a plugin | That plugin's field method, installed in the application.                                                |

Core's built-in field methods and their exact options are listed in the
[Field Builders reference](/docs/1.0.0/reference/core-api/fields). For numbers,
`int` and `float` use JavaScript `number`; `bigint` and `decimal` use strings to
preserve exact values. Use `object` when the nested shape is part of your model,
and `json` when it is deliberately unstructured. A list of record IDs is not a
substitute for a `pointer` or `relation` when you need relationship behavior.

## Common options and validation

Value fields share several options:

- `required: true` makes a complete value non-null. Create input must supply it
  unless a default or generator can provide it.
- `default` supplies a static value or a zero-argument factory when create input
  omits the field. A default alone does not make explicit `null` invalid.
- `list: true` creates one list level for a value field; nested arrays belong in
  a JSON document.
- `indexed: true` requests an index, while `indexed: 'unique'` requests a unique
  index from the database adapter.
- `immutable: true` allows a value on create but rejects developer updates.
- `description` supplies text for tooling and generated surfaces.

Core validates requiredness, nullability, canonical value shapes, enum values,
and decimal precision and scale. It does not impose application rules such as
string length, email format, or a business-specific numeric range. Add those
through the optional [Validation plugin](/docs/1.0.0/plugins/official/validation-and-lifecycle/validation).

## Virtual results

A `virtual` field declares an output shape, a `select` of persisted dependencies,
and a resolver. The resolver can use the request context and return a value or
a promise. Core loads dependency-only values privately and validates the
resolved output before returning it. Virtual fields are not stored, indexed,
filterable, orderable, or writable. [Virtual Fields](./virtual-fields) explains
dependencies, output typing, request context, and failure behavior.

## Plugin-owned field methods

Importing a plugin package alone does not add its field method. Install the
owning plugin in the application; compilation then adds the method only in the
contexts that plugin supports. Optional Typegen can generate the matching
application-specific TypeScript declarations. See
[Using Plugins](/docs/1.0.0/plugins/using-plugins) and
[Generate TypeScript Types](/docs/1.0.0/guides/generate-types).
