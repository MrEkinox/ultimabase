An embedded object is a structured value owned by one parent record. Use it
when the nested data has a known shape but no independent identity or lifecycle.

## Define the shape

The `Customer` schema of the
[modeling example](https://github.com/MrEkinox/ultimadatabase/tree/main/examples/modeling)
declares one reusable child shape:

<include cwd meta='title="src/address.ts"'>
	../../examples/modeling/src/address.ts#address
</include>

and uses it twice, for one address and for a list of addresses:

<include cwd meta='title="src/customers.ts"'>
	../../examples/modeling/src/customers.ts#customer
</include>

The reusable `addressFields` callback declares the same child shape in both
places; `EmbeddedFieldBuilder` types its builder, which has no pointer,
relation, or index options. `list: true` wraps that shape in one list; it does
not give each address its own record ID. `typeName` supplies a stable base
name for the object types that schema generators such as GraphQL derive. It
does not create a separate schema or change Runtime behavior. The other fields
of `Customer` appear in [Virtual Fields](./virtual-fields) and
[Relationships](./relationships).

## Create and read values

In the started application of the example, create a customer with only its
required address children:

<include cwd meta='title="tests/embedded.test.ts"'>
	../../examples/modeling/tests/embedded.test.ts#create-customer
</include>

In the result, `shippingAddress.line2` is `null` because it was omitted, and
`previousAddresses` is `[]` because of its default. A missing
required child such as `city`, an unknown child name, or a `null` list item is
rejected. The parent field's `required: true` makes the whole address non-null;
each child has its own requiredness. Without that parent option, an omitted
address would be `null` in a complete result. A narrowed selection or installed
output policy can still omit fields from the returned snapshot. See
[Defaults and Nullability](./defaults) for the general presence rules.

## Update an object or list

An update to a single embedded object is a **deep patch**. Omitted children
keep their stored values, required ones included; a supplied nested object is
patched the same way, while a supplied list or `null` replaces that child. By
contrast, updating an object list **replaces the entire list**: each supplied
item must include its required children. There is no index-based patch of one
list entry.

A patch keeps only what is stored. When an optional object, or an optional
object nested inside one, is stored as `null`, the patch becomes its whole
value and must supply every required child. Otherwise the update fails with a
`VALIDATION_ERROR` whose `field.required` issue names the missing child under
the operation value, for example `['update', 0, 'location', 'value', 'lng']`,
and nothing is written.

This update supplies only two children of `shippingAddress` and a new list,
so each list item includes its required children:

<include cwd meta='title="tests/embedded.test.ts"'>
	../../examples/modeling/tests/embedded.test.ts#update-addresses
</include>

`shippingAddress` keeps its stored `line1` and `countryCode`. The new list
contains only the supplied Paris address, with `line2: null`. The
returned `updated` result is a new frozen snapshot; `customer` is unchanged.
Setting an optional object or list to `null` clears the whole value, while
`[]` means an empty list. See [Update Records](/docs/1.0.0/core/writing-data/update)
for the general mutation contract.

## Boundaries

An embedded object is one logical stored value. Its children can be scalar
values, one-dimensional lists, or further embedded objects. They cannot be:

- pointers or relations, which need top-level schema fields;
- virtual fields, which are output-only;
- indexed or unique child fields, which have no independent index identity;
- auto-incrementing integer children, which need their own database column.

Use a separate schema plus a [pointer](./relationships#pointers) when the nested
thing needs its own `id`, independent updates, or relationships. An embedded
child may still participate in field-level Access and input resolution when
the corresponding plugins are installed; it is not independently addressable
as a record.

For deliberately unstructured documents or multidimensional arrays, use
`f.json()` instead of disguising them as typed field lists. Use the
optional Validation plugin for application-specific constraints on that JSON.
