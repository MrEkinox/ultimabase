A schema declares one kind of stored record: its stable `className` and the
fields that records of that kind can contain. `App.Schema.define()` returns the
inert schema class immediately and derives its local TypeScript contracts from
the field declaration. Registration remains explicit when an application lists
that class in `schemas`.

The [modeling example](https://github.com/MrEkinox/ultimadatabase/tree/main/examples/modeling)
is a small bookshop. Its `Book` schema declares one field of each built-in
value kind and two composite indexes; `App` is the configured factory of
[Application](/docs/1.0.0/core/application#configure-the-application):

</include>

## Declaration options

`UltimaBase.Schema.define()` accepts the following Core options:

| Option      | Required | Purpose                                                                                                             |
| ----------- | -------- | ------------------------------------------------------------------------------------------------------------------- |
| `className` | Yes      | Stable logical name for the schema.                                                                                 |
| `fields(f)` | Yes      | Synchronous callback that returns its stored, relationship, and virtual field declarations. See [Fields](./fields). |
| `indexes`   | No       | Composite indexes over top-level fields.                                                                            |

`define()` accepts no other option: plugin rules such as `access`, `hooks`,
`rest`, `graphql`, or `postgres` are rejected there and go in a final
`.with({ ... })` instead, as [Plugin methods and rules](#plugin-methods-and-rules)
shows. Field-level plugin options, such as a field's `validation`, stay on the
field. Use the configured factory's `App.Schema.define()` to obtain the
methods, rules, and field options of the installed plugins; the zero-plugin
root `UltimaBase.Schema.define()` declares portable Core-only schemas. Importing
a plugin package alone does not install it. See [Using Plugins](/docs/1.0.0/plugins/using-plugins).

## Indexes

An index helps the database find rows for a recurring filter or ordering
pattern. A unique index also rejects duplicate values. Neither kind filters
results or grants access: keep query predicates and authorization rules
explicit. Indexes take storage and add work to writes, so declare them for
queries or uniqueness requirements you actually have.

### Index one field

Set `indexed: true` on a stored field for an ordinary index, or
`indexed: 'unique'` when stored values must be distinct. Omit `indexed` or
use `indexed: false` when no index is needed. The `isbn` field of `Book` is
unique across all books.
An index does not make a field required: `required` and uniqueness are separate
decisions. If absence must be forbidden, also set `required: true`. A row with
`null` in an indexed field never conflicts: several rows may hold `null` in a
unique field. A duplicate fails with `UNIQUE_VIOLATION`, whose public details
list the schema and the index fields, never the values:

<include cwd meta='title="tests/schemas.test.ts"'>
	../../examples/modeling/tests/schemas.test.ts#unique-violation
</include>

Here `failure` is a `FrameworkError` with `code: 'UNIQUE_VIOLATION'` and
`publicDetails: { schema: 'Book', fields: ['isbn'] }`.

### Index a combination

Use the schema-level `indexes` array when the index covers several distinct
top-level fields or needs a `where` predicate. `Book` declares two such
indexes. The order in `fields` is preserved;
put the columns in the order that serves your common query pattern, then check
the database's query plan when performance matters. The database planner, not
Core, decides whether an ordinary index is used for a particular query.

The first index forbids two books with the same `author` **and** `title`, but
permits the same title for different authors. The second, over `genre` and the
framework-owned `createdAt` field, is an ordinary index for the latest books
of a genre; it permits duplicates. `unique`
defaults to `false`. Core rejects repeated or unknown fields, an empty `fields`
list, and an entry identical to a field-level `indexed` declaration. Index only
top-level stored fields or framework-owned system fields, not an embedded
child, relation, or virtual result.

### Index part of the rows

A `where` predicate restricts an index to the rows it matches; with `unique`,
values must be distinct only among those rows. Declare such `indexes` in the
final `.with`, which sees every field, including fields added by shape methods
such as `.softDelete()`. The [Soft Delete example](https://github.com/MrEkinox/ultimadatabase/tree/main/examples/soft-delete)
declares one:

<include cwd meta='title="src/schema.ts"'>
	../../examples/soft-delete/src/schema.ts#article
</include>

A deleted article no longer reserves its slug. The predicate is static and
portable: equality (a literal or `eq`), `gt`, `gte`, `lt` and `lte` on scalar
non-list fields, null tests (`null`, `isNull`, `isNotNull`) and conjunction
(several keys or `AND`). `OR`, `NOT`, `ne`, `in`, string, list, JSON, relation
and plugin operators are rejected by type and when the schema is compiled. The
database adapter must support partial indexes and the predicate's operators;
otherwise the application refuses to start with
`PLUGIN_ADAPTER_CAPABILITY_MISSING`.

A field declared `indexed: 'unique'` and a unique index of `define` without
`where` are exact [unique targets](/docs/1.0.0/core/writing-data/upserts#choose-a-valid-target)
of `updateOne`, `deleteOne`, and `upsertOne`. A partial unique index or one
declared in `.with` only enforces uniqueness: it is not a target. `Book` has
three targets, `{ id }`, `{ isbn }`, and `{ author, title }`:

<include cwd meta='title="tests/schemas.test.ts"'>
	../../examples/modeling/tests/schemas.test.ts#unique-targets
</include>

Both calls update the same book. A pointer in a target takes the target's ID.
The database plugin creates and enforces physical indexes; Core records
portable intent and does not expose SQL or index names. See
[PostgreSQL index preparation](/docs/1.0.0/plugins/official/postgresql#index-preparation)
before relying on a new index in an existing database.

## Register and compile

Register schemas you define directly in the application's `schemas` array,
and declare the application once in `Register` for short, name-keyed editor
types such as `Model<'Book'>`:

<include cwd meta='title="src/ultimabase.ts"'>
	../../examples/modeling/src/ultimabase.ts#application
</include>

Its factory installs PostgreSQL; call `start()` as shown in
[Application](/docs/1.0.0/core/application#start-and-dispose). At startup,
UltimaBase runs installed plugins' static declarations, then compiles the
complete schema graph before plugin setup or database connections. The
`fields` callback runs once when `catalog.ts` is imported to capture inert
builder calls. That capture
does not register the schema, connect infrastructure, or depend on application
lifecycle state.

Plugins can also contribute schemas during static declaration; those schemas
do not need an entry in the application's `schemas` array.

## Schema classes and application handles

`App.Schema.define()` returns the final schema class. Its fields, Core
operation inputs, filters, selections, and results infer from the source
declaration; no generation step is involved. Core-only declarations resolve their metadata
immediately; configured plugin builder calls resolve when a compatible
application compiles them. Ordinary schema commands execute against an owning
application. Use
`ultimabase.schema(Book)` only for application-specific mutation handles. Ordinary CRUD uses `Book` directly. The handle also accepts
the registered name of a plugin-contributed schema; its `.schema` is the
runtime class and can run ordinary commands. A plugin schema mutation can also
be declared directly on the frozen configured class before startup; execution
resolves the sole active application and verifies that application's compiled plugin graph. See
[Soft Delete](/docs/1.0.0/plugins/official/soft-delete)
for an example and [Models](./models) for plain data results.

## Schema identity

`className` is the stable logical identity used by relations, name-keyed types
such as `Model<'Book'>`, and adapters. Treat it like a persistent API name: changing it describes a
different schema, not a cosmetic rename.

## System fields

Every compiled schema receives three framework-owned fields:

| Field       | Type                   | Purpose                 |
| ----------- | ---------------------- | ----------------------- |
| `id`        | UUIDv7 `string`        | Stable record identity  |
| `createdAt` | ISO date-time `string` | Creation time           |
| `updatedAt` | ISO date-time `string` | Most recent update time |

They are always present on complete persisted models and are not accepted in
create or update data. UltimaBase generates all three at creation and refreshes
`updatedAt` on persisted updates; application code cannot set or redeclare
them.

## Compilation errors

Core-only declarations resolve field-dependent metadata immediately. A
declaration that captured configured plugin builder calls throws
`SchemaCompilationError` if code reads unresolved Runtime metadata before a
compatible application compiles it. Compilation also rejects duplicate or
reserved field names, unresolved relationship targets, and plugin rules
without one exact installed owner. These failures occur before plugin setup or
database connection, not on the first request. See
[Relationships](./relationships) for target declarations and
[Using Plugins](/docs/1.0.0/plugins/using-plugins) for installation and ownership.

## Plugin methods and rules

`define` holds the data, relation targets are functions that return the target
schema (as `author` of `Book` shows), plugins add methods such as
`.softDelete()`, and a final `.with` holds the plugin rules. The Soft Delete
example's `Post`:

<include cwd meta='title="src/schema.ts"'>
	../../examples/soft-delete/src/schema.ts#post
</include>

`.with` must be the last call and is optional: a schema without plugin rules
ends with `define(...)` or its last shape method. A plugin option passed to
`define` fails with
`Unknown schema option: access. define() takes className, fields and indexes; plugin rules go in the final .with(...) (ADR-0297)`
and is a TypeScript error. Core owns two `.with` rules itself: the partial
`indexes` above, and `relations`, which filters reads through a relation (see
[Relationships](./relationships#change-relation-membership)).

Schemas in separate files may reference each other, including circular
pointers and relations, because each target is a function. Role and User
schemas use the same chain from `App.RoleSchema.define(...)` and
`App.UserSchema.define(...)`.

## Types follow the declaration

The compiled schema graph is Runtime truth, and TypeScript types come from the
same source declarations: fields, complete filters, relationships, plugin
methods, rules, and their callbacks. There is no generated declaration file and
no generation step. Types never change what the application executes; a
JavaScript application runs the same compiled graph.

immutable instances, and [Relationships](./relationships) for schema targets.
