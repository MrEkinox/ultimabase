Bulk commands execute an ordered list of singular record operations in one
transaction. They are not set-based shortcuts: each item crosses Core's
structural validation and, when installed, the relevant policy and Hook
lifecycles.

The examples use the `Post` of the
[queries example](/docs/1.0.0/core/reading-data/overview), with required `slug`
and `title` fields, no other required fields, and a unique `slug`.

## Choose a batch command

| Command      | Input entries                       | Result without `select`              |
| ------------ | ----------------------------------- | ------------------------------------ |
| `createMany` | Create data                         | Models with only `id`                |
| `updateMany` | `{ where, data }`                   | Models with only `id`                |
| `upsertMany` | `{ where, create, update }`         | Models with only `id`                |
| `deleteMany` | Unique predicates in `where: [...]` | Models with only `id`, before delete |

Each command accepts one `select` for every result. A selected model still
includes `id`, even when it is not listed. `createMany` and `updateMany` also
accept `include`; upsert and delete batches do not.

## Create and update records

<include cwd meta='title="src/bulk.ts"'>
	../../examples/queries/src/bulk.ts#create-and-update
</include>

`updateMany` entries and the `deleteMany` target list use `where`, like the
singular commands; `where: { id }` is the equality shorthand of an ID target.
Each `where` must identify one unique target, not a broad filter; it is typed
by `UniqueWhereInput`, so a broad filter fails to compile.

## Upsert and delete records

<include cwd meta='title="src/bulk.ts"'>
	../../examples/queries/src/bulk.ts#upsert-and-delete
</include>

Upsert entries create a missing unique target or update an existing one. By
contrast, every `updateMany` or `deleteMany` entry must match one visible
record; a missing target raises `NOT_FOUND` and rolls back the whole batch.
Each `deleteMany` result contains the selected values from before deletion.
See [Unique Upserts](./upserts) and [Delete Records](./delete) for the singular
semantics.

## Verify and handle failures

All four commands return an immutable array with one model per input, in input
order. Each example specifies a selection, and every returned model also
includes its implicit `id`. An empty batch returns `[]` without starting an
item lifecycle or transaction.

An invalid input, unique-key conflict, missing directed target, installed
policy or Hook rejection, or persistence failure aborts the batch. All earlier
writes and Hook-started database work in that batch roll back; there is no
partial-success mode or public `atomic: false` option. A root batch starts an
automatic transaction, while a batch inside an explicit transaction reuses it.

Bulk create, update, and upsert inputs link a pointer with
`{ connect: target }` (an ID or a `Pointer` of the declared target) or unlink
it with `null`, never with a raw `Pointer` or ID. Each `connect` target must be
visible to the caller and is checked before the write; a hidden or missing
target fails the batch with `NOT_FOUND`. Nested `create`, `update`, and
relation commands are not available on bulk inputs. Use singular
[Nested Writes](./nested-writes) when one root operation must create related
records.
