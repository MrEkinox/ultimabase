Use `Post.deleteOne()` to delete one visible record. It returns an immutable
snapshot of that record **before** deletion, so select any values you need from
the result before the row becomes unavailable. That pre-image obeys the row
read rules: Core checks it on the locked target before deleting, and a caller
who may delete a row it cannot read requests `select: { id: true }`. A delete
that Soft Delete rewrites into a tombstone is checked the same way but returns
the row as written, with `isDeleted: true`.

The example uses the `Post` schema from [Create Records](./create), with `slug`
and `title` fields.

`where: { id: postId }` is the equality shorthand of
`where: { id: { eq: postId } }`. You may instead target one field declared
`indexed: 'unique'` or every field of one unique index of `define` without
`where`. A filter that could
match several rows is not a valid `deleteOne` target and fails to compile
(`UniqueWhereInput<'Post'>`, see
[Choose a valid target](/docs/1.0.0/core/writing-data/upserts#choose-a-valid-target)).

## Verify the result

If a visible post matches, `deletePost()` returns a `Post` containing its `id`,
`slug`, and `title` as they were before deletion. A later ordinary read by that
ID returns no record. The returned snapshot is not a live row or a way to undo
the delete. Without `select`, the result contains the complete visible
pre-delete row.

If no visible post matches, schema-level `deleteOne()` returns `null`; it does
not run item Hooks for a nonexistent record. Check for `null` before using the
result. A target hidden by an installed row-visibility rule also appears
absent; an explicit rejection of the delete operation may instead throw.

Delete results accept flat `select`, but not `include`. Selecting a pointer
does not load its target. If you need related data, read it before deleting the
record. See [Selections](/docs/1.0.0/core/reading-data/selections) for result
shaping.

## Delete a loaded row

Results have no `delete()` method (ADR-0310). When you already have a loaded
`Post`, pass its `id` as the target:

	../../examples/queries/src/writes.ts#delete-loaded-post
</include>

`findOneOrThrow()` throws `NOT_FOUND` if the record is already absent or
inaccessible; `deleteOne()` returns `null` if it disappears before deletion.
The prior `post` result remains unchanged.

## Integrity and soft deletion

Core runs a root delete in an automatic transaction and reuses an explicit
transaction when one is active. For physical deletion, pointers to the target
default to `onDelete: 'restrict'`; an explicitly configured `cascade` or
optional-pointer `setNull` changes that behavior. A referenced target fails
with `REFERENCE_VIOLATION`, whose public details name only the schema of the
deleted row; here an author who still has posts:

<include cwd meta='title="tests/writes.test.ts"'>
	../../examples/queries/tests/writes.test.ts#restrict
</include>

`attempt` rejects with `REFERENCE_VIOLATION` and `{ schema: 'Author' }`, and
the author remains. An integrity failure, or an installed policy or Hook
rejection, rolls back the deletion. Cascaded deletions are physical and
run no Hooks or policy on the referencing records. There is no
general option to skip installed Hooks. See [Relationships](/docs/1.0.0/core/data-modeling/relationships)
before deleting records that other schemas reference.

With no delete-rewriting plugin, native delete physically removes the row. On
a schema that sets `softDelete: true` in `define`, the optional Soft Delete
plugin instead stores a tombstone while preserving the same logical delete
result; `softDelete: { mode: 'command' }` leaves native delete physical and adds
separate `softDeleteOne` and `softDeleteMany` commands. Its own page covers
configuration, restore, purge, and tombstone visibility.
