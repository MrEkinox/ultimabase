Use `Post.upsertOne()` when the same unique key should create a record if absent
or update it if present. Pass separate `create` and `update` data; UltimaBase
executes only the branch selected by the unique target.

The `Post` of the [queries example](/docs/1.0.0/core/reading-data/overview)
declares a required `title` and a required `slug` with `indexed: 'unique'`,
and no other required fields.

## Verify the result

On the first call for a slug, the create branch stores `slug` and `title`. On a
later call with the same slug, the update branch replaces `title` and leaves
omitted fields unchanged. The result is an immutable `Post` in either case,
with its `id` plus the selected `slug` and `title`. The selection does not
change what is persisted. Without `select`, the result is the complete visible
model.

For the create branch, Core treats the unique equality in `where` as the
authoritative identity. It supplies missing target values to the create
candidate before required-value validation, for an untyped caller such as a
transport; in TypeScript the create data lists every required field. The
explicit `slug` in this example must match `where`; a mismatch fails with
`VALIDATION_ERROR` rather than creating a record under another key. Do not read first and choose separate create or
update commands: the upsert owns the atomic unique-key decision.

## Choose a valid target

`where` must contain non-null equality for exactly one unique target: the
framework `id`, one field declared `indexed: 'unique'`, or every field of one
unique index declared in `define({ indexes })` without `where`. Extra conditions, partial
composite keys, ranges, and multi-match filters are invalid. See
[Schemas](/docs/1.0.0/core/data-modeling/schemas) for index declarations.

The type of `where` is `UniqueWhereInput<'Translation'>`: a union with one
member per target, each value as a shorthand or `{ eq }`, never `null`. A wrong
target fails to compile. The `Translation` schema of the queries example
declares `indexes: [{ fields: ['post', 'locale'], unique: true }]`:

```ts twoslash title="Unique targets"
import '../../examples/queries/src/ultimabase.ts'
import { Translation } from '../../examples/queries/src/schema.ts'

declare const post: string
declare const locale: string
// ---cut---
type Target = Parameters<typeof Translation.deleteOne>[0]['where']
//   ^?

await Translation.deleteOne({ where: { post, locale } })
```

`{ locale }` alone fails to compile: `post` is missing from the
`{ post, locale }` target.

The same input types `updateOne`, `deleteOne`, and the items of
`updateMany`, `deleteMany`, and `upsertMany`. Runtime checks the target again,
because untyped transports reach it too, and accepts the same targets. A
partial unique index (with `where`) and a unique index a plugin adds with
`addSchemaIndex` are storage indexes, not
targets: they enforce uniqueness, and an untyped call that targets one fails
with `… must match id, a unique field or one non-partial unique index of
define`. A partial unique index identifies one row only among the rows its
`where` matches. Declare a unique index in `define`, without `where`, when a
command targets it.

If the proposed create values collide with a different unique key but no row
matches the chosen `where` target, the upsert fails; PostgreSQL reports a
`VALIDATION_ERROR` whose public message is
`The operation violates a data constraint.` It never redirects the update to a
row selected by that other key.

For `Translation`, the pair is the target. Both values must be present;
`locale` alone is not unique:

	../../examples/queries/src/writes.ts#save-translation
</include>

The create branch repeats the two target values, as TypeScript requires; they
must match `where`. Calling `saveTranslation()` twice with the same post and
locale creates one translation, then updates its `title`. The physical unique
index must exist before the command runs; PostgreSQL creates it at startup
outside production.

A root upsert runs in an automatic transaction and reuses an active explicit
transaction. Core structural validation always applies; optional Validation,
Access, and Hooks plugins participate when installed. A rejected branch or
persistence failure rolls back the operation.

## Boundaries and other paths

Upsert results support flat `select`, not `include`. Upsert `create` and
`update` accept ordinary field values, `{ connect: target }` links and `null`
for pointers, and `{ increment }` or `{ decrement }` in `update`, but not
nested relationship commands. The `connect` targets of both branches are
checked for visibility before the write. Those commands are available on singular
`createOne` and `updateOne` instead. See [Nested Writes](./nested-writes).
If an upsert must be combined with related writes, coordinate the separate
commands in an [explicit transaction](./transactions).

`upsertMany({ data, select? })` applies the same unique-target rule to an
ordered, atomic batch. See [Bulk Operations](./bulk-operations) for its input
and result shape.
