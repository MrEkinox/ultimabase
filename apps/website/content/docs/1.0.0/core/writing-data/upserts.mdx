Use `Post.upsertOne()` when the same unique key should create a record if absent
or update it if present. Pass separate `create` and `update` data; UltimaBase
executes only the branch selected by the unique target.

This example assumes `Post` declares a required `title` and a required `slug`
with `indexed: 'unique'`, and no other required fields. Register it in a
started application with a persistence plugin, as in
[Manual Installation](/docs/1.0.0/manual-installation).

## Upsert by unique slug

```ts title="src/upsert-post.ts"
import { Post } from './schemas.js'

export const savePost = (slug: string, title: string) =>
	Post.upsertOne({
		where: { slug: { eq: slug } },
		create: { slug, title },
		update: { title },
		select: { slug: true, title: true },
	})
```

## Verify the result

On the first call for a slug, the create branch stores `slug` and `title`. On a
later call with the same slug, the update branch replaces `title` and leaves
omitted fields unchanged. The result is an immutable `Post` in either case,
with its `id` plus the selected `slug` and `title`. The selection does not
change what is persisted. Without `select`, the result is the complete visible
model.

For the create branch, Core treats the unique equality in `where` as the
authoritative identity. It supplies missing target values to the create
candidate before required-value validation. The explicit `slug` in this
example must match `where`; a mismatch fails validation rather than creating
a record under another key. Do not read first and choose separate create or
update commands: the upsert owns the atomic unique-key decision.

## Choose a valid target

`where` must contain non-null equality for exactly one unique target: the
framework `id`, one field declared unique, or every field of one declared
composite unique index. Extra conditions, partial composite keys, ranges, and
multi-match filters are invalid. See [Schemas](/docs/1.0.0/core/data-modeling/schemas)
for index declarations.

If the proposed create values collide with a different unique key but no row
matches the chosen `where` target, the upsert fails. It never redirects the
update to a row selected by that other key.

For the `TenantArticle` schema in [Indexes](/docs/1.0.0/core/data-modeling/schemas#indexes),
the pair is the target. Both values must be present; `slug` alone is not
unique:

```ts title="src/upsert-tenant-article.ts"
import { TenantArticle } from './tenant-article.js'

export const saveTenantArticle = (
	tenantId: string,
	slug: string,
	title: string,
) =>
	TenantArticle.upsertOne({
		where: { tenantId: { eq: tenantId }, slug: { eq: slug } },
		create: { title },
		update: { title },
		select: { slug: true, title: true },
	})
```

Core supplies the two target values to the create branch before validating
required fields. Register `TenantArticle` in the same started application and
ensure its physical unique index has been prepared before this command runs.

A root upsert runs in an automatic transaction and reuses an active explicit
transaction. Core structural validation always applies; optional Validation,
Access, and Hooks plugins participate when installed. A rejected branch or
persistence failure rolls back the operation.

## Boundaries and other paths

Upsert results support flat `select`, not `include`. Upsert `create` and
`update` accept ordinary field values, including pointer values, but not
nested relationship commands. Those commands are available on singular
`createOne` and `updateOne` instead. See [Nested Writes](./nested-writes).
If an upsert must be combined with related writes, coordinate the separate
commands in an [explicit transaction](./transactions).

`upsertMany({ data, select? })` applies the same unique-target rule to an
ordered, atomic batch. See [Bulk Operations](./bulk-operations) for its input
and result shape. A draft model also has `upsert()`; see
[Models](/docs/1.0.0/core/data-modeling/models) for that command.
