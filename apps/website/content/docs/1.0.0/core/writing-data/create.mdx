Use `Post.createOne()` to persist one record. `data` describes the new record;
`select` and `include` shape the returned model, not the data being written.

This example assumes `Post` declares required `slug` and `title` fields, a
`published` boolean with `default: false`, and an `author` pointer to a schema
with `displayName`. Register the schemas in a started application with a
persistence plugin, as in [Manual Installation](/docs/1.0.0/manual-installation).
Pass the ID of an existing target that the operation may connect.

## Create one record

```ts title="src/create-post.ts"
import { Post } from './schemas.js'

export const createPost = (authorId: string, slug: string, title: string) =>
	Post.createOne({
		data: {
			author: { connect: authorId },
			slug,
			title,
		},
		include: { author: { select: { displayName: true } } },
		select: { published: true, slug: true, title: true },
	})
```

`connect` links the new post to an existing author; it does not create the
author. Core checks the target before the first write. To create an author in
the same command, use `author: { create: ... }` as described in
[Nested Writes](./nested-writes).

## Verify the result

The returned immutable `Post` contains its generated `id`, the supplied
`slug` and `title`, and `published: false` from the declared default. Its
included `author` contains `id` and `displayName` when that target is visible;
target read policy may instead make the inclusion `null`. Unselected post
fields are absent from `toJSON()` and from the selected TypeScript result
shape. See [Selections](/docs/1.0.0/core/reading-data/selections) for the
projection rules.

Core applies generated values and defaults once, validates the complete
structure, and commits the root and pointer connection in one automatic
transaction. The optional Validation, Access, and Hooks plugins participate
only when installed. If target validation, an installed policy or hook, or
persistence fails, the transaction rolls back; no partial post is committed.

The result obeys the row read rules of installed policies, like PostgreSQL's
`RETURNING` under row-level security. When the caller may create a row it
cannot read, a result selecting anything beyond `id` fails with
`PERMISSION_DENIED` and nothing is written; request `select: { id: true }`,
which is always allowed. The same holds for update, upsert and delete results
and for bulk commands, where one unreadable row rejects the call. Master skips
the check.

## Other create paths

Schemas are not constructible and results are frozen plain data (ADR-0310):
assemble create data as a plain object, typed with `CreateInput<typeof Post>`
when it is built separately, and pass it to `createOne`. See
[Models](/docs/1.0.0/core/data-modeling/models) for the result contract.

Use [Bulk Operations](./bulk-operations) for an itemized collection create.
Nested writes belong to singular `createOne`, not to bulk roots.
