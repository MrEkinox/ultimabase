Use a nested write when one post command must also create, connect, or update
related records. `createOne` and `updateOne` accept relationship commands
inside `data`. The root and every child run in
one transaction; a failure rolls back the whole graph.

The examples use the schemas of the
[queries example](/docs/1.0.0/core/reading-data/overview): `Post` has required
`slug` and `title` fields, an optional `author` pointer to an `Author` with
`displayName` and `email`, and an owning `comments` relation to a `Comment`
with `body`. See [Relationships](/docs/1.0.0/core/data-modeling/relationships)
for how to declare those fields.

## Create a post and its related records

<include cwd meta='title="src/nested-writes.ts"'>
	../../examples/queries/src/nested-writes.ts#create-graph
</include>

`author.create` creates an author and stores its pointer on the post.
`comments.create` creates two comments and connects them; `comments.connect`
adds an existing, visible comment by ID. These are different operations:
`connect` never creates a target. A `connect` target is an ID or a `Pointer`
of the declared target already in hand, such as `{ connect: post.author }`. The final returned post includes the
requested author and comments when they are visible to the caller; read
policy may omit some included targets.

## Update the related graph

<include cwd meta='title="src/nested-writes.ts"'>
	../../examples/queries/src/nested-writes.ts#revise-graph
</include>

`author.update` changes the currently linked, visible author; it needs no
author ID. `comments.update` requires an ID that is currently in this post's
visible relation. `comments.disconnect` removes membership but does not delete
the comment. Each ID in this example must refer to a distinct target.

## Choose a relationship command

| Field    | On `createOne`                                                  | On `updateOne`                                                                                           |
| -------- | --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Pointer  | `connect: target`, `create: data`, or `null` (optional pointer) | `connect: target`, `create: data`, `update: data`, or `null` (optional pointer)                          |
| Relation | `create: [data]`, `connect: [target]`                           | `create: [data]`, `connect: [target]`, `update: [{ id, data }]`, `disconnect: [target]`, `set: [target]` |

This is the only way to link rows (ADR-0308). A pointer command object
contains exactly one command, and `null` unlinks an optional pointer; a
required pointer cannot be `null`. A `Pointer` or an ID assigned directly to a
pointer field (`author: Author.pointer(id)`) is a type error and a
`VALIDATION_ERROR` whose message shows `{ connect: id }`; `Schema.pointer(id)`
stays a value for filters, comparisons, and ACL entries. Relation `create`,
`connect`, `update`, and `disconnect` may coexist; their arrays must be
non-empty. Core runs them in that order regardless of property order,
preserving order within each array. A `connect`, `disconnect`, or `set`
target is an ID or a `Pointer` of the declared target; another schema's
`Pointer` is a type error and a `VALIDATION_ERROR` naming the field. Do not
name the same target twice across those commands.

Pointer child creates and updates run before the root write. Relation child
mutations and membership changes run after it. The root's after-hooks see the
completed graph, and `select` / `include` project the final result.

`set` must be the sole command in its relation object. `set: []` removes every
visible membership; `set` can also replace them with specified visible
targets:

<include cwd meta='title="src/nested-writes.ts"'>
	../../examples/queries/src/nested-writes.ts#replace-links
</include>

The result has a `null` author and only the kept comments; the unlinked author
and comments still exist. `set` never deletes targets or removes policy-hidden
memberships. A relation mapped by a required inverse pointer cannot use `disconnect` or
`set`, because that would clear a required field. See
[Relationships](/docs/1.0.0/core/data-modeling/relationships) for owning and
inverse relations.

## Every link checks visibility

For a caller without Master authority, each target named by `connect` or `set`
must be visible as a single-row read under every installed policy, checked
in the mutation's transaction before the write. `disconnect` names only
visible linked targets. A missing or hidden target fails with the same
`NOT_FOUND`, whose public details name the field and target schema
(`{ field: 'author', schema: 'Author' }`), and the whole graph rolls back, so
a link never reveals that a hidden row exists. Master skips visibility but
never existence: it can link a hidden row and still fails on a missing one.

A relation's declared `where` limits reads, not unlinking: `disconnect` removes
a member that only the declared filter hides, and `set` replaces those members
too. A member hidden by an installed policy stays `NOT_FOUND` for a caller
without Master authority.

## Bounds and failure behavior

By default, the root is at depth zero and a graph may reach five nested target
levels and 100 operation nodes. The operation count includes the root, child
mutations, pointer actions, and relation membership actions; one relation
target creation counts as both a child create and a membership connection.
Configure `validation.nestedWrites.maxDepth` and `maxOperations` to raise or
lower these limits. `maxDepth` must be a non-negative safe integer;
`maxOperations` must be a positive safe integer.

Core checks the declared graph and existing target visibility before the first
business hook or write. A missing or inaccessible related target, conflicting IDs, a
limit violation, failed validation, policy rejection, or hook failure aborts
the whole transaction: there is no partial-success branch.

Nested delete and upsert commands are not available. Bulk roots and upserts
accept pointer links (`{ connect: target }` or `null`), checked like any other
link, but no nested `create`, `update`, or relation command. Use a singular
root command when you need this graph behavior.

To verify atomicity, make one part of the graph fail in a disposable test
database. The example's tests call `createPostGraph()` with a comment ID that
does not exist: the command rejects with `NOT_FOUND` naming
`{ field: 'comments', schema: 'Comment' }`, and neither the post, its new
author, nor its new comments remain.
