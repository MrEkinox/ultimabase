Test the application your code actually runs: `testApplication` starts the
production application itself (same plugins, same rules) on a PostgreSQL
schema that belongs to the test worker, and every test starts from empty
tables. Projects created by the initializer already contain this setup and a
first test in `tests/task.test.ts`.

## Prerequisites

- An application module that exports the configured application, such as
  `src/ultimabase.ts` with `export const ultimabase = new App({ schemas })`,
  and `postgresPlugin()` without `url` or `pool`: `testApplication` gives it
  the test schema through `DATABASE_URL`.
- Docker, so that Vitest can start a disposable PostgreSQL container, or a
  **separate, disposable** test database in `TEST_DATABASE_URL`. The test user
  needs permission to create and drop schemas in it. Never point it at shared
  development or production data.
- Node.js 24 or newer and the same package manager as your application.

## Shortest path

### Install test dependencies

```bash tab="npm" tab-group="package-manager"
npm install --save-dev vitest @ultimabase/testing
```

```bash tab="yarn"
yarn add --dev vitest @ultimabase/testing
```

```bash tab="pnpm"
pnpm add --save-dev vitest @ultimabase/testing
```

Add a `test` script to `package.json`:

```json title="package.json"
{
	"scripts": {
		"test": "vitest run"
	}
}
```

### Configure Vitest

`ultimabaseTesting()` starts PostgreSQL once per run (unless
`TEST_DATABASE_URL` is set), gives each worker its own schema and drops it
after each test file. It also starts the workers with
`--no-experimental-require-module`, so Node.js resolves packages as Vite does
and a package with both ESM and CommonJS builds, such as `graphql`, loads only
once:

```ts title="vitest.config.ts"
import { ultimabaseTesting } from '@ultimabase/testing/vitest'
import { defineConfig } from 'vitest/config'

export default defineConfig({ test: { ...ultimabaseTesting() } })
```

### Write the test

```ts title="tests/task.test.ts"
import { testApplication } from '@ultimabase/testing'
import { expect, it } from 'vitest'

import { Task } from '../src/schema.ts'
import { ultimabase } from '../src/ultimabase.ts'

it('creates a Task with its defaults', async () => {
	await using t = await testApplication(ultimabase)
	const task = await Task.createOne({ data: { title: 'Test the application' } })
	expect(task).toMatchObject({ done: false, title: 'Test the application' })
	await t.afterCommit()
})

it('starts each test from empty tables', async () => {
	await using t = await testApplication(ultimabase)
	expect(await Task.count()).toBe(0)
	await t.afterCommit()
})
```

The first call starts the application; a later call in the same file reuses
it after emptying its tables. Leaving the `await using` scope waits for
after-commit work. The application stops after the file and its schema is
dropped.

### Use the handle

| Member                           | Use it to                                                                                                                              |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `t.fetch(path, init?, options?)` | Send an in-memory HTTP request through the HTTP plugin, without a port, authenticated by its headers, from the local peer `127.0.0.1`. |
| `t.as(principal, fn)`            | Run direct calls as one user: `t.as(User.pointer(id), () => Task.findMany())`; rules see that principal.                               |
| `t.asMaster(fn)`                 | Seed or inspect data with Master authority, without a configured key; validation and hooks still run.                                  |
| `t.reset()`                      | Empty every table within a test; plugins' start seeding, such as Roles `ensure`, runs again.                                           |
| `t.afterCommit()`                | Wait for `afterCommit` hooks and event consumers before asserting their effects.                                                       |

```ts title="tests/rest.test.ts"
it('lists Tasks over REST', async () => {
	await using t = await testApplication(ultimabase)
	const task = await t.asMaster(() =>
		Task.createOne({ data: { title: 'Listed' } }),
	)
	const response = await t.fetch('/api/classes/Task')
	expect(await response.json()).toMatchObject({ results: [{ id: task.id }] })
})
```

`t.fetch` behaves like a local server: requests come from the socket peer
`127.0.0.1`, the address rate limits count and authentication records unless a
trusted `X-Forwarded-For` names another client. Pass
`{ remoteAddress: '203.0.113.7' }` as the third argument to send from another
peer, or `{ remoteAddress: undefined }` to send none and test an unknown client
address, as behind a fetch handler on an edge or serverless platform (see
[HTTP](/docs/1.0.0/plugins/official/http)).

`t.as` and `t.asMaster` exist only on a handle from `testApplication`, which
opens the application harness before the application starts. An application
started with `ultimabase.start()` can never gain those powers, and
`testApplication` refuses `NODE_ENV=production`.

## Verify the outcome

Run the tests:

```bash tab="npm" tab-group="package-manager"
npm test
```

```bash tab="yarn"
yarn test
```

```bash tab="pnpm"
pnpm test
```

Both tests should pass. Temporarily change the expected title to confirm that
the assertion fails, then restore it. If startup fails, check that Docker is
running or that `TEST_DATABASE_URL` points to a database where the test user
may create schemas.

## Limitations

These are integration tests: they need PostgreSQL. Workers share one database
and use separate schemas, `ultimabase_test_<worker>`; run one suite at a time
against a given `TEST_DATABASE_URL`. Tests that share one application in a
file run one after another. `testApplication` refuses an application whose
database plugin did not connect through `DATABASE_URL`, so it never empties
another database. With another test runner, `testApplication` works without
`ultimabaseTesting()`: it starts one container per process when
`TEST_DATABASE_URL` is unset, and you call `await ultimabase.dispose()` after
the suite.

Plugin conformance suites and lower-level helpers live in
`@ultimabase/testing/plugins`; they belong to the [plugin-author
workflow](/docs/1.0.0/plugins/build-a-plugin), not to ordinary application
assertions.
