## What you will build

The initializer creates a Node.js application with a `Task` schema,
PostgreSQL persistence, a REST API, a development script that writes one
Task, and a first test. You choose TypeScript or JavaScript, the HTTP APIs and
plugins, and either a local Docker database or one you already run. The
result is an ordinary project: you own its schema and application
configuration.

## Prerequisites

- Node.js 24 or newer and npm, yarn, or pnpm. Node 24 runs the TypeScript
  sources directly in development.
- For the path below, Docker Compose. When Docker is missing, the initializer
  says so and offers an existing database instead.
- For the existing-database path, a separate disposable PostgreSQL database
  and its connection URL. The initializer does not create that database.

<Callout type="warn" title="Use only disposable data">
	The generated application uses PostgreSQL's `override` schema policy for local
	development. Do not point it at shared or production data.
</Callout>

## Steps

### 1. Start the initializer

After publication, use the command for the package manager you want in the
generated project:

```bash tab="npm" tab-group="package-manager"
npm create @ultimabase/app@latest
```

```bash tab="yarn" tab-group="package-manager"
yarn dlx @ultimabase/create-app@latest
```

```bash tab="pnpm" tab-group="package-manager"
pnpm dlx @ultimabase/create-app@latest
```

`npx @ultimabase/create-app@latest` will also launch the same package after
publication. It detects npm as the invoking manager; add
`--package-manager yarn` or `--package-manager pnpm` if that manager should
install dependencies in the generated project.

### 2. Choose the project

For a first run, accept the defaults:

| Prompt                             | Default                               | Effect                                                                                      |
| ---------------------------------- | ------------------------------------- | ------------------------------------------------------------------------------------------- |
| Project name and destination       | `notes`; accept the `notes` directory | Creates a new directory. Existing paths are never overwritten.                              |
| Language                           | TypeScript                            | Node 24 runs the sources in development; `build` compiles them for production.              |
| How will clients access your data? | REST                                  | Installs HTTP, REST and a local Hono listener through `apiServer()`.                        |
| Official plugins                   | Access                                | A prototype opening: every operation works in development; production waits for your rules. |
| Starter                            | Runnable Task example                 | Defines `Task`, seeds one record on the first start and writes a first test.                |
| PostgreSQL                         | Local Docker Compose                  | Writes `compose.yaml` and a private `.env`.                                                 |
| Install dependencies now?          | Yes                                   | Installs with the invoking package manager before creating the destination.                 |
| Create this project?               | Yes                                   | Confirms the displayed plan.                                                                |

`--yes` selects the same defaults without prompts. The summary identifies
automatic dependencies. These are its key lines for the npm answers above:

```text
Language: TypeScript (run by Node 24 in development)
Data APIs: REST
Plugins: @ultimabase/access-plugin, @ultimabase/http-plugin (included), @ultimabase/postgres-plugin (included), @ultimabase/rest-plugin (included), @ultimabase/hono-server-plugin (included)
Starter: task; database: docker; manager: npm
Install dependencies: yes
```

The manager line reads `yarn` or `pnpm` when launched through those
managers. Cancelling before confirmation leaves the destination untouched.

The official plugin question groups 14 of the shipped plugins. PostgreSQL
Vector is not offered until vector storage ships, and
`--plugin @ultimabase/pg-vector-plugin` fails with that reason. The earlier API
answer and this selector share one selection:

| Group            | Available choices                                        |
| ---------------- | -------------------------------------------------------- |
| Data & behavior  | PostgreSQL, Hooks, Validation, Soft Delete               |
| Security         | Authentication, Access, Roles, Object ACLs               |
| HTTP & explorers | HTTP, Hono server, REST, GraphQL, GraphQL Yoga, GraphiQL |

REST includes HTTP and Hono. GraphQL selected as an HTTP API includes
GraphQL, Yoga, HTTP, and Hono. Advanced plugin choices can keep GraphQL
network-independent or add a development-only explorer. See [Using
Plugins](/docs/1.0.0/plugins/using-plugins) for the composition rules.

### 3. Inspect the generated files

The default choices create:

<Files>
	<Folder name="src" defaultOpen>
		<File name="schema.ts" />
		<File name="ultimabase.ts" />
		<File name="main.ts" />
	</Folder>
	<Folder name="tests" defaultOpen>
		<File name="task.test.ts" />
	</Folder>
	<File name=".env" />
	<File name=".env.example" />
	<File name=".gitignore" />
	<File name="compose.yaml" />
	<File name="package.json" />
	<File name="README.md" />
	<File name="tsconfig.json" />
	<File name="tsconfig.build.json" />
	<File name="vitest.config.ts" />
</Files>

`schema.ts` installs every plugin once, in one list, and declares `Task` in
the declaration form: data in `define(...)`, rules in a final `.with(...)`
when a schema has any. `ultimabase.ts` creates the application and declares
it once in `Register` for name-keyed editor types; there is no generation
step. `main.ts` starts the application and seeds a Task. The Access line of
`schema.ts` is the prototype opening:

```ts title="src/schema.ts"
export const SchemaApplication = UltimaBase.use(
	// Prototype: operations without an Access rule are open outside production.
	// Production refuses to start until you write .with({ access }) rules and
	// remove this opening.
	accessPlugin({ allowWithoutRule: { all: 'development' } }),
	...apiServer({ rest: true }),
	postgresPlugin(),
)
```

Its scripts are:

```json title="package.json — TypeScript scripts"
{
	"dev": "node --watch --env-file=.env src/main.ts",
	"build": "tsc -p tsconfig.build.json",
	"start": "node --env-file=.env dist/main.js",
	"typecheck": "tsc",
	"test": "vitest run"
}
```

JavaScript instead writes `src/schema.js`, `src/ultimabase.js`,
`src/main.js`, `tests/task.test.js` and `vitest.config.js`, without
TypeScript files or dependencies. Its scripts are `dev`, `start` and `test`.
With an existing database, either language writes `.env` only when you gave
its URL, and never `compose.yaml`. The generated README records the selected
plugins and exact next steps.

### 4. Start PostgreSQL and run the application

For the Docker choice, enter the directory and start the database:

```bash
cd notes
docker compose up -d --wait
```

For an existing database without a URL, copy `.env.example` to `.env` and
replace its `DATABASE_URL` placeholder with your disposable database URL.
Keep the file private. Object ACLs and Roles also configure a local Master
key; the generated README identifies the value without printing it.

The default flow installs dependencies during generation. If you chose
`--no-install` or answered No, first run `npm install`, `yarn install`, or
`pnpm install` in the generated directory. Then start the development server:

```bash tab="npm" tab-group="package-manager"
npm run dev
```

```bash tab="yarn" tab-group="package-manager"
yarn dev
```

```bash tab="pnpm" tab-group="package-manager"
pnpm dev
```

### 5. Run the first test

`tests/task.test.ts` starts the same application with `testApplication` on
its own PostgreSQL schema, creates a Task, and lists it over REST without a
port. Vitest starts a disposable PostgreSQL container once with Docker; set
`TEST_DATABASE_URL` to use an existing test database instead:

```bash tab="npm" tab-group="package-manager"
npm test
```

```bash tab="yarn" tab-group="package-manager"
yarn test
```

```bash tab="pnpm" tab-group="package-manager"
pnpm test
```

[Test an Application](/docs/1.0.0/guides/test-an-application) explains the
test helper.

## Expected result

The Task starter prints a new record with a generated `id`,
`title: 'Ship the first feature'`, and `done: false`. It seeds that record
only when no Task exists, so starting it again prints the same record instead
of writing another. Access logs one warning: the prototype opening is active.
The application listens on `127.0.0.1:1337` until you stop it; `GET /health`
reports its health, and the README supplies local requests, which need no
application header. With `NODE_ENV=production`, the application refuses to
start until rules replace the opening. The test command reports two passing
tests.

## Choose a different path

For automation, use flags. This example selects both HTTP APIs and Hooks
without installing dependencies:

```bash tab="npm" tab-group="package-manager"
npm create @ultimabase/app@latest -- --name api-notes --language ts --api rest --api graphql --plugin @ultimabase/hooks-plugin --starter task --database docker --package-manager npm --no-install
```

```bash tab="yarn" tab-group="package-manager"
yarn dlx @ultimabase/create-app@latest --name api-notes --language ts --api rest --api graphql --plugin @ultimabase/hooks-plugin --starter task --database docker --package-manager yarn --no-install
```

```bash tab="pnpm" tab-group="package-manager"
pnpm dlx @ultimabase/create-app@latest --name api-notes --language ts --api rest --api graphql --plugin @ultimabase/hooks-plugin --starter task --database docker --package-manager pnpm --no-install
```

Without a terminal, provide every choice as above or use `--yes` for the
defaults. `--api none` and `--plugin none` select nothing explicitly;
`--database-url` writes an existing database URL to `.env`. `--yes` never
permits overwriting an existing directory. Repeat `--plugin @ultimabase/<id>`
for multiple official plugins.

The selector does not invent capabilities. Authentication identifies callers
but does not grant Task access; Roles do not grant permission by themselves.
Selecting Authentication with Access generates User rules limited to the
current session owner, allowing authentication to return the required
profile, and denying direct User writes. Object ACLs start empty and hide
Tasks from ordinary reads. Authentication operations are served under
`/api/auth` and in a selected GraphQL API; REST hides them. GraphiQL,
including the introspection it needs, is development-only in the generated
configuration. Review [Password
Authentication](/docs/1.0.0/plugins/official/password-authentication),
[Access](/docs/1.0.0/plugins/official/access),
[REST](/docs/1.0.0/plugins/official/rest), and
[GraphQL](/docs/1.0.0/plugins/official/graphql) before changing those defaults.
