## Eager inclusion

Use `include` to make relationship I/O explicit and shape each target with its
own exact selection.

Understand [Relationships](/docs/1.0/core/data-modeling/relationships) first.
Select root scalar fields separately from related data.

Include a to-one author and a filtered, ordered, bounded comment collection:

```ts title="src/post-context.ts"
import { Post } from './schemas.js'
import { ultimabase } from './ultimabase.js'

export const readPostsWithContext = () =>
	Post.findMany(
		{
			include: {
				author: { select: { name: true } },
				comments: {
					limit: 3,
					orderBy: { createdAt: 'desc' },
					select: { body: true },
					where: { published: { eq: true } },
				},
			},
			select: { title: true },
		},
		{ ultimabase },
	)
```

Pointer and relation cardinality deliberately expose different nested clauses:

| Included field | Allowed shaping                                                   | Result                          |
| -------------- | ----------------------------------------------------------------- | ------------------------------- |
| Pointer        | `select`, nested `include`                                        | Selected target model or `null` |
| Relation       | `where`, `orderBy`, `offset`, `limit`, `select`, nested `include` | Readonly selected model array   |

A pointer already identifies at most one target. Allowing a nested `where`
would make an existing pointer look absent only because it missed a projection
filter, so Core rejects that clause.

Relation filtering runs before ordering, offset, and limit. Its offset applies
independently to each parent collection, not across all included targets.

## Verify

The inferred root model contains `id`, `title`, selected `author`, and included
`comments`. The author contains `id` and `name`; each comment contains `id` and
`body`. Unselected fields are absent from those nested model types.

Missing or inaccessible pointer targets become `null`. Relations contain only
visible targets and therefore become an empty array when none remain. Nested
target reads still apply installed policies, protected constraints, output
restrictions, and the relationship's declared shaping filter.

## Relation predicates

Relation predicates match source records without loading the related collection:

```ts title="src/relation-filters.ts"
export const readEstablishedAuthors = () =>
	Author.findMany(
		{
			where: {
				posts: {
					count: { gte: 3, where: { published: { eq: true } } },
					some: { score: { gte: 80 } },
				},
			},
		},
		{ ultimabase },
	)
```

`some` requires a visible match, `none` requires no visible match, and `every`
requires no visible violation. `every` is true for an empty visible relation.
Use `isEmpty: true` or `isNotEmpty: true` for existence semantics. `count`
accepts numeric comparisons and an optional target `where`.

Every predicate observes the same visible universe: physical membership, the
field's declared filter, target policies and constraints, then the caller's
predicate. Hidden targets are not counted.

## Contextual relation filters

A relation may declare one synchronous, request-aware `where` when every
traversal through that field represents the same narrower application view:

```ts title="src/channel.ts"
messages: field.relation({
	target: 'QueryMessage',
	where: ({ context, where }) =>
		context.access.mode === 'master' ? where : where.eq('published', true),
})
```

The immutable `WhereBuilder` starts empty and targets the exact related schema.
The callback receives request context but no source item, adapter, transaction,
transport request, or authority grant.

The declared filter intersects with caller filters, authorization row filters,
and protected constraints. It shapes reads but does not authorize them, modify
physical membership, or change `connect`, `disconnect`, `set`, or `clear`.
